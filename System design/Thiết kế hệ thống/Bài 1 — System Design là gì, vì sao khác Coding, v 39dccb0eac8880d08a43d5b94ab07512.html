Bài 1 — System Design là gì, vì sao khác Coding, và mindset của Senior Engineer

System Design không tập trung vào việc viết code cụ thể, mà tập trung vào cách ghép nhiều thành phần lại thành một hệ thống chạy được, scale được, đáng tin cậy và phục vụ được người dùng thật.

Kỹ năng phân biệt mid-level developer với senior engineer:

senior không chỉ nhận task rõ ràng rồi code, mà còn biết thiết kế kiến trúc từ yêu cầu mơ hồ, đưa ra trade-off và quyết định ảnh hưởng đến performance, data storage, reliability, customer experience.

1. System Design là gì?

System Design là quá trình thiết kế cách một hệ thống phần mềm hoạt động ở mức tổng thể.

Không chỉ là:

“Viết function này như thế nào?”

Mà là:

“Làm sao để hàng triệu user cùng dùng được hệ thống này mà nó vẫn nhanh, ổn định, bảo mật, dễ mở rộng và dễ bảo trì?”

Ví dụ, nếu bạn xây một app đặt đồ ăn, coding sẽ quan tâm:

- Viết API tạo đơn hàng
- Validate input
- Lưu đơn hàng vào database
- Trả response cho client

Nhưng System Design sẽ hỏi:

- Nếu 1 triệu người đặt đồ ăn cùng lúc thì sao?
- Nếu database chính bị chết thì sao?
- Làm sao tránh user bấm đặt hàng 2 lần bị tạo 2 đơn?
- Làm sao xử lý thanh toán chậm?
- Làm sao gửi email/SMS mà không làm API bị chậm?
- Nên dùng SQL hay NoSQL?
- Nên cache dữ liệu nào?
- Nên scale service nào trước?
- Làm sao monitor lỗi?

Nói ngắn gọn:

Coding là xây từng viên gạch. System Design là thiết kế cả tòa nhà.

  • File lưu ở đâu? Local disk hay S3/object storage?

  • Resize đồng bộ hay qua background worker?
  • Ảnh có cần CDN không?

  • Nếu file lớn quá thì sao?
  • Nếu server chết giữa lúc upload thì sao?
  • Có cần signed URL không?

System Design không phải một công nghệ cụ thể. Nó là cách suy nghĩ về hệ thống.

4. Cốt lõi của System Design: trade-off

Một senior engineer hiếm khi nói:

“Cách này luôn luôn tốt nhất.”

Thay vào đó họ nói:

“Với traffic này, yêu cầu này, ràng buộc này, cách A tốt hơn cách B vì... nhưng ta phải chấp nhận trade-off là...”

Ví dụ:

SQL vs NoSQL

Nếu bạn làm hệ thống ngân hàng:

Ưu tiên: consistency, transaction, correctness
=> SQL thường phù hợp hơn

Nếu bạn làm hệ thống feed mạng xã hội:

Ưu tiên: scale lớn, đọc nhanh, dữ liệu linh hoạt
=> NoSQL/cache/search index có thể phù hợp hơn

Cache vs Database

Dùng cache giúp nhanh hơn:

User --> API --> Cache --> Response nhanh

Nhưng cache tạo thêm vấn đề:

- Dữ liệu cache có bị cũ không?
- Khi nào invalidate cache?
- Nếu cache chết thì sao?
- Cache miss quá nhiều có làm database sập không?

Monolith vs Microservices

Monolith dễ bắt đầu:

Một codebase
Một deploy
Dễ debug

Nhưng khi lớn lên có thể khó scale từng phần.

Microservices linh hoạt hơn:

User Service
Order Service
Payment Service
Notification Service

Nhưng đổi lại:

- Phức tạp hơn
- Cần network call
- Cần tracing
- Cần retry
- Cần xử lý distributed failure

Bài học quan trọng:

System Design không phải chọn công nghệ “xịn nhất”, mà là chọn giải pháp phù hợp nhất với bài toán hiện tại.

5. Mindset của Senior Engineer

Video bạn đưa nhấn mạnh rằng senior engineer khác mid-level developer ở khả năng thiết kế từ đầu, xử lý yêu cầu chưa rõ, đưa ra quyết định kiến trúc và trade-off.

Mình tóm lại thành 7 mindset chính.

Mindset 1: Không lao vào code ngay

Junior thường nghe đề xong sẽ nghĩ:

Mình viết API nào?
Mình tạo table nào?
Mình dùng framework gì?

Senior sẽ hỏi trước:

Ai dùng hệ thống này?
Có bao nhiêu user?
Read nhiều hay write nhiều?
Dữ liệu có cần chính xác tuyệt đối không?
Latency yêu cầu bao nhiêu?
Có cần realtime không?
Có cần audit log không?
Có yêu cầu bảo mật/pháp lý không?

Ví dụ đề bài: “Thiết kế hệ thống chat.”

Senior sẽ không vẽ ngay. Họ hỏi:

- Chat 1-1 hay group chat?
- Có cần read receipt không?
- Có cần typing indicator không?
- Có cần gửi ảnh/video/file không?
- Tin nhắn có cần mã hóa không?
- Có cần sync đa thiết bị không?
- Có bao nhiêu DAU?
- Tin nhắn cần lưu bao lâu?

Mindset 2: Tách functional và non-functional requirements

Đây là nền tảng cực quan trọng.

Functional requirements là hệ thống phải làm gì.

Ví dụ với YouTube:

- User upload video
- User xem video
- User search video
- User like/comment/subscribe

Non-functional requirements là hệ thống phải làm tốt đến mức nào.

- Video load nhanh
- Hệ thống chịu được hàng triệu user
- Dữ liệu không mất
- Có thể phục vụ user toàn cầu
- Có bảo mật
- Có monitoring

Coding thường tập trung vào functional requirement.

System Design bắt buộc phải quan tâm rất nhiều đến non-functional requirement.

Mindset 3: Luôn nghĩ về scale

Một app chạy được cho 100 user chưa chắc chạy được cho 1 triệu user.

Ví dụ kiến trúc ban đầu:

flowchart LR
    U[Users] --> A[One App Server]
    A --> D[(One Database)]

Chạy tốt khi nhỏ.

Nhưng khi traffic tăng:

flowchart LR
    U[Users] --> LB[Load Balancer]
    LB --> A1[App Server 1]
    LB --> A2[App Server 2]
    LB --> A3[App Server 3]

    A1 --> C[Cache]
    A2 --> C
    A3 --> C

    C --> DB[(Primary DB)]
    DB --> R1[(Read Replica)]
    DB --> R2[(Read Replica)]

Lúc này bạn bắt đầu có:

- Load balancer
- Multiple app servers
- Cache
- Database replication
- Read/write separation

Senior không nhất thiết build phức tạp từ đầu, nhưng họ biết khi nào hệ thống sẽ đau ở đâu.

Mindset 4: Luôn tìm bottleneck

Bottleneck là điểm nghẽn.

Ví dụ hệ thống chậm, nguyên nhân có thể là:

- Database query chậm
- Không có index
- API gọi quá nhiều service
- Cache miss cao
- Network latency cao
- Lock contention
- Queue backlog
- Third-party API chậm

Senior sẽ không nói mơ hồ “server yếu”. Họ sẽ hỏi:

- Latency p95/p99 là bao nhiêu?
- Database CPU/memory thế nào?
- Query nào chậm nhất?
- Cache hit rate bao nhiêu?
- Error rate tăng ở endpoint nào?
- Traffic tăng ở read hay write?

Mindset 5: Thiết kế để failure xảy ra

Junior thường nghĩ:

“Nếu mọi thứ chạy bình thường…”

Senior nghĩ:

“Nếu một phần hệ thống chết thì sao?”

Ví dụ:

- Database chết
- Redis chết
- Payment gateway timeout
- Email service lỗi
- Một region mất mạng
- Message queue bị backlog
- Một service deploy bug

Một hệ thống production tốt không phải là hệ thống “không bao giờ lỗi”.

Mà là:

Lỗi một phần nhưng toàn hệ thống không sập hoàn toàn.

Ví dụ order system:

sequenceDiagram
    participant User
    participant API
    participant OrderService
    participant DB
    participant Queue
    participant EmailService

    User->>API: Place order
    API->>OrderService: Create order
    OrderService->>DB: Save order
    OrderService->>Queue: Publish OrderCreated
    API-->>User: Order created

    Queue->>EmailService: Send confirmation email

Nếu EmailService chết, user vẫn đặt hàng thành công. Email có thể retry sau.

Đây là tư duy rất quan trọng:

Không để tác vụ phụ làm hỏng tác vụ chính.

Mindset 6: Đơn giản trước, phức tạp sau

Một sai lầm phổ biến khi học System Design là thấy công nghệ gì cũng muốn nhét vào:

Kubernetes
Kafka
Redis
Elasticsearch
Microservices
CQRS
Event Sourcing
Multi-region

Nhưng senior thật sự sẽ hỏi:

Có cần chưa?
Traffic hiện tại bao nhiêu?
Đội ngũ có vận hành nổi không?
Độ phức tạp thêm vào có đáng không?

Một thiết kế tốt thường bắt đầu đơn giản:

flowchart LR
    User --> API[Backend API]
    API --> DB[(PostgreSQL)]

Sau đó scale theo vấn đề thật:

Chậm vì đọc nhiều? Thêm cache/read replica.
File lớn? Thêm object storage/CDN.
Task chậm? Thêm queue/background worker.
Search phức tạp? Thêm search engine.
Service quá lớn? Tách service.

Nguyên tắc:

Đừng dùng kiến trúc phức tạp để giải quyết vấn đề bạn chưa có.

Mindset 7: Biết giao tiếp bằng sơ đồ

Senior engineer phải biết biến ý tưởng thành hình.

Ví dụ một thiết kế e-commerce cơ bản:

flowchart TD
    User[User] --> Web[Web/Mobile App]
    Web --> API[API Gateway]

    API --> Auth[Auth Service]
    API --> Product[Product Service]
    API --> Order[Order Service]
    API --> Payment[Payment Service]

    Product --> ProductDB[(Product DB)]
    Order --> OrderDB[(Order DB)]
    Payment --> PaymentProvider[Payment Provider]

    Order --> Queue[Message Queue]
    Queue --> Email[Email Worker]
    Queue --> Inventory[Inventory Worker]

Nhìn vào sơ đồ, bạn thấy ngay:

- User đi qua API Gateway
- Auth xử lý đăng nhập
- Product xử lý catalog
- Order xử lý đơn hàng
- Payment gọi cổng thanh toán
- Queue xử lý việc phụ bất đồng bộ

Sơ đồ giúp bạn nhớ lâu hơn vì bạn không còn học từng khái niệm rời rạc.

6. Công thức tư duy khi gặp đề System Design

Khi gặp bất kỳ đề nào, bạn có thể dùng khung này:

1. Clarify requirements
2. Estimate scale
3. Define API
4. Design data model
5. Draw high-level architecture
6. Identify bottlenecks
7. Add scaling strategies
8. Add reliability/failure handling
9. Add security
10. Add observability

Sơ đồ:

flowchart TD
    A[Đề bài] --> B[Clarify Requirements]
    B --> C[Estimate Traffic & Storage]
    C --> D[API Design]
    D --> E[Data Model]
    E --> F[High-level Architecture]
    F --> G[Find Bottlenecks]
    G --> H[Scale]
    H --> I[Reliability]
    I --> J[Security]
    J --> K[Monitoring]

Bạn có thể áp dụng cho mọi bài:

- Design YouTube
- Design Instagram
- Design TikTok
- Design Uber
- Design Shopee
- Design Chat App
- Design URL Shortener
- Design Notification System

7. Ví dụ thực tế: thiết kế URL Shortener

Giả sử đề bài là:

Thiết kế hệ thống rút gọn link như bit.ly.

Nếu tư duy coding

Bạn nghĩ:

- API nhận long URL
- Generate short code
- Save vào database
- Redirect khi user truy cập short URL

Nếu tư duy system design

Bạn hỏi:

Functional:
- User tạo short URL?
- Có custom alias không?
- Có expiration không?
- Có analytics click không?

Non-functional:
- Redirect phải cực nhanh?
- Hệ thống read nhiều hơn write bao nhiêu lần?
- Short URL có cần unique toàn cầu không?
- Có chống spam/phishing không?
- Có rate limit không?

Kiến trúc ban đầu:

flowchart TD
    User[User] --> API[API Server]
    API --> DB[(URL Database)]

Kiến trúc scale hơn:

flowchart TD
    User[User] --> CDN[CDN / Edge]
    CDN --> LB[Load Balancer]
    LB --> API1[API Server 1]
    LB --> API2[API Server 2]

    API1 --> Cache[Redis Cache]
    API2 --> Cache

    Cache --> DB[(Primary DB)]
    DB --> Replica[(Read Replica)]

    API1 --> Queue[Click Event Queue]
    API2 --> Queue
    Queue --> Analytics[Analytics Worker]
    Analytics --> AnalyticsDB[(Analytics DB)]

Tại sao thiết kế như vậy?

- Redirect cần nhanh => dùng cache.
- Read nhiều hơn write => read replica/cache hữu ích.
- Analytics không cần xử lý đồng bộ => đưa vào queue.
- API server scale ngang qua load balancer.
- Database là nguồn dữ liệu chính.

Đây chính là System Design.

8. Những khái niệm bạn phải nhớ từ Bài 1

Scalability

Khả năng hệ thống xử lý tăng trưởng.

100 users -> 10,000 users -> 1,000,000 users

Có 2 kiểu scale:

Vertical scaling: tăng sức mạnh một máy
Horizontal scaling: thêm nhiều máy

Reliability

Khả năng hệ thống hoạt động đúng và ổn định.

Ví dụ:

- Không mất đơn hàng
- Không tạo duplicate payment
- Không mất tin nhắn

Availability

Khả năng hệ thống luôn sẵn sàng phục vụ user.

Ví dụ:

99.9% uptime nghĩa là hệ thống gần như luôn truy cập được.

Latency

Thời gian user chờ response.

Ví dụ:

User click -> 200ms sau thấy kết quả

Throughput

Lượng request hệ thống xử lý trong một khoảng thời gian.

Ví dụ:

10,000 requests/second

Consistency

Dữ liệu có đồng nhất ở mọi nơi không.

Ví dụ:

Bạn chuyển tiền xong, số dư phải cập nhật chính xác.

Fault tolerance

Hệ thống vẫn hoạt động khi một phần bị lỗi.

Ví dụ:

Một app server chết, load balancer chuyển request sang server khác.

[ ] User là ai?
[ ] Tính năng chính là gì?
[ ] Traffic khoảng bao nhiêu?
[ ] Read nhiều hay write nhiều?

[ ] Latency yêu cầu bao nhiêu?
[ ] Thành phần nào dễ thành bottleneck?
[ ] Nếu database/cache/service chết thì sao?
[ ] Có cần cache không?
[ ] Có cần queue không?
[ ] Có cần CDN không?
[ ] Có cần rate limit không?
[ ] Làm sao monitor lỗi?
[ ] Thiết kế này có đơn giản quá không?
[ ] Thiết kế này có phức tạp quá không?

10. Cách ghi nhớ bài này

Bạn chỉ cần nhớ một câu:

System Design = thiết kế cách nhiều thành phần phối hợp với nhau để hệ thống chạy đúng, nhanh, ổn định, bảo mật và mở rộng được.

Hoặc hình dung như sau:

Coding:
"Tôi xây một bánh răng."

System Design:
"Tôi thiết kế cả cỗ máy, biết bánh răng nào nối với bánh răng nào, chỗ nào dễ gãy, chỗ nào cần bôi trơn, và khi máy chạy lớn hơn thì nâng cấp ở đâu."
