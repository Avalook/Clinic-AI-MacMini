Bài 21 — Architecture Evolution

Kiến trúc phần mềm hiếm khi được thiết kế hoàn hảo ngay từ ngày đầu.

Một hệ thống thường tiến hóa theo con đường:

Ứng dụng nhỏ
→ Monolith
→ Modular Monolith
→ Một số services độc lập
→ Microservices ở các khu vực thực sự cần

Sai lầm phổ biến là bắt đầu bằng suy nghĩ:

“Sau này hệ thống sẽ rất lớn,
nên ngay bây giờ phải dùng microservices.”

Điều này thường khiến một đội nhỏ phải vận hành sớm:

- Hàng chục repository
- API calls xuyên service
- Message broker
- Distributed tracing
- Service discovery
- Retry, timeout và circuit breaker
- Distributed transactions
- Nhiều deployment pipelines

trong khi sản phẩm còn chưa xác định rõ business model.

Nguyên tắc trung tâm của bài:

Kiến trúc nên tiến hóa theo độ phức tạp thực tế của sản phẩm, dữ liệu, lưu lượng và tổ chức; không nên tiến hóa theo sơ đồ đẹp hoặc xu hướng công nghệ.

1. Architecture Evolution là gì?

Architecture evolution là quá trình thay đổi cấu trúc hệ thống khi các yêu cầu thay đổi:

- Số người dùng tăng
- Số team tăng
- Business domain phức tạp hơn
- Một số module cần scale riêng
- Release trở nên chậm
- Database trở thành bottleneck
- Reliability requirement tăng
- Data residency thay đổi

Mục tiêu không nhất thiết là:

Monolith → Microservices

Mục tiêu thực sự là:

Kiến trúc hiện tại
→ Kiến trúc phù hợp hơn với constraint hiện tại

Có hệ thống lớn vẫn vận hành tốt dưới dạng modular monolith.

Có hệ thống cần microservices ở một số khu vực nhưng giữ phần còn lại trong monolith.

2. Kiến trúc không phải đích đến cố định

Một kiến trúc tốt hôm nay có thể trở thành kiến trúc không phù hợp sau ba năm.

Ví dụ:

Năm 1:
5 engineers
1 sản phẩm
10.000 users

Năm 3:
50 engineers
10 business capabilities
5 triệu users

Một monolith đơn giản có thể rất hiệu quả năm đầu.

Nhưng khi 10 teams cùng sửa cùng repository và deploy cùng artifact, coordination cost có thể trở thành bottleneck lớn hơn compute cost.

Do đó cần đánh giá đồng thời:

- Technical scale
- Organizational scale
- Product complexity
- Operational maturity

3. Monolith là gì?

Monolith là application được phát triển và triển khai như một đơn vị chính.

flowchart TD
    Users --> Monolith[Monolithic Application]

    Monolith --> Auth[Authentication Code]
    Monolith --> Catalog[Catalog Code]
    Monolith --> Order[Order Code]
    Monolith --> Payment[Payment Code]

    Monolith --> DB[(Shared Database)]

Đặc điểm thường gặp:

- Một codebase hoặc repository chính
- Một deployment artifact
- Các module chạy trong cùng process
- Thường dùng chung database
- Function call nội bộ thay vì network call

Monolith không đồng nghĩa với:

- Code xấu
- Không scale được
- Chỉ chạy trên một server

Một monolith vẫn có thể chạy hàng trăm instances sau load balancer.

4. Monolith vẫn có thể Horizontal Scale

flowchart TD
    Users --> LB[Load Balancer]

    LB --> M1[Monolith Instance 1]
    LB --> M2[Monolith Instance 2]
    LB --> M3[Monolith Instance 3]

    M1 --> DB[(Database)]
    M2 --> DB
    M3 --> DB

Nếu application stateless:

- Tăng instances
- Thêm cache
- Thêm read replicas
- Dùng CDN
- Dùng message queue

Monolith không ngăn horizontal scaling ở application layer.

Bottleneck thực tế thường nằm ở:

- Database
- Shared mutable state
- Một module nóng
- Lock contention
- Deployment coordination

5. Ưu điểm của Monolith

Đơn giản để phát triển

Function call
thay vì
HTTP/gRPC call

Không cần:

- Serialization
- Network retry
- Distributed tracing
- Service discovery

Transaction đơn giản

Nhiều thay đổi có thể nằm trong một local ACID transaction.

BEGIN;

INSERT INTO orders ...;
UPDATE inventory ...;
INSERT INTO payments ...;

COMMIT;

Debug dễ hơn

Một request có thể được trace trong một process.

Deployment đơn giản

Một build, một artifact, một pipeline chính.

Test end-to-end dễ hơn

Không cần khởi động hàng chục services.

Chi phí vận hành thấp

Phù hợp với đội nhỏ và sản phẩm mới.

6. Nhược điểm của Monolith

Khi hệ thống lớn, monolith có thể gặp:

- Build chậm
- Test suite chạy lâu
- Deploy một thay đổi nhỏ phải deploy toàn hệ thống
- Một bug có thể ảnh hưởng toàn process
- Các team chạm vào cùng code
- Module boundaries bị phá
- Database schema trở thành shared global state

Một module sử dụng nhiều CPU có thể buộc phải scale toàn bộ application:

Image Processing cần 100 instances
Order API chỉ cần 10 instances

Nhưng vì cùng monolith:

Phải chạy 100 instances chứa cả hai module

7. Monolith có thể trở thành “Big Ball of Mud”

Monolith xấu thường không phải vì nó là một deployable unit.

Nó xấu vì thiếu boundaries:

Order code gọi trực tiếp bảng Payment
Payment code import Inventory internals
User module sửa Catalog state
Mọi module truy cập mọi table

flowchart TD
    A[Order] <--> B[Payment]
    B <--> C[Inventory]
    C <--> D[User]
    D <--> A
    A <--> C
    B <--> D

Kết quả:

Thay đổi một module
→ không biết module nào khác bị ảnh hưởng

Vấn đề chính là:

High coupling
+
Low cohesion

không phải chỉ là số lượng dòng code.

8. Khi nào Monolith là lựa chọn đúng?

Monolith thường phù hợp khi:

- Team còn nhỏ
- Domain chưa ổn định
- Product-market fit chưa rõ
- Cần thử nghiệm nhanh
- Lưu lượng chưa quá lớn
- Deployment chung chưa tạo bottleneck
- Local transactions mang lại nhiều giá trị

Một đội năm người có thể phát triển nhanh hơn nhiều với một monolith có cấu trúc tốt so với 20 microservices.

9. Modular Monolith

Modular monolith vẫn là một application deploy chung, nhưng code được chia thành các module có boundary rõ.

flowchart TD
    Users --> App[Modular Monolith]

    subgraph App
        Order[Order Module]
        Inventory[Inventory Module]
        Payment[Payment Module]
        Customer[Customer Module]
    end

    Order --> OrderSchema[(Order Tables)]
    Inventory --> InventorySchema[(Inventory Tables)]
    Payment --> PaymentSchema[(Payment Tables)]
    Customer --> CustomerSchema[(Customer Tables)]

Các module giao tiếp qua:

- Public interfaces
- Commands
- Events nội bộ
- DTOs ổn định

Không nên truy cập trực tiếp internals của module khác.

10. Modular Monolith khác Monolith thông thường thế nào?

Đặc điểm Monolith thiếu cấu trúc Modular monolith
Module boundaries Mờ Rõ
Database ownership Mọi code truy cập mọi bảng Mỗi module sở hữu tables
Dependency Tùy ý Có quy tắc
API nội bộ Không rõ Interface rõ
Khả năng tách service Khó Dễ hơn
Deployment Chung Chung
Network calls nội bộ Không Không

Modular monolith giữ được lợi ích của local process nhưng chuẩn bị tốt hơn cho tương lai.

11. Module Boundary

Một module tốt thường bao quanh một business capability.

Ví dụ e-commerce:

Catalog
Inventory
Ordering
Payment
Fulfillment
Customer Support

Không nên chia chỉ theo technical layer:

Controller module
Service module
Repository module
Database module

Các technical layers vẫn có thể tồn tại bên trong từng business module.

12. Business Capability

Business capability là khả năng nghiệp vụ tương đối độc lập.

Ví dụ:

Ordering:
- Tạo order
- Thay đổi order status
- Tính order total
- Quản lý order lifecycle

Payment:
- Tạo payment attempt
- Authorize
- Capture
- Refund
- Reconciliation

Mỗi capability có:

- Business rules
- Data
- State transitions
- Ownership

Đây là ứng viên tự nhiên cho module hoặc service boundary.

13. Bounded Context

Trong Domain-Driven Design, bounded context là phạm vi mà một model và thuật ngữ có nghĩa nhất quán.

Ví dụ từ “Product”:

Catalog context:
Tên, mô tả, hình ảnh

Inventory context:
SKU, quantity, reservation

Pricing context:
Base price, promotion, currency

Shipping context:
Weight, dimensions

Không nên buộc toàn hệ thống dùng một Product object khổng lồ chứa mọi field.

Mỗi context có thể có model riêng.

14. High Cohesion

Các chức năng thay đổi cùng nhau nên nằm cùng nhau.

Ví dụ:

- Payment authorization
- Payment capture
- Payment refund
- Payment reconciliation

có cohesion cao.

Nếu chúng bị tách thành bốn services nhỏ:

Authorization Service
Capture Service
Refund Service
Reconciliation Service

mỗi payment workflow phải đi qua nhiều network calls không cần thiết.

15. Low Coupling

Hai module có coupling thấp khi thay đổi internals của module này ít ảnh hưởng module kia.

Ví dụ Order chỉ biết interface:

reserveInventory(orderId, items)

không biết:

- Inventory tables
- Locking strategy
- Shard layout
- Cache implementation

Boundary tốt che giấu implementation details.

16. Encapsulation trong Modular Monolith

Không tốt:

# Order module
db.execute("""
    UPDATE inventory_items
    SET available = available - 1
    WHERE sku = ?
""")

Order module trực tiếp sửa table Inventory.

Tốt hơn:

inventory.reserve(
    reservation_id=reservation_id,
    items=items,
)

Inventory module tự bảo vệ invariant.

17. Database trong Modular Monolith

Có thể vẫn dùng một physical database nhưng chia ownership logic:

order.*
inventory.*
payment.*
customer.*

Ví dụ:

Order module:
orders
order_items

Inventory module:
stock_items
reservations

Payment module:
payment_attempts
refunds

Quy tắc:

Chỉ module sở hữu dữ liệu mới được phép ghi trực tiếp vào tables đó.

Module khác dùng API nội bộ hoặc event.

18. Có nên dùng Foreign Key xuyên Module?

Foreign key xuyên module tạo coupling schema mạnh.

Ví dụ:

payment_attempts.order_id
FOREIGN KEY → orders.id

Trong modular monolith, điều này có thể chấp nhận trong giai đoạn đầu.

Nhưng nếu dự kiến tách service, cần cân nhắc:

- FK sẽ không tồn tại xuyên database
- Migration khó hơn
- Lifecycle của hai module bị ràng buộc

Có thể giữ ID reference mà không cho phép module khác join tùy ý.

19. Query xuyên Module

Một admin dashboard cần:

Order + Payment + Customer

Không nên vì dashboard mà phá ownership và cho mọi module join mọi table.

Các lựa chọn:

- Application-level composition
- Read-only reporting view
- Materialized projection
- Data warehouse

Đường đọc và đường ghi không nhất thiết dùng cùng model.

20. Modular Monolith mang lại điều gì?

- Local calls nhanh
- Local transactions khi cần
- Một deployment đơn giản
- Boundaries rõ
- Dễ test
- Dễ tách dần sau này

Đây thường là kiến trúc mặc định rất tốt cho:

- Startup
- Internal platform
- Sản phẩm có domain vừa phải
- Team dưới vài chục engineers

Con số cụ thể không phải quy tắc; coordination cost mới là yếu tố quyết định.

21. Microservices là gì?

Microservices architecture chia hệ thống thành nhiều services deploy độc lập.

flowchart TD
    Client --> Gateway

    Gateway --> Order[Order Service]
    Gateway --> Catalog[Catalog Service]
    Gateway --> Customer[Customer Service]

    Order --> Inventory[Inventory Service]
    Order --> Payment[Payment Service]

    Order --> OrderDB[(Order DB)]
    Inventory --> InventoryDB[(Inventory DB)]
    Payment --> PaymentDB[(Payment DB)]
    Catalog --> CatalogDB[(Catalog DB)]

Một service thường có:

- Business capability riêng
- Data ownership riêng
- API hoặc event contracts
- Deployment lifecycle riêng
- Operational ownership rõ

22. “Micro” không nói về số dòng Code

Một service không cần nhỏ đến mức:

200 dòng code

“Micro” nhấn mạnh:

- Scope tập trung
- Ownership rõ
- Khả năng triển khai độc lập

Một service có thể chứa hàng chục nghìn dòng code nhưng vẫn là một boundary hợp lý.

23. Database per Service

Nguyên tắc microservices phổ biến:

Mỗi service sở hữu dữ liệu của mình.

Không nhất thiết mỗi service phải có một database server vật lý riêng.

Có thể:

- Cùng database cluster
- Khác schema
- Khác credentials
- Cấm truy cập chéo

Điểm cốt lõi:

Order Service không trực tiếp sửa Inventory tables.

24. Shared Database Anti-Pattern

Nếu services deploy riêng nhưng cùng đọc/ghi một database schema:

flowchart TD
    Order[Order Service] --> Shared[(Shared Database)]
    Payment[Payment Service] --> Shared
    Inventory[Inventory Service] --> Shared
    Shipping[Shipping Service] --> Shared

Hệ quả:

- Schema thay đổi ảnh hưởng mọi service
- Service không thực sự độc lập
- Transaction boundaries không rõ
- Một query xấu ảnh hưởng toàn hệ thống

Đây thường là một dạng distributed monolith.

25. Distributed Monolith

Distributed monolith có vẻ là microservices nhưng vẫn phải release và hoạt động như một khối.

Dấu hiệu:

- Deploy Order phải deploy Payment cùng lúc
- Một request cần gọi tuần tự 12 services
- Services chia sẻ database
- API thay đổi làm toàn hệ thống vỡ
- Không service nào có thể chạy khi service khác lỗi
- Local development cần khởi động 40 services

Ta nhận:

Complexity của distributed system
+
Coupling của monolith

Đây là trạng thái tệ hơn cả monolith có cấu trúc.

26. Lợi ích thật sự của Microservices

Independent deployment

Payment có thể release mà không deploy Catalog.

Independent scaling

Search:
1.000 instances

Admin:
5 instances

Failure isolation

Lỗi Recommendation không nhất thiết làm Checkout chết.

Team autonomy

Mỗi team sở hữu:

Code
Data
Deployment
On-call
SLO

Technology fit

Một số workload có thể dùng technology khác nhau.

Nhưng không nên biến thành “mỗi service dùng một ngôn ngữ” tùy sở thích.

27. Chi phí của Microservices

- Network latency
- Partial failure
- Timeout và retry
- API versioning
- Distributed tracing
- Data consistency
- Message duplication
- Deployment orchestration
- Service discovery
- Security giữa services
- Nhiều repositories và pipelines
- Nhiều on-call surfaces

Một function call:

result = inventory.reserve(items)

khi chuyển thành network call cần xử lý:

- Request có tới không?
- Server có xử lý nhưng response bị mất không?
- Có nên retry không?
- Retry có duplicate không?
- Timeout bao lâu?
- Circuit breaker khi nào mở?

28. Khi nào Microservices đáng giá?

Microservices thường đáng giá khi có ít nhất một số áp lực rõ ràng:

- Nhiều teams cần deploy độc lập
- Module có scaling profile rất khác
- Failure isolation có giá trị lớn
- Một capability có security/compliance boundary riêng
- Một phần hệ thống cần technology/runtime đặc biệt
- Release coordination trong monolith trở thành bottleneck
- Domain boundaries đã tương đối ổn định

Không nên tách chỉ vì:

- Codebase đã lớn
- Muốn dùng Kubernetes
- Công ty khác dùng microservices
- Muốn “scale trong tương lai”

29. Organizational Scale

Khi một team duy nhất sở hữu monolith:

Coordination đơn giản.

Khi 20 teams cùng sửa:

- Merge conflicts
- Shared release calendar
- Ownership mờ
- Review bottleneck
- Incident khó phân trách nhiệm

Service boundaries có thể giảm coordination giữa teams.

Nhưng boundary sai lại làm tăng coordination qua network contracts.

30. Conway’s Law ở mức trực giác

Cấu trúc hệ thống thường phản ánh cấu trúc giao tiếp của tổ chức.

Nếu teams được tổ chức theo technical layer:

Frontend Team
Backend Team
Database Team
QA Team

mọi feature phải đi qua nhiều team.

Nếu tổ chức theo business capability:

Checkout Team
Catalog Team
Fulfillment Team

mỗi team có thể sở hữu flow end-to-end tốt hơn.

Architecture và team structure nên hỗ trợ nhau.

31. Service Boundary tốt

Một service boundary tốt thường có:

- Business capability rõ
- Data ownership rõ
- Ít synchronous dependencies
- Có thể deploy tương đối độc lập
- SLO và owner rõ
- Failure mode hiểu được

Ví dụ:

Payment Service:
Authorize, capture, refund, payment state, reconciliation

Boundary này có cohesion cao.

32. Chia Service theo Entity có thể sai

Thiết kế:

User Service
Address Service
Email Service
Phone Service

Một thao tác update profile phải gọi bốn services.

Các entities nhỏ không nhất thiết là business capability độc lập.

Tốt hơn có thể là:

Customer Profile Service

bao gồm thông tin cùng lifecycle.

33. Chia theo CRUD thường không đủ

Một service chỉ có:

create/read/update/delete

cho một table chưa chắc có ý nghĩa nghiệp vụ.

Service nên sở hữu behavior và invariants, không chỉ data container.

Ví dụ Payment không chỉ CRUD payment row.

Nó phải bảo vệ:

- Không capture hai lần
- Refund không vượt số đã charge
- State transitions hợp lệ

34. Service Granularity

Service quá lớn:

Khó deploy độc lập
Nhiều team cùng chạm

Service quá nhỏ:

Quá nhiều network calls
Quá nhiều repositories
Workflow phân mảnh

Không có kích thước cố định.

Hãy hỏi:

- Những phần nào thay đổi cùng nhau?
- Những phần nào cần scale cùng nhau?
- Invariant nào phải atomic?
- Team nào sở hữu?

35. Consistency Boundary ảnh hưởng Service Boundary

Nếu hai dữ liệu gần như luôn phải thay đổi atomically, tách chúng sang hai services có thể là sai.

Ví dụ:

Order
và
Order Items

nên thường cùng service.

Tách thành:

Order Service
Order Item Service

biến mọi create order thành distributed transaction.

Nguyên tắc:

Những invariant cần local atomicity thường nên nằm cùng consistency boundary.

36. Synchronous Communication

Ví dụ Order gọi Inventory:

sequenceDiagram
    participant Client
    participant Order
    participant Inventory

    Client->>Order: Create order
    Order->>Inventory: Reserve stock
    Inventory-->>Order: Reserved
    Order-->>Client: Order created

Ưu điểm:

- Kết quả ngay
- Flow dễ hiểu

Nhược điểm:

- Temporal coupling
- Inventory chậm làm Order chậm
- Partial failure
- Retry complexity

37. Asynchronous Communication

sequenceDiagram
    participant Order
    participant Broker
    participant Inventory

    Order->>Broker: OrderCreated
    Broker->>Inventory: OrderCreated
    Inventory->>Broker: InventoryReserved

Ưu điểm:

- Decoupling theo thời gian
- Buffer traffic
- Failure isolation tốt hơn

Nhược điểm:

- Eventual consistency
- Debug khó hơn
- Duplicate/out-of-order
- Workflow state phức tạp

Không nên dùng event cho mọi interaction chỉ để “decouple”.

38. Service phải chịu được Partial Failure

Trong monolith:

Function call thành công hoặc throw exception.

Trong distributed system:

Request timeout

không cho biết chắc:

- Server chưa nhận
- Server đã nhận nhưng chưa xử lý
- Server đã xử lý nhưng response mất

Do đó cần:

- Idempotency
- Timeout
- Retry policy
- Circuit breaker
- Reconciliation

39. Transaction khi tách Service

Monolith:

BEGIN
Create order
Reserve inventory
COMMIT

Microservices:

Order DB
Inventory DB
Payment DB

Không còn một local transaction chung.

Cần:

- Saga
- Reservation
- Outbox
- Idempotency
- Compensation
- Reconciliation

Do đó tách service là thay đổi consistency model, không chỉ thay đổi repository.

Một cách tư duy:

Benefit của independent service
>
Distributed tax của boundary đó

Nếu chưa, giữ module trong monolith thường tốt hơn.

41. Dấu hiệu Monolith cần tiến hóa

Release contention

Nhiều teams phải chờ một release train.

Build/test quá lâu

Một thay đổi nhỏ mất hàng giờ CI.

Scaling không đồng đều

Một module nóng buộc scale toàn application.

Fault propagation

Một memory leak làm toàn hệ thống restart.

Ownership mờ

Không ai chịu trách nhiệm rõ cho capability.

Security boundary

Một phần cần compliance hoặc isolation riêng.

Technology constraint

Ví dụ video transcoding cần runtime khác biệt rõ.

42. Dấu hiệu chưa nên tách

- Module boundaries còn thay đổi hàng tuần
- Chưa có observability tốt
- Chưa có CI/CD ổn định
- Chưa hiểu data ownership
- Team chưa trực on-call
- Không có contract testing
- Không xử lý được retry/idempotency

Microservices khuếch đại những điểm yếu vận hành hiện có.

43. Extract Service hay chỉ Modularize?

Trước khi tạo network boundary, hãy thử:

- Tách package/module
- Tạo interface
- Cấm database access chéo
- Tách schema ownership
- Tách background worker
- Tách deployment pipeline nội bộ

Nếu modularization giải quyết được vấn đề, chưa cần microservice.

44. Service Extraction Candidate

Một module là ứng viên tốt khi:

- Boundary rõ
- Ít transaction xuyên module
- Data ownership rõ
- Có scaling profile riêng
- Có team owner
- API tương đối ổn định
- Có thể chịu eventual consistency

Ví dụ thường dễ tách hơn:

- Notification
- Search indexing
- Image processing
- Reporting
- Recommendation

so với:

- Order và order items
- Seat và active reservation

45. Bắt đầu bằng Peripheral Capability

Không nên lần đầu tách service bằng phần khó nhất như:

Payment ledger
Booking inventory

Có thể bắt đầu:

- Email/Notification
- File processing
- Search indexing
- Audit log

Những phần này giúp đội học:

- Deployment
- Monitoring
- Messaging
- Ownership

với rủi ro thấp hơn.

46. Strangler Pattern

Strangler pattern thay thế hệ thống cũ từng phần thay vì rewrite toàn bộ.

flowchart TD
    Users --> Router[Gateway / Strangler Facade]

    Router -->|Old routes| Legacy[Legacy Monolith]
    Router -->|Migrated routes| New[New Service]

Ban đầu:

100% request → Monolith

Sau đó:

Một nhóm endpoint → New Service

Cuối cùng:

Monolith cũ dần bị “siết lại” và loại bỏ.

47. Vì sao Big-Bang Rewrite nguy hiểm?

Big-bang rewrite thường yêu cầu:

- Viết lại toàn bộ
- Dừng feature development
- Chờ nhiều tháng hoặc năm
- Cutover một lần

Rủi ro:

- Business thay đổi trong lúc rewrite
- Hidden behavior không được ghi lại
- Không có feedback production
- Scope tăng liên tục
- Cutover khó rollback

Strangler cho phép delivery giá trị từng phần.

48. Strangler Facade

Facade hoặc gateway quyết định request đi đâu.

Ví dụ:

/api/v1/search → Search Service
/api/v1/orders → Legacy Monolith
/api/v1/payments → Legacy Monolith

Sau khi Order được tách:

/api/v1/orders → Order Service

Client không cần biết migration nội bộ.

49. Vertical Slice Migration

Nên migrate một capability end-to-end:

API
Business logic
Data ownership
Background jobs
Observability

Không nên chỉ tách controller nhưng vẫn để logic và database trong monolith.

Một vertical slice tạo ownership thực sự.

50. Branch by Abstraction

Thay vì sửa mọi nơi cùng lúc, tạo abstraction:

class InventoryGateway:
    def reserve(self, request):
        ...

Ban đầu implementation gọi code monolith.

Sau đó implementation mới gọi Inventory Service.

Callers không thay đổi.

Pattern này giúp migration dần trong cùng codebase.

51. Anti-Corruption Layer

Hệ thống legacy có model:

customer_record
order_row
payment_flag

Service mới có domain model rõ hơn.

Anti-corruption layer chuyển đổi:

Legacy model
↔
New domain model

Nó ngăn model cũ lan vào service mới.

52. Shadow Traffic

Gửi bản sao request sang service mới nhưng chưa dùng response cho user.

flowchart TD
    Request --> Legacy
    Request -. copy .-> NewService

    Legacy --> Response[User Response]
    NewService --> Compare[Compare Results]

Dùng để kiểm tra:

- Functional differences
- Latency
- Error rate
- Capacity

Không nên shadow các side-effecting writes một cách mù quáng.

53. Dark Launch

Service mới được deploy production nhưng chưa nhận user traffic chính.

Có thể:

- Consume production events
- Xây state
- Chạy synthetic traffic
- Shadow reads

Mục tiêu là kiểm chứng trước cutover.

54. Canary Cutover

Thay vì chuyển 100%:

1%
→ 5%
→ 20%
→ 50%
→ 100%

Theo dõi:

- Error rate
- Latency
- Business invariants
- Data divergence

Cần routing ổn định để cùng user hoặc entity không bị chuyển liên tục giữa hai implementations nếu state chưa đồng bộ.

55. Data Migration là phần khó nhất

Tách code thường dễ hơn tách dữ liệu.

Ban đầu:

Monolith DB:
orders
inventory
payments
customers

Sau tách:

Order DB
Inventory DB
Payment DB

Cần giải quyết:

- Historical data
- Ongoing writes
- Foreign keys
- Joins
- Consistency
- Rollback

56. Shared Database như Trạng thái Chuyển tiếp

Một service mới có thể tạm thời dùng database cũ.

Phase 1:
Code tách, data chưa tách

Phase 2:
Service có credentials giới hạn

Phase 3:
Data được chuyển sang database riêng

Đây có thể là bước migration thực tế.

Nhưng phải có kế hoạch thoát khỏi shared DB; nếu không sẽ dừng ở distributed monolith.

57. Database View để Giảm Coupling

Monolith legacy có schema phức tạp.

Service mới có thể tạm đọc qua view ổn định:

CREATE VIEW order_service_projection AS
SELECT
    order_id,
    customer_id,
    status,
    total
FROM legacy_orders;

View là adapter tạm thời.

Nó không giải quyết write ownership lâu dài.

58. Copy Data bằng Backfill

Quy trình cơ bản:

1. Tạo database mới.
2. Copy historical data.
3. Ghi nhận vị trí hoặc version tại lúc snapshot.
4. Apply changes phát sinh sau snapshot.
5. Catch up.
6. Cutover reads/writes.

flowchart LR
    Legacy[(Legacy DB)] --> Backfill[Historical Backfill]
    Backfill --> New[(New Service DB)]

    Legacy --> CDC[CDC / Change Stream]
    CDC --> New

59. Backfill + CDC

Chỉ backfill không đủ vì writes vẫn tiếp tục.

Ví dụ:

10:00:
Bắt đầu copy

10:10:
User update order

11:00:
Backfill hoàn tất

Nếu không có CDC:

Order update lúc 10:10 có thể thiếu ở DB mới.

CDC hoặc outbox capture delta trong lúc backfill.

60. Snapshot Boundary

Backfill cần biết thay đổi nào thuộc trước hoặc sau snapshot.

Có thể dùng:

- Database log position
- Transaction ID
- Commit timestamp
- Monotonic version

Ví dụ:

Snapshot tại LSN 1000

Backfill snapshot
→ Sau đó replay CDC từ LSN 1001

61. Dual Write rất nguy hiểm

Trong migration, có thể muốn:

Write Legacy DB
Write New DB

Nếu một bên thất bại:

Dữ liệu lệch.

Nếu buộc phải dual-write, cần:

- Durable outbox
- Retry
- Idempotency
- Reconciliation
- Versioning

Ưu tiên:

Một authoritative write
→ Change stream sang hệ thống kia

thay vì hai independent writes trong request path.

62. Chọn Source of Truth trong Migration

Mỗi giai đoạn phải có một nguồn authoritative rõ.

Ví dụ:

Phase 1:
Legacy DB authoritative

Phase 2:
Legacy write, New read shadow

Phase 3:
New DB authoritative
Legacy nhận replicated compatibility data

Phase 4:
Legacy copy bị loại bỏ

Không được để cả hai cùng “có thể đúng”.

63. Read Migration

Quy trình:

1. New service đọc shadow.
2. So sánh kết quả với legacy.
3. Chuyển một phần read traffic.
4. Theo dõi divergence.
5. Chuyển toàn bộ reads.

Read migration thường ít rủi ro hơn write migration.

64. Write Migration

Write cutover cần cẩn thận hơn:

1. Đảm bảo new DB đã catch up.
2. Tạm ổn định hoặc fence old writer.
3. Chuyển ownership epoch.
4. Route writes sang new service.
5. Replicate ngược nếu legacy còn cần đọc.
6. Theo dõi.

Không nên có hai write owners cùng lúc.

65. Fencing khi Chuyển Ownership

Old monolith có thể còn worker hoặc request đang chạy.

Dùng ownership version:

Legacy writer epoch = 7
New service epoch = 8

Database hoặc control plane từ chối writes epoch cũ.

Nếu không, request cũ đến muộn có thể ghi đè state mới.

66. Data Verification

Trước cutover, so sánh:

- Row count
- Checksums
- Per-entity versions
- Aggregate totals
- Business invariants

Ví dụ payment:

Tổng captured amount
Tổng refunded amount
Số payment ở mỗi state

Không chỉ so số row.

67. Reconciliation trong Migration

Sau cutover vẫn cần job kiểm tra:

Legacy order version
vs
New order version

Nếu mismatch:

- Repair tự động
- Re-enqueue event
- Manual review

Migration hoàn tất về routing không có nghĩa dữ liệu chắc chắn hoàn hảo.

68. Zero-Downtime Migration

Zero downtime không có nghĩa không có bất kỳ rủi ro nào.

Nó thường dựa trên:

- Backward compatibility
- Incremental rollout
- Dual-compatible schema
- Online backfill
- Canary
- Rollback

Các thay đổi phải được chia thành nhiều bước nhỏ.

69. Expand–Contract Pattern

Ví dụ đổi column:

full_name
→
first_name + last_name

Không nên:

1. Xóa full_name
2. Deploy code mới

Quy trình an toàn:

Expand

- Thêm first_name và last_name
- Code cũ vẫn chạy

Migrate

- Backfill dữ liệu
- Code mới đọc/ghi field mới
- Có thể tạm ghi cả hai

Contract

- Xác nhận không còn reader cũ
- Xóa full_name

70. Database Schema Migration không Downtime

Thay đổi nguy hiểm:

- Rename column trực tiếp
- Drop column ngay
- Add NOT NULL trên bảng rất lớn
- Rebuild index blocking

Cách an toàn:

- Add nullable column
- Backfill theo batch
- Add validation
- Chuyển reads
- Enforce constraint sau

Cần hiểu locking behavior của database cụ thể.

71. API Backward Compatibility

Service mới có nhiều client versions.

Không nên đổi:

{
  "amount": 100
}

thành:

{
  "totalAmount": 100
}

và xóa amount ngay.

Quy trình:

1. Thêm totalAmount.
2. Giữ amount.
3. Chuyển clients.
4. Theo dõi usage.
5. Loại amount sau deprecation period.

72. Tolerant Reader

Consumer nên bỏ qua field chưa biết nếu contract cho phép.

Producer nên tránh thay đổi breaking:

- Đổi type
- Đổi ý nghĩa
- Xóa field bắt buộc

Event và API evolution cần quy tắc rõ.

73. Event Schema Evolution

Event v1:

{
  "orderId": "o1",
  "amount": 100
}

Event v2:

{
  "orderId": "o1",
  "amount": 100,
  "currency": "VND"
}

Consumer cũ có thể bỏ qua currency.

Consumer mới phải có default cho event v1.

Không nên đổi amount từ integer minor units sang decimal major units mà giữ cùng tên và không version.

74. Consumer-Driven Contract Testing

Provider thay API cần biết client nào bị ảnh hưởng.

Consumer contract mô tả expectation:

Order Service kỳ vọng Inventory response có:
reservationId
status
expiresAt

CI của Inventory kiểm tra contract trước khi release.

Contract test không thay thế integration test, nhưng giảm breaking changes.

75. Zero-Downtime Deployment

Các chiến lược:

- Rolling deployment
- Blue–green
- Canary

Rolling

Thay instances từng phần.

Cần version cũ và mới cùng hoạt động trong một thời gian.

Blue–green

Hai environments đầy đủ:

Blue = current
Green = new

Chuyển traffic nhanh.

Canary

Chuyển tỷ lệ traffic nhỏ trước.

76. Version Skew

Trong rolling deployment:

Instance v1
Instance v2

cùng chạy.

Do đó:

- API nội bộ phải tương thích
- Database schema phải dùng được cho cả hai
- Events không được làm consumer cũ crash

Mọi migration phải giả định có version skew.

77. Rollback không phải lúc nào cũng đơn giản

Code v2 đã ghi dữ liệu theo schema mới.

Rollback về v1 có thể không đọc được.

Do đó cần:

- Forward-compatible schema
- Feature flags
- Reversible data changes
- Roll-forward plan

Nhiều tình huống roll-forward an toàn hơn rollback binary cũ.

78. Feature Flags

Feature flag tách:

Code deployment

khỏi:

Feature activation

Có thể:

- Deploy code tắt
- Bật cho internal users
- Bật 1%
- Tăng dần

Nhưng flags cũng tạo complexity:

- Nhiều code paths
- Flag stale
- Configuration dependency

Flag cần owner và expiration.

79. Migration by Feature Flag

Ví dụ chuyển từ legacy pricing sang Pricing Service.

pricing_service_enabled:
false → true

Theo:

- Tenant
- Region
- User cohort
- Request percentage

Nếu có lỗi:

Tắt flag
→ quay lại legacy path

Chỉ an toàn nếu data writes vẫn tương thích.

80. Observability trước khi Tách Service

Trước extraction, cần biết:

- Module được gọi bao nhiêu?
- Latency ở đâu?
- Dependencies nào?
- Error rate?
- Database queries?
- Business invariants?

Nếu không có telemetry, team sẽ tách dựa trên phỏng đoán.

81. Observability sau khi Tách

Mỗi request cần:

- Trace ID
- Correlation ID
- Service name
- Version
- Region

Theo dõi:

- Synchronous call latency
- Retry count
- Circuit breaker state
- Queue lag
- Event processing failures
- Data reconciliation mismatch

Microservices không có distributed tracing sẽ rất khó debug.

82. SLO theo Service và User Journey

Service SLO:

Inventory Reserve:
99.95% dưới 200 ms

Nhưng user journey:

Checkout:
Order + Inventory + Payment + Confirmation

có thể tệ hơn vì nhiều dependencies.

Cần cả:

- Service-level SLO
- End-to-end business SLO

83. Reliability giảm theo Dependency Chain

Nếu một request gọi tuần tự năm services, mỗi service availability 99.9% và độc lập hoàn toàn:

End-to-end availability xấp xỉ:
0,999^5 ≈ 99,5%

Đây chỉ là mô hình minh họa; failure thực tế không độc lập.

Thông điệp:

Nhiều synchronous dependencies có thể làm reliability tổng giảm đáng kể.

85. API Composition

87. Local Read Model

94. Authorization xuyên Service

Service vẫn cần kiểm tra authorization cho resource mình sở hữu.

Không nên phụ thuộc toàn bộ vào gateway cho các operation nhạy cảm.

flowchart TD

    App --> Notification

Team:

8 engineers

catalog/
cart/

sequenceDiagram

102. Bước 6 — Inventory và Ordering

110. Các sai lầm phổ biến

Lỗi 1: Bắt đầu bằng Microservices quá sớm

Tạo distributed complexity trước khi có domain ổn định.

Lỗi 2: Nghĩ Monolith không Scale

Monolith vẫn có thể horizontal scale.

Lỗi 3: Không Modularize trước khi Tách

Service boundaries được chọn từ code rối, dẫn đến coupling qua network.

Lỗi 4: Một Service cho mỗi Table

Tạo quá nhiều calls và distributed transactions.

Lỗi 5: Shared Database giữa Services

Services không thực sự độc lập.

Lỗi 6: Tách Code nhưng không Tách Ownership

Monolith vẫn quyết định data và release của service mới.

Lỗi 7: Tách Boundary có nhiều Invariant Atomic

Biến local transaction thành Saga không cần thiết.

Lỗi 8: Mọi Interaction đều Synchronous

Tạo dependency chain dài và reliability thấp.

Lỗi 9: Mọi Interaction đều Event-Driven

Flow khó hiểu và debug dù không cần async.

Lỗi 10: Big-Bang Rewrite

Rủi ro cao, feedback chậm, rollback khó.

Lỗi 11: Dual-Write DB Cũ và Mới không kiểm soát

Dữ liệu lệch sau partial failure.

Lỗi 12: Không xác định Source of Truth trong Migration

Hai databases cùng được coi là authoritative.

Lỗi 13: Cutover Write trước khi Data Catch Up

Service mới thiếu state.

Lỗi 14: Không Fence Writer Cũ

Legacy request có thể ghi sau cutover.

Lỗi 15: Drop Column ngay khi Deploy Code mới

Instances cũ vẫn có thể đang chạy.

Lỗi 16: API/Event Breaking Change trực tiếp

Consumers không nâng cấp đồng thời.

Lỗi 17: Không có Observability trước Extraction

Không biết behavior cũ để so sánh.

Lỗi 18: Không có Rollback hoặc Roll-Forward Plan

Migration lỗi trở thành incident kéo dài.

Lỗi 19: Mỗi Team tự xây Platform riêng

Operational fragmentation tăng.

Lỗi 20: Tách quá nhiều Services

Nhận distributed monolith thay vì autonomy.

111. Cách trình bày trong System Design Interview

Không nên nói:

Ban đầu em dùng microservices để dễ scale.

Nên nói:

Tôi bắt đầu bằng modular monolith vì domain còn thay đổi nhanh và local transactions giúp giữ business logic đơn giản. Các module được chia theo business capability, mỗi module sở hữu tables và chỉ expose public interfaces. Application stateless nên vẫn có thể horizontal scale sau load balancer.

Khi nói về evolution:

Tôi chỉ tách một module khi có áp lực rõ như scaling profile riêng, yêu cầu failure isolation hoặc một team cần deploy độc lập. Các capability async và ít phụ thuộc như notification, search indexing hoặc media processing thường được tách trước. Tôi tránh một service trên mỗi entity vì điều đó tạo chatty calls và distributed transactions.

Về migration:

Tôi dùng strangler pattern. Gateway chuyển từng route sang service mới. Dữ liệu lịch sử được backfill từ snapshot, sau đó CDC bắt các thay đổi mới. Legacy DB vẫn là source of truth cho tới khi new store bắt kịp và verification đạt yêu cầu. Write cutover sử dụng ownership epoch để fence writer cũ, sau đó chạy reconciliation trước khi xóa legacy path.

Về zero downtime:

Schema migration dùng expand–migrate–contract. Tôi thêm field mới trước, deploy code hỗ trợ cả schema cũ và mới, backfill online, chuyển reads/writes rồi chỉ xóa field cũ khi không còn instances hoặc consumers cũ. API và event changes cũng phải backward compatible trong giai đoạn version skew.
