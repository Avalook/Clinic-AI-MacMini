Bài 33 — Case Study 12: Thiết kế Distributed Web Crawler

Distributed Web Crawler là hệ thống tự động:

Nhận một tập URL ban đầu
→ Chọn URL được phép crawl
→ Tải nội dung
→ Phân tích trang
→ Trích xuất liên kết mới
→ Chuẩn hóa và loại trùng URL
→ Đưa URL hợp lệ trở lại hàng đợi
→ Lặp lại

Crawler là nền tảng của:

- Công cụ tìm kiếm
- Hệ thống lưu trữ web
- Price comparison
- News aggregation
- SEO monitoring
- Security scanning
- Dataset collection
- Broken-link detection

Bề ngoài, crawler chỉ cần gửi HTTP request và lấy HTML. Nhưng một crawler production phải xử lý:

- Hàng tỷ URL
- Hàng triệu domain và host
- robots.txt khác nhau
- Giới hạn tốc độ cho từng website
- DNS lỗi hoặc chậm
- Redirect loops
- Duplicate URL và duplicate content
- Infinite calendars và URL parameters
- Website trả nội dung động
- Retry mà không tấn công website
- Lịch recrawl khác nhau cho từng trang
- Multi-region nhưng vẫn giữ politeness toàn cục

Kiến trúc cốt lõi:

Seeds
→ URL normalization và deduplication
→ URL frontier
→ Host-aware scheduler
→ DNS và robots policy
→ Fetchers
→ Parser
→ Content deduplication
→ Link extraction
→ Frontier

1. Xác định phạm vi

Ta thiết kế một crawler web tổng quát hỗ trợ:

1. Nhận seed URLs.
2. Crawl HTTP và HTTPS.
3. Tôn trọng robots.txt.
4. Tôn trọng crawl-delay hoặc policy nội bộ.
5. Giới hạn concurrency theo host/domain.
6. Theo dõi redirect.
7. Chuẩn hóa URL.
8. Loại URL trùng.
9. Phân tích HTML và trích xuất links.
10. Loại content trùng hoặc gần trùng.
11. Retry lỗi tạm thời.
12. Phát hiện crawler traps.
13. Lên lịch recrawl.
14. Scale nhiều máy và nhiều region.

Tạm chưa đi sâu vào:

- Xếp hạng kết quả tìm kiếm
- Full web indexing
- Semantic understanding
- Browser engine hoàn chỉnh
- CAPTCHA solving
- Bypass anti-bot systems
- Crawl nội dung yêu cầu đăng nhập

Crawler phải hoạt động có trách nhiệm, không cố vượt qua các cơ chế kiểm soát truy cập.

2. Functional Requirements

URL ingestion

- Nhận seed URLs.
- Nhận URLs từ parser.
- Nhận sitemap URLs.
- Nhận URLs từ external feeds.

Fetching

- HTTP GET và HEAD khi phù hợp.
- Redirect handling.
- Compression.
- Conditional requests.
- Timeouts.
- Response size limits.

Policy

- robots.txt.
- Politeness.
- Domain allowlist/denylist.
- Content-type filtering.
- Crawl budget.

Parsing

- Parse HTML.
- Extract links.
- Resolve relative URLs.
- Extract canonical URL.
- Extract metadata.
- Detect language/content type.

Scheduling

- New URL scheduling.
- Retry scheduling.
- Recrawl scheduling.
- Priority.
- Per-host pacing.

3. Non-Functional Requirements

- Không gửi quá nhiều request tới một host.
- Không crawl URL bị robots.txt cấm.
- Không fetch cùng URL quá nhiều lần không cần thiết.
- Có khả năng xử lý hàng tỷ URL.
- Không để một domain lớn chiếm toàn bộ tài nguyên.
- Không để một host lỗi làm treo worker.
- Dữ liệu frontier phải durable.
- Duplicate processing phải idempotent.
- Có thể phục hồi sau worker hoặc region failure.
- Dễ mở rộng thêm fetchers và parsers.

4. Những khái niệm chính

Seed URL

URL khởi đầu:

https://example.com/
https://news.example.org/

URL frontier

Tập các URL đang chờ được crawl.

Fetcher

Worker tải nội dung qua HTTP.

Parser

Phân tích response và trích xuất links.

Politeness

Không gửi request quá nhanh hoặc quá nhiều tới cùng website.

Recrawl

Crawl lại trang đã từng fetch để phát hiện thay đổi.

5. Capacity Estimation

Giả sử mục tiêu:

10 tỷ URL đã biết
1 tỷ URL crawl mỗi ngày
Average response body = 500 KB

Average fetch rate:

1.000.000.000 / 86.400
≈ 11.600 requests/giây

Peak:

≈ 50.000–100.000 requests/giây

Bandwidth raw:

1 tỷ × 500 KB
≈ 500 TB/ngày

Chưa tính:

- HTTP headers
- Retries
- Redirects
- Compression differences
- Rendered resources
- Replication

Crawler thường bị giới hạn bởi:

- Network bandwidth
- Remote host politeness
- DNS
- Parsing CPU
- Storage throughput

không chỉ bởi số lượng worker.

Giả sử 300 bytes/URL:

7. High-Level Architecture

flowchart TD
    Seeds[Seed URLs / Sitemaps / External Feeds] --> Ingest[URL Ingestion]

    Ingest --> Normalize[URL Normalize + Canonicalize]
    Normalize --> URLDedup[URL Deduplication]
    URLDedup --> Frontier[(Distributed URL Frontier)]

    Frontier --> Scheduler[Host-Aware Scheduler]
    Scheduler --> Robots[Robots Policy Service]
    Scheduler --> DNS[DNS Resolver / Cache]
    Scheduler --> FetchQueue[Ready Fetch Queue]

    FetchQueue --> Fetchers[Distributed Fetchers]
    Fetchers --> RawStore[(Raw Content Store)]
    Fetchers --> ResponseEvents[Fetch Result Stream]

    ResponseEvents --> Parser[HTML / Content Parser]
    Parser --> ContentDedup[Content Deduplication]
    Parser --> LinkExtractor[Link Extraction]

    LinkExtractor --> Normalize
    ContentDedup --> IndexPipeline[Downstream Index / Archive]

    ResponseEvents --> RetryScheduler[Retry / Recrawl Scheduler]
    RetryScheduler --> Frontier

9. URL Frontier là gì?

URL frontier không chỉ là một FIFO queue.

Nó phải quyết định:

- URL nào có priority cao hơn?
- Host nào đã đủ thời gian chờ?
- Website nào đang bị rate limited?
- URL nào đang retry?
- URL nào cần recrawl?
- URL nào đã hết crawl budget?

Một frontier tốt kết hợp:

Priority scheduling
+
Per-host politeness
+
Delayed scheduling
+
Durability

10. Vì sao một Queue toàn cục không đủ?

Nếu đặt mọi URL vào một queue:

example.com/a
example.com/b
example.com/c
other.com/x

Nhiều workers có thể lấy ba URL đầu cùng lúc và bombard example.com.

Ngoài ra:

- Không kiểm soát khoảng cách giữa requests cùng host.
- Một domain lớn có thể chiếm queue.
- Không hỗ trợ delayed retry tốt.

Cần host-aware scheduling.

11. Kiến trúc Frontier hai tầng

Một mô hình phổ biến:

Front queues:
Sắp xếp theo priority.

Back queues:
Sắp xếp theo host và politeness.

flowchart LR
    NewURLs --> P0[Priority Queue 0]
    NewURLs --> P1[Priority Queue 1]
    NewURLs --> P2[Priority Queue 2]

    P0 --> Selector[Priority Selector]
    P1 --> Selector
    P2 --> Selector

    Selector --> H1[Host Queue example.com]
    Selector --> H2[Host Queue news.com]
    Selector --> H3[Host Queue shop.com]

    H1 --> HostHeap[Next-Eligible-Time Heap]
    H2 --> HostHeap
    H3 --> HostHeap

    HostHeap --> Fetchers

12. Front Queues theo Priority

Priority có thể dựa trên:

- Seed importance
- Page quality
- Link depth
- Domain reputation
- Page freshness
- Sitemap priority
- Historical change frequency
- Product/business value

Ví dụ:

Priority 0:
Critical news/homepages

Priority 1:
Recently changed pages

Priority 2:
Normal discovered links

Priority 3:
Deep/low-value pages

13. Không để Low-Priority Starvation

Nếu luôn chọn priority cao nhất:

Low-priority URLs có thể không bao giờ được crawl.

Có thể dùng weighted scheduling:

Priority 0: 50%
Priority 1: 30%
Priority 2: 15%
Priority 3: 5%

Hoặc aging:

URL chờ càng lâu
→ effective priority tăng

14. Back Queue theo Host

Mỗi host có queue riêng:

example.com
→ /a
→ /b
→ /c

Scheduler chỉ cho host đó xuất URL khi:

now >= nextEligibleFetchTime(host)

Sau khi dispatch:

nextEligibleFetchTime =
now + politenessDelay

15. Next-Eligible-Time Heap

Scheduler giữ min-heap:

(nextEligibleTime, hostId)

Host có thời gian nhỏ nhất được chọn trước.

Nếu chưa tới thời gian:

Scheduler ngủ hoặc chờ delayed queue.

Điều này hỗ trợ hàng triệu host mà không cần poll tất cả.

Cần phân biệt:

Politeness có thể áp theo:

- Host

17. Vì sao chỉ Rate Limit theo Host chưa đủ?

Các host:

a.example.com
b.example.com
c.example.com

có thể cùng trỏ tới một server/IP.

Nếu mỗi host được crawl mạnh:

Cùng một origin infrastructure vẫn bị quá tải.

Có thể áp nhiều tầng:

- Per-host limit
- Per-domain limit
- Per-IP limit
- Global network limit

18. Politeness

Politeness có hai thành phần:

1. Delay giữa requests.
2. Maximum concurrent requests.

Ví dụ:

example.com:
delay = 2 giây
maxConcurrency = 1

Website lớn hoặc crawler được phép có thể:

delay = 100 ms
maxConcurrency = 8

19. Adaptive Politeness

Không nên dùng cùng delay cho mọi host.

Có thể dựa trên:

- robots.txt crawl-delay nếu hỗ trợ
- Historical response latency
- HTTP 429/503 rate
- Server capacity signals
- Site size
- Explicit crawl agreement

Ví dụ:

Host trả 429
→ Tăng delay

Host phản hồi nhanh, không lỗi
→ Có thể tăng dần concurrency trong giới hạn

20. Politeness phải được phối hợp toàn cục

Nếu ba regions cùng crawl example.com độc lập:

Mỗi region nghĩ mình chỉ gửi 1 request/giây
→ Website thực tế nhận 3 request/giây.

Multi-region cần:

- Một host owner duy nhất
- Hoặc distributed global rate limiter
- Hoặc partition host ranges theo region

Host ownership thường đơn giản hơn.

21. URL Canonicalization và Normalization

Cùng một tài nguyên có thể có nhiều URL forms:

HTTP://EXAMPLE.COM:80/a
http://example.com/a
http://example.com/a#section

URL normalization giảm duplicate crawl.

Nhưng normalization quá mạnh có thể gộp hai tài nguyên khác nhau.

22. Các bước URL Normalization an toàn

Có thể:

- Lowercase scheme.
- Lowercase host.
- Remove default port.
- Normalize percent encoding.
- Remove fragment.
- Resolve dot segments.
- Normalize empty path thành "/".
- Convert IDN host sang canonical form.

Ví dụ:

HTTPS://Example.COM:443/a/../b#top

thành:

https://example.com/b

23. Fragment

Phần sau # thường không được gửi tới server:

https://example.com/page#section1
https://example.com/page#section2

HTTP fetch giống nhau.

Crawler thường bỏ fragment.

Ngoại lệ:

Single-page applications

có thể dùng client-side routing, nhưng crawler không nên mặc định coi mọi hash route là tài nguyên khác.

24. Query Parameters

URL:

/product?id=123&utm_source=email

utm_source thường không thay đổi nội dung chính.

Nhưng:

/product?color=red
/product?color=blue

có thể khác nội dung.

Không thể xóa mọi query parameter.

Cần:

- Parameter allowlist/denylist.
- Per-domain rules.
- Canonical tag.
- Content similarity feedback.

25. Query Parameter Ordering

Các URL:

/search?a=1&b=2
/search?b=2&a=1

có thể tương đương, nhưng không phải mọi server đều xử lý như nhau.

Chỉ sort query parameters khi policy cho phép.

Một normalization an toàn hơn:

Giữ semantics gốc,
nhưng có thể tạo secondary fingerprint để phát hiện duplicates.

26. Trailing Slash

https://example.com/docs
https://example.com/docs/

có thể:

- Giống nhau
- Redirect
- Hoàn toàn khác

Không tự động gộp nếu chưa có evidence.

Có thể học từ redirect hoặc canonical tag.

27. Percent Encoding

Các URL:

/a%2Fb
/a/b

không phải lúc nào tương đương.

Normalization phải hiểu:

- Reserved characters
- Unreserved characters

Chỉ decode/normalize unreserved characters an toàn.

28. URL Identity

Một URL record nên có:

canonicalNormalizedUrl
urlHash
hostId
discoveredFrom
depth
firstSeenAt
lastSeenAt

urlHash giúp:

- Dedup lookup
- Partitioning
- Compact storage

Nhưng collision phải được xử lý hoặc dùng hash đủ mạnh.

29. URL Deduplication

Mục tiêu:

Không đưa cùng normalized URL vào frontier nhiều lần không cần thiết.

Các cách:

- Exact key-value set
- Database unique constraint
- Bloom filter
- Cuckoo filter
- Partitioned URL registry

30. Exact URL Registry

Record:

urlHash
normalizedUrl
crawlState
lastFetchAt
nextFetchAt

Ưu điểm:

- Chính xác
- Hỗ trợ metadata

Nhược điểm:

- Storage và lookup lớn

31. Bloom Filter

Bloom filter trả lời:

URL có thể đã thấy chưa?

Đặc điểm:

- Không có false negative.
- Có false positive.

False positive:

URL mới bị coi nhầm là đã thấy
→ Có thể bỏ lỡ crawl.

Phù hợp như L1 filter trước exact registry, không nhất thiết làm source of truth duy nhất.

32. Layered URL Dedup

Một thiết kế:

1. In-process cache cho URLs rất gần đây.
2. Bloom filter theo shard.
3. Exact URL registry.

Flow:

L1 miss
→ Bloom says definitely new
→ Exact insert

Bloom says maybe exists
→ Check exact registry

33. URL Discovery Idempotency

Parser có thể phát hiện cùng link từ nhiều pages.

Command:

DiscoverURL(normalizedUrl, sourcePageId)

Insert dùng unique key trên normalized URL.

Nếu đã tồn tại:

- Cập nhật in-link count.
- Cập nhật lastSeenAt.
- Có thể tăng priority.

Không enqueue bản sao mới vô điều kiện.

34. Canonical URL từ HTML

Trang có thể khai báo:

<link rel="canonical" href="https://example.com/article">

Crawler có thể dùng để:

- Nhóm duplicates.
- Chọn URL đại diện.
- Giảm indexing trùng.

Nhưng canonical tag chỉ là hint.

Website có thể cấu hình sai hoặc độc hại.

35. Redirect Canonicalization

Nếu:

http://example.com
→ 301
https://www.example.com/

Crawler có thể ghi:

source URL
→ redirect target

Permanent redirects là tín hiệu canonical mạnh hơn temporary redirects.

Cần giới hạn redirect chain.

36. Redirect Handling

Các status:

301 / 308:
Permanent

302 / 307:
Temporary

303:
See Other

Crawler cần:

- Resolve relative Location header.
- Normalize target.
- Check robots cho target.
- Deduplicate target.
- Detect loop.

37. Redirect Loop

Ví dụ:

A → B
B → C
C → A

Cần:

- Visited URLs trong chain.
- Maximum redirect hops, ví dụ 10.

Nếu vượt:

REDIRECT_LOOP hoặc TOO_MANY_REDIRECTS

38. robots.txt

Crawler tải:

https://example.com/robots.txt

File có thể chứa:

User-agent: *
Disallow: /private/
Allow: /private/public/

Crawler phải xác định:

URL nào được phép fetch cho user-agent của mình.

39. Robots Policy Service

Trách nhiệm:

- Fetch robots.txt.
- Parse rules.
- Cache policy.
- Apply theo user-agent.
- Track expiration.
- Handle unavailable robots.

Không nên mỗi fetcher tự tải robots độc lập.

40. Robots Cache

Key:

origin/host + crawlerUserAgent

Value:

rules
fetchedAt
expiresAt
HTTP status
ETag
Last-Modified

Robots thường cache vài giờ hoặc một ngày, nhưng policy tùy crawler.

41. robots.txt Fetch cũng cần Politeness

Không được mỗi worker cùng nhận URL mới của host và đồng thời tải robots.txt.

Dùng single-flight:

Một worker fetch robots.
Các requests khác chờ policy.

42. Robots Failure Policy

Các trường hợp:

404

Thường được hiểu:

Không có robots file
→ Không có rule cấm

401/403

Có thể xem là không được crawl hoặc áp policy thận trọng.

5xx/timeout

Không nên ngay lập tức crawl toàn site.

Có thể:

- Retry robots.
- Temporarily pause host.
- Dùng cached policy cũ nếu còn hợp lệ.

43. Robots và Redirect

robots.txt có thể redirect.

Cần giới hạn redirects và xác định policy rõ.

Không để redirect robots sang domain tùy ý làm thay đổi quyền crawl của host gốc.

44. Sitemap

robots.txt có thể khai báo:

Sitemap: https://example.com/sitemap.xml

Sitemap giúp:

- Discover pages không được link trực tiếp.
- Nhận lastmod.
- Nhận cấu trúc lớn.

Crawler nên xử lý sitemap riêng với size/depth limits.

45. Sitemap Index

Một sitemap index có thể trỏ tới nhiều sitemap:

<sitemapindex>
  <sitemap>
    <loc>https://example.com/sitemap-1.xml</loc>
  </sitemap>
</sitemapindex>

Cần:

- Recursion limit.
- Entry count limit.
- Compression limit.
- Domain policy.

46. DNS Resolution

Fetcher cần:

host → IP addresses

DNS có thể trở thành bottleneck nếu mọi request tự resolve.

Cần:

- Shared DNS cache.
- Async resolver.
- TTL.
- Negative caching.
- Resolver redundancy.

47. DNS Cache

Record:

host
A/AAAA records
TTL
resolvedAt
status

Không giữ IP quá TTL tùy tiện vì host có thể đổi địa chỉ.

Nhưng TTL quá ngắn tạo DNS load lớn.

48. Negative DNS Caching

Nếu host không tồn tại:

NXDOMAIN

cache trong khoảng phù hợp.

Không retry DNS mỗi giây cho domain lỗi.

Nhưng negative cache cũng phải có expiry vì DNS có thể được tạo sau.

49. DNS Rebinding và SSRF

Crawler fetch URLs từ nguồn không đáng tin.

Attacker có thể đưa URL trỏ tới:

- 127.0.0.1
- 169.254.169.254
- Internal database
- Private network

Crawler phải chống SSRF.

50. Network Egress Policy

Trước fetch:

- Resolve DNS.
- Kiểm tra tất cả IP.
- Chặn private, loopback, link-local, metadata ranges.
- Kiểm tra lại sau redirect.
- Kiểm tra lại khi DNS thay đổi.

Không chỉ validate hostname text.

51. DNS Pinning

Giữa lúc kiểm tra và kết nối, DNS có thể đổi.

An toàn hơn:

1. Resolve.
2. Validate IP.
3. Kết nối trực tiếp tới IP đã validate.
4. Gửi đúng Host/SNI.

Redirect target lại phải được resolve và validate riêng.

52. Fetcher Architecture

Fetcher worker chịu trách nhiệm:

- Nhận fetch task.
- Resolve DNS.
- Mở connection.
- Gửi HTTP request.
- Enforce timeout.
- Enforce size limit.
- Stream response.
- Tính checksum.
- Ghi raw response.
- Phát result event.

Không nên parser nặng ngay trong fetcher.

53. Fetch Task

{
  "fetchTaskId": "ft_123",
  "urlId": "url_456",
  "url": "https://example.com/article",
  "hostId": "host_789",
  "robotsPolicyVersion": 12,
  "maxBytes": 10485760,
  "deadline": "...",
  "attempt": 1
}

Task cần stable ID để retry idempotently.

54. HTTP Request Headers

Crawler thường gửi:

User-Agent
Accept
Accept-Encoding
If-None-Match
If-Modified-Since

User-Agent nên minh bạch và có contact information khi phù hợp.

Không giả mạo browser nếu không có lý do hợp lệ.

55. Connection Pooling

Reuse TCP/TLS connections giảm:

- Handshake latency
- CPU
- Network overhead

Nhưng phải tôn trọng:

- Per-host concurrency
- Connection timeout
- Server keep-alive policy

Fetcher pool có thể giữ connections theo origin.

56. HTTP/2 và HTTP/3

Multiplexing có thể tăng hiệu quả, nhưng:

Một connection có thể gửi nhiều streams cùng lúc.

Politeness vẫn phải giới hạn request concurrency logic.

Không vì HTTP/2 hỗ trợ 100 streams mà crawler gửi 100 requests đồng thời.

57. Timeouts

Cần nhiều timeout riêng:

- DNS timeout
- Connection timeout
- TLS timeout
- Header timeout
- Idle read timeout
- Overall deadline

Một timeout tổng duy nhất khó debug và không xử lý slowloris tốt.

58. Response Size Limit

Website có thể trả file cực lớn hoặc vô hạn.

Cần:

- Maximum Content-Length.
- Maximum streamed bytes.
- Per-content-type limits.
- Early abort.

Ví dụ:

HTML: 10 MB
PDF: 100 MB
Video: không crawl hoặc giới hạn riêng

59. Content-Type Filtering

Crawler có thể chỉ quan tâm:

text/html

application/pdf
text/plain

Nếu không cần media:

image/*
video/*
application/octet-stream

có thể bỏ hoặc lưu metadata בלבד.

Không tin hoàn toàn Content-Type; có thể sniff có kiểm soát.

60. Compression Bomb

Cần giới hạn:

- Compressed bytes
- Decompressed bytes
- Expansion ratio
- CPU time

Không chỉ kiểm tra Content-Length của compressed body.

61. Streaming Fetch

Không nên giữ toàn response trong RAM.

Flow:

→ Size/checksum enforcement
→ Raw content storage
→ Parser stream hoặc event

Giúp xử lý responses lớn và giảm memory pressure.

Retry-After

69. Retry Budget

Không retry vô hạn.

- Max retry age.
- Host circuit breaker.

Sau ngưỡng:

DEAD / DEFERRED

và recrawl sau thời gian dài hơn.

Nội dung có khả năng gần trùng.

86. Faceted Navigation Explosion

101. Fetch Scheduling Idempotency

103. Crawl Generation

Một URL có thể được crawl nhiều lần theo thời gian.

Attempt:
Retry trong cùng planned crawl.

105. URL Registry và Frontier tách nhau

URL Registry lưu long-lived metadata:

URL đã biết
last fetch
content hash
next fetch

Frontier chỉ chứa pending scheduling state.

Không nên giữ toàn bộ lịch sử URL trong queue system.

106. Frontier Partitioning

Có thể partition theo:

hostHash

Lợi ích:

Mọi URL cùng host về cùng scheduler shard.

Điều này giúp:

- Politeness.
- Host queue.
- Host circuit breaker.
- Robots cache locality.

107. Hot Host

Một domain lớn có hàng tỷ URL.

Nếu toàn host nằm một shard:

Hot shard.

Các lựa chọn:

- Giữ scheduling owner duy nhất nhưng phân tán storage.
- Chia host queues theo path, phối hợp rate limiter.
- Dedicated scheduler cho large domains.
- Virtual shards với một host-level token allocator.

Politeness vẫn cần một điểm coordination logic.

108. Domain Fairness

Một site lớn không nên chiếm mọi fetch slot.

Scheduler có thể giới hạn:

- Slots/host.
- Slots/domain.
- Bytes/day/domain.
- URLs/day/domain.

Kết hợp weighted fair queuing giữa hosts.

109. Multi-Region Architecture

flowchart TD
    GlobalSeeds --> GlobalRegistry[(Global URL Registry)]
    GlobalRegistry --> HostDirectory[Host Ownership Directory]

    HostDirectory --> RegionA[Scheduler Region A]
    HostDirectory --> RegionB[Scheduler Region B]

    RegionA --> FetchA[Fetchers A]

110. Host Ownership theo Region

Mỗi host được gán một scheduling owner:

hostId → ownerRegion

Mọi URL của host được fetch từ owner region hoặc thông qua owner scheduler.

Lợi ích:

- Politeness toàn cục.
- Robots policy nhất quán.
- DNS cache locality.
- Dễ theo dõi crawl budget.

111. Chọn Owner Region

Có thể dựa trên:

- Latency tới host.
- DNS/IP geography.
- Network egress cost.
- Legal constraints.
- Regional capacity.

Không cần owner gần người dùng; crawler không có interactive user latency.

112. Host Migration giữa Regions

Khi cần rebalance:

1. Pause host scheduling.
2. Drain in-flight leases.
3. Transfer host frontier state.
4. Increase host owner epoch.
5. Activate new region.

Không để hai regions cùng crawl host trong lúc chuyển.

113. Host Owner Epoch

Host state có:

ownerRegion
ownerEpoch

Fetch task chứa epoch.

Result từ epoch cũ có thể được lưu nhưng không được dùng để cập nhật scheduling state nếu đã bị fence.

114. Multi-Region URL Dedup

URL discovery từ nhiều regions có thể trùng.

Cần:

- Global exact registry.
- Hoặc partition URL ownership theo host/hash.

Vì host đã có owner, normalized URLs của host có thể route về cùng registry shard.

115. Content Storage Multi-Region

Raw content có thể:

- Ghi vào region fetch.
- Replicate async.
- Dùng object storage global.

Metadata cần ghi:

content object location
replication status
checksum

Crawler có thể chấp nhận RPO khác nhau tùy mục tiêu archive hay search.

116. Data Residency và Legal Policy

Một crawler có thể cần:

- Không lưu một số nội dung ngoài region.
- Tuân thủ takedown.
- Không crawl domain bị hạn chế.
- Xóa nội dung theo retention.

Policy phải áp cho:

- Raw content
- Extracted text
- Screenshots
- Search index
- Backups

117. Failure Mode — Scheduler Worker chết

Task leases hết hạn và được giao lại.

Host next-eligible time phải được lưu durable hoặc có thể reconstruct.

Không để restart làm mất politeness delay và gửi burst.

118. Failure Mode — Frontier Store lỗi

Có thể:

- Dừng dispatch mới.
- Cho in-flight fetches hoàn thành.
- Buffer discovered URLs có giới hạn.
- Replay từ event log/outbox.

Không dùng memory queue duy nhất.

119. Failure Mode — URL Registry chậm

Parser không nên block vô hạn.

Có thể:

- Buffer discovery events.
- Batch dedup inserts.
- Backpressure parsers.

Không enqueue URLs mù nếu registry unavailable lâu.

120. Failure Mode — Robots Service lỗi

Không fail-open cho host chưa có policy.

Có thể:

- Dùng cache còn hiệu lực.
- Pause host.
- Retry robots.

Với host đã có policy cũ, có thể dùng stale policy trong giới hạn theo internal rules.

121. Failure Mode — DNS Resolver lỗi

Dùng nhiều resolver pools.

Nếu lỗi toàn cục:

- Pause new fetches.
- Dùng cache còn TTL.
- Không dùng IP stale quá policy.

122. Failure Mode — Fetcher chết giữa Response

Lease hết và task retry.

Partial body object phải:

- Có temporary object ID.
- Chỉ publish khi complete/checksum verified.
- Được GC nếu bỏ dở.

123. Failure Mode — Raw Content lưu thành công nhưng Result Event mất

Dùng transactional metadata/outbox hoặc write-ahead result record:

Fetch result committed
+
Processing event intent

Parser có thể replay.

124. Failure Mode — Parser lỗi

Raw response vẫn tồn tại.

Parser task retry hoặc được gửi tới dead-letter queue.

Một parser bug không nên buộc fetch lại website.

125. Failure Mode — Parser tạo URL Storm

Một malformed page có hàng triệu links.

Giới hạn:

- Maximum links/page.
- Maximum unique links/page.
- Maximum processing time.
- Per-page discovered URL budget.

126. Failure Mode — Domain trả 429 hàng loạt

Scheduler:

- Tăng delay.
- Giảm concurrency.
- Tôn trọng Retry-After.
- Mở host circuit breaker.

Không để nhiều workers retry độc lập.

127. Failure Mode — Domain đổi robots.txt

Robots cache hết hạn và fetch version mới.

URLs trước đây được phép có thể bị cấm.

Frontier phải recheck robots policy trước dispatch, không chỉ lúc discovery.

128. Failure Mode — Duplicate Fetch Results

Hai workers fetch cùng generation do lease race.

Consumer chọn một accepted result bằng conditional state transition:

FETCHING generation 17
→ FETCHED generation 17

Result thứ hai trở thành duplicate/audit record.

129. Failure Mode — Region Partition

Nếu owner region mất liên lạc:

Không nên tự động để region khác crawl cùng host ngay lập tức.

Cần:

- Lease/epoch expiry.
- Authoritative owner failover.
- Fencing.

Financial correctness không cần, nhưng politeness và duplicate cost vẫn quan trọng.

130. Security Isolation

Fetcher và parser phải chạy trong sandbox vì nội dung không đáng tin.

Cần:

- No internal network access.
- Read-only runtime.
- Resource limits.
- Ephemeral filesystem.
- Restricted syscalls.
- Frequent patching.

131. MIME Confusion

Server có thể khai báo:

text/html

nhưng trả binary hoặc ngược lại.

Type detector cần:

- Header
- Magic bytes
- Safe sniffing

Không tự động thực thi nội dung.

132. Authentication và Cookies

General public crawler thường không lưu session cookies giữa hosts.

Nếu crawler hỗ trợ authenticated crawl:

- Cookie jar phải tenant-scoped.
- Secrets phải được bảo vệ.
- Không leak cookie qua redirect domain.
- Crawl scope phải giới hạn.

Đây là một mode riêng, không nên trộn với public crawler.

142. Thiết kế Khuyến nghị

Một thiết kế cân bằng:

1. URL Registry lưu identity và lịch sử URL.
2. Frontier được partition theo host owner.
3. Front queues xử lý priority.
4. Back queues xử lý politeness theo host.
5. Scheduler dùng next-eligible-time heap.
6. Robots và DNS được cache tập trung theo host.
7. Fetchers chỉ tải và lưu raw content.
8. Parsers xử lý async và phát discovered URLs.
9. URL dedup dùng Bloom filter + exact registry.
10. Content dedup dùng exact hash và near-duplicate fingerprint.

143. Trade-Off — FIFO hay Priority Frontier?

FIFO

- Đơn giản.
- Công bằng theo thời điểm đến.
- Không đảm bảo important pages fresh.

Priority

- Crawl tài nguyên quan trọng trước.
- Có nguy cơ starvation.

Khuyến nghị:

Weighted priority + aging.

144. Trade-Off — Per-Host Queue hay Global Rate Limiter?

Per-host queue

- Politeness tự nhiên.
- Host locality tốt.
- Hot-host sharding khó.

Global rate limiter

- Linh hoạt.
- Coordination lớn.
- Mỗi fetch cần distributed check.

Host-owned queues thường hiệu quả hơn.

145. Trade-Off — Exact URL Set hay Bloom Filter?

Exact set

- Không false positive.
- Storage và lookup lớn.

Bloom filter

- Memory nhỏ.
- Có false positive.

Kết hợp:

Bloom làm prefilter
+
Exact registry làm authority.

146. Trade-Off — Full Raw Content hay Chỉ Extracted Data?

Lưu raw content

- Có thể reparse.
- Audit tốt.
- Storage lớn.

Chỉ lưu extracted content

- Storage thấp.
- Parser bug buộc refetch.

Search crawler lớn thường lưu raw content ít nhất một khoảng retention.

147. Trade-Off — Fetch Rendered JavaScript hay Chỉ HTML?

HTTP HTML

- Nhanh.
- Rẻ.
- Bỏ lỡ nội dung động.

Headless rendering

- Coverage tốt.
- CPU/memory rất đắt.
- Security risk cao.

Dùng two-tier rendering theo priority.

148. Trade-Off — Global Host Ownership hay Regional Independent Crawl?

Global host owner

- Politeness chính xác.
- Failover/migration phức tạp.

Regions crawl độc lập

- Kiến trúc đơn giản cục bộ.
- Duplicate fetch và quá tải website.

Crawler toàn cầu nên có coordination theo host/domain.

149. Trade-Off — Recrawl thường xuyên hay Coverage rộng?

Frequent recrawl

- Freshness cao.
- Ít budget cho URLs mới.

Broad discovery

- Coverage cao.
- Pages cũ stale.

Scheduler phải tối ưu theo page value và change probability.

150. Cách trình bày trong Phỏng vấn

Có thể mở đầu:

Tôi xem URL frontier là phần trung tâm của crawler. Nó không phải FIFO queue mà là scheduler kết hợp priority, delayed retries và politeness theo host. Mỗi host có queue riêng và thời điểm được fetch tiếp theo.

Về URL:

Mọi URL được normalize thận trọng, loại fragment, chuẩn hóa host và default port, sau đó deduplicate qua Bloom filter và exact URL registry. Tôi không xóa query parameters tùy tiện; canonical tags, redirects và content fingerprints chỉ được xem là signals.

Về fetch:

Fetchers là stateless workers nhận task có lease, kiểm tra DNS/SSRF, robots policy version và response limits. Raw response được stream vào object storage, còn parsing và link extraction chạy bất đồng bộ để parser lỗi không buộc fetch lại.

Về multi-region:

Mỗi host có một owner region để giữ politeness toàn cục. Tất cả URLs của host route tới owner scheduler. Failover tăng owner epoch và fence task cũ để hai regions không crawl cùng host đồng thời.
