Bài 7 — CDN và Object Storage

CDN và Object Storage thường xuất hiện cùng nhau trong các hệ thống phục vụ:

- Ảnh
- Video
- Audio
- File tải xuống
- CSS, JavaScript
- Thumbnail
- Avatar
- Backup
- Tài liệu người dùng upload

Nhưng chúng giải quyết hai vấn đề khác nhau:

Object Storage:
Lưu file bền vững.

CDN:
Phân phối file nhanh đến người dùng ở nhiều vị trí địa lý.

Các tài liệu System Design bạn cung cấp đặt CDN trong nhóm thành phần quan trọng để giảm latency và giảm tải server gốc khi phục vụ nội dung tĩnh hoặc media ở quy mô lớn.

1. Vấn đề khi lưu file trực tiếp trên application server

Giả sử bạn xây một ứng dụng cho phép user upload avatar.

Kiến trúc đơn giản:

flowchart LR
    User --> App[Application Server]
    App --> Disk[(Local Disk)]

Khi user upload file:

/avatar/user_123.jpg

file được lưu trên ổ đĩa của application server.

Cách này có thể hoạt động cho prototype nhỏ, nhưng sẽ nhanh chóng gặp vấn đề.

1.1 Không scale ngang tốt

Giả sử có ba application server:

flowchart TD
    User --> LB[Load Balancer]
    LB --> A1[App Server 1]
    LB --> A2[App Server 2]
    LB --> A3[App Server 3]

User upload ảnh vào Server 1.

Request xem ảnh sau đó được load balancer gửi đến Server 2.

Server 2 không có file.

Server 1:
Có avatar.jpg

Server 2:
Không có avatar.jpg

Server 3:
Không có avatar.jpg

Bạn có thể dùng shared filesystem, nhưng nó lại tạo thêm bottleneck và complexity.

1.2 Server chết có thể mất file

Nếu file chỉ nằm trong local disk và máy bị hỏng:

- Avatar mất
- Tài liệu mất
- Video mất
- Backup cũng có thể mất

Application server thường được thiết kế để có thể thay thế hoặc scale động. Vì thế không nên phụ thuộc vào local disk để lưu dữ liệu người dùng quan trọng.

1.3 Deploy trở nên khó khăn

Container hoặc virtual machine có thể bị:

- Restart
- Replace
- Auto-scale down
- Redeploy

Local storage thường không phải nơi phù hợp để lưu file bền vững.

1.4 Application server phải gánh bandwidth

Nếu mỗi ảnh có kích thước 2 MB và có 10.000 lượt tải mỗi giây:

10.000 × 2 MB
= 20.000 MB/s
= 20 GB/s

Application server phải dùng CPU, network connection và bandwidth chỉ để truyền file.

Đây là công việc CDN và object storage làm tốt hơn.

2. Object Storage là gì?

Object Storage là hệ thống lưu dữ liệu dưới dạng object.

Mỗi object thường gồm:

- Key hoặc object name
- File content
- Metadata
- Bucket/container

Ví dụ:

Bucket:
user-uploads

Object key:
avatars/user_123/7f9a2c.jpg

Content:
Dữ liệu ảnh

Metadata:
Content-Type: image/jpeg
Size: 240 KB
Uploaded-By: user_123

Các dịch vụ phổ biến:

Amazon S3
Google Cloud Storage
Azure Blob Storage
Cloudflare R2
MinIO

3. Object Storage khác filesystem như thế nào?

Filesystem tổ chức dữ liệu theo thư mục và file:

/home/app/uploads/avatar.jpg

Object storage tổ chức dữ liệu theo bucket và key:

s3://user-uploads/avatars/user_123/avatar.jpg

Mặc dù key trông giống thư mục:

avatars/user_123/avatar.jpg

nó thường chỉ là một chuỗi key có prefix, không nhất thiết là thư mục thật như filesystem.

So sánh

Tiêu chí Local filesystem Object storage
Đơn vị lưu File Object
Khả năng scale Giới hạn theo máy Scale rất lớn
Durability Phụ thuộc máy Thường rất cao
Truy cập File path API/HTTP
Chia sẻ nhiều server Khó hơn Tự nhiên
Metadata Hạn chế Linh hoạt
Phù hợp File local, tạm thời Media, backup, upload
Thay đổi một phần file Dễ hơn Thường phải ghi lại object

4. Khi nào dùng Object Storage?

Phù hợp cho:

- Ảnh
- Video
- Audio
- PDF
- User uploads
- Log archive
- Database backup
- Static website files
- Machine learning datasets
- Large downloadable files

Không phải lựa chọn tự nhiên cho:

- Query dữ liệu quan hệ
- Transaction
- Update một field nhỏ trong record
- Search theo nhiều thuộc tính
- Lock và concurrency phức tạp

Metadata nghiệp vụ vẫn thường nằm trong database.

Ví dụ:

Object storage:
Nội dung file thật

Database:
file_id
owner_id
object_key
mime_type
size
status
created_at
permissions

5. Object Storage không thay thế Database

Giả sử user upload một ảnh.

Object storage giữ:

photos/user_123/photo_456.jpg

Database giữ:

{
  "id": "photo_456",
  "ownerId": "user_123",
  "objectKey": "photos/user_123/photo_456.jpg",
  "status": "ready",
  "visibility": "private",
  "sizeBytes": 2845000,
  "createdAt": "2026-07-10T08:00:00Z"
}

Tại sao cần database?

Vì ứng dụng cần query:

- Ảnh nào thuộc user này?
- Ảnh có public không?
- Ảnh đã xử lý xong chưa?
- Ảnh thuộc album nào?
- Ai được quyền xem?

Object storage chỉ biết object key và metadata cơ bản. Nó không nên thay relational hoặc application database cho nghiệp vụ.

6. CDN là gì?

CDN — Content Delivery Network là một mạng lưới server phân bố ở nhiều khu vực địa lý.

Các server gần người dùng được gọi là:

Edge server
Point of Presence — PoP
Edge location

Mục tiêu:

Đưa nội dung đến gần user hơn.

Thay vì user ở Việt Nam tải ảnh từ server gốc tại Mỹ, CDN có thể phục vụ ảnh từ một edge ở Singapore, Bangkok hoặc khu vực gần hơn.

7. Origin và Edge

Origin

Origin là nơi chứa bản gốc của nội dung.

Có thể là:

- Object storage
- Web server
- Application server
- Media server

Edge

Edge là server CDN nằm gần người dùng và lưu bản cache của nội dung.

flowchart LR
    UserVN[User Việt Nam] --> EdgeAsia[CDN Edge châu Á]
    UserEU[User châu Âu] --> EdgeEU[CDN Edge châu Âu]
    UserUS[User Mỹ] --> EdgeUS[CDN Edge Mỹ]

    EdgeAsia --> Origin[(Object Storage Origin)]
    EdgeEU --> Origin
    EdgeUS --> Origin

8. CDN hoạt động như thế nào?

Giả sử user truy cập:

https://cdn.example.com/images/product-123.jpg

Lần đầu tại một edge

sequenceDiagram
    participant User
    participant Edge
    participant Origin

    User->>Edge: GET product-123.jpg
    Edge->>Edge: Cache lookup
    Note over Edge: Cache miss
    Edge->>Origin: Fetch original file
    Origin-->>Edge: File
    Edge->>Edge: Store in cache
    Edge-->>User: File

Các lần tiếp theo

sequenceDiagram
    participant User
    participant Edge

    User->>Edge: GET product-123.jpg
    Edge->>Edge: Cache lookup
    Note over Edge: Cache hit
    Edge-->>User: File

Origin không bị gọi lại cho tới khi:

- Cache hết TTL
- File bị purge
- Edge eviction file
- URL thay đổi

9. CDN giúp gì?

9.1 Giảm latency

Khoảng cách địa lý ngắn hơn:

User Việt Nam → Edge châu Á

thay vì:

User Việt Nam → Origin Mỹ

9.2 Giảm tải origin

Một file được xem một triệu lần không có nghĩa object storage phải phục vụ một triệu lần.

Phần lớn request được xử lý ở edge.

9.3 Giảm bandwidth origin

Nội dung lớn như video và ảnh được phân phối từ CDN.

9.4 Hấp thụ traffic spike

Ví dụ một bài viết viral hoặc flash sale.

Nếu nội dung đã được cache ở edge, origin không phải chịu toàn bộ traffic.

9.5 Tăng availability

Nếu một edge có lỗi, CDN có thể route sang edge khác hoặc về origin.

Tuy nhiên CDN không thay thế hoàn toàn chiến lược high availability của origin.

10. Push CDN và Pull CDN

10.1 Pull CDN

Đây là mô hình phổ biến.

Khi edge cache miss, CDN tự fetch từ origin.

User → CDN
       ↓ miss
     Origin

Ưu điểm:

- Dễ triển khai
- Không cần chủ động upload đến từng edge
- Chỉ cache nội dung có traffic

Nhược điểm:

- Request đầu tiên chậm hơn
- Origin bị gọi khi cache miss

10.2 Push CDN

Hệ thống chủ động đẩy nội dung lên CDN trước khi user request.

Phù hợp khi:

- Nội dung chắc chắn sẽ rất hot
- Live event
- Software release
- Game patch
- Video premiere

Nhược điểm:

- Quản lý phức tạp hơn
- Có thể push nội dung không được dùng

Phần lớn ứng dụng thông thường dùng pull CDN kết hợp prewarming khi cần.

11. Cache-Control là gì?

Cache-Control là HTTP header hướng dẫn browser, proxy và CDN cách cache response.

Ví dụ:

Cache-Control: public, max-age=3600

Ý nghĩa:

- Response có thể được shared cache lưu
- Có thể dùng trong 3.600 giây

12. Các directive quan trọng

12.1 public

Cache-Control: public, max-age=3600

Response có thể được cache bởi:

- Browser
- CDN
- Shared proxy

Phù hợp dữ liệu công khai.

12.2 private

Cache-Control: private, max-age=60

Chỉ cache ở client riêng, không nên lưu ở shared CDN.

Phù hợp:

- User profile riêng
- Dashboard cá nhân
- Dữ liệu tùy user

12.3 no-store

Cache-Control: no-store

Không được lưu response.

Phù hợp:

- Dữ liệu tài chính nhạy cảm
- Token
- Thông tin bí mật
- Payment response

12.4 no-cache

Tên dễ gây nhầm.

Cache-Control: no-cache

Không có nghĩa “không được lưu”.

Nó có nghĩa:

Có thể lưu, nhưng phải revalidate với origin trước khi sử dụng lại.

12.5 max-age

Cache-Control: max-age=3600

Thời gian browser hoặc cache có thể xem response là fresh.

12.6 s-maxage

Cache-Control: public, max-age=60, s-maxage=3600

Ý nghĩa:

Browser cache:
60 giây

Shared cache/CDN:
3.600 giây

s-maxage thường dùng để điều khiển CDN riêng biệt với browser.

12.7 immutable

Cache-Control: public, max-age=31536000, immutable

Nói với client:

Nội dung URL này sẽ không thay đổi.

Phù hợp với versioned assets:

app.7f9a2c.js
logo.a12b9e.png

12.8 stale-while-revalidate

Cache-Control: public, max-age=300, stale-while-revalidate=60

Sau 5 phút, CDN có thể tạm trả bản cũ trong thêm 60 giây trong khi refresh background.

Giúp tránh request chờ origin.

12.9 stale-if-error

Cache-Control: public, max-age=300, stale-if-error=86400

Nếu origin lỗi, cache được phép trả dữ liệu cũ.

Rất hữu ích để tăng availability cho nội dung không quá nhạy về freshness.

13. ETag và conditional request

Origin có thể trả:

ETag: "photo-123-v7"

Lần sau client hoặc CDN gửi:

If-None-Match: "photo-123-v7"

Nếu file không đổi:

304 Not Modified

Không cần gửi lại toàn bộ file.

sequenceDiagram
    participant Client
    participant Server

    Client->>Server: GET file + If-None-Match v7
    Server->>Server: Compare ETag
    Server-->>Client: 304 Not Modified

Điều này giảm bandwidth.

14. Last-Modified

Server có thể trả:

Last-Modified: Fri, 10 Jul 2026 08:00:00 GMT

Client gửi:

If-Modified-Since: Fri, 10 Jul 2026 08:00:00 GMT

Nếu chưa thay đổi:

304 Not Modified

ETag thường chính xác hơn vì dựa trên version hoặc content hash.

15. Cache invalidation trên CDN

Giả sử URL:

https://cdn.example.com/logo.png

File đã được cache 24 giờ.

Bạn thay logo nhưng giữ nguyên URL.

Các edge có thể tiếp tục trả logo cũ.

Có ba chiến lược chính.

15.1 Chờ TTL hết

Đơn giản nhưng nội dung cũ tồn tại cho tới khi TTL hết.

15.2 Purge/invalidate CDN

Gửi yêu cầu xóa:

/logo.png

khỏi các edge.

Ưu điểm:

- Nội dung mới xuất hiện nhanh

Nhược điểm:

- Purge có thể mất thời gian
- Tốn chi phí
- Có rate limit
- Có thể gây origin spike sau purge

15.3 Versioned URL

Thay vì giữ:

/logo.png

dùng:

/logo.v1.png
/logo.v2.png

Hoặc content hash:

/logo.7f9a2c.png

Khi nội dung đổi, URL đổi.

File cũ vẫn cache nhưng không còn được tham chiếu.

Đây thường là cách tốt nhất cho static assets.

Cache-Control: public, max-age=31536000, immutable

16. Vì sao không nên overwrite cùng một object key?

Giả sử avatar:

avatars/user_123/avatar.jpg

User thay avatar nhưng key không đổi.

CDN, browser và proxy có thể vẫn giữ ảnh cũ.

Tốt hơn:

avatars/user_123/64f2a9.jpg

Khi upload ảnh mới:

avatars/user_123/b81c7d.jpg

Database cập nhật URL mới.

Lợi ích:

- Không cần purge ngay
- Cache được đặt TTL rất dài
- Tránh user thấy ảnh cũ
- Rollback dễ hơn

Đây gọi là immutable object naming hoặc versioned key.

17. Luồng upload truyền thống

Một cách đơn giản:

sequenceDiagram
    participant Client
    participant API
    participant Storage

    Client->>API: Upload file
    API->>Storage: Store file
    Storage-->>API: Success
    API-->>Client: Upload complete

Client upload toàn bộ file qua application server.

Vấn đề:

- Application server gánh bandwidth
- File lớn chiếm connection lâu
- Tốn memory hoặc temporary disk
- Khó scale
- Timeout dễ xảy ra

Với video 2 GB, đây là thiết kế không tối ưu.

18. Upload trực tiếp bằng signed URL

Thiết kế tốt hơn:

Client xin quyền upload từ API.
API tạo signed URL.
Client upload trực tiếp vào object storage.

sequenceDiagram
    participant Client
    participant API
    participant DB
    participant Storage

    Client->>API: POST /uploads
    API->>DB: Create pending file record
    API-->>Client: Signed upload URL + object key

    Client->>Storage: PUT file using signed URL
    Storage-->>Client: Upload success

    Client->>API: Confirm upload
    API->>Storage: Verify object metadata
    API->>DB: Mark file as uploaded
    API-->>Client: File ready or processing

Application server không truyền file.

Nó chỉ:

- Xác thực user
- Kiểm tra quyền
- Chọn object key
- Tạo signed URL
- Lưu metadata

19. Signed URL là gì?

Signed URL là URL tạm thời chứa chữ ký cho phép thực hiện một hành động giới hạn.

Ví dụ quyền:

PUT một object cụ thể
trong vòng 10 phút
với content type image/jpeg
và kích thước tối đa nhất định

Signed URL có thể dùng cho:

- Upload
- Download
- Xem file private

Nó cho phép client giao tiếp trực tiếp với storage mà không cần storage bucket public.

20. Tại sao Signed URL an toàn hơn bucket public?

Bucket private:

Không ai truy cập trực tiếp nếu không có quyền.

API sau khi xác thực user tạo URL có thời hạn:

Expires in 5 minutes
Allowed method: GET
Allowed object: private/user_123/report.pdf

Sau khi hết hạn, URL không còn hợp lệ.

21. Signed URL không phải authorization hoàn chỉnh

Một sai lầm:

Có signed URL nghĩa là file được bảo vệ hoàn toàn.

Thực tế:

  • Ai có URL còn hiệu lực thường có thể dùng nó.
  • URL có thể bị chia sẻ.
  • URL có thể xuất hiện trong log hoặc history.
  • Sau khi phát hành, khó thu hồi ngay nếu TTL dài.

Do đó:

- TTL nên ngắn
- Chỉ cấp sau khi kiểm tra authorization
- Không chứa secrets khác trong URL
- Dùng HTTPS
- Không log toàn bộ query string nhạy cảm

22. Signed URL cho upload

Ví dụ client yêu cầu:

POST /v1/uploads
Authorization: Bearer <token>

{
  "fileName": "avatar.jpg",
  "contentType": "image/jpeg",
  "sizeBytes": 250000
}

API trả:

{
  "uploadId": "upl_123",
  "objectKey": "uploads/user_456/upl_123/original.jpg",
  "uploadUrl": "https://storage.example.com/...",
  "expiresAt": "2026-07-10T08:10:00Z"
}

Client upload:

PUT <signed-upload-url>
Content-Type: image/jpeg

Sau đó confirm:

POST /v1/uploads/upl_123/complete

23. Tại sao cần bước confirm?

Signed URL được tạo không có nghĩa file đã upload thành công.

Database có thể có record:

status = pending

Sau khi client confirm, API kiểm tra:

- Object có tồn tại không?
- Size có đúng không?
- Content type có phù hợp không?
- Checksum có đúng không?

Sau đó chuyển:

pending → uploaded → processing → ready

24. Đừng tin Content-Type từ client

Client có thể nói:

Content-Type: image/jpeg

nhưng file thật lại là executable hoặc nội dung khác.

Nên kiểm tra:

- Magic bytes/file signature
- MIME type thực tế
- File size
- Image dimensions
- Virus/malware scan
- File extension

Không nên chỉ tin tên file:

malware.exe.jpg

25. Luồng xử lý ảnh sau upload

Ảnh gốc thường không được phục vụ trực tiếp ngay.

flowchart TD
    Client --> Storage[(Original Upload)]
    Storage --> Event[Object Created Event]
    Event --> Queue[Processing Queue]
    Queue --> Worker[Image Worker]

    Worker --> Scan[Malware Scan]
    Worker --> Resize[Resize]
    Worker --> Compress[Compress]
    Worker --> Metadata[Extract Metadata]

    Resize --> Derived[(Derived Images)]
    Derived --> CDN[CDN]
    Worker --> DB[(Update status = ready)]

Có thể tạo:

original.jpg
thumbnail_200.jpg
medium_800.jpg
large_1600.jpg

Client nhận kích thước phù hợp thay vì luôn tải ảnh gốc.

26. Tại sao xử lý media nên bất đồng bộ?

Upload ảnh/video có thể cần:

- Scan virus
- Resize
- Compress
- Transcode
- Generate thumbnail
- Extract metadata
- Content moderation

Các tác vụ này có thể mất vài giây hoặc vài phút.

Không nên giữ HTTP request mở cho tới khi hoàn tất.

Luồng tốt hơn:

Upload xong
→ Trả trạng thái processing
→ Worker xử lý
→ Cập nhật ready

27. Video transcoding

Một video upload có thể cần chuyển thành nhiều chất lượng:

240p
360p
480p
720p
1080p
4K

Và nhiều bitrate.

flowchart LR
    Original[Original Video] --> Transcoder[Transcoding Workers]
    Transcoder --> V1[360p]
    Transcoder --> V2[720p]
    Transcoder --> V3[1080p]
    V1 --> Storage[(Object Storage)]
    V2 --> Storage
    V3 --> Storage
    Storage --> CDN[CDN]

Tại sao?

User có:

- Thiết bị khác nhau
- Màn hình khác nhau
- Tốc độ mạng khác nhau

Streaming system chọn chất lượng phù hợp.

28. Adaptive bitrate streaming

Video thường được chia thành các đoạn nhỏ:

segment_001.ts
segment_002.ts
segment_003.ts

Hoặc các format tương đương.

Client đo tốc độ mạng và chuyển bitrate.

Mạng tốt:
1080p

Mạng giảm:
720p

Mạng yếu:
360p

CDN cache các segment này rất hiệu quả vì chúng là object tĩnh và immutable.

29. Multipart upload

File lớn không nên upload bằng một request duy nhất.

Ví dụ video 10 GB.

Multipart upload chia file thành nhiều phần:

Part 1: 10 MB
Part 2: 10 MB
Part 3: 10 MB
...

flowchart TD
    Client --> P1[Upload Part 1]
    Client --> P2[Upload Part 2]
    Client --> P3[Upload Part 3]

    P1 --> Storage
    P2 --> Storage
    P3 --> Storage

    Storage --> Complete[Complete Multipart Upload]

Ưu điểm:

- Upload song song
- Retry riêng phần lỗi
- Không phải upload lại toàn file
- Phù hợp mạng không ổn định

30. Resumable upload

Nếu upload bị ngắt ở 80%, user không muốn bắt đầu lại.

Resumable upload ghi nhận:

- Upload ID
- Các part đã hoàn thành
- Checksum từng part
- Expiration

Client tiếp tục phần còn thiếu.

Cần cleanup các multipart upload bị bỏ dở để tránh tốn storage.

31. Checksum

Checksum giúp kiểm tra file có bị lỗi trong quá trình upload không.

Ví dụ:

MD5
SHA-256
CRC

Client hoặc storage tính checksum.

Nếu checksum không khớp:

Upload bị corrupt hoặc sai dữ liệu.

Với multipart upload, có thể kiểm tra từng part.

32. Download file public

File public có thể đi theo luồng:

flowchart LR
    User --> CDN
    CDN --> ObjectStorage[(Public or protected origin)]

URL:

https://cdn.example.com/public/products/p_123/image.7f9a.jpg

Cache-Control:

Cache-Control: public, max-age=31536000, immutable

Phù hợp khi object key không thay đổi nội dung.

33. Download file private

Ví dụ:

- Hóa đơn
- Hồ sơ cá nhân
- Tài liệu nội bộ
- Video trả phí

Không nên để bucket public.

Luồng:

sequenceDiagram
    participant User
    participant API
    participant CDN
    participant Storage

    User->>API: Request private file
    API->>API: Authenticate + authorize
    API-->>User: Signed download URL

    User->>CDN: GET signed URL
    CDN->>Storage: Fetch if needed
    Storage-->>CDN: File
    CDN-->>User: File

34. Signed URL và Signed Cookie

Signed URL

Quyền gắn với một URL cụ thể.

Phù hợp:

- Download một file
- Xem một ảnh private
- Upload một object

Signed Cookie

Quyền có thể áp dụng cho một nhóm URL.

Phù hợp:

- Xem nhiều video segment
- Truy cập cả thư mục nội dung
- Streaming private media

Ví dụ một video có hàng trăm segment. Tạo signed URL cho từng segment có thể không thuận tiện; signed cookie có thể phù hợp hơn.

35. Origin protection

Nếu CDN dùng object storage làm origin, cần tránh user bỏ qua CDN và gọi origin trực tiếp.

Nếu không:

- Không tận dụng cache
- Origin bị abuse
- Có thể bypass security rule
- Tăng bandwidth cost

Giải pháp:

- Bucket private
- Chỉ cho CDN identity truy cập origin
- Origin access control
- Firewall
- Signed origin request

Luồng mong muốn:

User → CDN → Private Origin

Không phải:

User → Private Origin trực tiếp

36. Origin shield

Trong CDN lớn, nhiều edge có thể cùng cache miss.

Nếu 100 edge cùng request một file từ origin, origin nhận 100 request.

Origin shield thêm một tầng cache trung gian:

flowchart TD
    E1[Edge 1] --> Shield[Origin Shield]
    E2[Edge 2] --> Shield
    E3[Edge 3] --> Shield
    E4[Edge 4] --> Shield

    Shield --> Origin[(Origin)]

Origin có thể chỉ nhận một request.

Đây giống request coalescing ở cấp CDN.

37. Cache key của CDN

CDN cần quyết định request nào là cùng một object cache.

Cache key có thể bao gồm:

- Host
- Path
- Query string
- Header
- Cookie

Ví dụ:

/image.jpg?width=200
/image.jpg?width=800

Nếu width ảnh hưởng response, query phải thuộc cache key.

Nhưng nếu query chỉ là tracking:

/image.jpg?utm_source=email

không nên tạo một cache entry mới cho mỗi tracking parameter.

38. Sai cache key có thể gây rò rỉ dữ liệu

Giả sử response thay đổi theo:

Authorization: Bearer user-token

nhưng CDN cache key chỉ dựa trên URL:

/account

Response của User A có thể bị trả cho User B.

Do đó private API response thường:

Cache-Control: private

hoặc:

Cache-Control: no-store

Shared CDN chỉ nên cache khi cache key và authorization model được thiết kế rất cẩn thận.

39. CORS khi upload trực tiếp

Khi browser upload trực tiếp vào object storage, storage phải cho phép origin của web app.

Ví dụ policy cho phép:

Origin:
https://app.example.com

Methods:
PUT, POST

Headers:
Content-Type, checksum headers

Nếu cấu hình CORS sai, browser sẽ chặn upload dù signed URL hợp lệ.

CORS không thay thế authentication. Nó chỉ là chính sách của browser về cross-origin request.

40. File lifecycle

Không phải file nào cũng cần giữ mãi.

Object storage thường hỗ trợ lifecycle policy:

- Sau 30 ngày chuyển sang storage rẻ hơn
- Sau 1 năm archive
- Sau 7 năm xóa
- Xóa multipart upload chưa hoàn thành sau 24 giờ

Ví dụ:

flowchart LR
    Hot[Hot Storage] -->|30 days| Cool[Cool Storage]
    Cool -->|180 days| Archive[Archive Storage]
    Archive -->|Retention expires| Delete[Delete]

Phù hợp cho:

- Logs
- Backup
- Compliance records
- Old video originals

41. Storage class

Các lớp lưu trữ khác nhau cân bằng:

- Chi phí lưu
- Chi phí đọc
- Thời gian khôi phục
- Availability

Dữ liệu thường xuyên truy cập:

Hot storage

Dữ liệu hiếm truy cập:

Cold/archive storage

Không nên để log 5 năm trong lớp storage đắt nhất nếu hầu như không được đọc.

42. Replication và durability của object storage

Object storage thường sao chép dữ liệu qua nhiều thiết bị hoặc zone để tăng durability.

Nhưng cần phân biệt:

Durability:
Khả năng không mất object.

Availability:
Khả năng truy cập object ngay lúc này.

Một hệ thống có thể có durability rất cao nhưng đôi khi request vẫn timeout.

43. Cross-region replication

Có thể sao chép object sang region khác.

flowchart LR
    Primary[(Asia Object Storage)] --> Replica[(Europe Object Storage)]

Lợi ích:

- Disaster recovery
- Data locality
- Multi-region delivery

Nhược điểm:

- Chi phí
- Replication lag
- Data residency
- Conflict khi ghi nhiều region

CDN không đồng nghĩa với cross-region replication.

CDN cache file, còn replication tạo bản sao lưu trữ bền vững.

44. Xóa file và cache

Giả sử user xóa ảnh private.

Cần xử lý:

1. Đánh dấu file deleted trong DB
2. Không cấp signed URL mới
3. Xóa hoặc quarantine object
4. Purge CDN nếu cần
5. Xử lý backup/retention theo chính sách

Nếu chỉ xóa DB record nhưng CDN vẫn cache file public, URL cũ có thể tiếp tục hoạt động tới khi cache hết hạn.

Với nội dung nhạy cảm, cần:

- TTL ngắn hơn
- Purge CDN
- Signed access
- Không dùng public immutable URL

45. Soft delete và hard delete

Soft delete

status = deleted
deleted_at = timestamp

Object vẫn tồn tại tạm thời.

Phù hợp:

- Undo
- Audit
- Recovery
- Retention policy

Hard delete

Object bị xóa vật lý.

Có thể xảy ra sau thời gian grace period.

Ví dụ:

Soft delete ngay
Hard delete sau 30 ngày

46. Orphan object

Orphan object là file tồn tại trong storage nhưng không còn record tương ứng trong database.

Có thể xảy ra khi:

1. Upload object thành công
2. Ghi DB thất bại

Hoặc:

1. Xóa DB record
2. Xóa object thất bại

Cần cleanup job:

- Tìm pending uploads quá hạn
- Tìm object không có metadata record
- Retry deletion

47. Orphan database record

Ngược lại:

Database nói file tồn tại,
nhưng object đã mất hoặc upload chưa hoàn tất.

Do đó metadata nên có trạng thái:

pending
uploaded
processing
ready
failed
deleted

Không nên chỉ có một boolean:

uploaded = true/false

48. Idempotency trong upload

Client có thể retry:

POST /uploads

Nếu mỗi retry tạo object key mới, có thể tạo nhiều file trùng.

Dùng:

Idempotency-Key: ...

hoặc client-generated upload ID.

Server trả lại cùng upload session nếu request được retry.

Multipart upload cũng cần complete operation idempotent nếu có thể.

49. Ví dụ hoàn chỉnh — upload avatar

Bước 1: Xin upload URL

POST /v1/avatar-uploads
Authorization: Bearer <token>
Idempotency-Key: 91c4...

{
  "contentType": "image/jpeg",
  "sizeBytes": 420000
}

Response:

{
  "uploadId": "upl_123",
  "objectKey": "avatars/user_456/upl_123/original.jpg",
  "uploadUrl": "<signed-url>",

}

Bước 2: Upload trực tiếp

PUT <signed-url>

Bước 3: Confirm

202 Accepted

{
  "uploadId": "upl_123",
  "status": "processing"

Bước 4: Worker xử lý

- Verify image
- Virus scan

Tạo:

avatars/user_456/upl_123/avatar_512.jpg

Bước 5: Cập nhật profile

Database đổi avatar_object_key.

CDN URL:

https://cdn.example.com/avatars/user_456/upl_123/avatar_512.jpg

Vì key mới hoàn toàn, có thể cache dài.

51. CDN cho API response

CDN không chỉ cache file.

Một số API public cũng có thể cache.

Ví dụ:

GET /public/products/p_123

Response:

Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=60

CDN cache 5 phút, browser cache 1 phút.

Phù hợp khi:

- Response public
- Giống nhau cho mọi user
- Không cần consistency tức thời
- Read-heavy

Không phù hợp nếu response chứa dữ liệu cá nhân hoặc permission khác nhau theo user.

52. CDN và dynamic content

CDN hiện đại có thể:

- TLS termination
- Compression
- Image optimization
- Edge functions
- Request routing
- Bot protection
- Rate limiting

Nhưng không nên đẩy business logic phức tạp ra edge chỉ vì có thể.

Phải cân nhắc:

- Debugging
- Deployment consistency
- Vendor lock-in
- Data locality
- Runtime limits

53. Range requests

Video và file lớn thường hỗ trợ tải một phần:

Range: bytes=1000000-1999999

Server trả:

206 Partial Content

Điều này cho phép:

- Seek video
- Resume download
- Không tải toàn bộ file

CDN và object storage thường hỗ trợ range request hiệu quả.

54. Compression

Nội dung text như:

HTML
CSS
JavaScript
JSON
SVG

có thể nén bằng:

gzip
Brotli

Ảnh JPEG/PNG/video vốn đã được nén; nén HTTP thêm thường không mang lại nhiều lợi ích.

Header:

Content-Encoding: br

CDN có thể tự động nén theo Accept-Encoding.

55. Image optimization tại CDN

CDN có thể tạo biến thể dựa trên query:

/image.jpg?width=400&format=webp

Nhưng phải kiểm soát số biến thể.

Nếu attacker yêu cầu:

width=401
width=402
width=403
...

có thể tạo vô số object/cache key.

Nên giới hạn kích thước hợp lệ:

128
256
512
1024

56. Chi phí

CDN và object storage có nhiều loại chi phí:

- Storage per GB/month
- Request count
- Data transfer
- CDN egress
- Cache invalidation
- Image processing
- Cross-region replication
- Retrieval from archive

Một thiết kế nhanh nhưng không kiểm soát cache key có thể làm chi phí tăng mạnh.

Ví dụ cache hit ratio thấp:

CDN liên tục fetch origin
→ origin request cost tăng
→ egress tăng

58. Failure modes

CDN down

Có thể:

- Route sang CDN khác
- Fallback origin
- Serve cached content từ browser

Nhưng fallback origin cần rate limit, nếu không origin có thể bị overload.

Origin down

Nếu CDN còn cache:

Serve stale-if-error

Nếu file chưa được cache:

Request có thể fail.

Do đó origin vẫn cần HA phù hợp.

Storage upload thành công nhưng event mất

File nằm trong storage nhưng không được xử lý.

Giải pháp:

- Durable event delivery
- Periodic reconciliation
- Scan pending uploads
- Transactional state machine

Worker xử lý thất bại

Cần:

- Retry
- Dead-letter queue
- Error status
- Manual reprocessing

Signed URL hết hạn giữa upload

Với file nhỏ, client xin URL mới và retry.

Với multipart upload, cần renew authorization cho các part còn lại mà không bắt đầu lại toàn bộ.

59. Security checklist

[ ] Bucket có private mặc định không?
[ ] API có kiểm tra owner và permission không?
[ ] Signed URL có TTL ngắn không?
[ ] Signed URL giới hạn đúng method và object key không?
[ ] Có giới hạn file size không?
[ ] Có validate MIME bằng nội dung thật không?
[ ] Có malware scan không?
[ ] Có ngăn path/key injection không?
[ ] Có dùng HTTPS không?
[ ] Có tránh log signed URL đầy đủ không?
[ ] CDN có thể truy cập origin nhưng user không thể bypass không?
[ ] File private có bị shared-cache nhầm không?

60. Sai lầm phổ biến

Lỗi 1: Lưu file trên app server

Khiến scale ngang và deploy khó khăn.

Lỗi 2: Upload file lớn qua API server

Làm application server thành proxy bandwidth đắt đỏ.

Lỗi 3: Cho bucket public toàn bộ

Dễ rò rỉ file private.

Lỗi 4: Signed URL có thời hạn quá dài

Nếu bị lộ, người khác có thể truy cập lâu.

Lỗi 5: Tin file extension và Content-Type

Có thể bị upload file độc hại.

Lỗi 6: Overwrite cùng URL nhưng đặt TTL dài

User liên tục thấy nội dung cũ.

Lỗi 7: CDN cache response cá nhân

Có thể làm rò rỉ dữ liệu giữa user.

Lỗi 8: Không cleanup upload dở

Multipart và pending object tích tụ, tăng chi phí.

Lỗi 9: Không có status xử lý

Database báo file tồn tại dù media pipeline chưa hoàn tất.

Lỗi 10: Không giới hạn biến thể ảnh

Tạo vô số cache key và chi phí xử lý.

65. Những điều phải nhớ sau Bài 7

1. Object storage dùng để lưu file; CDN dùng để phân phối file.
2. Không nên lưu user uploads trên local disk của application server.
3. Metadata nghiệp vụ nằm trong database, content nằm trong object storage.
4. CDN cache nội dung tại edge gần user và giảm tải origin.
5. Origin có thể là object storage hoặc web server.
6. Static assets nên dùng immutable/versioned URL và TTL dài.
7. Không nên overwrite cùng URL nếu CDN cache lâu.
8. Upload file lớn nên đi trực tiếp từ client đến object storage.
9. API chỉ xác thực, cấp signed URL và lưu metadata.
10. Signed URL phải có phạm vi hẹp và thời hạn ngắn.
11. Không được tin file extension hoặc Content-Type từ client.
12. Resize, scan và transcode nên xử lý bất đồng bộ.
13. File lớn nên dùng multipart và resumable upload.
14. File private không nên đặt trong public bucket.
15. CDN cache key sai có thể gây rò rỉ dữ liệu.
16. CDN không thay thế database, object durability hoặc origin high availability.
17. Cần cleanup pending upload và orphan object.
18. Phải theo dõi CDN hit ratio, origin load và media processing queue.

Tóm tắt cuối bài

Object Storage giữ bản gốc bền vững, CDN đưa bản sao đến gần người dùng, còn API kiểm soát metadata, authorization và workflow. Thiết kế tốt sẽ không bắt application server vận chuyển từng byte media, không để bucket private trở thành public và không phụ thuộc vào việc purge cache mỗi khi nội dung thay đổi.
