Bài 8 — Load Balancing và Horizontal Scaling

Khi một application server không còn đủ sức xử lý traffic, chúng ta có hai hướng mở rộng:

Vertical Scaling:
Nâng cấp máy hiện tại mạnh hơn.

Horizontal Scaling:
Thêm nhiều máy cùng xử lý traffic.

Load balancer là thành phần đứng trước nhóm server, nhận traffic từ client và phân phối request đến các server phù hợp. Trong video/tài liệu của bạn, horizontal scaling được giới thiệu như cách thêm server để chia sẻ tải, còn load balancer đảm nhận việc phân phối traffic, kiểm tra sức khỏe server và tránh gửi request đến node đã lỗi.

1. Vì sao một server cuối cùng sẽ không đủ?

Kiến trúc ban đầu:

flowchart LR
    User[Users] --> App[Application Server]
    App --> DB[(Database)]

Khi hệ thống nhỏ, kiến trúc này rất hợp lý:

- Dễ triển khai
- Dễ debug
- Chi phí thấp
- Ít thành phần

Nhưng một server có giới hạn:

- CPU
- RAM
- Network bandwidth
- Số connection
- Disk I/O
- Số thread/process

Traffic tăng có thể khiến:

CPU lên 100%
Connection pool đầy
Request phải xếp hàng
Latency tăng
Timeout tăng
Client retry
Traffic càng tăng thêm

Chuỗi sự cố:

flowchart LR
    A[Traffic tăng] --> B[Server quá tải]
    B --> C[Latency tăng]
    C --> D[Timeout]
    D --> E[Client retry]
    E --> B

Đây là retry amplification: server đã quá tải nhưng retry lại tạo thêm tải.

2. Vertical Scaling — Scale Up

Vertical scaling là tăng tài nguyên cho máy hiện tại:

- Tăng CPU
- Tăng RAM
- Dùng ổ đĩa nhanh hơn
- Tăng network capacity

Ví dụ:

Trước:
4 CPU, 8 GB RAM

Sau:
32 CPU, 128 GB RAM

flowchart LR
    A[Server nhỏ] -->|Nâng cấp| B[Server lớn hơn]

Ưu điểm

- Đơn giản
- Không cần chia traffic
- Ít thay đổi application
- Không có vấn đề distributed state giữa nhiều server

Nhược điểm

- Có giới hạn phần cứng
- Máy càng lớn càng đắt
- Có thể cần downtime khi nâng cấp
- Vẫn là single point of failure
- Không xử lý tốt traffic tăng đột biến

Vertical scaling không xấu. Nó thường là bước đầu hợp lý.

Nhưng cuối cùng:

Một máy dù mạnh đến đâu vẫn là một máy.

3. Horizontal Scaling — Scale Out

Horizontal scaling là thêm nhiều server:

flowchart LR
    Users --> LB[Load Balancer]

    LB --> A1[Application 1]
    LB --> A2[Application 2]
    LB --> A3[Application 3]

Thay vì một server xử lý 15.000 RPS:

Server 1:
15.000 RPS

Ta có thể dùng ba server:

Server 1: 5.000 RPS
Server 2: 5.000 RPS
Server 3: 5.000 RPS

Ưu điểm

- Tăng capacity bằng cách thêm server
- Có thể tự động scale
- Một server chết chưa chắc làm toàn hệ thống chết
- Có thể deploy dần
- Dễ phân tán qua nhiều availability zone

Nhược điểm

- Phải có load balancer
- Session và local state trở thành vấn đề
- Debug khó hơn
- Có network failure
- Cần service discovery và health check
- Database có thể trở thành bottleneck tiếp theo

4. Load Balancer là gì?

Load balancer là thành phần nhận connection/request từ client và chọn một backend server để xử lý.

flowchart LR
    Client --> LB[Load Balancer]

    LB --> S1[Server 1]
    LB --> S2[Server 2]
    LB --> S3[Server 3]

Nhiệm vụ chính:

1. Phân phối traffic
2. Không gửi request đến server lỗi
3. Tránh một server chịu quá nhiều tải
4. Hỗ trợ thêm hoặc loại bỏ server
5. Có thể terminate TLS
6. Có thể route theo host/path/header
7. Thu thập metrics và access logs

Load balancer không chỉ giúp performance.

Nó còn giúp:

- Availability
- Fault tolerance
- Rolling deployment
- Autoscaling
- Security

5. Một request đi qua Load Balancer như thế nào?

sequenceDiagram
    participant Client
    participant DNS
    participant LB as Load Balancer
    participant App as Application Server
    participant DB as Database

    Client->>DNS: Resolve api.example.com
    DNS-->>Client: Load balancer IP

    Client->>LB: HTTPS request
    LB->>LB: Select healthy backend
    LB->>App: Forward request
    App->>DB: Query/update
    DB-->>App: Result
    App-->>LB: HTTP response
    LB-->>Client: HTTP response

Client thường chỉ biết domain của load balancer:

api.example.com

Client không cần biết:

Server 1 có IP gì?
Server 2 vừa được thêm chưa?
Server 3 có đang lỗi không?

Những thay đổi đó được che giấu phía sau load balancer.

6. Load Balancing ở Layer 4 và Layer 7

Hai loại quan trọng nhất:

L4 Load Balancer:
Transport layer

L7 Load Balancer:
Application layer

7. L4 Load Balancer

L4 hoạt động chủ yếu dựa trên thông tin mạng và transport:

- Source IP
- Destination IP
- Source port
- Destination port
- Protocol TCP/UDP

Nó không cần hiểu sâu nội dung HTTP.

Ví dụ:

TCP connection tới port 443
→ chuyển tới backend 10.0.1.12:443

flowchart LR
    Client -->|TCP :443| L4[L4 Load Balancer]
    L4 --> S1[Server 1]
    L4 --> S2[Server 2]

Ưu điểm

- Nhanh
- Overhead thấp
- Throughput cao
- Hỗ trợ nhiều protocol TCP/UDP
- Không phụ thuộc HTTP

Nhược điểm

Không dễ đưa ra quyết định dựa trên:

- URL path
- HTTP header
- Cookie
- HTTP method
- User identity

L4 phù hợp với:

- TCP services
- Database connection
- Game server
- Low-latency network service
- Traffic rất lớn
- TLS passthrough

8. L7 Load Balancer

L7 hiểu protocol ứng dụng như HTTP hoặc HTTPS.

Nó có thể đọc:

- Host
- URL path
- Query string
- Header
- Cookie
- HTTP method

Ví dụ:

/api/users/*    → User Service
/api/orders/*   → Order Service
/images/*       → Image Service

flowchart TD
    Client --> L7[L7 Load Balancer]

    L7 -->|/users/*| User[User Service]
    L7 -->|/orders/*| Order[Order Service]
    L7 -->|/payments/*| Payment[Payment Service]

Ưu điểm

- Content-based routing
- TLS termination
- Authentication integration
- Header manipulation
- Redirect
- Rate limiting
- Canary routing
- A/B testing
- Web Application Firewall

Nhược điểm

- Overhead lớn hơn L4
- Phải parse protocol
- Cấu hình phức tạp hơn
- Thêm CPU và latency

9. So sánh L4 và L7

Tiêu chí L4 L7
Dựa trên IP, port, TCP/UDP HTTP host, path, header, cookie
Hiểu HTTP Không sâu Có
Hiệu năng Thường cao hơn Overhead lớn hơn
TLS Passthrough hoặc terminate tùy thiết kế Thường terminate
Route theo path Không Có
Dùng cho TCP/UDP services Web/API/microservices
Logic routing Đơn giản Linh hoạt

Nhiều hệ thống dùng cả hai tầng:

flowchart TD
    Users --> L4[Global/L4 Load Balancer]
    L4 --> L7A[L7 Load Balancer Zone A]
    L4 --> L7B[L7 Load Balancer Zone B]

    L7A --> A1[App A1]
    L7A --> A2[App A2]

    L7B --> B1[App B1]
    L7B --> B2[App B2]

10. TLS Termination

Nếu load balancer terminate TLS:

Client → HTTPS → Load Balancer
Load Balancer → HTTP hoặc HTTPS → Backend

flowchart LR
    Client -->|Encrypted HTTPS| LB[TLS Termination]
    LB -->|HTTP/HTTPS nội bộ| App[Application]

Lợi ích:

- Backend không phải tự xử lý TLS cho từng request
- Quản lý certificate tập trung
- Load balancer đọc được HTTP để route L7
- Dễ thêm WAF và security rules

Nhưng traffic nội bộ có thể vẫn cần mã hóa:

Client → HTTPS → LB → HTTPS → Backend

Đặc biệt khi:

- Network không hoàn toàn tin cậy
- Có yêu cầu compliance
- Có nhiều cluster/region

11. Các thuật toán Load Balancing

Load balancer cần trả lời:

Request tiếp theo nên được gửi đến server nào?

Không có thuật toán tốt nhất cho mọi workload.

12. Round Robin

Request được gửi tuần tự:

Request 1 → Server A
Request 2 → Server B
Request 3 → Server C
Request 4 → Server A

flowchart LR
    R1[Request 1] --> A[Server A]
    R2[Request 2] --> B[Server B]
    R3[Request 3] --> C[Server C]
    R4[Request 4] --> A

Ưu điểm

- Đơn giản
- Overhead thấp
- Phân phối đều số request

Nhược điểm

Round Robin giả định các request và server tương đối giống nhau.

Nhưng thực tế:

Request A xử lý 10 ms
Request B xử lý 5 giây

Nếu chỉ đếm số request, server nhận request nặng có thể quá tải.

Phù hợp khi:

- Server giống nhau
- Request tương đối đồng đều
- Connection ngắn

13. Weighted Round Robin

Mỗi server có weight khác nhau.

Ví dụ:

Server A: weight 1
Server B: weight 2
Server C: weight 4

C có thể nhận nhiều traffic hơn vì mạnh hơn.

A: 1 phần
B: 2 phần
C: 4 phần

Phù hợp khi server không cùng cấu hình:

- CPU khác nhau
- RAM khác nhau
- Version mới cần ít traffic hơn
- Canary instance chỉ nên nhận 5%

14. Least Connections

Load balancer chọn server có ít connection đang hoạt động nhất.

Ví dụ:

Server A: 100 connections
Server B: 40 connections
Server C: 75 connections

→ Chọn Server B

Phù hợp khi:

- Connection tồn tại lâu
- Request duration không đồng đều
- WebSocket
- Streaming
- Long polling

Nhưng ít connection không phải lúc nào cũng nghĩa là ít tải.

Ví dụ:

Server A:
100 connection nhẹ

Server B:
10 connection xử lý video nặng

Server B vẫn có thể bận hơn.

15. Weighted Least Connections

Kết hợp số connection và capacity của server.

Ví dụ server mạnh gấp đôi có thể chịu nhiều connection hơn.

Đây thường hợp lý hơn least connections thuần túy khi backend không đồng nhất.

16. Least Response Time

Load balancer cân nhắc:

- Response time
- Active connections
- Server performance

Server phản hồi nhanh và ít bận được ưu tiên.

Ưu điểm:

Có thể thích nghi với backend đang chậm.

Nhược điểm:

- Cần đo latency liên tục
- Metric có thể nhiễu
- Có thể tạo feedback loop

Ví dụ server vừa nhanh hơn một chút được gửi nhiều traffic hơn, rồi nhanh chóng trở nên quá tải.

17. Random

Chọn ngẫu nhiên một server khỏe mạnh.

Nghe đơn giản nhưng với số lượng request lớn, traffic thường phân bố tương đối đều.

Một biến thể tốt là Power of Two Choices:

1. Chọn ngẫu nhiên hai server
2. So sánh tải
3. Gửi request đến server nhẹ hơn

Cách này đạt cân bằng tốt mà không cần theo dõi toàn bộ cluster quá chi tiết.

18. IP Hash

Load balancer hash IP của client để chọn server:

server = hash(client_ip) mod N

Kết quả:

Cùng client IP
→ thường đi đến cùng server

Ưu điểm:

- Tạo session affinity đơn giản
- Có thể hữu ích khi backend có local state

Nhược điểm:

- Nhiều user có thể dùng chung IP qua NAT
- Mobile IP có thể thay đổi
- Khi thêm hoặc xóa server, mapping thay đổi
- Traffic có thể phân bố không đều

19. Consistent Hashing

Consistent hashing ánh xạ server và key lên một hash ring.

flowchart TD
    Ring((Hash Ring))
    A[Server A] --> Ring
    B[Server B] --> Ring
    C[Server C] --> Ring

Khi thêm hoặc loại bỏ một server, chỉ một phần key bị remap thay vì gần như toàn bộ.

Phù hợp với:

- Distributed cache
- Sharded storage
- Stateful connection assignment
- Partition-aware routing

Consistent hashing không chỉ là thuật toán load balancing; nó còn là kỹ thuật phân phối dữ liệu.

20. Geographic Load Balancing

Traffic được route theo vị trí user:

User châu Á → Asia region
User châu Âu → Europe region
User Mỹ → US region

flowchart TD
    User[Global Users] --> G[Global Traffic Manager]

    G --> Asia[Asia Region]
    G --> Europe[Europe Region]
    G --> US[US Region]

Mục tiêu:

- Giảm latency
- Phân tải toàn cầu
- Hỗ trợ disaster recovery
- Tuân thủ data residency

Routing có thể dựa trên:

- DNS
- Anycast
- Client IP
- Network latency
- Region health

21. Health Check là gì?

Load balancer không nên gửi traffic đến server đã lỗi.

Health check là cơ chế kiểm tra backend có sẵn sàng nhận request hay không.

sequenceDiagram
    participant LB as Load Balancer
    participant App as Application Server

    loop Every few seconds
        LB->>App: GET /health
        App-->>LB: 200 OK
    end

Khi health check thất bại đủ số lần:

Backend bị đánh dấu unhealthy
→ ngừng nhận traffic

Khi thành công trở lại đủ số lần:

Backend được thêm lại vào pool

22. Active và Passive Health Check

Active health check

Load balancer chủ động gửi request:

GET /health
GET /ready

Ví dụ mỗi 5 giây.

Ưu điểm:

- Phát hiện lỗi trước khi có user request
- Kiểm tra định kỳ

Nhược điểm:

- Tạo thêm traffic
- Endpoint health có thể không phản ánh toàn bộ hệ thống

Passive health check

Load balancer quan sát request thật:

- Connection refused
- Timeout
- 5xx liên tục
- Reset connection

Sau một số lỗi, backend bị loại.

Ưu điểm:

- Dựa trên traffic thực
- Phát hiện lỗi mà endpoint health có thể bỏ sót

Nhược điểm:

- Một số user request phải thất bại trước

Hệ thống tốt thường kết hợp cả hai.

23. Liveness, Readiness và Startup Check

Ba loại health check thường bị nhầm.

23.1 Liveness

Câu hỏi:

Process có còn sống hay bị treo?

Ví dụ:

GET /health/live

Nếu liveness fail lâu:

Process có thể cần restart.

Liveness không nên kiểm tra quá nhiều dependency.

Nếu database tạm thời lỗi mà mọi app instance cùng fail liveness, toàn bộ app có thể bị restart hàng loạt, làm sự cố nghiêm trọng hơn.

23.2 Readiness

Câu hỏi:

Instance có sẵn sàng nhận traffic không?

GET /health/ready

Một instance có thể còn sống nhưng chưa ready vì:

- Chưa load configuration
- Chưa warm cache
- Chưa kết nối database
- Đang migrate
- Đang shutdown

Nếu readiness fail:

Ngừng gửi traffic đến instance,
nhưng không nhất thiết restart nó.

23.3 Startup check

Câu hỏi:

Application đã khởi động hoàn tất chưa?

Hữu ích với ứng dụng khởi động chậm.

Nếu không có startup check, liveness có thể kết luận app chết trong khi nó chỉ đang khởi động.

24. Health endpoint nên kiểm tra gì?

Một health endpoint tốt không chỉ trả 200 vì process còn chạy.

Nhưng cũng không nên phụ thuộc mù quáng vào mọi dependency.

Ví dụ readiness có thể kiểm tra:

- Application event loop/thread pool còn hoạt động
- Configuration đã load
- Dependency bắt buộc có thể truy cập
- Instance không trong trạng thái draining

Không nên gọi hàng chục service sâu:

App health
→ Database
→ Payment provider
→ Email provider
→ Analytics

Nếu email provider lỗi, order API có thể vẫn xử lý order bình thường.

Phải phân biệt:

Dependency bắt buộc
Dependency tùy chọn

25. Threshold và chống Health Check Flapping

Một lần timeout chưa chắc server đã chết.

Nếu loại server ngay sau một lỗi:

Server có thể liên tục:
healthy → unhealthy → healthy → unhealthy

Đó là flapping.

Cấu hình thường gồm:

Interval:
Bao lâu kiểm tra một lần

Timeout:
Chờ response bao lâu

Unhealthy threshold:
Bao nhiêu lần fail liên tiếp mới loại

Healthy threshold:
Bao nhiêu lần thành công mới thêm lại

Ví dụ:

Check mỗi 5 giây
Timeout 2 giây
3 lần fail → unhealthy
2 lần success → healthy

26. Connection Draining

Khi một server cần dừng, không nên cắt toàn bộ connection đang xử lý.

Thay vào đó:

1. Đánh dấu server không nhận request mới
2. Chờ request hiện tại hoàn thành
3. Đóng connection
4. Tắt server

sequenceDiagram
    participant LB
    participant App

    LB->>App: Mark draining
    Note over LB: Không gửi request mới
    App->>App: Hoàn thành request đang chạy
    App-->>LB: Connections completed
    Note over App: Safe shutdown

Connection draining rất quan trọng khi:

- Deploy version mới
- Scale in
- Maintenance
- Spot/preemptible instance sắp bị thu hồi

Nếu không draining:

- Request đang chạy bị cắt
- Upload hỏng
- Payment có trạng thái không rõ
- WebSocket disconnect đột ngột

27. Sticky Session là gì?

Sticky session, hay session affinity, nghĩa là các request của một user được gửi về cùng một backend server.

flowchart LR
    U1[User A] --> LB
    U2[User B] --> LB

    LB -->|User A luôn tới đây| S1[Server 1]
    LB -->|User B luôn tới đây| S2[Server 2]

Có thể implement bằng:

- Cookie
- Client IP hash
- Session ID hash

28. Tại sao người ta dùng Sticky Session?

Giả sử session đăng nhập được lưu trong RAM của Server 1:

Server 1 memory:
session_abc → user_123

Request đầu:

User → Server 1 → đăng nhập thành công

Request tiếp theo tới Server 2:

Server 2 không biết session_abc
→ user bị xem như chưa đăng nhập

Sticky session ép user quay lại Server 1.

29. Vấn đề của Sticky Session

29.1 Load không đều

Một server có thể nhận nhiều user nặng.

Server 1:
10 user xử lý video nặng

Server 2:
100 user chỉ đọc profile

Số user không phản ánh tải thật.

29.2 Server chết làm mất session

Nếu session chỉ ở local memory:

Server 1 chết
→ session trên Server 1 mất
→ user phải đăng nhập lại

29.3 Scale và deploy khó hơn

Khi scale in, phải xử lý user đang dính với server bị xóa.

Rolling deployment cũng khó vì traffic không linh hoạt.

29.4 Giảm fault tolerance

Server không còn dễ thay thế vì nó đang giữ trạng thái riêng của user.

30. Stateless Service

Một application server là stateless khi nó không giữ state lâu dài cần thiết cho request tiếp theo trong local memory hoặc local disk.

Mỗi request mang đủ context để bất kỳ server nào xử lý.

flowchart TD
    User --> LB

    LB --> A1[Stateless API 1]
    LB --> A2[Stateless API 2]
    LB --> A3[Stateless API 3]

    A1 --> Shared[(Shared State)]
    A2 --> Shared
    A3 --> Shared

Shared state có thể nằm ở:

- Database
- Redis/session store
- Object storage
- Message broker

31. Ví dụ Stateful và Stateless

Stateful

Server 1 RAM:
shopping_cart_user_123

Chỉ Server 1 biết cart.

Stateless application

Redis:
cart:user_123

Bất kỳ API server nào cũng đọc được cart.

flowchart LR
    User --> LB
    LB --> A1[API 1]
    LB --> A2[API 2]
    A1 --> Redis[(Redis)]
    A2 --> Redis

32. Authentication stateless có nghĩa gì?

Với access token:

Authorization: Bearer <token>

Bất kỳ server nào có thể:

- Verify token
- Xác định user
- Kiểm tra quyền
- Xử lý request

Nhưng cần lưu ý:

JWT không làm toàn bộ hệ thống tự động stateless.

Hệ thống vẫn có thể cần:

- Token revocation
- Refresh token storage
- User permission lookup
- Rate limit state
- Business data

Mục tiêu không phải “không có state”.

Mà là:

Không khóa state quan trọng vào một application instance cụ thể.

33. Khi nào Sticky Session vẫn hợp lý?

Sticky session không phải lúc nào cũng sai.

Có thể phù hợp khi:

- Legacy application lưu session local
- WebSocket connection dài
- In-memory processing tạm thời
- Migrating dần sang stateless
- Một workflow ngắn cần affinity

Nhưng nên xem nó là trade-off rõ ràng, không phải mặc định.

Với WebSocket, một connection vật lý đương nhiên được giữ với một server trong thời gian connection tồn tại. Tuy nhiên state bền vững vẫn nên được externalize để reconnect sang server khác.

34. Service Discovery

Khi autoscaling thêm hoặc xóa server, load balancer cần biết backend nào đang tồn tại.

Đây là service discovery.

Hai mô hình:

Client-side discovery
Server-side discovery

34.1 Server-side discovery

Client gọi load balancer.

Load balancer biết danh sách backend.

flowchart LR
    Client --> LB[Load Balancer]
    LB --> Registry[Service Registry]
    LB --> S1[Service 1]
    LB --> S2[Service 2]

Đây là mô hình phổ biến với external traffic.

34.2 Client-side discovery

Service gọi registry để lấy danh sách instance, sau đó tự chọn instance.

flowchart LR
    ServiceA[Service A] --> Registry
    Registry --> ServiceA
    ServiceA --> B1[Service B1]
    ServiceA --> B2[Service B2]

Ưu điểm:

- Bỏ bớt network hop
- Client có thể chọn routing strategy

Nhược điểm:

- Logic discovery nằm trong client
- Nhiều ngôn ngữ cần implementation
- Phức tạp hơn

35. Autoscaling là gì?

Autoscaling là tự động tăng hoặc giảm số lượng instance dựa trên nhu cầu.

flowchart LR
    Metrics[Metrics] --> Controller[Autoscaling Controller]
    Controller -->|Scale out| Add[Add Instances]
    Controller -->|Scale in| Remove[Remove Instances]
    Add --> Pool[Backend Pool]
    Remove --> Pool

Mục tiêu:

Traffic tăng → thêm instance
Traffic giảm → giảm instance

Lợi ích:

- Duy trì performance
- Hấp thụ traffic spike
- Giảm chi phí khi ít traffic
- Giảm thao tác thủ công

36. Horizontal và Vertical Autoscaling

Horizontal autoscaling

3 instances → 10 instances

Phổ biến với stateless services.

Vertical autoscaling

4 CPU → 8 CPU
8 GB RAM → 16 GB RAM

Có thể cần restart hoặc reschedule workload.

Trong bài này, autoscaling chủ yếu nói về horizontal autoscaling.

37. Autoscaling dựa trên CPU

Ví dụ rule:

Nếu average CPU > 70% trong 5 phút:
Thêm 2 instance

Nếu average CPU < 30% trong 15 phút:
Giảm 1 instance

Ưu điểm:

- Dễ hiểu
- Có sẵn ở nhiều nền tảng

Nhược điểm:

CPU không luôn phản ánh tải.

Ví dụ service đang chờ database:

CPU chỉ 20%
Latency rất cao
Connection pool đầy

Autoscaler dựa trên CPU có thể không scale dù user đang gặp timeout.

38. Autoscaling dựa trên Memory

Phù hợp với application có memory usage tỷ lệ với workload:

- In-memory processing
- Large object transformation
- Cache-heavy service

Nhưng memory có thể không giảm sau khi request hoàn tất do:

- Runtime garbage collection
- Memory fragmentation
- Local cache

Dùng memory làm metric cần hiểu behavior của runtime.

39. Autoscaling dựa trên RPS

Ví dụ mỗi instance chịu an toàn:

500 RPS

Peak hiện tại:

10.000 RPS

Số instance cơ bản:

10.000 / 500 = 20 instance

Nên thêm headroom:

Khoảng 25–30 instance tùy SLO và traffic burst.

RPS phù hợp với request tương đối đồng đều.

Nhưng nếu:

GET /health = 1 ms
POST /video/process = 10 giây

thì tổng RPS không phản ánh tải thật.

40. Autoscaling dựa trên Latency

Có thể scale khi:

p95 latency > 300 ms

Ưu điểm:

- Gần với trải nghiệm user

Nhược điểm:

Latency có thể tăng vì:

- Database chậm
- Third-party API chậm
- Network lỗi

Thêm application instance không giải quyết được dependency chậm, thậm chí còn tăng tải lên database.

41. Autoscaling dựa trên Queue Depth

Rất phù hợp với worker bất đồng bộ.

flowchart LR
    API --> Queue[Message Queue]
    Queue --> W1[Worker 1]
    Queue --> W2[Worker 2]

Scale dựa trên:

- Số message đang chờ
- Tuổi của message cũ nhất
- Thời gian xử lý trung bình

Ví dụ:

Mỗi worker xử lý 10 jobs/giây
Queue nhận 500 jobs/giây

Cần ít nhất:
500 / 10 = 50 workers

Đây thường là metric tốt hơn CPU cho background workers.

42. Autoscaling dựa trên Active Connections

Phù hợp:

- WebSocket
- Long polling
- Streaming
- Proxy

Ví dụ mỗi WebSocket server giữ an toàn 20.000 connection.

Có 200.000 connection:

Cần tối thiểu 10 server,
cộng thêm headroom.

43. Composite Metrics

Trong thực tế, có thể kết hợp:

- CPU
- RPS
- p95 latency
- Queue depth
- Active connections
- Error rate

Không nên scale mù quáng từ một metric duy nhất.

Ví dụ:

Scale out nếu:
CPU > 65%
HOẶC
RPS/instance > 400
HOẶC
queue oldest age > 30 giây

Nhưng rule quá phức tạp cũng khó dự đoán và debug.

44. Reactive, Scheduled và Predictive Scaling

Reactive scaling

Traffic tăng rồi mới scale.

CPU cao → thêm instance

Nhược điểm:

Có độ trễ trước khi instance mới sẵn sàng.

Scheduled scaling

Scale trước thời điểm biết trước.

Ví dụ:

11:00 → tăng capacity trước giờ ăn trưa
19:45 → tăng capacity trước trận bóng lúc 20:00

Phù hợp traffic có chu kỳ.

Predictive scaling

Dùng dữ liệu lịch sử để dự đoán traffic và chuẩn bị trước.

Có thể hiệu quả nhưng phức tạp và phụ thuộc chất lượng dự báo.

Hệ thống lớn thường kết hợp:

Scheduled/Predictive baseline
+
Reactive adjustment

45. Autoscaling Lag

Autoscaling không diễn ra tức thời.

Quá trình có thể gồm:

1. Metric tăng
2. Hệ thống thu thập metric
3. Rule được kích hoạt
4. Tạo instance/container
5. Khởi động application
6. Load configuration
7. Warm cache
8. Readiness thành công
9. Load balancer bắt đầu gửi traffic

Quá trình này có thể mất từ vài giây đến nhiều phút.

Trong thời gian đó, instance cũ vẫn phải chịu traffic.

Vì vậy cần:

- Headroom
- Minimum instances
- Prewarming
- Scheduled scaling
- Fast startup
- Queue buffering

46. Cooldown và Stabilization Window

Nếu autoscaler phản ứng quá nhanh:

Scale out
→ CPU giảm
→ Scale in
→ CPU tăng
→ Scale out

Đây là autoscaling oscillation hoặc thrashing.

Giải pháp:

Cooldown:
Chờ một khoảng thời gian sau khi scale.

Stabilization window:
Chỉ scale nếu metric duy trì đủ lâu.

Scale-in chậm hơn scale-out:
Thêm nhanh, giảm từ từ.

Nguyên tắc thực tế:

Scale out cần nhanh; scale in nên thận trọng.

47. Scale In nguy hiểm hơn Scale Out

Thêm server thường ít rủi ro.

Xóa server có thể làm:

- Cắt request đang xử lý
- Mất local state
- Ngắt WebSocket
- Giảm capacity quá nhanh
- Tăng tải đột ngột lên server còn lại

Scale-in an toàn:

1. Chọn instance cần loại
2. Mark not ready
3. Load balancer ngừng gửi traffic mới
4. Drain connection
5. Hoàn thành jobs
6. Shutdown

48. Capacity và Headroom

Giả sử peak traffic dự kiến:

30.000 RPS

Mỗi application instance xử lý an toàn:

500 RPS

Tối thiểu:

30.000 / 500 = 60 instances

Nhưng chạy đúng 60 nghĩa là không có dự phòng.

Nếu một availability zone mất 20 instance, hệ thống quá tải ngay.

Có thể thiết kế:

60 instance cho tải
+ 20–30% headroom
≈ 75–80 instances

Headroom bảo vệ trước:

- Traffic burst
- Instance failure
- Deployment
- Autoscaling lag
- Uneven load

49. N+1 và Zone Failure Capacity

Giả sử có ba zone:

Zone A: 30 servers
Zone B: 30 servers
Zone C: 30 servers

Tổng 90.

Nếu hệ thống chỉ chạy ổn khi có đủ 90, mất một zone sẽ gây quá tải.

Thiết kế tốt có thể yêu cầu:

Hai zone còn lại vẫn chịu được toàn bộ traffic.

Tức là capacity mỗi zone phải tính theo failure scenario, không chỉ traffic bình thường.

flowchart TD
    LB[Regional Load Balancer]

    LB --> A[Zone A]
    LB --> B[Zone B]
    LB --> C[Zone C]

    C -.Failure.-> X[Traffic chuyển sang A và B]

50. Load Balancer có thể trở thành Single Point of Failure

Kiến trúc này chưa thực sự high availability:

flowchart LR
    Users --> LB[Single Load Balancer]
    LB --> S1
    LB --> S2
    LB --> S3

Nếu LB chết, toàn bộ backend khỏe mạnh cũng không truy cập được.

Giải pháp:

- Nhiều load balancer
- Active-active
- Active-passive
- Anycast
- DNS failover
- Managed load balancer
- Health check và self-healing

flowchart TD
    Users --> DNS[DNS/Global Routing]

    DNS --> LB1[Load Balancer 1]
    DNS --> LB2[Load Balancer 2]

    LB1 --> Apps[Application Pool]
    LB2 --> Apps

51. Active-Active và Active-Passive

Active-active

Cả hai load balancer đều nhận traffic.

LB1: 50%
LB2: 50%

Ưu điểm:

- Sử dụng toàn bộ capacity
- Failover nhanh

Nhược điểm:

- Đồng bộ configuration
- Routing phức tạp hơn

Active-passive

LB chính nhận traffic, LB dự phòng chờ.

LB1: active
LB2: standby

Khi LB1 lỗi, traffic chuyển sang LB2.

Ưu điểm:

- Đơn giản hơn

Nhược điểm:

- Capacity dự phòng không được dùng thường xuyên
- Failover có thể chậm hơn
- Phải thường xuyên kiểm tra standby thật sự hoạt động

52. Database trở thành Bottleneck tiếp theo

Scale application server không tự động scale database.

flowchart TD
    LB --> A1[App 1]
    LB --> A2[App 2]
    LB --> A3[App 3]
    LB --> A4[App 4]

    A1 --> DB[(One Database)]
    A2 --> DB
    A3 --> DB
    A4 --> DB

Thêm app server có thể tạo:

- Nhiều DB connection hơn
- Nhiều query hơn
- Nhiều lock contention hơn

Ví dụ:

100 app instances
× 50 DB connections
= 5.000 connections

Database có thể không chịu được.

Cần:

- Connection pooling
- Cache
- Read replica
- Query optimization
- Rate limit
- Backpressure

Horizontal scaling phải được nhìn end-to-end, không chỉ application tier.

53. Load Balancer không biết mọi thứ

Load balancer có thể biết:

- Connection count
- Response time
- Health status
- HTTP status

Nhưng nó có thể không biết:

- Thread pool gần đầy
- DB connection pool cạn
- Internal queue quá dài
- Garbage collection sắp xảy ra
- Tenant cụ thể đang rất nặng

Vì thế application có thể expose:

- Readiness status
- Custom load metrics
- Queue depth

Hoặc dùng service mesh/autoscaler theo application metrics.

54. Overload Protection và Backpressure

Scale không phải phản ứng duy nhất.

Nếu traffic vượt capacity, hệ thống cần bảo vệ chính nó.

Các chiến lược:

- Rate limiting
- Request queue có giới hạn
- Load shedding
- Circuit breaker
- Timeout
- Retry budget
- Priority queue
- Degrade non-critical features

Ví dụ:

Payment request:
Ưu tiên cao

Analytics event:
Có thể drop hoặc xử lý chậm

Recommendation:
Có thể trả fallback

Một hệ thống tốt đôi khi phải từ chối một phần request để phần quan trọng vẫn hoạt động.

55. Load Shedding

Load shedding là chủ động từ chối request khi hệ thống quá tải.

Ví dụ:

503 Service Unavailable
Retry-After: 5

Tốt hơn việc nhận mọi request rồi tất cả cùng timeout sau 30 giây.

flowchart LR
    Requests --> Gate{Capacity available?}
    Gate -->|Có| Service
    Gate -->|Không| Reject[Fail fast / fallback]

56. Retry phải được kiểm soát

Nếu backend lỗi, load balancer hoặc client có thể retry sang server khác.

Nhưng retry nguy hiểm khi:

- Operation không idempotent
- Server cũ đã xử lý nhưng response bị mất
- Retry storm

Ví dụ:

POST /payments

Không nên retry mù quáng nếu không có idempotency key.

Retry nên có:

- Timeout hợp lý
- Exponential backoff
- Jitter
- Retry limit
- Idempotency
- Retry budget

57. Rolling Deployment

Load balancer hỗ trợ deploy không downtime.

Luồng:

1. Thêm instance version mới
2. Chờ readiness
3. Gửi một phần traffic
4. Theo dõi errors và latency
5. Drain instance version cũ
6. Tắt version cũ

flowchart TD
    LB --> V1A[v1]
    LB --> V1B[v1]
    LB --> V2A[v2 Canary]

    V2A --> Check{Metrics tốt?}
    Check -->|Có| More[Deploy thêm v2]
    Check -->|Không| Rollback

58. Canary Deployment

Chỉ gửi một phần nhỏ traffic đến version mới:

v1: 95%
v2: 5%

L7 load balancer có thể route theo:

- Percentage
- Cookie
- Header
- User group
- Region

Ví dụ:

X-Canary: true

Nếu metrics tốt, tăng dần:

5% → 20% → 50% → 100%

59. WebSocket và Load Balancing

WebSocket tạo connection dài.

Sau khi handshake, connection thường gắn với một backend.

flowchart LR
    Client --> LB
    LB --> WS1[WebSocket Server 1]

Load balancing cần cân nhắc:

- Least connections
- Active connection count
- Connection draining
- Reconnect
- Presence state
- Message routing

Nếu User A nối với Server 1 và User B nối với Server 2, message cần đi qua shared infrastructure:

flowchart TD
    A[User A] --> S1[WS Server 1]
    B[User B] --> S2[WS Server 2]

    S1 --> Broker[Message Broker]
    Broker --> S2

Không nên giả định hai user chat luôn ở cùng server.

60. Multi-region Load Balancing

Một hệ thống toàn cầu có thể có nhiều region:

flowchart TD
    Users --> Global[Global Load Balancer]

    Global --> Asia[Asia Region]
    Global --> Europe[Europe Region]
    Global --> US[US Region]

    Asia --> AsiaLB[Regional LB]
    Europe --> EuropeLB[Regional LB]
    US --> USLB[Regional LB]

Global load balancer route theo:

- Latency
- Geography
- Region health
- Capacity
- Data residency

Nếu Asia region lỗi:

Traffic có thể chuyển sang region khác.

Nhưng application và database phải hỗ trợ việc đó.

Load balancer không tự giải quyết:

- Data replication
- Cross-region consistency
- User session
- Regional failover data

61. DNS Load Balancing

DNS có thể trả nhiều IP:

api.example.com:
IP A
IP B
IP C

Ưu điểm:

- Đơn giản
- Hữu ích ở global level
- Có thể route theo region

Nhược điểm:

- DNS caching
- Failover không tức thời
- Không biết chính xác tải từng request
- Client có thể giữ IP cũ

DNS load balancing thường là tầng ngoài, không thay thế hoàn toàn regional load balancer.

62. Các failure mode phổ biến

Server treo nhưng vẫn trả health 200

Process còn chạy nhưng thread pool đã kẹt.

Giải pháp:

Readiness phản ánh khả năng xử lý thực tế
Passive health checks
Timeout

Health check quá nặng

Mỗi check query database phức tạp.

100 load balancer × nhiều server × check mỗi giây có thể tự tạo tải lớn.

Toàn bộ server khởi động cùng lúc

Cache lạnh và kết nối DB cùng tăng, gây startup storm.

Autoscaler scale quá mạnh

Nhiều instance mới cùng kết nối DB:

Connection storm

Scale in cắt request

Không có connection draining.

Sticky session làm hotspot

Một số server nhận toàn user nặng.

Load balancer fail

Không có HA cho chính load balancer.

App scale được nhưng DB không scale

Tăng app instance làm database sập nhanh hơn.

12 application instances

flowchart TD

66. Framework thiết kế Load Balancing như Senior Engineer

Khi thiết kế, hãy trả lời:

1. Peak RPS hoặc active connections là bao nhiêu?
2. Mỗi instance chịu an toàn bao nhiêu tải?
3. Service có stateless không?
4. State/session nằm ở đâu?
5. Cần L4 hay L7?
6. Thuật toán balancing nào phù hợp?
7. Backend có giống nhau không?
8. Request ngắn hay connection dài?
9. Health check kiểm tra điều gì?
10. Có liveness/readiness riêng không?
11. Làm sao connection draining?
12. Autoscaling dựa trên metric nào?
13. Instance startup mất bao lâu?
14. Có cooldown/stabilization không?
15. Load balancer có HA không?
16. Mất một zone có đủ capacity không?
17. Database và cache có chịu được khi app scale không?
18. Khi quá tải, hệ thống shed load thế nào?

68. Cách trình bày trong System Design Interview

Không nên chỉ nói:

Em thêm load balancer và nhiều server.

Nên nói:

API server sẽ stateless để bất kỳ instance nào cũng xử lý được request. Một L7 load balancer đứng trước application pool để terminate TLS và route HTTP traffic. Vì các instance có cấu hình tương đương và request tương đối ngắn, ban đầu tôi dùng round robin; nếu workload có duration không đồng đều, tôi chuyển sang least-connections hoặc least-response-time. Load balancer chỉ gửi traffic đến instance đã vượt qua readiness check. Autoscaling dựa trên RPS mỗi instance và p95 latency, có headroom để bù startup lag. Khi scale in hoặc deploy, instance được đưa vào trạng thái draining trước khi shutdown.

Đây là câu trả lời thể hiện:

- Loại load balancer
- State management
- Routing algorithm
- Health check
- Autoscaling
- Safe deployment

69. Những sai lầm phổ biến

Lỗi 1: Thêm server nhưng vẫn giữ session local

Khiến request phụ thuộc vào một server cụ thể.

Lỗi 2: Dùng Round Robin cho mọi workload

Không phù hợp khi request duration hoặc server capacity khác nhau nhiều.

Lỗi 3: Health check chỉ kiểm tra process

Process sống nhưng không thể xử lý request vẫn được xem là healthy.

Lỗi 4: Health check phụ thuộc mọi service

Một dependency phụ lỗi làm toàn bộ backend bị loại.

Lỗi 5: Không có draining

Deploy hoặc scale-in cắt request đang chạy.

Lỗi 6: Autoscale chỉ dựa vào CPU

Service I/O-bound hoặc queue-based có thể quá tải dù CPU thấp.

Lỗi 7: Scale in quá nhanh

Gây oscillation và thiếu capacity.

Lỗi 8: Không tính startup time

Traffic spike xảy ra trước khi instance mới ready.

Lỗi 9: Load balancer là single point of failure

Backend có nhiều server nhưng cửa vào chỉ có một node.

Lỗi 10: App scale ngang nhưng database không được bảo vệ

Hàng trăm app instance làm DB connection pool quá tải.

72. Những điều phải nhớ sau Bài 8

1. Vertical scaling tăng sức mạnh một máy; horizontal scaling thêm nhiều máy.
2. Load balancer phân phối traffic và loại backend không khỏe.
3. L4 route theo IP, port và protocol; L7 hiểu HTTP.
4. Round Robin phù hợp server và request tương đối đồng đều.
5. Least Connections phù hợp connection dài hoặc request duration khác nhau.
6. Weighted algorithm phù hợp backend khác capacity hoặc canary deployment.
7. Health check phải phân biệt liveness và readiness.
8. Server còn sống chưa chắc đã sẵn sàng nhận traffic.
9. Connection draining giúp deploy và scale-in an toàn.
10. Sticky session giải quyết local state tạm thời nhưng giảm khả năng scale và failover.
11. Stateless không nghĩa là không có state; state phải nằm ngoài application instance.
12. Autoscaling nên dùng metric phản ánh workload thật.
13. CPU không phải lúc nào cũng là metric tốt nhất.
14. Worker nên scale theo queue depth hoặc message age.
15. WebSocket service nên cân nhắc active connections.
16. Autoscaling có độ trễ nên luôn cần headroom.
17. Scale out nhanh nhưng scale in cần thận trọng.
18. Load balancer cũng phải có high availability.
19. Mất một zone vẫn phải còn đủ capacity.
20. Scale application tier có thể khiến database trở thành bottleneck.
21. Khi vượt capacity, hệ thống cần backpressure và load shedding.
22. Retry chỉ an toàn khi có timeout, backoff, giới hạn và idempotency.

73. Bài tập thực hành

Thiết kế tầng application và load balancing cho một hệ thống bán vé concert.

Giả định:

- Bình thường: 2.000 RPS
- Khi mở bán: 100.000 RPS
- Mỗi API instance chịu an toàn 1.000 RPS
- User giữ kết nối chờ mua vé trong vài phút
- Reservation và payment không được thực hiện trùng

Hãy trả lời:

1. Cần L4 hay L7 load balancer?
2. Thuật toán phân tải nào phù hợp?
3. Bình thường cần bao nhiêu instance?
4. Khi mở bán cần bao nhiêu instance và bao nhiêu headroom?
5. Autoscaling dựa trên CPU, RPS, connection hay queue depth?
6. Làm sao chuẩn bị trước traffic spike đã biết?
7. Có nên dùng sticky session không?
8. Session và waiting-room state nằm ở đâu?
9. Health check nên kiểm tra gì?
10. Khi scale in, làm sao không ngắt user đang thanh toán?
11. Làm sao tránh load balancer thành single point of failure?
12. Làm sao bảo vệ database khi 100.000 RPS tới?
13. Khi capacity đầy, request nào được ưu tiên?
14. Retry reservation/payment thế nào để không tạo duplicate?
