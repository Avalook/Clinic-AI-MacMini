Bài 26 — Case Study 5: Thiết kế Video Streaming Platform

Ta sẽ thiết kế một nền tảng Video on Demand — VOD tương tự hệ thống chia sẻ video:

Creator upload video
→ Hệ thống xử lý và transcoding
→ Video được phân phối qua CDN
→ Viewer phát video với chất lượng tự động thích nghi
→ Hệ thống thu thập analytics, view count và engagement

Các chức năng chính:

- Upload video dung lượng lớn
- Resume upload khi mất mạng
- Transcode nhiều độ phân giải và bitrate
- Tạo thumbnail, preview và subtitle
- Adaptive bitrate streaming
- Phân phối video toàn cầu qua CDN
- Theo dõi playback quality
- Đếm lượt xem
- Recommendation
- Copyright detection
- Content moderation

Kiến trúc cốt lõi:

3. Non-Functional Requirements

- Upload phải chịu được mạng không ổn định.
- Video đã upload thành công không được mất.

- Playback latency thấp.

- Hệ thống phải hoạt động ở nhiều region.

6. Capacity Estimation

Giả sử nền tảng có:

100 triệu DAU
5 triệu video uploads/ngày
1 tỷ video playback sessions/ngày

Giả sử video gốc trung bình:

500 MB

Dung lượng upload mỗi ngày:

5.000.000 × 500 MB
= 2,5 PB/ngày

Đây là giả định rất lớn để minh họa hệ thống quy mô toàn cầu.

7. Playback Bandwidth Estimation

Giả sử:

1 tỷ playback sessions/ngày
Average watch time = 10 phút
Average bitrate thực tế = 2 Mbps

Dữ liệu mỗi session:

2 Mb/s × 600 giây
= 1.200 Mb
≈ 150 MB

Tổng dữ liệu/ngày:

1 tỷ × 150 MB
≈ 150 PB/ngày

Bandwidth playback lớn hơn rất nhiều metadata traffic.

Do đó:

CDN và video delivery mới là phần có chi phí dữ liệu lớn nhất, không phải API servers.

14. Multipart Upload

File lớn được chia thành parts:

Part 1: bytes 0–16 MB
Part 2: bytes 16–32 MB
Part 3: bytes 32–48 MB
...

Ưu điểm:

- Retry từng phần
- Upload song song
- Resume
- Không cần gửi lại toàn bộ file

Client có thể upload 4–8 parts song song tùy:

- Network
- Device
- Battery
- Storage limits

15. Chọn Part Size

Part quá nhỏ:

- Nhiều requests
- Nhiều metadata
- Nhiều signed URLs
- Completion manifest lớn

Part quá lớn:

- Retry tốn nhiều bandwidth
- Parallelism thấp
- Memory pressure

Ví dụ:

16 MB
32 MB
64 MB

Nhưng part size nên tùy theo tổng file size.

16. Dynamic Part Size

Có thể chọn:

File < 1 GB:
16 MB/part

1–10 GB:
64 MB/part

> 10 GB:
128 MB/part

Mục tiêu:

- Số part không quá lớn
- Retry vẫn đủ nhỏ
- Parallelism hiệu quả

19. File Fingerprint

Client nên xác minh rằng file resume là cùng file ban đầu.

Fingerprint có thể dựa trên:

- File size
- Filename
- Last modified time
- Hash một số blocks
- Full checksum nếu khả thi

Không nên resume một file khác vào cùng upload session.

20. Checksums

Mỗi part có thể có checksum.

Sau khi complete, hệ thống xác minh:

- Part list đầy đủ
- Tổng kích thước
- Object checksum
- Content length

Checksum bảo vệ khỏi:

- Corruption
- Upload lỗi
- Client bug

Không nên chỉ tin Content-Type do client cung cấp.

21. Upload Completion

Client gọi:

POST /v1/uploads/{uploadSessionId}/complete

{
  "parts": [
    {
      "partNumber": 1,
      "etag": "..."
    }
  ]
}

Server:

1. Conditional claim upload session.
2. Gọi object storage complete multipart.
3. Kiểm tra object metadata.
4. Chuyển trạng thái sang UPLOADED.
5. Phát VideoUploaded event.

Completion API phải idempotent.

22. Idempotent Completion

Client có thể timeout sau khi upload đã complete.

Retry không được tạo object mới hoặc processing job mới.

State transition:

UPLOADING
→ COMPLETING
→ UPLOADED

Conditional transition:

Chỉ một worker được chuyển UPLOADING → COMPLETING.

Retry sau đó trả trạng thái hiện tại.

23. Abandoned Multipart Uploads

User bắt đầu upload nhưng không hoàn tất.

Object storage có thể giữ parts và tính phí.

Cần cleanup:

Upload session quá 24 giờ
→ ABANDONED
→ Abort multipart upload

Retention tùy sản phẩm.

Metrics:

- Upload completion rate
- Abandoned bytes
- Average resume count

24. Upload Quotas

Cần giới hạn:

- File size tối đa
- Tổng storage/user
- Uploads/day
- Concurrent upload sessions
- Video duration

Quota phải kiểm tra trước khi cấp signed URL.

Nếu chỉ kiểm tra sau upload, attacker có thể tiêu tốn storage và bandwidth.

25. Upload Security

- Ghi sang bucket khác
- Chọn arbitrary path

originals/{tenantId}/{videoId}/{uploadVersion}/source

Không dùng trực tiếp filename của user làm storage key.

27. Immutability và Versioning

Processed outputs nên immutable.

Khi re-transcode:

processingVersion = 2

Không ghi đè trực tiếp version 1 đang được CDN cache.

Playback metadata chuyển:

activeProcessingVersion: 1 → 2

Sau đó version cũ được cleanup sau grace period.

36. Fixed Ladder và Per-Title Encoding

Mọi video dùng cùng cấu hình.

Ưu điểm:

- Đơn giản
- Dự đoán capacity dễ

Nhược điểm:

Per-Title Encoding

Phân tích từng video để chọn ladder phù hợp.

Ưu điểm:

Nhược điểm:

- Cần analysis

- Pipeline phức tạp hơn

37. Codec Selection

Các codec có trade-off khác nhau.

H.264

- Tương thích rộng
- Encode tương đối nhanh
- Compression kém hơn codec mới

H.265/HEVC

- Compression tốt
- Licensing/device compatibility phức tạp

VP9

- Compression tốt
- Hỗ trợ rộng trên nhiều web/device
- Encode đắt hơn H.264

AV1

- Compression rất tốt
- Encode compute-intensive
- Device support đang tăng

38. Multi-Codec Strategy

Có thể tạo:

H.264:
Tất cả video

AV1:
Video phổ biến hoặc dài

Lý do:

Video ít view:
Chi phí AV1 encode có thể không hoàn vốn.

Video hàng tỷ views:
Tiết kiệm bandwidth rất lớn.

Encoding strategy có thể dựa trên expected popularity.

39. Re-Encode theo Popularity

Ban đầu:

Encode H.264 nhanh để publish sớm.

Nếu video trở nên phổ biến:

Background encode VP9/AV1.

Playback API sau đó ưu tiên codec phù hợp với client.

Đây là một ví dụ kiến trúc tiến hóa theo workload thực tế.

40. Keyframes và GOP

Video được chia thành nhóm frames.

- Segment boundaries align với keyframes
- Renditions có keyframe alignment giống nhau

Nếu không, chuyển chất lượng giữa segment có thể bị giật hoặc lỗi.

5. Publish active manifest.

Nếu upload region chết trong khi upload:

- Existing multipart session có thể không tiếp tục được.
- Client tạo session mới ở DR region.
- Đã upload parts có thể cần upload lại.

Nếu object storage multi-region hỗ trợ replication/session continuity, RTO tốt hơn nhưng complexity cao.

125. Processing Region Failure

Processing jobs nằm trong durable queue.

Nếu worker region lỗi:

- Jobs được lease lại
- Chạy tại region khác nếu original accessible
- Hoặc chờ region phục hồi

Task outputs phải idempotent.

Không để hai regions cùng publish hai active manifests khác nhau.

126. Origin Failure

Nếu origin object storage unavailable:

- CDN cache hits vẫn hoạt động.
- Cache misses lỗi.

Giải pháp:

- Replicated origin
- Origin failover
- Multi-region bucket
- Long immutable cache TTL

127. CDN Failure

Có thể:

- Multi-CDN routing
- Alternate manifest base URLs
- Player retry
- Regional failover

Playback API cần theo dõi CDN health.

Không chuyển toàn bộ traffic sang CDN B vượt capacity hợp đồng.

128. Metadata Store Failure

Playback có thể dùng:

- Cached playback metadata
- Signed token đã phát hành

Nhưng private/removed content cần policy cẩn thận.

Create/update APIs có thể tạm unavailable trong khi playback public vẫn hoạt động.

129. Event Stream Failure

Nếu metadata commit và outbox cùng transaction:

- Upload/video state vẫn bền vững.
- Processing bị trễ.
- Outbox publisher retry.

Không mất workflow intent.

130. Transcoding Worker Failure

Task lease hết hạn.

Job được retry.

Đầu ra tạm nằm trong staging.

160. Cách trình bày trong Phỏng vấn

Một câu trả lời tốt có thể bắt đầu:

Tôi tách control plane khỏi media data plane. Metadata API chỉ tạo video và multipart upload session; client upload trực tiếp vào object storage bằng signed URLs. Điều này tránh truyền nhiều GB video qua application servers.

Về processing:

Khi upload hoàn tất, một durable event khởi động processing DAG. Probe task xác minh container và codec, sau đó các transcoding jobs cho từng rendition chạy song song. Output được ghi vào staging, kiểm tra checksum và segment completeness trước khi master manifest được publish atomically.

Về playback:

Playback API kiểm tra visibility và entitlement rồi trả signed manifest URL. Client dùng HLS hoặc DASH để chọn rendition theo bandwidth và buffer. CDN cache immutable manifests, segments và thumbnails; origin shield bảo vệ object storage khỏi viral cache misses.

Về analytics:

Player gửi playback telemetry bất đồng bộ. View count được xác định từ qualified watch sessions thay vì request manifest, sau đó aggregate bằng sharded counters. Recommendation dùng watch history, completion và negative signals nhưng không nằm trong playback critical path.
