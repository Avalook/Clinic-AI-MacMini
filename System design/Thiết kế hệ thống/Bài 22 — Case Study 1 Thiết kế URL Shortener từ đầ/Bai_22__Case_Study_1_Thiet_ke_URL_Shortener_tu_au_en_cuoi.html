Bài 22 — Case Study 1: Thiết kế URL Shortener từ đầu đến cuối

URL Shortener nhận một URL dài:

https://example.com/products/mechanical-keyboard?
campaign=summer-2026&utm_source=facebook

và tạo một đường dẫn ngắn:

https://sho.rt/aZ91Kx2

Khi người dùng truy cập URL ngắn, hệ thống chuyển hướng tới URL gốc.

Bề ngoài đây là một bài toán đơn giản:

shortCode → originalURL

Nhưng ở quy mô lớn, nó bao gồm gần như toàn bộ kiến thức đã học:

- Requirements
- Capacity estimation
- API design
- Distributed ID generation
- Database và sharding
- Caching
- High availability
- Event streaming
- Analytics
- Security và abuse prevention
- Multi-region
- Consistency và disaster recovery

1. Bắt đầu bằng Requirements

Trong phỏng vấn System Design, không nên lập tức vẽ kiến trúc.

Trước hết cần làm rõ hệ thống phải làm gì.

Functional Requirements

Các chức năng cốt lõi:

1. Tạo URL ngắn từ URL dài.
2. Redirect URL ngắn tới URL gốc.
3. Cho phép custom alias.
4. Cho phép đặt expiration time.
5. Cho phép người sở hữu xem, sửa hoặc vô hiệu hóa link.
6. Thu thập analytics:
   - Số lượt click
   - Thời gian
   - Referrer
   - Quốc gia
   - Thiết bị
7. Phát hiện và chặn link độc hại.

Non-Functional Requirements

- Redirect latency rất thấp.
- Redirect availability rất cao.
- Hệ thống read-heavy.
- Short code phải unique.
- Không được redirect sai URL.
- Analytics có thể eventual consistent.
- Hệ thống phải chịu được hot links.
- Có thể phục vụ nhiều region.

2. Những gì chưa cần làm ở phiên bản đầu

Để giữ phạm vi phỏng vấn hợp lý, có thể tạm loại:

- Trình chỉnh sửa landing page
- Quảng cáo trước khi redirect
- Recommendation
- Social feed
- Blockchain-based links
- Full marketing automation

Ta tập trung vào lõi:

Create
→ Store
→ Redirect
→ Track

3. Access Pattern

URL Shortener có access pattern lệch mạnh về phía đọc.

Ví dụ minh họa:

100 triệu URL mới mỗi tháng
10 tỷ redirect mỗi tháng

Tỷ lệ:

Redirect : Create ≈ 100 : 1

Điều này ảnh hưởng trực tiếp tới kiến trúc:

- Redirect path phải cực kỳ tối ưu.
- Cache mang lại giá trị lớn.
- Write path có thể phức tạp hơn một chút.
- Analytics không nên nằm đồng bộ trong redirect path.

4. Capacity Estimation

Các con số sau là giả định để luyện thiết kế, không phải số liệu của một dịch vụ cụ thể.

URL Creation Traffic

Giả sử:

100 triệu links / tháng

Một tháng khoảng:

2,59 triệu giây

Average creation QPS:

100.000.000 / 2.590.000 ≈ 39 requests/giây

Nếu peak gấp 10 lần:

Peak creation QPS ≈ 400 requests/giây

Write traffic không quá lớn so với redirect.

5. Redirect Traffic

Giả sử:

10 tỷ redirects / tháng

Average redirect QPS:

10.000.000.000 / 2.590.000
≈ 3.860 requests/giây

Peak có thể cao hơn 10 lần:

Peak redirect QPS ≈ 40.000 requests/giây

Một hot link riêng lẻ có thể tạo:

100.000+ requests/giây

nếu được người nổi tiếng hoặc chiến dịch lớn chia sẻ.

Do đó không thể chỉ dựa vào average QPS.

6. Storage Estimation

Giả sử mỗi link record trung bình khoảng 700 byte, gồm:

- Short code
- Destination URL
- Owner ID
- Timestamps
- Expiration
- Status
- Metadata
- Index overhead chưa đầy đủ

Trong 5 năm:

100 triệu × 60 tháng = 6 tỷ links

Raw data:

6 tỷ × 700 byte
≈ 4,2 TB

Sau khi tính thêm:

- Database indexes
- Replication
- Storage engine overhead
- Backups

có thể cần hàng chục TB.

Đây vẫn là quy mô có thể xử lý bằng database sharding hoặc distributed key-value store.

7. Analytics Storage

Analytics thường lớn hơn link metadata rất nhiều.

Giả sử:

10 tỷ click events / tháng
300 byte / event

Raw event data:

≈ 3 TB / tháng

Trong 5 năm:

≈ 180 TB raw

Vì vậy không nên lưu từng click event trực tiếp trong database phục vụ redirect.

Analytics cần pipeline riêng:

Event stream
→ Stream processing
→ Object storage / OLAP

8. High-Level Architecture

flowchart TD
    Client --> Edge[CDN / WAF / Global Load Balancer]

    Edge --> Redirect[Redirect Service]
    Edge --> Management[Link Management API]

    Redirect --> L1[Local Cache]
    L1 --> L2[(Distributed Cache)]
    L2 --> LinkStore[(Link Store)]

    Management --> ID[ID Generator]
    Management --> LinkStore
    Management --> L2

    Redirect --> Events[Click Event Stream]
    Events --> Stream[Analytics Processing]
    Stream --> Analytics[(Analytics Store)]

    Management --> Abuse[Abuse Detection]

Có hai đường xử lý chính:

Write path:
Tạo hoặc quản lý link.

Read path:
Redirect người dùng.

Hai đường này có yêu cầu latency và consistency khác nhau.

9. API Design

Tạo Link

POST /v1/links
Authorization: Bearer ...
Idempotency-Key: request-123
Content-Type: application/json

Request:

{
  "destinationUrl": "https://example.com/products/123",
  "customAlias": "summer-sale",
  "expiresAt": "2026-12-31T23:59:59Z",
  "redirectType": 302
}

Response:

201 Created

{
  "id": "link_873921",
  "shortCode": "summer-sale",
  "shortUrl": "https://sho.rt/summer-sale",
  "destinationUrl": "https://example.com/products/123",
  "expiresAt": "2026-12-31T23:59:59Z",

10. Vì sao Create API cần Idempotency?

Client gửi request tạo link.

Server tạo thành công nhưng response bị mất.

Client retry:

Request 1 → tạo code abc123
Response bị mất

Request 2 → có thể tạo code xyz789

Một yêu cầu nghiệp vụ tạo ra hai links.

Với:

Idempotency-Key: request-123

server có thể lưu:

(ownerId, idempotencyKey)
→ kết quả đã tạo

Request retry nhận lại cùng kết quả.

11. Redirect API

Người dùng gọi:

GET /aZ91Kx2

Response mặc định:

302 Found
Location: https://example.com/products/123
Cache-Control: private, no-cache

Hoặc trong một số trường hợp:

307 Temporary Redirect

12. 301 hay 302?

301 Moved Permanently

Browser và intermediary có thể cache mạnh.

Ưu điểm:

- Giảm tải server
- Redirect nhanh

Nhược điểm:

- Sau này đổi destination khó có hiệu lực ngay
- Có thể mất click analytics tại server
- Browser có thể không hỏi hệ thống lần nữa

302 Found

Redirect tạm thời.

Ưu điểm:

- Mọi click thường quay lại hệ thống
- Destination có thể thay đổi
- Analytics dễ thu thập hơn

Nhược điểm:

- Tăng traffic tới redirect service

Đối với URL Shortener thông thường:

Mặc định nên dùng 302 hoặc 307, trừ khi link được tuyên bố bất biến và permanent rõ ràng.

13. 302 và 307 khác nhau thế nào?

Với request GET, sự khác biệt thường không đáng kể.

Tuy nhiên về semantics:

302:
Client lịch sử có thể đổi HTTP method trong một số trường hợp.

307:
Phải giữ nguyên method và body.

URL Shortener chủ yếu redirect GET, nên 302 được dùng rất phổ biến.

14. Link Management APIs

GET /v1/links/{shortCode}
PATCH /v1/links/{shortCode}
DELETE /v1/links/{shortCode}
GET /v1/links/{shortCode}/analytics

Update request:

{
  "destinationUrl": "https://example.com/new-page",
  "expiresAt": "2027-01-01T00:00:00Z"
}

Delete có thể là soft delete:

status = DISABLED

thay vì xóa vật lý ngay.

15. Data Model

Một model đơn giản:

CREATE TABLE short_links (
    short_code       VARCHAR(16) PRIMARY KEY,
    link_id          BIGINT NOT NULL,
    destination_url  TEXT NOT NULL,
    owner_id         BIGINT,
    status           VARCHAR(20) NOT NULL,
    redirect_type    SMALLINT NOT NULL,
    created_at       TIMESTAMP NOT NULL,
    updated_at       TIMESTAMP NOT NULL,
    expires_at       TIMESTAMP,
    version          BIGINT NOT NULL
);

Các trạng thái:

ACTIVE
DISABLED
EXPIRED
BLOCKED
DELETED

16. Access Pattern của Link Store

Redirect query chủ yếu là:

SELECT destination_url,
       status,
       redirect_type,
       expires_at,
       version
FROM short_links
WHERE short_code = ?;

Đây là exact key lookup.

Không cần:

- Full-text search
- Complex joins
- Multi-row transactions trên redirect path

Vì vậy một distributed key-value store rất phù hợp:

shortCode → LinkRecord

17. SQL hay NoSQL?

SQL phù hợp khi

- Hệ thống còn nhỏ hoặc vừa
- Cần transaction và uniqueness đơn giản
- Cần quản lý links theo owner
- Team quen relational database

Một relational database được partition tốt có thể đi rất xa.

Distributed Key-Value Store phù hợp khi

- Hàng tỷ links
- QPS redirect rất lớn
- Cần horizontal sharding tự nhiên
- Lookup chủ yếu theo short code
- Multi-region replication quan trọng

Một thiết kế thực tế có thể dùng:

Link metadata authoritative:
Distributed KV hoặc sharded relational DB

Analytics:
OLAP store

Owner dashboard:
Relational read model hoặc secondary indexes

18. Secondary Indexes

Ngoài lookup bằng code, user cần xem links của mình:

WHERE owner_id = ?
ORDER BY created_at DESC

Cần index:

(owner_id, created_at)

Expiration cleanup có thể cần:

(expires_at)

Tuy nhiên index toàn cục theo expires_at trên hàng tỷ rows có thể đắt.

Có thể dùng:

- Time buckets
- TTL feature của storage
- Expiration queue

19. Sinh Short Code

Short code cần:

- Unique
- Ngắn
- URL-safe
- Tạo nhanh
- Có thể phân tán

Các lựa chọn chính:

1. Auto-increment ID + Base62
2. Snowflake-like ID + Base62
3. Random code
4. Hash của URL
5. Range allocation

20. Base62 Encoding

Base62 sử dụng:

0–9
A–Z
a–z

Tổng cộng:

62 ký tự

Một integer:

125

có thể được encode thành chuỗi Base62 ngắn.

Không gian code:

62^6 ≈ 56,8 tỷ
62^7 ≈ 3,52 nghìn tỷ
62^8 ≈ 218 nghìn tỷ

Với vài tỷ links, code 7–8 ký tự thường đủ về mặt không gian.

21. Base62 là Encoding, không phải Hashing

Base62 không làm ID bí mật.

Nếu:

link_id = 1.000.001

được encode Base62, người biết thuật toán có thể đoán các ID gần đó.

Điều này có thể gây:

- Enumeration
- Lộ volume
- Crawl toàn bộ links

Có thể giảm bằng:

- Random permutation
- Feistel-based obfuscation
- Random code
- Non-sequential distributed IDs

Nhưng không nên coi short code là access-control secret.

22. Phương án 1 — Database Sequence

Quy trình:

1. Database cấp ID tăng dần.
2. Encode ID sang Base62.
3. Lưu mapping.

Ví dụ:

ID 1258392
→ Base62 "5hDa"

Ưu điểm:

- Không collision
- Đơn giản
- Code ngắn

Nhược điểm:

- Central sequence
- Khó active–active multi-region
- Có thể đoán code

Phù hợp với phiên bản đầu hoặc single-region system.

23. Phương án 2 — Snowflake-Like ID

ID gồm:

timestamp + region/worker ID + sequence

Sau đó encode Base62.

Ưu điểm:

- Tạo phân tán
- Không cần database call cho mỗi ID
- Throughput cao
- Gần sort theo thời gian

Nhược điểm:

- Clock rollback
- Worker ID management
- Code có thể dài hơn
- Vẫn lộ approximate creation time

Đây là lựa chọn tốt khi hệ thống có nhiều writers hoặc nhiều region.

24. Phương án 3 — Random Code

Sinh ngẫu nhiên chuỗi:

aZ91Kx2Q

Sau đó conditional insert:

INSERT IF short_code DOES NOT EXIST

Nếu collision:

Sinh lại.

Với 8 ký tự Base62:

62^8 ≈ 218 nghìn tỷ combinations

Ngay cả khi đã có 6 tỷ links, xác suất một lần sinh mới đụng code đang tồn tại xấp xỉ:

6 tỷ / 218 nghìn tỷ
≈ 0,00275%

Có thể retry rất nhanh.

Ưu điểm:

- Khó đoán hơn sequence
- Tạo độc lập
- Không cần central ID service

Nhược điểm:

- Phải xử lý collision
- Code thường cần dài hơn
- Cần random generator chất lượng tốt

25. Birthday Paradox và Random Code

Nếu sinh rất nhiều code, khả năng “đã từng có ít nhất một collision” sẽ tăng nhanh hơn trực giác.

Tuy nhiên vấn đề được kiểm soát bằng:

- Unique constraint
- Conditional write
- Retry

Ta không cần bảo đảm random generator tuyệt đối không bao giờ collision.

Ta cần bảo đảm:

Collision không thể tạo hai records có cùng short code.

26. Phương án 4 — Hash của URL

Có thể lấy:

hash(destinationURL)

rồi lấy vài ký tự đầu.

Ưu điểm:

- Cùng URL có thể tạo cùng code
- Không cần ID service

Nhược điểm:

- Hash collision
- User khác nhau có thể muốn expiry khác nhau
- Analytics và ownership khác nhau
- URL có tracking parameters tạo hash khác
- Không dễ sửa destination

Do đó không nên mặc định deduplicate toàn cục theo destination URL.

Hai người tạo cùng URL có thể cần hai links khác nhau.

27. Phương án khuyến nghị

Cho thiết kế quy mô lớn:

Generated link:
Snowflake-like ID hoặc random code 8–10 ký tự

Custom alias:
Conditional unique insert

Một lựa chọn cân bằng:

- Sinh distributed numeric ID.
- Obfuscate hoặc permute ID.
- Encode Base62.
- Dùng unique conditional write.

Trong phỏng vấn, điều quan trọng là trình bày trade-off, không phải chọn duy nhất một thuật toán.

28. Case Sensitivity

Base62 phân biệt:

abc
ABC
AbC

Điều này tăng không gian code nhưng dễ gây nhầm khi đọc hoặc nhập tay.

Có thể chọn Base58, loại các ký tự dễ nhầm:

0, O
I, l

Trade-off:

Base62:
Không gian lớn hơn

Base58:
Dễ đọc hơn

29. Custom Alias

User muốn:

https://sho.rt/summer-sale

Yêu cầu:

- Alias phải unique.
- Cấm reserved names.
- Có quy tắc normalize rõ.
- Phải chống race condition.

Reserved aliases:

admin
api
login
support
health
robots.txt
favicon.ico

30. Normalize Custom Alias

Có thể quy định:

- 4–32 ký tự
- Chỉ [a-z0-9-_]
- Không khoảng trắng
- Chuyển về lowercase

Ví dụ:

Summer-Sale
→ summer-sale

Nếu giữ case-sensitive alias, user dễ tạo:

Sale
sale
SALE

gây nhầm lẫn và phishing.

Lowercase namespace thường đơn giản hơn cho custom alias.

31. Race Condition khi Tạo Alias

Hai requests đồng thời:

A: tạo summer-sale
B: tạo summer-sale

Không được làm:

1. SELECT alias
2. Nếu chưa có thì INSERT

vì cả hai có thể cùng thấy chưa tồn tại.

Phải dựa vào:

- Unique constraint
- Compare-and-set
- Conditional insert

Một request thắng, request kia nhận:

409 Conflict

32. Không nên Tái sử dụng Short Code

Link cũ bị xóa:

sho.rt/abc123

Không nên cấp abc123 cho URL mới.

Người dùng có thể còn:

- Bookmark cũ
- Email cũ
- QR code cũ
- Cache cũ

Nếu code được tái sử dụng, người truy cập link cũ bị đưa tới nội dung hoàn toàn khác.

Đây là rủi ro:

- Security
- Phishing
- Data integrity

Tốt hơn giữ tombstone:

abc123 → DELETED

và trả:

410 Gone

33. Create Link Write Path

sequenceDiagram
    participant Client
    participant API as Link API
    participant ID as ID Generator
    participant DB as Link Store
    participant Cache
    participant Abuse

    Client->>API: POST /v1/links
    API->>API: Validate URL and quota
    API->>Abuse: Basic reputation check
    API->>ID: Generate short code
    ID-->>API: aZ91Kx2
    API->>DB: Conditional insert
    DB-->>API: Success

Điểm consistency quan trọng:

Không trả success trước khi mapping đã được ghi bền vững vào authoritative store.

34. URL Validation

Destination URL phải được parse bằng URL parser chuẩn.

Không nên chỉ kiểm tra:

Chuỗi bắt đầu bằng "http"

Cho phép:

http://
https://

Thường nên chặn:

javascript:
data:
file:
ftp:

để giảm rủi ro browser hoặc application xử lý scheme nguy hiểm.

35. Normalize Destination URL?

Có thể normalize một số phần:

- Lowercase hostname
- Chuẩn hóa default port
- Punycode domain quốc tế

Nhưng không được tùy tiện:

- Xóa query parameters
- Đổi path case
- Reorder query
- Xóa trailing slash

vì có thể thay đổi resource.

URL normalization phải bảo toàn semantics.

36. Redirect Read Path

sequenceDiagram
    participant Client
    participant Edge
    participant Service as Redirect Service
    participant L1 as Local Cache
    participant Redis as Distributed Cache
    participant DB as Link Store
    participant Events as Event Stream

    Client->>Edge: GET /aZ91Kx2
    Edge->>Service: Forward request

    Service->>L1: Lookup
    alt L1 hit
        L1-->>Service: Link record
    else L1 miss
        Service->>Redis: Lookup
        alt Redis hit
            Redis-->>Service: Link record
            Service->>L1: Populate
        else Redis miss
            Service->>DB: Lookup short code
            DB-->>Service: Link record
            Service->>Redis: Populate
            Service->>L1: Populate
        end
    end

    Service->>Events: Publish click asynchronously
    Service-->>Client: 302 Location: destination

37. Redirect Validation

Sau khi lấy record, Redirect Service phải kiểm tra:

- Code có tồn tại không?
- Status có ACTIVE không?
- Link có hết hạn không?
- Link có bị abuse system BLOCKED không?
- Destination có hợp lệ không?

Các response có thể là:

404 Not Found:
Code chưa từng tồn tại

410 Gone:
Link đã xóa hoặc hết hạn vĩnh viễn

451 Unavailable For Legal Reasons:
Bị chặn theo yêu cầu pháp lý trong một số trường hợp

302/307:
Redirect hợp lệ

Không nhất thiết expose chính xác lý do block để tránh giúp attacker thăm dò hệ thống.

38. Cache Architecture

URL Shortener là use case cache lý tưởng vì:

- Read-heavy
- Mapping nhỏ
- Nhiều code được đọc lặp lại
- Redirect không cần query phức tạp

Có thể dùng nhiều tầng:

L0:
CDN/edge cache

L1:
In-process cache tại Redirect Service

L2:
Distributed cache như Redis

L3:
Authoritative Link Store

39. L1 Local Cache

Mỗi application instance giữ cache memory nhỏ.

Ưu điểm:

- Không network call
- Latency rất thấp
- Giảm tải Redis

Nhược điểm:

- Mỗi instance có state khác nhau
- Invalidation khó
- Capacity giới hạn

Phù hợp với hot links và TTL ngắn.

40. Distributed Cache

L2 cache dùng chung giữa application instances.

shortCode → serialized LinkRecord

Ưu điểm:

- Hit ratio cao hơn L1
- Dễ warm hơn
- Giảm tải database

Nhược điểm:

- Network hop
- Có thể trở thành bottleneck
- Cần sharding và replication

41. Cache-Aside Pattern

Redirect Service:

1. Đọc cache.
2. Nếu miss, đọc database.
3. Ghi kết quả vào cache.
4. Trả response.

Đây là cache-aside.

Create path có thể chủ động populate cache để bảo đảm read-after-write nhanh hơn.

42. Cache TTL

Ví dụ:

Default TTL:
5–30 phút

Nhưng nếu link sắp hết hạn:

expiresAt còn 2 phút

cache TTL không được là 30 phút.

Nên dùng:

cacheTTL =
min(defaultTTL, expiresAt - now)

Nếu link đã bị block hoặc delete, cache cần invalidation nhanh.

43. Cache Invalidation sau Update

User đổi destination.

Nếu database cập nhật nhưng cache còn URL cũ:

Redirect tiếp tục đi sai destination.

Các cách:

1. Update DB rồi delete cache.
2. Update DB rồi write-through cache.
3. Phát cache invalidation event.
4. Dùng TTL ngắn.

Pattern phổ biến:

Database authoritative update
→ Delete cache key
→ Request tiếp theo reload

44. Race trong Cache Invalidation

Có thể xảy ra:

1. Reader miss cache.
2. Reader đọc URL cũ từ DB.
3. Writer update DB và xóa cache.
4. Reader ghi URL cũ trở lại cache.

Giải pháp:

- Version trong record
- Cache write conditional theo version
- Double delete trong một số hệ thống
- Short TTL
- Read DB từ consistent source

Cache value nên chứa:

linkVersion

45. Negative Caching

Nếu attacker gọi hàng triệu code không tồn tại:

/a000001
/a000002
/a000003

mỗi request đi database sẽ rất tốn.

Có thể cache:

code → NOT_FOUND

trong TTL ngắn:

30–120 giây

Nhưng phải tránh negative cache quá lâu khi code vừa được tạo.

Create path có thể xóa negative cache hoặc populate record mới.

46. Cache Stampede

Một hot link hết TTL.

Hàng nghìn requests cùng miss và gọi database.

Giải pháp:

- Request coalescing
- Single-flight
- Stale-while-revalidate
- Randomized TTL
- Proactive refresh

Với stale-while-revalidate:

- Trả cached value hơi cũ.
- Một worker refresh phía sau.

Chỉ nên dùng khi staleness nhỏ được chấp nhận.

47. Hot Link

Một code có thể nhận lượng traffic khổng lồ.

Giải pháp:

- CDN hoặc edge caching
- L1 cache trên mọi redirect instance
- Replicated distributed cache
- Không update click counter đồng bộ
- Rate limiting cho traffic bất thường

Do destination mapping gần như read-only, hot key dễ scale bằng replication hơn write-heavy hot key.

48. CDN Edge Redirect

CDN có thể cache response:

302 Location: ...

Ưu điểm:

- Redirect gần user
- Giảm tải origin
- Chịu hot link tốt

Trade-off:

- Update/delete propagation chậm
- Origin không thấy mọi click
- Analytics phải lấy từ CDN logs hoặc edge events

Có thể dùng TTL ngắn:

30–300 giây

và purge CDN khi link bị block.

49. Analytics không được nằm trên Critical Path

tùy contract.

if now >= expiresAt:
    return 410

57. Lazy Expiration

- Không cần scheduler chính xác tuyệt đối

Nhược điểm:

- Record hết hạn vẫn chiếm storage

58. Active Expiration Cleanup

Không nên mỗi phút chạy:

SELECT *

Các phương án:

- Database TTL
- Time-partitioned expiration buckets
- Delayed queue
- Priority queue phân tán
- Index theo expires_at

Ví dụ bucket:

expiration/2026-12-31/23/

Worker chỉ xử lý bucket đến hạn.

68. Sharding Link Store

Shard key tự nhiên:

flowchart TD
    Router --> S1[(Shard 1)]

Hot link vẫn tạo hot key, nhưng cache/CDN xử lý tốt hơn việc cố chia một record qua nhiều shards.

69. Vì sao không Range-Shard theo ID tăng dần?

Nếu IDs tăng dần:

1001
1002
1003
...

range sharding khiến toàn bộ writes mới đi shard cuối.

→ Hot write shard

Hash sharding phân phối writes tốt hơn.

Nếu cần listing theo owner, có thể có secondary index hoặc storage riêng theo ownerId.

70. Virtual Shards

Thay vì mapping trực tiếp:

hash(code) mod physicalShardCount

có thể dùng nhiều logical partitions:

4.096 virtual shards

sau đó map virtual shard sang physical node.

Lợi ích:

- Rebalancing dễ hơn
- Chuyển một phần nhỏ dữ liệu
- Phân phối tải linh hoạt

71. Consistency Requirements

Không phải mọi phần cần cùng consistency.

Short-code uniqueness

Strong consistency

Hai records không được có cùng code.

Redirect mapping sau creation

Read-your-writes

Link vừa tạo phải dùng được ngay.

Destination update

Có thể bounded stale trong vài giây nếu contract cho phép, nhưng block/delete nên propagate rất nhanh.

Analytics

Eventual consistency

Dashboard chậm vài giây hoặc vài phút thường chấp nhận được.

72. Read-After-Write

Client tạo link rồi lập tức truy cập.

Nếu write vào Region A nhưng redirect được route tới replica Region B đang lag:

404 dù create đã trả success.

Giải pháp:

- Route link mới về home region trong khoảng ngắn
- Synchronous replication trước success
- Session/routing token
- Populate global cache
- Global strongly consistent store

Hệ thống phải chọn rõ trade-off giữa latency và immediate global visibility.

73. Delete và Block Consistency

Nếu link phishing bị block, không muốn edge cache tiếp tục redirect trong 30 phút.

Có thể dùng:

- Urgent invalidation channel
- CDN purge
- Short cache TTL cho untrusted links
- Blocklist checked tại edge
- Versioned cache

Security state thường cần propagation nhanh hơn destination update thông thường.

74. Multi-Region Option 1 — Active–Passive

flowchart LR
    Users --> GlobalRouter

    GlobalRouter --> Active[Region A Active]
    GlobalRouter -. standby .-> DR[Region B Standby]

    Active --> Primary[(Primary Link Store)]
    Primary -->|Replication| Replica[(DR Replica)]

Ưu điểm:

- Đơn giản
- Code uniqueness dễ
- Một write owner
- Conflict thấp

Nhược điểm:

- User xa primary có write latency cao
- Regional outage cần failover
- Async replication có RPO lớn hơn 0

Phù hợp với phiên bản đầu có yêu cầu DR.

- Shard
- Worker

Ưu điểm:

- Không cần global lookup trước mỗi redirect
- Partitioning rõ

Nhược điểm:

- Lộ topology một phần
- Migration region khó hơn
- Code format bị gắn với kiến trúc

Có thể dùng virtual shard thay vì physical region để giảm coupling.

78. Global Custom Alias khó hơn Generated Code

Generated code có thể bảo đảm uniqueness bằng region bits.

không chứa region.

Để bảo đảm global uniqueness, cần một trong các cách:

- Global consensus store
- Một alias-owner region duy nhất
- Partition alias namespace theo tenant/domain
- Conditional write vào globally consistent database

Đây là ví dụ rõ ràng của trade-off active–active.

80. Regional Failover

Nếu Region A lỗi:

1. Global router ngừng gửi traffic tới A.
2. Promote replica hoặc chuyển ownership.
3. Fence writers cũ ở A.
4. Redirect traffic sang B.
5. Warm caches.
6. Reconcile replication lag.

Redirect service có thể vẫn hoạt động từ cache ngay cả khi primary store tạm unavailable.

81. Cache trong Disaster

Nếu Link Store tạm lỗi:

- Cache hits vẫn redirect được.
- Cache misses thất bại.

Availability cao hơn

82. Failure Mode — Distributed Cache Down

Khi Redis lỗi, toàn bộ traffic đổ vào database có thể gây cascading failure.

- Circuit breaker
- Database rate limit
- Load shedding
- Stale cache
- Cache cluster replication

Không nên cho mọi request miss cache đồng thời hit database không giới hạn.

83. Failure Mode — Link Store Down

Có thể degrade:

Cache hit:
Vẫn redirect

Cache miss:
Trả 503 hoặc fallback sang replica

Link creation:
Tạm unavailable

Redirect thường quan trọng hơn create, nên có thể ưu tiên tài nguyên cho read path.

84. Failure Mode — Analytics Pipeline Down

Redirect không nên dừng.

Có thể:

- Buffer giới hạn
- Ghi local logs
- Drop/sampling low-priority events
- Alert analytics lag

Tùy business, mất một phần click analytics có thể tốt hơn làm redirect unavailable.

85. Failure Mode — ID Generator Down

Nếu ID generator là service trung tâm và nó lỗi, create link dừng.

Giải pháp:

- Snowflake generation local trong application
- Preallocated ID ranges
- Replicated ID service
- Random code generation

Redirect path không phụ thuộc ID generator.

86. Failure Mode — Abuse Scanner Down

Không nên luôn chọn một behavior.

Có thể:

Fail open

Cho phép tạo link rồi scan sau.

Availability cao
Abuse risk cao hơn

Fail closed

Từ chối tạo link khi scanner lỗi.

An toàn hơn
Availability thấp hơn

Có thể phân tầng:

Trusted accounts:
Fail open với async scan

Anonymous/new accounts:
Fail closed hoặc PENDING_REVIEW

96. Trade-Off — Random Code hay Sequential ID?

Sequential ID + Base62

Ưu:
Ngắn, không collision, đơn giản.

Nhược:
Dễ enumerate, central coordination.

Random Code

Ưu:
Khó đoán, tạo phân tán.

Nhược:
Collision retry, code dài hơn.

Snowflake + Base62

Ưu:
Distributed, unique, throughput cao.

Nhược:
Clock/worker complexity, vẫn có cấu trúc đoán được.

Không có lựa chọn tốt tuyệt đối.

97. Trade-Off — Cache nhiều hay ít?

Cache TTL dài:

- Hit ratio cao
- Database nhẹ
- Update/block propagation chậm

Cache TTL ngắn:

- Fresh hơn
- Database/cache backend tải cao hơn

Có thể dùng TTL khác nhau:

Trusted immutable links:
TTL dài

Editable links:
TTL vừa

Untrusted/new links:
TTL ngắn

98. Trade-Off — Dedupe Destination URL?

Dedupe toàn cục cùng URL thành một short code:

Ưu:
Giảm storage

Nhược:
Ownership, expiry, alias và analytics bị trộn

Thông thường không nên dedupe toàn cục.

Có thể dedupe theo:

ownerId + normalizedURL + settings

nếu sản phẩm muốn tránh user tự tạo duplicate.

99. Trade-Off — Edge Cache và Analytics

Cache redirect tại CDN:

Ưu:
Latency và scale rất tốt.

Nhược:
Origin không thấy từng click.

Giải pháp:

- Edge logs
- CDN event streaming
- Sampled analytics
- Không edge-cache links cần realtime click tracking

Sản phẩm có thể cho user chọn:

Maximum performance
vs
Maximum analytics freshness

100. Trade-Off — Strong Global Custom Alias

Muốn custom alias unique toàn cầu trong active–active:

Cần global coordination.

Các lựa chọn:

- Chấp nhận write latency cao
- Chỉ cho tạo alias tại một region
- Namespace alias theo custom domain/tenant
- Cho generated codes local nhưng custom aliases global

Đây là cách tách consistency requirement theo feature.

101. Cách Trình bày trong Phỏng vấn

Một câu trả lời tốt có thể bắt đầu:

Hệ thống có hai access pattern chính: tạo link và redirect. Redirect nhiều hơn create khoảng hai bậc độ lớn, nên tôi tối ưu read path bằng edge cache, local cache và distributed cache. Authoritative data store là một sharded key-value store được partition theo hash của short code.

Về ID:

Generated links dùng một distributed 64-bit ID, chẳng hạn Snowflake-like ID, sau đó encode Base62. Custom aliases đi qua conditional insert vào namespace có unique constraint. Short codes đã xóa không được tái sử dụng vì bookmarks và QR codes cũ vẫn có thể tồn tại.

Về redirect:

Redirect Service lookup code qua L1, distributed cache rồi Link Store. Nó kiểm tra status và expiration, phát click event bất đồng bộ rồi trả 302. Analytics không nằm trong critical path để sự cố analytics không làm redirect lỗi.

Về multi-region:

Vì redirect nhiều hơn create rất nhiều, tôi ưu tiên active–active reads tại nhiều region nhưng giữ write ownership rõ ràng. Generated IDs có region/worker uniqueness; custom alias toàn cầu cần globally consistent conditional write hoặc một alias-owner region duy nhất. Link records được replicate tới read regions và cache edge.

103. Những Sai lầm Phổ biến

Lỗi 1: Bắt đầu ngay bằng Microservices

URL Shortener phiên bản đầu có thể rất đơn giản.

Lỗi 2: Không ước lượng Read/Write Ratio

Bỏ lỡ vai trò quan trọng của cache.

Lỗi 3: Dùng Hash URL rồi bỏ qua Collision

Truncated hash vẫn có collision.

Lỗi 4: Dùng Random Code nhưng không có Unique Conditional Write

Hai links có thể nhận cùng code.

Lỗi 5: Coi Base62 là Encryption

Sequential IDs vẫn có thể bị enumerate.

Lỗi 6: Tái sử dụng Code đã Xóa

Link cũ có thể redirect sang nội dung mới nguy hiểm.

Lỗi 7: Ghi Analytics đồng bộ

Analytics failure làm redirect chậm.

Lỗi 8: Lưu Click Counter trực tiếp trong Link Record

Hot links tạo write contention trên một record.

Lỗi 9: Cache mà không có Invalidation Strategy

Update hoặc block không có hiệu lực.

Lỗi 10: Cache TTL dài hơn Expiration

Link hết hạn vẫn redirect.

Lỗi 11: Không Negative Cache

Random code scanning làm quá tải database.

Lỗi 12: Dùng Search Index để Redirect

Redirect cần exact key-value lookup, không cần full-text search.

Lỗi 13: Không phân biệt 301 và 302

Browser cache làm mất khả năng update và track.

Lỗi 14: Multi-Region nhưng không giải quyết Global Alias Uniqueness

Hai regions có thể tạo cùng alias.

Lỗi 15: Coi Short Code là Access Control

Ai có URL vẫn có thể truy cập destination.

Lỗi 16: Preview Destination không chống SSRF

Attacker truy cập internal network qua preview service.

Lỗi 17: Không có Abuse Pipeline

Shortener nhanh chóng trở thành hạ tầng phishing.

Lỗi 18: Không xử lý Hot Link

Một link viral làm nóng một cache shard hoặc analytics partition.

Lỗi 19: Dùng Average QPS để Capacity Planning

Peak và skew mới là vấn đề chính.

Lỗi 20: Không có Tombstone

Không phân biệt code chưa từng tồn tại và code đã bị thu hồi.
