Bài 13 — Sharding và Data Partitioning

Khi một database còn đủ sức chứa và xử lý workload, kiến trúc đơn giản nhất thường là:

flowchart LR
    Application --> DB[(Single Database)]

Ta có thể kéo dài khả năng của database bằng:

- Tối ưu query
- Tạo index đúng
- Vertical scaling
- Caching
- Read replicas
- Archive dữ liệu cũ
- Table partitioning

Nhưng đến một quy mô nào đó, một database node có thể không còn đáp ứng được:

- Dung lượng dữ liệu
- Write throughput
- Disk I/O
- CPU
- Memory cho index
- Số connection
- Thời gian backup và restore
- Thời gian maintenance

Khi đó, ta có thể phải chia dữ liệu sang nhiều node. Đây là bài toán sharding và data partitioning.

Các tài liệu System Design bạn cung cấp đặt partitioning, horizontal scaling và distributed storage vào nhóm kỹ thuật mở rộng hệ thống khi một node không còn đủ khả năng phục vụ toàn bộ dữ liệu và traffic.

1. Partitioning là gì?

Partitioning là chia một tập dữ liệu lớn thành nhiều phần nhỏ hơn gọi là partition.

Ví dụ bảng orders chứa 10 tỷ bản ghi:

orders_2025
orders_2026
orders_2027

Hoặc chia theo user:

Partition 1:
User A–F

Partition 2:
User G–M

Partition 3:
User N–Z

Mục tiêu:

- Mỗi partition nhỏ hơn
- Query có thể chỉ đọc partition liên quan
- Maintenance dễ hơn
- Dữ liệu và traffic có thể được phân phối

2. Sharding là gì?

Sharding là một dạng horizontal partitioning trong đó các partition được đặt trên nhiều database server hoặc cluster độc lập.

flowchart TD
    Application --> Router[Shard Router]

    Router --> S1[(Shard 1)]
    Router --> S2[(Shard 2)]
    Router --> S3[(Shard 3)]

Ví dụ:

Shard 1:
User 1–1.000.000

Shard 2:
User 1.000.001–2.000.000

Shard 3:
User 2.000.001–3.000.000

Mỗi shard có thể có:

- CPU riêng
- Memory riêng
- Disk riêng
- Connection pool riêng
- Replicas riêng

3. Partitioning và Sharding khác nhau thế nào?

Hai thuật ngữ đôi khi được dùng lẫn nhau, nhưng có thể hiểu:

Khái niệm Ý nghĩa thường gặp
Partitioning Chia dữ liệu logic thành nhiều phần
Table partitioning Các partition vẫn do cùng database quản lý
Sharding Các phần dữ liệu nằm trên nhiều database node độc lập

Ví dụ PostgreSQL partition theo tháng:

transactions_2026_01
transactions_2026_02
transactions_2026_03

Các partition vẫn có thể nằm trong cùng một database instance.

Sharding:

Shard Asia
Shard Europe
Shard America

Mỗi shard là một database riêng.

4. Vertical và Horizontal Partitioning

Vertical partitioning

Chia theo cột hoặc nhóm chức năng.

Ví dụ bảng user ban đầu:

users:
id
email
password_hash
name
avatar
bio
preferences
last_login

Tách thành:

users_auth:
id
email
password_hash

users_profile:
id
name
avatar
bio

users_preferences:
id
preferences

Mục tiêu:

- Tách dữ liệu nhạy cảm
- Tách field lớn
- Giảm row size
- Tách workload

Vertical partitioning gần với việc tách service/database theo domain.

Horizontal partitioning

Chia theo row.

Partition 1:
users có id 1–1.000.000

Partition 2:
users có id 1.000.001–2.000.000

Sharding chủ yếu nói về horizontal partitioning.

5. Khi nào chưa nên Sharding?

Sharding làm hệ thống phức tạp hơn rất nhiều.

Trước khi shard, nên kiểm tra:

1. Query đã tối ưu chưa?
2. Index đã đúng chưa?
3. Có query N+1 không?
4. Có cache được read-heavy workload không?
5. Có dùng read replica được không?
6. Có thể vertical scale không?
7. Có thể archive dữ liệu cũ không?
8. Có thể table partition trong một database không?
9. Có thể batch write không?
10. Bottleneck có thực sự là database không?

Không nên shard vì:

“Sau này hệ thống có thể lớn.”

Nên shard khi có bằng chứng:

- Storage vượt giới hạn một node
- Write QPS vượt khả năng một leader
- Index không còn vừa memory
- Maintenance quá lâu
- Backup/restore không đạt RTO
- Một tenant lớn làm node quá tải

6. Sharding giải quyết được gì?

Tăng storage capacity

Nếu một node chứa được 10 TB:

10 shards × 10 TB
≈ 100 TB tổng capacity

Tăng write throughput

Write được phân phối sang nhiều shard:

flowchart LR
    Writes --> Router

    Router --> S1[(Shard 1)]
    Router --> S2[(Shard 2)]
    Router --> S3[(Shard 3)]

Nếu mỗi shard chịu 5.000 writes/giây:

10 shards
≈ 50.000 writes/giây về lý thuyết

Thực tế còn phụ thuộc phân bố tải và coordination.

Giảm kích thước index trên mỗi node

Thay vì một index cho 10 tỷ row:

Mỗi shard có index cho khoảng 1 tỷ row.

Index nhỏ hơn có thể:

- Vừa memory hơn
- Dễ rebuild hơn
- Query nhanh hơn

Giảm blast radius

Nếu một shard lỗi:

Chỉ user trên shard đó bị ảnh hưởng

thay vì toàn bộ hệ thống.

Điều này chỉ đúng nếu các dependency khác cũng được cô lập phù hợp.

7. Sharding không giải quyết được gì?

Sharding không tự động sửa:

- Query thiết kế tệ
- Index sai
- N+1 query
- Lock contention trong cùng một record nóng
- Một partition key cực nóng
- Logic transaction không tốt
- Retry storm
- Connection leak

Thậm chí sharding có thể làm những vấn đề đó khó debug hơn.

8. Shard Key là gì?

Shard key là field hoặc tổ hợp field dùng để xác định record thuộc shard nào.

Ví dụ:

user_id
tenant_id
order_id
conversation_id
region

Routing:

shard = shard_function(shard_key)

Ví dụ:

shard = hash(user_id) mod 16

9. Một Shard Key tốt cần đặc điểm gì?

Cardinality cao

Có nhiều giá trị khác nhau.

Tốt:

user_id
order_id

Không tốt:

country_code
status
gender

Nếu chỉ có vài giá trị, traffic khó phân phối đều.

Phân bố tương đối đều

Không để một shard chứa phần lớn dữ liệu hoặc traffic.

Có mặt trong query chính

Nếu query thường là:

Lấy toàn bộ task của user X

shard theo user_id rất tự nhiên.

Nếu query không có shard key, router có thể phải hỏi mọi shard.

Ổn định

Shard key không nên thay đổi thường xuyên.

Nếu shard theo country, user đổi country có thể phải chuyển toàn bộ dữ liệu sang shard khác.

Phù hợp phạm vi transaction

Các record thường được transaction cùng nhau nên cố gắng nằm cùng shard.

Ví dụ:

Order và order_items

nên cùng shard theo order_id hoặc customer_id, tùy access pattern.

10. Shard Key quyết định kiến trúc

Giả sử ứng dụng Todoist.

Query chính:

- Lấy project của user
- Lấy task của user
- Cập nhật task của user

Shard theo:

user_id

Tất cả dữ liệu của một user có thể nằm cùng shard.

flowchart TD
    UserA[User A] --> S1[(Shard 1)]
    UserB[User B] --> S2[(Shard 2)]
    UserC[User C] --> S1

Lợi ích:

- Query một user chỉ chạm một shard
- Transaction giữa task/project của user dễ hơn

Nhược điểm:

- Một enterprise tenant cực lớn có thể làm shard nóng
- Query toàn hệ thống phải fan-out

11. Range-based Sharding

Range sharding chia key theo khoảng.

Ví dụ:

Shard 1:
user_id 1–1.000.000

Shard 2:
user_id 1.000.001–2.000.000

Shard 3:
user_id 2.000.001–3.000.000

flowchart LR
    ID[User ID] --> Range{Which range?}

    Range -->|1–1M| S1[(Shard 1)]
    Range -->|1M–2M| S2[(Shard 2)]
    Range -->|2M–3M| S3[(Shard 3)]

12. Ưu điểm của Range Sharding

- Dễ hiểu
- Routing đơn giản
- Range query hiệu quả
- Dữ liệu gần nhau có thể nằm cùng shard

Ví dụ dữ liệu theo thời gian:

January → Shard 1
February → Shard 2
March → Shard 3

Query tháng 2 chỉ đọc Shard 2.

13. Nhược điểm của Range Sharding

Hot shard với ID tăng dần

Nếu order ID tăng liên tục:

Order mới nhất đều vào shard cuối.

Shard 1: gần như không có write mới
Shard 2: gần như không có write mới
Shard 3: nhận toàn bộ write mới

Dữ liệu phân bố không đều

Một khoảng có thể chứa tenant lớn hơn nhiều khoảng khác.

Rebalancing cần đổi boundary

Ví dụ:

Shard 1: A–M
Shard 2: N–Z

Shard 1 quá lớn, cần chia:

Shard 1: A–F
Shard 3: G–M
Shard 2: N–Z

Phải di chuyển dữ liệu G–M.

14. Range Sharding theo thời gian

Phù hợp với:

- Logs
- Events
- Time-series
- Transactions

Ví dụ:

2026-01 → Partition January
2026-02 → Partition February

Ưu điểm:

- Query theo khoảng thời gian tốt
- Archive partition cũ dễ
- Drop dữ liệu cũ nhanh

Nhược điểm:

Mọi write hiện tại vào partition mới nhất.

Có thể tạo hotspot.

15. Hash-based Sharding

Dùng hàm hash:

shard = hash(shard_key) mod number_of_shards

Ví dụ có bốn shard:

hash(user_123) mod 4 = 2

user_123 nằm ở Shard 2.

flowchart TD
    Key[user_id] --> Hash[Hash Function]
    Hash --> Mod[Modulo N]

    Mod --> S0[(Shard 0)]
    Mod --> S1[(Shard 1)]
    Mod --> S2[(Shard 2)]
    Mod --> S3[(Shard 3)]

16. Ưu điểm của Hash Sharding

- Phân phối dữ liệu tương đối đều
- Tránh hotspot do key tăng dần
- Routing nhanh
- Phù hợp lookup theo key

Nếu hash function tốt và key có cardinality cao, dữ liệu thường được trải tương đối đều.

17. Nhược điểm của Hash Sharding

Range query khó

User IDs gần nhau không nhất thiết cùng shard.

Query:

user_id từ 1.000 đến 2.000

có thể phải đọc nhiều shard.

Thay đổi số shard gây remap lớn

Ban đầu:

shard = hash(key) mod 4

Sau đó tăng lên tám shard:

shard = hash(key) mod 8

Rất nhiều key đổi shard.

Ví dụ:

hash(key) = 14

14 mod 4 = 2
14 mod 8 = 6

Record phải chuyển từ Shard 2 sang Shard 6.

18. Modulo Sharding và bài toán Resharding

Giả sử có 100 triệu user và bốn shard.

hash(user_id) mod 4

Khi thêm shard thứ năm:

hash(user_id) mod 5

Phần lớn user có mapping mới.

Điều này có thể yêu cầu di chuyển gần như toàn bộ dữ liệu.

Đó là lý do modulo đơn giản khó mở rộng động.

19. Consistent Hashing

Consistent hashing ánh xạ cả key và shard lên một vòng hash.

flowchart TD
    Ring((Hash Ring))

    S1[Shard A] --> Ring
    S2[Shard B] --> Ring
    S3[Shard C] --> Ring

Một key được đặt vào shard đầu tiên theo chiều kim đồng hồ sau vị trí hash của key.

Ý tưởng quan trọng:

Khi thêm hoặc xóa một shard, chỉ một phần key gần shard đó cần di chuyển.

Không phải toàn bộ key bị remap như modulo thông thường.

20. Ví dụ Consistent Hashing

Ban đầu:

A → B → C → A trên hash ring

Key giữa A và B thuộc B.

Khi thêm Shard D giữa A và B:

Chỉ các key trong khoảng A → D chuyển từ B sang D.

Các key thuộc C hoặc A không đổi.

flowchart LR
    A[Shard A] --> D[New Shard D]
    D --> B[Shard B]
    B --> C[Shard C]
    C --> A

21. Virtual Nodes

Nếu mỗi physical shard chỉ có một điểm trên vòng hash, phân bố có thể không đều.

Giải pháp: mỗi shard có nhiều virtual nodes.

Shard A:
A1, A2, A3, A4

Shard B:
B1, B2, B3, B4

flowchart TD
    Ring((Hash Ring))

    A1[A1] --> Ring
    A2[A2] --> Ring
    A3[A3] --> Ring

    B1[B1] --> Ring
    B2[B2] --> Ring
    B3[B3] --> Ring

Lợi ích:

- Phân phối đều hơn
- Rebalancing mượt hơn
- Server mạnh có thể sở hữu nhiều virtual nodes hơn

22. Consistent Hashing không tự động giải quyết Hot Key

Giả sử một key:

celebrity_123

nhận 1 triệu request/giây.

Dù consistent hashing phân bố hàng triệu key rất đều:

celebrity_123 vẫn chỉ nằm ở một shard.

Shard đó vẫn nóng.

Consistent hashing giải quyết:

Phân bố nhiều key

không tự động giải quyết:

Một key cực nóng.

23. Directory-based Sharding

Có một bảng hoặc service ánh xạ:

shard_key → shard

Ví dụ:

tenant_A → Shard 7
tenant_B → Shard 2
tenant_C → Shard 7

flowchart TD
    Request --> Directory[Shard Directory]

    Directory -->|tenant A| S7[(Shard 7)]
    Directory -->|tenant B| S2[(Shard 2)]

24. Ưu điểm của Directory Sharding

- Mapping linh hoạt
- Dễ di chuyển từng tenant
- Có thể đặt tenant lớn vào shard riêng
- Không phụ thuộc hash cố định

Ví dụ:

Tenant A trở nên rất lớn
→ chuyển Tenant A từ Shard 2 sang Shard 10

chỉ cần cập nhật directory sau migration.

25. Nhược điểm của Directory Sharding

Shard directory trở thành dependency quan trọng.

Nếu directory lỗi:

Application không biết dữ liệu nằm đâu.

Cần:

- High availability
- Cache mapping
- Versioning
- Consistent updates

Nếu cache directory cũ, request có thể đi nhầm shard.

26. Geographic Sharding

Chia dữ liệu theo khu vực.

EU users → EU shard
Asia users → Asia shard
US users → US shard

flowchart TD
    GlobalRouter[Global Router]

    GlobalRouter --> EU[(EU Shard)]
    GlobalRouter --> Asia[(Asia Shard)]
    GlobalRouter --> US[(US Shard)]

Lợi ích:

- Latency thấp hơn
- Data residency
- Giảm cross-region traffic

Nhược điểm:

- User di chuyển region
- Global query khó
- Cross-region transaction
- Region lớn nhỏ không đều

27. Composite Shard Key

Shard key có thể gồm nhiều field.

Ví dụ:

(tenant_id, user_id)
(region, customer_id)
(conversation_id, bucket_id)

Composite key giúp cân bằng giữa:

- Data locality
- Distribution
- Hotspot avoidance

28. Ví dụ Composite Key chống Hot Tenant

Nếu chỉ shard theo tenant_id:

Một enterprise tenant có 100 triệu user
→ toàn bộ tenant nằm một shard

Có thể dùng:

(tenant_id, bucket_id)

Trong đó:

bucket_id = hash(user_id) mod 16

Tenant lớn được trải qua 16 shard hoặc logical partitions.

Trade-off:

Query toàn tenant phải đọc 16 bucket.

29. Hot Partition là gì?

Hot partition là partition nhận tải vượt xa các partition khác.

Shard 1: 2.000 QPS
Shard 2: 2.100 QPS
Shard 3: 50.000 QPS
Shard 4: 1.900 QPS

Mặc dù tổng cluster còn capacity, Shard 3 vẫn quá tải.

flowchart TD
    Traffic --> S1[Shard 1: normal]
    Traffic --> S2[Shard 2: normal]
    Traffic --> S3[Shard 3: HOT]
    Traffic --> S4[Shard 4: normal]

30. Nguyên nhân Hot Partition

- Shard key có cardinality thấp
- Một tenant cực lớn
- Một celebrity hoặc product viral
- Range sharding với key tăng dần
- Temporal hotspot
- Hash function phân phối kém
- Query pattern tập trung vào một tập nhỏ dữ liệu

31. Data Skew và Traffic Skew

Hai vấn đề liên quan nhưng khác nhau.

Data skew

Một shard chứa nhiều dữ liệu hơn.

Shard A: 5 TB
Shard B: 5 TB
Shard C: 30 TB

Traffic skew

Dữ liệu có thể đều, nhưng traffic không đều.

Shard A: 10 TB, 2K QPS
Shard B: 10 TB, 100K QPS
Shard C: 10 TB, 3K QPS

Cả hai cần được theo dõi riêng.

32. Cách giảm Hot Partition

Thêm bucket vào key

partition_key = celebrity_id + random_bucket

Ví dụ:

celebrity_123:0
celebrity_123:1
...
celebrity_123:99

Write được phân tán.

Nhưng read phải tổng hợp nhiều bucket.

Cache dữ liệu nóng

Nếu workload read-heavy:

CDN
Local cache
Distributed cache

giúp giảm request đến shard.

Replicate hot data

Tạo nhiều read replica hoặc cache copy cho key nóng.

Tách tenant nóng

Directory-based sharding cho phép chuyển tenant lớn sang shard riêng.

Precompute hoặc aggregate

Không query lại dữ liệu nặng cho mỗi request.

Rate limiting

Một tenant hoặc key không được sử dụng toàn bộ capacity.

33. Celebrity Problem

Trong social network, người bình thường có ít follower.

Một celebrity có hàng trăm triệu follower.

Nếu fan-out on write:

Celebrity đăng bài
→ phải cập nhật hàng trăm triệu feed.

Nếu partition theo celebrity ID:

Một partition nhận workload cực lớn.

Thường cần chiến lược riêng:

Normal users:
Fan-out on write

Celebrities:
Fan-out on read hoặc hybrid

Đây là ví dụ một access pattern cần xử lý đặc biệt, không thể chỉ dựa vào hash trung bình.

34. Routing Request tới Shard

Có ba vị trí phổ biến cho shard routing.

Application-side routing

Application tính shard:

shard_id = hash(user_id) % shard_count

Ưu điểm:

- Không thêm network hop
- Logic nhanh

Nhược điểm:

- Mọi application phải biết topology
- Deploy khó khi mapping thay đổi
- Nhiều ngôn ngữ phải implement giống nhau

Proxy-based routing

flowchart LR
    Application --> Proxy[Shard Proxy]
    Proxy --> S1[(Shard 1)]
    Proxy --> S2[(Shard 2)]
    Proxy --> S3[(Shard 3)]

Ưu điểm:

- Application không cần biết topology
- Quản lý routing tập trung

Nhược điểm:

- Thêm network hop
- Proxy phải HA
- Có thể thành bottleneck

Coordinator trong database

Distributed database tự route request.

Client gửi key, database cluster quyết định node.

Đơn giản hơn cho application nhưng logic phức tạp nằm trong database engine.

35. Scatter–Gather Query

Nếu query không có shard key, phải gửi đến mọi shard.

Ví dụ:

Tìm 100 order mới nhất toàn hệ thống.

flowchart TD
    Query --> Coordinator

    Coordinator --> S1[(Shard 1)]
    Coordinator --> S2[(Shard 2)]
    Coordinator --> S3[(Shard 3)]

    S1 --> Merge[Merge + Sort]
    S2 --> Merge
    S3 --> Merge

Đây là scatter–gather.

36. Chi phí của Scatter–Gather

Latency thường bị quyết định bởi shard chậm nhất:

Shard 1: 20 ms
Shard 2: 25 ms
Shard 3: 500 ms

Tổng query phải chờ khoảng 500 ms hoặc hơn.

Ngoài ra:

- Tăng network calls
- Tăng CPU coordinator
- Phải merge/sort
- Một shard lỗi có thể làm query thất bại

Nếu có 1.000 shard:

Một query có thể tạo 1.000 subqueries.

37. Tránh Scatter–Gather

- Đưa shard key vào API/query
- Tạo global index riêng
- Dùng search engine
- Precompute aggregate
- Dùng data warehouse cho analytics
- Duy trì materialized view

Ví dụ:

GET /users/{userId}/orders

tốt hơn query toàn cục nếu hệ thống shard theo user.

38. Secondary Index trong hệ thống Sharded

Giả sử shard theo user_id, nhưng cần tìm user theo email.

Email không phải shard key.

Có hai cách lớn.

Local secondary index

Mỗi shard có index email riêng.

Để tìm email:

Phải query mọi shard.

Ưu điểm:

Index update nằm cùng shard.

Nhược điểm:

Global lookup cần scatter–gather.

Global secondary index

Có một hệ thống mapping:

email → user_id → shard

flowchart LR
    EmailQuery --> GlobalIndex[(Global Email Index)]
    GlobalIndex --> Router
    Router --> UserShard[(User Shard)]

Ưu điểm:

Lookup nhanh.

Nhược điểm:

- Global index cần HA
- Phải đồng bộ với shard
- Có consistency lag
- Unique constraint khó hơn

39. Global Uniqueness

Ví dụ email phải unique toàn hệ thống.

Nếu mỗi shard chỉ kiểm tra local:

Shard 1:
luna@example.com tồn tại

Shard 2:
cũng có thể tạo luna@example.com

Giải pháp:

- Global uniqueness service
- Dedicated global index
- Shard theo normalized email
- Reservation protocol
- Database hỗ trợ global constraint

Mỗi giải pháp có trade-off.

40. ID Generation trong hệ thống Sharded

Auto-increment ID trên từng shard có thể xung đột.

Shard 1 tạo order ID 100
Shard 2 cũng tạo order ID 100

Các lựa chọn:

- UUID
- Time-based distributed ID
- Snowflake-like ID
- Prefix shard ID
- Central ID service

41. ID chứa Shard Information

Ví dụ:

order_id = shard_id + local_sequence

Hoặc một số bit đại diện:

timestamp
machine/shard ID
sequence

Ưu điểm:

- Unique toàn hệ thống
- Có thể route từ ID

Nhược điểm:

- Lộ topology
- Khó thay đổi shard
- ID generation phức tạp

Không phải mọi ID đều nên encode vị trí vật lý vì record có thể được di chuyển khi resharding.

42. Cross-Shard JOIN

Giả sử:

Users shard theo user_id
Products shard theo product_id
Orders shard theo order_id

Query:

Lấy order, user và product details

có thể phải đọc ba shard hoặc ba cluster.

flowchart TD
    API --> OrderShard[(Order Shard)]
    API --> UserShard[(User Shard)]
    API --> ProductShard[(Product Shard)]

Database JOIN truyền thống không còn đơn giản.

43. Cách xử lý Cross-Shard JOIN

- Join ở application
- Denormalize dữ liệu
- Dùng data warehouse
- Dùng search/index projection
- Co-locate dữ liệu liên quan
- Precompute materialized view

Ví dụ order lưu snapshot:

{
  "orderId": "ord_123",
  "userId": "user_456",
  "customerName": "Luna",
  "items": [
    {
      "productId": "p_789",
      "productName": "Keyboard",
      "unitPrice": 2500000
    }
  ]
}

Không cần JOIN Product Service để hiển thị order lịch sử.

44. Co-location

Co-location là đặt dữ liệu thường được xử lý cùng nhau vào cùng shard.

Ví dụ:

Order
Order items
Payment attempt

có thể shard theo order_id.

Lợi ích:

- Local transaction
- Local JOIN
- Latency thấp

Đây là lý do shard key phải được chọn từ access pattern, không phải chọn ngẫu nhiên.

45. Cross-Shard Transaction

Transaction chạm nhiều shard.

Ví dụ chuyển tiền:

Account A nằm Shard 1
Account B nằm Shard 2

Cần:

1. Trừ tiền A
2. Cộng tiền B

Hoặc cả hai thành công, hoặc không bước nào thành công.

Đây là distributed transaction.

46. Vì sao Cross-Shard Transaction khó?

Trong một database node:

Database engine kiểm soát transaction.

Qua nhiều shard:

- Một shard có thể commit
- Shard khác có thể fail
- Network có thể timeout
- Coordinator có thể crash

Ví dụ:

Shard A đã trừ tiền
Shard B chưa cộng tiền

Hệ thống ở trạng thái không nhất quán.

47. Two-Phase Commit — 2PC

Một protocol kinh điển cho distributed transaction.

Phase 1 — Prepare

Coordinator hỏi các shard:

Bạn có thể commit không?

Các shard:

- Validate
- Lock resource
- Ghi prepare log
- Trả YES hoặc NO

Phase 2 — Commit/Abort

Nếu tất cả YES:

Coordinator gửi COMMIT.

Nếu một shard NO:

Coordinator gửi ABORT.

48. Sơ đồ 2PC

sequenceDiagram
    participant Coordinator
    participant ShardA
    participant ShardB

    Coordinator->>ShardA: PREPARE
    Coordinator->>ShardB: PREPARE

    ShardA-->>Coordinator: YES
    ShardB-->>Coordinator: YES

    Coordinator->>ShardA: COMMIT
    Coordinator->>ShardB: COMMIT

Nếu Shard B trả NO:

sequenceDiagram
    participant Coordinator
    participant ShardA
    participant ShardB

    Coordinator->>ShardA: PREPARE
    Coordinator->>ShardB: PREPARE

    ShardA-->>Coordinator: YES
    ShardB-->>Coordinator: NO

    Coordinator->>ShardA: ABORT
    Coordinator->>ShardB: ABORT

49. Nhược điểm của 2PC

- Latency cao
- Lock được giữ lâu
- Coordinator là thành phần quan trọng
- Participant có thể bị block nếu coordinator chết
- Khó vận hành xuyên region
- Throughput giảm

2PC cung cấp atomicity mạnh hơn nhưng trả giá bằng availability và performance.

50. Saga Pattern

Saga chia transaction lớn thành nhiều local transaction.

Mỗi bước có một hành động bù trừ nếu bước sau thất bại.

Ví dụ đặt chuyến du lịch:

1. Book flight
2. Book hotel
3. Charge payment

Nếu bước 3 thất bại:

- Cancel hotel
- Cancel flight

51. Saga cho Order

stateDiagram-v2
    [*] --> OrderCreated
    OrderCreated --> InventoryReserved
    InventoryReserved --> PaymentCompleted
    PaymentCompleted --> Confirmed

    InventoryReserved --> InventoryReleased: Payment failed
    OrderCreated --> Cancelled: Inventory failed

Các compensating actions:

Reserve inventory
↔ Release inventory

Charge payment
↔ Refund payment

Create shipment
↔ Cancel shipment

52. Saga không giống Rollback Database

Compensation là một operation nghiệp vụ mới.

Ví dụ refund payment:

- Có thể mất phí
- Có thể mất thời gian
- Có thể thất bại
- Có audit record riêng

Không phải hệ thống quay về trạng thái “chưa từng xảy ra gì”.

Saga cung cấp eventual consistency, không phải atomic rollback hoàn hảo.

53. Saga Orchestration và Choreography

Orchestration

Một orchestrator điều khiển workflow.

flowchart TD
    Orchestrator --> Inventory
    Orchestrator --> Payment
    Orchestrator --> Shipping

Ưu điểm:

- Workflow rõ ràng
- Dễ theo dõi state

Nhược điểm:

- Orchestrator phức tạp
- Có thể trở thành thành phần trung tâm lớn

Choreography

Các service phản ứng qua event.

flowchart LR
    OrderCreated --> Inventory
    Inventory --> InventoryReserved
    InventoryReserved --> Payment
    Payment --> PaymentSucceeded
    PaymentSucceeded --> Shipping

Ưu điểm:

- Decoupled
- Không có orchestrator trung tâm

Nhược điểm:

- Workflow khó nhìn
- Debug phức tạp
- Dependency ẩn

54. Tránh Cross-Shard Transaction bằng thiết kế dữ liệu

Cách tốt nhất thường là giảm số transaction cross-shard.

Ví dụ shard theo account có thể làm chuyển tiền luôn cross-shard.

Có thể:

- Dùng ledger trung tâm
- Shard theo nhóm account có tương tác nhiều
- Dùng clearing account
- Xử lý bằng event và reconciliation

Không phải lúc nào cũng tránh được, nhưng nên coi cross-shard transaction là chi phí kiến trúc rõ ràng.

55. Rebalancing là gì?

Rebalancing là di chuyển partition giữa các node để cân bằng:

- Dữ liệu
- Traffic
- CPU
- Disk
- Số leader

Ví dụ:

Trước:
Shard A = 5 TB
Shard B = 5 TB
Shard C = 20 TB

Sau:
A = 10 TB
B = 10 TB
C = 10 TB

56. Khi nào cần Rebalancing?

- Thêm node
- Xóa node
- Node lỗi
- Dữ liệu tăng không đều
- Traffic skew
- Một tenant tăng trưởng mạnh
- Thay đổi capacity server

57. Rebalancing có chi phí gì?

Di chuyển dữ liệu tạo:

- Network traffic
- Disk I/O
- CPU serialization
- Cache miss
- Replication traffic
- Latency tăng

Nếu rebalancing quá mạnh trong giờ cao điểm:

Có thể làm production chậm hoặc mất ổn định.

Cần throttling và headroom.

58. Online Rebalancing

Mục tiêu:

Di chuyển dữ liệu mà hệ thống vẫn phục vụ request.

Quy trình khái niệm:

1. Copy dữ liệu từ source sang target
2. Theo dõi các write mới
3. Đồng bộ phần thay đổi
4. Chuyển routing
5. Xác minh
6. Xóa bản cũ

59. Resharding là gì?

Resharding là thay đổi cách dữ liệu được chia shard.

Ví dụ:

4 shards → 8 shards

Hoặc chia một shard nóng:

Shard A
→ Shard A1 + Shard A2

Hoặc hợp nhất shard nhỏ:

Shard B + Shard C
→ Shard BC

60. Split một Shard

Ban đầu:

Shard A:
user IDs A–M

Chia:

Shard A1:
A–F

Shard A2:
G–M

flowchart LR
    Old[(Shard A: A–M)] --> New1[(Shard A1: A–F)]
    Old --> New2[(Shard A2: G–M)]

Cần di chuyển dữ liệu G–M hoặc cả hai range tùy triển khai.

61. Online Resharding với Dual Write

Một chiến lược:

1. Bắt đầu copy dữ liệu sang shard mới
2. Write mới ghi cả old và new
3. Read vẫn từ old
4. Catch up
5. Chuyển read sang new
6. Ngừng write old
7. Xóa old sau khi xác minh

sequenceDiagram
    participant App
    participant Old
    participant New

    Note over App,New: Migration phase
    App->>Old: Write
    App->>New: Dual write

    App->>Old: Read

    Note over App,New: Cutover
    App->>New: Read and write

62. Vấn đề của Dual Write

Write old thành công
Write new thất bại

Hai bên lệch dữ liệu.

Cần:

- Retry
- Idempotency
- Change log
- CDC
- Reconciliation

Dual write trực tiếp thường không atomic.

63. Online Resharding bằng Change Log

Một chiến lược an toàn hơn:

1. Copy snapshot
2. Ghi mọi thay đổi vào log
3. Replay log sang shard mới
4. Khi lag gần 0, cutover

flowchart LR
    Old[(Old Shard)] --> Snapshot[Snapshot Copy]
    Old --> ChangeLog[Change Log / CDC]

    Snapshot --> New[(New Shard)]
    ChangeLog --> New

Giống mô hình database migration hoặc replication.

64. Read During Migration

Trong migration, routing có thể ở các trạng thái:

- Read old
- Read new
- Read old rồi fallback new
- Read new rồi fallback old
- Compare cả hai

Có thể dùng shadow reads:

Response trả từ old
nhưng âm thầm query new để so sánh.

Không ảnh hưởng user nhưng giúp kiểm tra dữ liệu.

65. Cutover

Khi shard mới đã catch up:

1. Tạm dừng hoặc giới hạn write rất ngắn
2. Đồng bộ delta cuối
3. Cập nhật routing version
4. Chuyển traffic
5. Theo dõi error

Cần rollback plan nếu shard mới có lỗi.

66. Routing Version

Shard mapping nên có version:

Mapping version 17:
tenant A → Shard 2

Mapping version 18:
tenant A → Shard 7

Application hoặc proxy dùng version hiện tại.

Nếu request dùng mapping cũ, shard cũ có thể trả redirect hoặc lookup lại.

67. Rebalancing và Consistent Hashing

Consistent hashing giúp giảm số key phải di chuyển khi thêm node.

Nhưng không loại bỏ hoàn toàn migration.

Vẫn cần:

- Copy dữ liệu
- Update ownership
- Handle writes trong quá trình chuyển
- Verify consistency

Consistent hashing giải quyết việc chọn key nào di chuyển, không tự thực hiện toàn bộ quy trình an toàn.

68. Virtual Shards / Logical Partitions

Một chiến lược tốt là tạo nhiều logical partitions hơn physical nodes.

Ví dụ:

1.024 logical partitions
20 physical database nodes

Mapping:

Logical partition 0–49 → Node A
50–101 → Node B
...

Khi thêm node:

Chuyển một số logical partition sang node mới.

Không cần thay đổi hash function.

69. Lợi ích Virtual Shards

- Rebalancing nhỏ hơn
- Dễ phân phối capacity
- Tách logical partition khỏi physical server
- Server mạnh có thể nhận nhiều partition hơn

Đây là ý tưởng gần virtual nodes trong consistent hashing.

70. Shard Replication

Mỗi shard thường cũng có replica.

flowchart TD
    Router --> S1L[(Shard 1 Leader)]
    Router --> S2L[(Shard 2 Leader)]

    S1L --> S1R1[(Shard 1 Replica)]
    S1L --> S1R2[(Shard 1 Replica)]

    S2L --> S2R1[(Shard 2 Replica)]
    S2L --> S2R2[(Shard 2 Replica)]

Sharding giải quyết:

Capacity

Replication giải quyết:

Availability và read scaling

Một hệ thống production thường dùng cả hai.

71. Shard Failure

Nếu một shard leader lỗi:

Chỉ partition thuộc shard đó bị ảnh hưởng.

Replica được promote.

Nhưng router phải biết leader mới.

Cần theo dõi:

- Shard availability
- Replica lag
- Leader election
- Routing updates

72. Correlated Failure

Không nên đặt leader và replicas của cùng shard trên cùng máy hoặc zone.

Shard 1 leader → Zone A
Shard 1 replica 1 → Zone B
Shard 1 replica 2 → Zone C

Nếu tất cả cùng Zone A:

Zone A lỗi
→ mất toàn bộ Shard 1.

73. Noisy Neighbor

Nhiều tenant dùng chung shard.

Một tenant chạy query nặng:

- CPU shard tăng
- Connection pool đầy
- User khác trên shard bị ảnh hưởng

Đây là noisy-neighbor problem.

Giải pháp:

- Per-tenant rate limit
- Query quotas
- Resource groups
- Move tenant lớn
- Tenant isolation

74. Dedicated Shard cho Tenant lớn

Mô hình hybrid:

Tenant nhỏ:
Dùng shared shards

Tenant lớn:
Dedicated shard

flowchart TD
    Router --> Shared[(Shared Shards)]
    Router --> EnterpriseA[(Dedicated Tenant A)]
    Router --> EnterpriseB[(Dedicated Tenant B)]

Directory-based routing phù hợp mô hình này.

75. Multi-Tenant Shard Key

Nếu dùng SaaS multi-tenant:

tenant_id

là shard key tự nhiên vì:

- Query thường scope theo tenant
- Dễ cô lập dữ liệu
- Dễ backup/migrate tenant

Nhưng tenant size không đều.

Có thể dùng tiering:

Small tenant → shared shard
Large tenant → bucketed hoặc dedicated shard

76. Pagination qua nhiều Shard

Query:

Lấy 20 order mới nhất toàn hệ thống.

Mỗi shard trả 20 record mới nhất.

Coordinator merge và lấy top 20 tổng thể.

flowchart TD
    Query --> S1[(Shard 1: top 20)]
    Query --> S2[(Shard 2: top 20)]
    Query --> S3[(Shard 3: top 20)]

    S1 --> Merge[Merge top K]
    S2 --> Merge
    S3 --> Merge

Cursor cần chứa trạng thái từng shard hoặc một global ordering mechanism.

Rất phức tạp so với pagination trong một database.

77. Global Aggregate

Query:

Tổng doanh thu hôm nay.

Có thể scatter query:

SUM trên từng shard rồi cộng lại.

Nhưng với dashboard thường xuyên, nên:

- Stream events vào analytics store
- Duy trì aggregate table
- Dùng data warehouse

Không nên chạy heavy global query trực tiếp trên production shards liên tục.

78. Search trong hệ thống Sharded

Full-text search qua nhiều database shard khó.

Thường dùng:

Primary shards = source of truth
Search engine = global searchable projection

flowchart LR
    Shards[(Database Shards)] --> CDC[CDC / Events]
    CDC --> Search[(Search Index)]
    Client --> Search

Search index có thể eventual consistent.

79. Cache và Sharding

Cache key thường không cần biết shard nếu cache lookup theo entity ID:

user:user_123

Nhưng cache miss cần router tìm shard.

Có thể cache shard mapping:

user_123 → Shard 7

Cần invalidation khi resharding.

80. Backup và Restore trong hệ thống Sharded

Mỗi shard có backup riêng.

Khó khăn:

- Snapshot phải nhất quán giữa các shard
- Restore nhiều shard cùng thời điểm
- Global transaction có thể bị lệch
- Mapping directory cũng cần backup

Nếu cần point-in-time recovery toàn hệ thống:

Tất cả shard phải phục hồi về một logical time phù hợp.

81. Schema Migration qua nhiều Shard

Thay đổi schema phải áp dụng cho hàng chục hoặc hàng trăm shard.

Không nên chạy đồng thời toàn bộ:

- Tạo load spike
- Lock đồng loạt
- Tăng blast radius

Nên:

1. Canary một shard
2. Theo dõi
3. Rollout theo batch
4. Hỗ trợ schema cũ và mới trong app
5. Có rollback

82. Operational Complexity

Sharding làm tăng số đối tượng vận hành:

- Nhiều database
- Nhiều replica
- Nhiều backup
- Nhiều connection pools
- Nhiều failover
- Nhiều schema migration
- Nhiều dashboard

Nếu có 100 shard, mỗi shard 3 replica:

300 database nodes hoặc instances logic.

Automation trở thành bắt buộc.

83. Observability cho Sharding

Metrics theo từng shard:

- Storage usage
- Row count
- Read QPS
- Write QPS
- CPU
- Memory
- Disk latency
- Connection saturation
- Replication lag
- Error rate
- Hot keys

Cluster-level average không đủ.

Ví dụ:

Average CPU = 35%

Shard 17 CPU = 98%

Average che giấu hotspot.

84. Metrics về phân bố

Cần đo:

- Largest shard size / average shard size
- Highest QPS shard / average QPS
- Top tenants theo load
- Partition growth rate
- Rebalancing lag
- Data movement throughput

Ví dụ:

Skew ratio = max shard QPS / average shard QPS

Nếu ratio quá cao, shard key hoặc workload có vấn đề.

85. Alert quan trọng

- Replication lag

Tất cả seat của một show nằm cùng shard.

Ưu điểm:

- Reservation trong một show là local transaction
- Unique seat constraint local

Rủi ro:

Show cực hot làm một shard quá tải.

Nếu chia một show qua nhiều shard theo seat section:

(show_id, section_id)

thì tăng parallelism, nhưng booking nhiều ghế ở nhiều section có thể thành cross-shard transaction.

Đây là trade-off điển hình:

Local consistency
↕
Hotspot avoidance

91. Shard theo Show hay Seat?

Theo show_id

Ưu:
- Toàn bộ ghế cùng show ở một shard
- Transaction đơn giản
- Tránh bán trùng dễ hơn

Nhược:
- Concert lớn tạo hotspot

Theo hash(seat_id)

Ưu:
- Traffic phân tán

Nhược:
- Booking nhiều ghế chạm nhiều shard
- Cross-shard transaction

Có thể dùng hierarchical design:

Mỗi show được cấp một nhóm partitions,
không nhất thiết chỉ một shard.

92. Case Study — Social Feed

Nếu shard posts theo author_id:

Dễ lấy bài của một author.

Nhưng xây feed user cần đọc nhiều author shards.

Nếu shard feed theo user_id:

Dễ đọc feed cá nhân.

Nhưng fan-out on write có thể lớn.

Thường dùng nhiều storage model:

Post store:
Shard theo author

Feed inbox:
Shard theo viewer/user

Đây là denormalization để phục vụ hai access pattern.

96. Cách trình bày trong System Design Interview

Không nên chỉ nói:

Em shard database theo user ID.

Nên nói:

Phần lớn access pattern được scope theo user, chẳng hạn lấy project, task và notification của một user, nên tôi chọn user_id làm shard key để các transaction chính nằm trong một shard. Tôi dùng hash hoặc virtual partitions để phân phối user tương đối đều. Global analytics và search không chạy scatter–gather trên production shards mà được xây từ event stream vào search engine hoặc data warehouse. Với enterprise tenant lớn, directory mapping cho phép tách tenant sang shard riêng. Tôi theo dõi cả data skew và traffic skew, vì consistent hashing không ngăn một tenant hoặc key đơn lẻ trở thành hotspot.

Nếu nói về migration:

Khi cần resharding, tôi copy snapshot sang shard mới, dùng CDC để đồng bộ write phát sinh, shadow-read để kiểm tra, rồi cutover bằng một routing version mới. Shard cũ chỉ bị xóa sau khi dữ liệu và traffic đã được xác minh.

Nếu nói về transaction:

Tôi cố co-locate dữ liệu cần transaction bằng shard key phù hợp. Những workflow bắt buộc chạm nhiều shard dùng Saga hoặc distributed transaction tùy yêu cầu consistency; 2PC chỉ dùng khi atomicity mạnh đáng để đánh đổi latency và availability.

97. Những sai lầm phổ biến

Lỗi 1: Sharding quá sớm

Tạo complexity trước khi có bottleneck thật.

Lỗi 2: Chọn shard key chỉ dựa trên dữ liệu

Không xét access pattern và transaction.

Lỗi 3: Chỉ kiểm tra data distribution

Dữ liệu đều nhưng traffic vẫn có thể lệch.

Lỗi 4: Shard key có cardinality thấp

Ví dụ country hoặc status.

Lỗi 5: Range shard theo ID tăng dần

Mọi write mới vào shard cuối.

Lỗi 6: Dùng modulo nhưng không có kế hoạch resharding

Thêm shard làm phần lớn key đổi vị trí.

Lỗi 7: Nghĩ consistent hashing giải quyết hot key

Một key cực nóng vẫn nằm một nơi.

Lỗi 8: Không đưa shard key vào query/API

Dẫn đến scatter–gather thường xuyên.

Lỗi 9: Dựa vào cross-shard JOIN như database đơn node

Latency và complexity tăng mạnh.

Lỗi 10: Global unique constraint không được thiết kế

Tạo duplicate email, username hoặc ID.

Lỗi 11: Cross-shard transaction tràn lan

Làm mất lợi ích của sharding.

Lỗi 12: Dual write khi resharding nhưng không có reconciliation

Old và new shard bị lệch.

Lỗi 13: Rebalance toàn tốc độ trong giờ cao điểm

Data movement làm production quá tải.

Lỗi 14: Directory mapping là SPOF

Router không biết request đi đâu khi directory lỗi.

Lỗi 15: Chỉ monitor cluster average

Không thấy một shard đang ở 100% CPU.

100. Những điều phải nhớ sau Bài 13

1. Partitioning chia dữ liệu; sharding phân phối các partition qua nhiều node.
2. Sharding chủ yếu giải quyết storage và write capacity.
3. Không nên shard trước khi tối ưu query, index, cache và replicas.
4. Shard key quyết định phần lớn độ khó của hệ thống.
5. Shard key tốt có cardinality cao, phân bố đều và xuất hiện trong query chính.
6. Range sharding hỗ trợ range query nhưng dễ hot range.
7. Hash sharding phân phối đều hơn nhưng range query khó.
8. Modulo sharding làm resharding khó khi số shard thay đổi.
9. Consistent hashing giảm số key phải remap.
10. Virtual nodes giúp phân phối và rebalance đều hơn.
11. Consistent hashing không ngăn hot key.
12. Directory sharding linh hoạt nhưng directory phải có HA.
13. Geographic sharding hỗ trợ latency và data residency.
14. Hot partition có thể do data skew hoặc traffic skew.
15. Cache, bucket và dedicated shard có thể giảm hotspot.
16. Query không có shard key thường tạo scatter–gather.
17. Scatter–gather có latency phụ thuộc shard chậm nhất.
18. Global secondary index giúp lookup xuyên shard nhưng tạo consistency complexity.
19. Global uniqueness không thể chỉ kiểm tra từng shard độc lập.
20. Dữ liệu cần transaction nên được co-locate trong cùng shard.
21. Cross-shard JOIN nên được giảm bằng denormalization hoặc projection.
22. Cross-shard transaction có thể dùng 2PC hoặc Saga.
23. 2PC mạnh về atomicity nhưng làm tăng latency và blocking.
24. Saga dùng compensation và chấp nhận eventual consistency.
25. Rebalancing di chuyển dữ liệu để cân bằng cluster.
26. Resharding thay đổi cách dữ liệu được chia.
27. Online resharding thường cần snapshot, change log/CDC và cutover.
28. Dual write không tự atomic và cần reconciliation.
29. Sharding thường đi cùng replication cho HA.
30. Phải monitor từng shard, không chỉ cluster average.
