Bài 10 — Reliability Patterns

Một hệ thống đáng tin cậy không phải là hệ thống “không bao giờ lỗi”.

Trong production, những việc sau chắc chắn sẽ xảy ra:

- Network chậm hoặc mất kết nối
- Service bị crash
- Database quá tải
- Cache bị mất
- Third-party API timeout
- Một availability zone gặp sự cố
- Deploy phiên bản có bug
- Traffic tăng đột ngột
- Message bị xử lý trùng

Mục tiêu của Reliability Engineering là:

Khi lỗi xảy ra, lỗi phải được giới hạn, hệ thống phục hồi được, và chức năng cốt lõi tiếp tục hoạt động ở mức chấp nhận được.

Video System Design bạn cung cấp mô tả resilience là việc “dự kiến điều bất ngờ”, dùng redundancy và thiết kế graceful degradation để dù một số tính năng không khả dụng, chức năng cốt lõi vẫn còn hoạt động.

Các pattern trọng tâm của bài:

- Timeout
- Retry
- Exponential backoff
- Jitter
- Retry budget
- Circuit breaker
- Bulkhead
- Graceful degradation
- Fault isolation
- Load shedding
- Redundancy và failover

1. Reliability, Availability và Resilience khác nhau thế nào?

Reliability

Hệ thống có thực hiện đúng chức năng một cách ổn định không?

Ví dụ:

- Không mất order
- Không charge payment hai lần
- Không trả nhầm dữ liệu user
- Không bỏ sót message quan trọng

Availability

Hệ thống có sẵn sàng phục vụ request không?

Ví dụ:

User gọi API
→ API có trả response hay không?

Một hệ thống có thể available nhưng không reliable:

API luôn trả 200,
nhưng dữ liệu trả sai.

Resilience

Khả năng hệ thống chống chịu và phục hồi sau lỗi.

Ví dụ:

Recommendation Service lỗi
→ trang sản phẩm vẫn hiển thị
→ chỉ mất phần gợi ý sản phẩm

Đây là resilience thông qua graceful degradation.

Fault tolerance

Khả năng hệ thống tiếp tục vận hành khi một thành phần bị lỗi.

Ví dụ:

Một app server chết
→ load balancer chuyển traffic sang server khác.

2. Failure propagation — lỗi lan truyền

Giả sử một request đi qua nhiều service:

flowchart LR
    User --> Gateway
    Gateway --> Order
    Order --> Inventory
    Order --> Payment
    Payment --> Fraud
    Fraud --> External[External Risk API]

Nếu External Risk API chậm:

External API chậm
→ Fraud Service chờ
→ Payment Service chờ
→ Order Service chờ
→ API Gateway chờ
→ User timeout

Nhưng hậu quả không chỉ là một request chậm.

Mỗi service có thể giữ:

- Thread
- Connection
- Memory
- DB connection
- Queue slot

Khi hàng nghìn request cùng chờ:

flowchart TD
    A[External dependency chậm] --> B[Request giữ connection lâu]
    B --> C[Thread pool đầy]
    C --> D[Request mới phải xếp hàng]
    D --> E[Latency tăng]
    E --> F[Client retry]
    F --> G[Traffic tăng thêm]
    G --> C

Đây là cách một dependency nhỏ kéo sập cả hệ thống.

3. Single Point of Failure

Single Point of Failure — SPOF là một thành phần mà khi nó lỗi, toàn bộ hệ thống hoặc một phần rất lớn của hệ thống ngừng hoạt động.

Ví dụ:

flowchart LR
    Users --> LB[Single Load Balancer]
    LB --> A1[App 1]
    LB --> A2[App 2]
    A1 --> DB[(Single Database)]
    A2 --> DB

Dù có hai application server:

Load balancer chết
→ Không user nào vào được.

Database chết
→ Tất cả application server mất chức năng.

Tài liệu/video của bạn nhấn mạnh rằng một single point of failure có thể kéo toàn hệ thống xuống; các biện pháp giảm rủi ro gồm redundancy, health checks, failover và self-healing.

Giải pháp không chỉ là “thêm một bản sao”.

Bạn còn phải trả lời:

- Làm sao phát hiện node lỗi?
- Ai chuyển traffic?
- Failover mất bao lâu?
- Bản sao có dữ liệu mới nhất không?
- Failover đã được test chưa?

4. Timeout — giới hạn thời gian chờ

Timeout là giới hạn thời gian một operation được phép chờ.

Ví dụ:

Order Service gọi Payment Service.
Nếu quá 2 giây chưa có kết quả,
Order Service ngừng chờ.

Không có timeout:

sequenceDiagram
    participant Order
    participant Payment

    Order->>Payment: Process payment
    Note over Payment: Service treo
    Note over Order: Chờ vô hạn

Có timeout:

sequenceDiagram
    participant Order
    participant Payment

    Order->>Payment: Process payment
    Note over Order: Timeout = 2s
    Note over Payment: Không phản hồi
    Order-->>Order: Stop waiting after 2s

Timeout giúp giải phóng:

- Thread
- Connection
- Memory
- Request slot
- User waiting time

5. Các loại timeout

5.1 Connection timeout

Thời gian tối đa để thiết lập connection.

Ví dụ:

Không thể kết nối Payment Service trong 200 ms
→ connection timeout.

Connection timeout thường ngắn hơn request timeout.

5.2 Read timeout

Sau khi kết nối thành công, chờ dữ liệu tối đa bao lâu.

Đã connect được,
nhưng server không trả response.

5.3 Write timeout

Thời gian tối đa để gửi request body hoặc ghi dữ liệu.

Quan trọng với:

- Upload file
- Request body lớn
- Network chậm

5.4 Request timeout

Thời gian tối đa cho toàn bộ một remote call.

Connect
+ send request
+ server processing
+ receive response

5.5 Idle timeout

Connection được giữ nhưng không có dữ liệu truyền trong một khoảng thời gian.

Phù hợp với:

- HTTP keep-alive
- WebSocket
- Streaming
- Proxy

5.6 End-to-end deadline

Thời gian tối đa cho toàn bộ request từ user.

Ví dụ:

User request budget = 2 giây

Request đi qua:

Gateway → Order → Payment → Fraud

Mỗi service không được tự cho mình 2 giây.

Nếu mỗi tầng chờ 2 giây:

Gateway: 2s
Order:   2s
Payment: 2s
Fraud:   2s

Tổng có thể vượt xa trải nghiệm mong muốn.

6. Timeout budget

Giả sử end-to-end deadline là 2 giây.

Ta có thể phân bổ:

API Gateway overhead:       100 ms
Order Service processing:   200 ms
Inventory call:             300 ms
Payment call:               800 ms
Serialization/network:      200 ms
Safety margin:              400 ms
---------------------------------
Tổng:                     2.000 ms

Không nhất thiết mọi call chạy tuần tự. Nhưng mỗi dependency phải biết budget còn lại.

7. Deadline propagation

Gateway nhận deadline:

Deadline còn lại: 2.000 ms

Sau khi xử lý 300 ms, gọi Order Service:

Deadline còn lại: 1.700 ms

Order xử lý 200 ms rồi gọi Payment:

Deadline còn lại: 1.500 ms

sequenceDiagram
    participant Client
    participant Gateway
    participant Order
    participant Payment

    Client->>Gateway: Request, deadline=2s
    Gateway->>Order: Remaining deadline=1.7s
    Order->>Payment: Remaining deadline=1.5s
    Payment-->>Order: Result
    Order-->>Gateway: Result
    Gateway-->>Client: Response

Lợi ích:

- Downstream không xử lý một request mà upstream đã bỏ cuộc
- Giảm công việc vô ích
- Giữ đúng end-to-end latency budget

8. Cancellation propagation

Timeout ở upstream nên được truyền xuống downstream.

Nếu user đã đóng request:

Gateway không còn cần Order response.
Order không còn cần Payment response.
Payment không nên tiếp tục giữ tài nguyên.

Nếu không cancel:

Client đã đi
nhưng toàn bộ backend vẫn xử lý công việc vô ích.

Tuy nhiên cancellation không phải lúc nào cũng được phép.

Ví dụ:

Payment đã được gửi sang payment provider.
Client timeout không có nghĩa được phép hủy transaction.

Với operation có side effect, cần kiểm tra trạng thái thay vì giả định timeout đồng nghĩa thất bại.

9. Timeout không có nghĩa operation thất bại

Đây là điểm cực kỳ quan trọng.

Luồng:

sequenceDiagram
    participant Client
    participant PaymentAPI
    participant Provider

    Client->>PaymentAPI: Charge
    PaymentAPI->>Provider: Charge
    Provider-->>PaymentAPI: Success
    Note over PaymentAPI,Client: Response bị mất
    Client-->>Client: Timeout

Client thấy timeout, nhưng payment có thể đã thành công.

Do đó trạng thái là:

Unknown

Không phải chắc chắn:

Failed

Giải pháp:

- Idempotency key
- Query payment status
- Reconciliation job
- Webhook
- Transaction ID ổn định

10. Chọn timeout thế nào?

Timeout quá dài:

- Giữ tài nguyên lâu
- Failure lan rộng
- User chờ lâu
- Queue tích tụ

Timeout quá ngắn:

- Request bình thường bị cắt
- Retry không cần thiết
- Tăng error rate
- Lãng phí công việc đã bắt đầu

Cần dựa vào latency distribution:

p50
p95
p99
p99.9

Ví dụ dependency:

p50 = 50 ms
p95 = 120 ms
p99 = 300 ms

Timeout 100 ms sẽ cắt quá nhiều request hợp lệ.

Timeout 10 giây có thể quá rộng.

Có thể bắt đầu khoảng:

Timeout > p99 bình thường
nhưng nhỏ hơn end-to-end deadline.

Con số thực tế phải được đo và điều chỉnh.

11. Retry — thử lại sau lỗi

Retry phù hợp khi lỗi có khả năng tạm thời.

Ví dụ:

- Network interruption
- Connection reset
- 502 Bad Gateway
- 503 Service Unavailable
- 504 Gateway Timeout
- Rate limiting tạm thời
- Optimistic concurrency conflict

Retry không phù hợp với lỗi vĩnh viễn:

- 400 Invalid Request
- 401 Unauthorized
- 403 Forbidden
- Validation failure
- Unsupported operation
- Resource chắc chắn không tồn tại

12. Retry chỉ an toàn với operation idempotent

Các operation thường retry an toàn:

GET /products/p_123
PUT /users/123/preferences
DELETE /notes/note_123

Operation nguy hiểm:

POST /payments
POST /orders
POST /money-transfers

Nếu retry mà không có idempotency:

- Tạo hai order
- Charge hai lần
- Chuyển tiền hai lần

Giải pháp:

Idempotency-Key: <unique-logical-operation-id>

13. Immediate retry

Retry ngay lập tức chỉ hữu ích trong một số lỗi rất ngắn:

- Connection bị reset do một backend vừa shutdown
- Retry sang replica/backend khác

Nhưng nếu dependency thật sự đang quá tải:

Request 1 thất bại
→ Retry ngay
→ Dependency nhận thêm tải
→ Thất bại nhiều hơn

Immediate retry có thể biến lỗi nhỏ thành outage.

14. Exponential Backoff

Thời gian chờ tăng dần theo mỗi lần retry.

Công thức khái niệm:

delay = base × 2^attempt

Ví dụ:

Lần đầu:  100 ms
Retry 1:  200 ms
Retry 2:  400 ms
Retry 3:  800 ms
Retry 4: 1.600 ms

Thường đặt giới hạn:

maxDelay = 5 giây
maxAttempts = 3

Pseudo-code:

import time


def call_with_backoff(operation, max_attempts: int = 3):
    base_delay = 0.2
    max_delay = 2.0

    for attempt in range(max_attempts):
        try:
            return operation()
        except TemporaryError:
            if attempt == max_attempts - 1:
                raise

            delay = min(base_delay * (2**attempt), max_delay)
            time.sleep(delay)

15. Jitter

Nếu 10.000 client cùng retry sau đúng 1 giây:

Tất cả lại gọi cùng lúc
→ dependency tiếp tục quá tải.

Jitter thêm ngẫu nhiên vào thời gian retry.

Retry 1:
200–400 ms

Retry 2:
400–800 ms

Retry 3:
800–1.600 ms

Các request được trải đều hơn.

16. Các kiểu jitter

Full jitter

delay = random(0, exponentialDelay)

Ví dụ exponential delay là 800 ms:

Chờ ngẫu nhiên 0–800 ms.

Equal jitter

delay = exponentialDelay / 2
      + random(0, exponentialDelay / 2)

Đảm bảo có thời gian chờ tối thiểu.

Decorrelated jitter

Delay mới dựa trên delay trước nhưng vẫn ngẫu nhiên.

Mục tiêu chung:

Không cho toàn bộ client đồng bộ retry cùng lúc.

Trong hầu hết bài System Design, chỉ cần nêu:

Retry dùng exponential backoff kèm jitter.

17. Retry amplification

Giả sử một request đi qua ba tầng:

Gateway → Order → Payment → Fraud

Mỗi tầng retry tối đa ba lần.

Trong trường hợp xấu:

Gateway gọi Order: 3 lần
Mỗi Order gọi Payment: 3 lần
Mỗi Payment gọi Fraud: 3 lần

Fraud Service có thể nhận:

3 × 3 × 3 = 27 calls

chỉ từ một request ban đầu.

flowchart TD
    Client[1 request] --> G[Gateway: 3 attempts]
    G --> O[Order: 3 attempts each]
    O --> P[Payment: 3 attempts each]
    P --> F[Fraud: up to 27 calls]

Nếu 10.000 user cùng gặp lỗi:

10.000 × 27 = 270.000 downstream calls

Đây là retry storm.

18. Retry ở một tầng phù hợp

Một nguyên tắc hữu ích:

Đừng retry ở mọi tầng.

Ví dụ:

- SDK hoặc client service chịu trách nhiệm retry
- Các tầng còn lại trả lỗi rõ ràng

Hoặc retry ở tầng biết đủ context:

Gateway không biết payment có idempotent không.
Payment Service biết rõ hơn.

Cần xác định ownership cho retry.

19. Retry budget

Retry budget giới hạn lượng retry so với request thật.

Ví dụ:

Tối đa 10% tổng traffic là retry.

Nếu có:

100.000 request/phút

cho phép khoảng:

10.000 retry/phút

Khi vượt budget:

- Ngừng retry
- Fail fast
- Dùng fallback
- Mở circuit breaker

Retry budget ngăn retry trở thành nguồn traffic lớn hơn traffic gốc.

20. Retry-After

Khi server quá tải hoặc rate limit, server có thể trả:

429 Too Many Requests
Retry-After: 30

Hoặc:

503 Service Unavailable
Retry-After: 5

Client nên tôn trọng hướng dẫn này nếu phù hợp.

Không nên tất cả client retry đúng giây thứ 30; vẫn nên thêm jitter.

21. Circuit Breaker

Circuit breaker ngăn một service tiếp tục gọi dependency đang lỗi hoặc rất chậm.

Ý tưởng giống cầu dao điện:

Dependency khỏe:
Cho request đi qua.

Dependency lỗi liên tục:
Ngắt mạch, fail fast.

Sau một thời gian:
Cho một số request thử nghiệm.

Ba trạng thái chính:

Closed
Open
Half-open

22. Closed State

Circuit bình thường.

Request → Dependency

Circuit breaker theo dõi:

- Failure rate
- Timeout rate
- Slow-call rate

stateDiagram-v2
    [*] --> Closed
    Closed --> Open: Failure threshold exceeded

23. Open State

Khi lỗi vượt threshold:

Circuit mở.

Request mới không gọi dependency nữa.

Request → Fail fast hoặc fallback

sequenceDiagram
    participant App
    participant Breaker
    participant Dependency

    App->>Breaker: Call
    Note over Breaker: State = OPEN
    Breaker-->>App: Fail fast
    Note over Dependency: Không nhận thêm request

Lợi ích:

- Dependency có thời gian phục hồi
- Không giữ thread chờ timeout
- Giảm retry storm
- Giảm failure propagation

24. Half-open State

Sau một khoảng cooldown:

Circuit chuyển sang half-open.

Cho phép một số request thử nghiệm.

stateDiagram-v2
    Open --> HalfOpen: Cooldown elapsed
    HalfOpen --> Closed: Probe requests succeed
    HalfOpen --> Open: Probe requests fail

Nếu thử nghiệm thành công:

Half-open → Closed

Nếu tiếp tục lỗi:

Half-open → Open

25. Circuit Breaker State Machine

stateDiagram-v2
    [*] --> Closed

    Closed --> Open: Error/timeout rate vượt threshold
    Open --> HalfOpen: Sau cooldown
    HalfOpen --> Closed: Probe thành công
    HalfOpen --> Open: Probe thất bại

26. Circuit Breaker nên đo gì?

Không nên chỉ đếm tổng số lỗi.

Ví dụ:

2 lỗi trong 3 request

khác với:

2 lỗi trong 1 triệu request.

Cấu hình có thể gồm:

Minimum request volume:
Ít nhất 100 request mới đánh giá.

Failure rate threshold:
50% lỗi.

Slow call threshold:
Call trên 1 giây được xem là slow.

Open duration:
Mở circuit 30 giây.

Half-open probes:
Cho 10 request thử.

27. Circuit Breaker theo dependency và operation

Không nên có một circuit chung cho toàn bộ Payment Service nếu các operation rất khác nhau.

Ví dụ:

GET /payment-methods
POST /payments
POST /refunds

Refund lỗi không nhất thiết phải chặn đọc payment methods.

Circuit có thể scope theo:

- Dependency
- Endpoint
- Tenant
- Region
- Operation type

Nhưng circuit quá chi tiết cũng làm vận hành khó hơn.

28. Circuit Breaker không thay thế timeout

Nếu không có timeout:

Circuit breaker phải chờ call treo vô hạn
→ không có kết quả lỗi để đo.

Thứ tự logic:

Timeout giới hạn một call.
Circuit breaker giới hạn nhiều call liên tiếp.

Cả hai thường được dùng cùng nhau.

29. Circuit Breaker không thay thế retry

Circuit breaker và retry giải quyết hai vấn đề khác nhau:

Retry:
Lỗi tạm thời của một request.

Circuit breaker:
Dependency đang lỗi hệ thống hoặc liên tục.

Kết hợp sai:

Circuit mở
→ retry liên tục
→ tất cả retry fail fast
→ tốn CPU và tạo noise.

Khi circuit mở, thường không nên retry liên tục.

30. Circuit Breaker có thể gây thundering herd khi đóng lại

Nếu circuit mở 30 giây rồi đóng hoàn toàn:

Hàng nghìn request cùng tràn vào dependency vừa phục hồi.

Do đó cần half-open:

Chỉ cho một lượng nhỏ probe request.

Có thể kết hợp:

- Gradual traffic ramp-up
- Rate limiting
- Concurrency limiting

31. Bulkhead Pattern

Bulkhead bắt nguồn từ tàu biển.

Một con tàu được chia thành nhiều khoang kín. Nếu một khoang bị ngập, nước không tràn ra toàn bộ tàu.

Trong phần mềm:

Chia tài nguyên thành các nhóm độc lập để một workload lỗi không sử dụng hết tài nguyên của workload khác.

32. Không có Bulkhead

Giả sử một application dùng chung thread pool:

flowchart TD
    Requests --> Pool[Shared Thread Pool]

    Pool --> Payment
    Pool --> Recommendation
    Pool --> Report

Report Service chậm và chiếm toàn bộ thread:

- Payment không có thread
- Login không có thread
- Product API không có thread

Một tính năng phụ kéo sập chức năng chính.

33. Có Bulkhead

Tách tài nguyên:

flowchart TD
    PaymentRequests --> PPool[Payment Pool]
    RecommendationRequests --> RPool[Recommendation Pool]
    ReportRequests --> ReportPool[Report Pool]

    PPool --> Payment
    RPool --> Recommendation
    ReportPool --> Report

Nếu Report Pool đầy:

Report fail hoặc chậm,
nhưng Payment Pool vẫn còn tài nguyên.

34. Các loại Bulkhead

34.1 Thread pool isolation

Mỗi dependency hoặc workload có thread pool riêng.

Payment pool:       50 threads
Email pool:         10 threads
Recommendation:     20 threads

34.2 Connection pool isolation

Không cho một dependency dùng hết connection.

Ví dụ:

Primary DB pool:      100 connections
Analytics DB pool:     20 connections
External API pool:     30 connections

34.3 Queue isolation

Mỗi loại job có queue riêng.

flowchart LR
    High[Payment Jobs] --> HQ[High-priority Queue]
    Low[Analytics Jobs] --> LQ[Low-priority Queue]

    HQ --> HW[Payment Workers]
    LQ --> LW[Analytics Workers]

Analytics backlog không chặn payment.

34.4 Instance isolation

Chạy workload trên nhóm server khác nhau.

API instances
Background worker instances
Report-generation instances

Report nặng không tranh CPU với API real-time.

34.5 Tenant isolation

Khách hàng lớn hoặc tenant lỗi có thể được đặt trong cell hoặc resource pool riêng.

Tenant A không được dùng hết capacity của Tenant B.

35. Bulkhead trade-off

Bulkhead tăng khả năng cô lập lỗi nhưng có thể giảm hiệu quả sử dụng tài nguyên.

Không tách:

100 threads dùng chung
→ sử dụng linh hoạt.

Tách:

Payment: 60
Report: 20
Email: 20

Nếu Payment nhàn nhưng Report quá tải:

40 thread Payment có thể rảnh
trong khi Report vẫn bị giới hạn.

Đây là trade-off:

Resource utilization
↕
Fault isolation

Có thể dùng dynamic limits, nhưng độ phức tạp tăng.

36. Concurrency Limiting

Ngay cả khi service chưa lỗi, bạn có thể giới hạn số request đồng thời.

Ví dụ Payment Service chịu an toàn:

200 concurrent requests

Request thứ 201:

- Chờ trong queue có giới hạn
- Hoặc fail fast

Không nên cho 10.000 request cùng vào rồi tất cả timeout.

flowchart LR
    Requests --> Limit{Concurrency < 200?}
    Limit -->|Có| Service
    Limit -->|Không| Reject[Queue nhỏ / Fail fast]

Concurrency limit thường bảo vệ tốt hơn chỉ dựa trên RPS khi request duration biến động.

37. Queue phải có giới hạn

Queue vô hạn không thực sự bảo vệ hệ thống.

Nếu consumer xử lý chậm:

Queue dài vô hạn
→ memory tăng
→ latency tăng
→ request hết giá trị nhưng vẫn nằm trong queue

Ví dụ:

User chờ search result tối đa 2 giây.
Request nằm trong queue 10 giây.

Dù xử lý thành công, kết quả đã vô nghĩa.

Một bounded queue tốt hơn:

Nếu queue đầy:
→ reject sớm
→ trả fallback
→ shed load

38. Graceful Degradation

Graceful degradation nghĩa là khi một phần hệ thống lỗi, hệ thống giảm chức năng có kiểm soát thay vì sập hoàn toàn.

Ví dụ trang sản phẩm có:

- Product details
- Price
- Inventory
- Reviews
- Recommendations
- Recently viewed

Các mức quan trọng:

Core:
Product details, price, purchase

Optional:
Reviews, recommendations, recently viewed

Nếu Recommendation Service lỗi:

Trang vẫn hiển thị,
chỉ ẩn phần recommendation.

39. Graceful Degradation theo mức ưu tiên

Có thể phân loại:

Tier 0 — chức năng sống còn

- Login
- Checkout
- Payment
- Order status

Tier 1 — quan trọng

- Search
- Inventory display
- User profile

Tier 2 — có thể bỏ tạm thời

- Recommendation
- Analytics
- Recently viewed
- Social sharing

Khi hệ thống quá tải:

Tắt Tier 2 trước,
sau đó giảm Tier 1,
bảo vệ Tier 0.

40. Các chiến lược Graceful Degradation

40.1 Trả dữ liệu cache cũ

Recommendation Service lỗi
→ trả recommendation cache của 10 phút trước.

Phù hợp khi stale data chấp nhận được.

40.2 Trả giá trị mặc định

Personalized homepage lỗi
→ trả generic popular content.

40.3 Bỏ qua tính năng phụ

Review Service timeout
→ không hiển thị review section.

40.4 Chuyển sang chế độ read-only

Nếu write database gặp sự cố:

User vẫn đọc dữ liệu,
nhưng tạm thời không chỉnh sửa.

Ví dụ:

- Wiki
- Documentation
- Dashboard
- Social feed

40.5 Xử lý bất đồng bộ

Nếu downstream chưa sẵn sàng:

Nhận request
→ đưa vào queue
→ xử lý sau.

Chỉ phù hợp nếu user không cần kết quả ngay.

40.6 Giảm chất lượng

Ví dụ video:

4K không khả dụng
→ phục vụ 720p.

Ảnh:

Ảnh độ phân giải cao lỗi
→ trả thumbnail.

Search:

Full ranking lỗi
→ trả kết quả theo từ khóa đơn giản.

41. Fallback cũng có thể lỗi

Giả sử Recommendation lỗi và fallback query thẳng database:

Recommendation lỗi
→ tất cả request fallback DB
→ DB quá tải
→ toàn hệ thống lỗi.

Fallback phải:

- Rẻ
- Nhanh
- Ít dependency
- Có giới hạn

Fallback tốt:

- Static response
- Local cache
- Precomputed list
- Bỏ section

Fallback nguy hiểm:

- Query phức tạp
- Gọi service còn nặng hơn
- Retry vô hạn

42. Fault Isolation

Fault isolation là thiết kế ranh giới để lỗi ở một phần không lan sang phần khác.

Có thể cô lập theo:

- Process
- Container
- Server
- Service
- Queue
- Database
- Availability zone
- Region
- Tenant
- Cell

43. Process Isolation

Chạy background job và API trong process riêng.

Không tốt:

Một process:
- HTTP API
- Video transcoding
- Report generation

Video job dùng hết CPU khiến API chậm.

Tốt hơn:

flowchart LR
    APIRequests --> APIPool[API Processes]
    VideoJobs --> VideoPool[Video Workers]
    Reports --> ReportPool[Report Workers]

44. Service Isolation

Tách service có thể giúp lỗi không lan trực tiếp.

Nhưng microservices không tự động tạo isolation.

Nếu tất cả service:

- Dùng chung database
- Dùng chung thread pool
- Gọi đồng bộ sâu
- Không timeout

thì một service lỗi vẫn lan toàn hệ thống.

Isolation cần cả:

- Timeout
- Circuit breaker
- Resource limits
- Independent scaling
- Clear dependency boundaries

45. Availability Zone Isolation

Triển khai qua nhiều zone:

flowchart TD
    LB[Regional Load Balancer]

    LB --> ZA[Zone A]
    LB --> ZB[Zone B]
    LB --> ZC[Zone C]

Nếu Zone A lỗi:

Traffic chuyển sang B và C.

Nhưng B và C phải đủ capacity.

Nếu bình thường mỗi zone chạy 33% và đều gần 100% capacity:

Mất một zone
→ hai zone còn lại không chịu nổi 50% mỗi zone.

Cần headroom để chịu zone failure.

46. Region Isolation

Multi-region giúp chống lỗi cấp region.

flowchart TD
    Global[Global Traffic Manager]

    Global --> Asia[Asia Region]
    Global --> Europe[Europe Region]
    Global --> US[US Region]

Nhưng phức tạp hơn nhiều:

- Data replication
- Consistency
- Failover
- Data residency
- Split-brain
- Cost

Không phải mọi hệ thống cần active-active multi-region.

47. Cell-based Architecture

Cell là một đơn vị triển khai tương đối độc lập, phục vụ một phần user hoặc tenant.

flowchart TD
    Router[Cell Router]

    Router --> C1[Cell 1]
    Router --> C2[Cell 2]
    Router --> C3[Cell 3]

    C1 --> DB1[(DB 1)]
    C2 --> DB2[(DB 2)]
    C3 --> DB3[(DB 3)]

Ví dụ:

User hash 0–999   → Cell 1
User hash 1000–1999 → Cell 2

Nếu Cell 2 lỗi:

Chỉ một phần user bị ảnh hưởng.

Thay vì:

Toàn bộ user bị ảnh hưởng.

Đây là cách giới hạn blast radius.

48. Blast Radius

Blast radius là phạm vi ảnh hưởng của một lỗi.

Ví dụ:

Một instance lỗi:
Ảnh hưởng nhỏ.

Một zone lỗi:
Ảnh hưởng lớn hơn.

Database global lỗi:
Ảnh hưởng toàn hệ thống.

Reliability design cố gắng:

- Giảm xác suất lỗi
- Giảm phạm vi lỗi
- Giảm thời gian phục hồi

Không chỉ cố ngăn mọi lỗi xảy ra.

49. Shared Dependency làm phá vỡ Isolation

Bạn có thể chia application thành nhiều cell, nhưng nếu tất cả dùng chung một Redis:

flowchart TD
    C1[Cell 1] --> Redis[(Shared Redis)]
    C2[Cell 2] --> Redis
    C3[Cell 3] --> Redis

Redis lỗi:

Tất cả cell cùng lỗi.

Cell isolation thực sự có thể cần:

- Cache riêng
- Database shard riêng
- Queue riêng
- Limits riêng

Ít nhất các dependency quan trọng phải được phân vùng phù hợp.

50. Load Shedding

Load shedding là chủ động từ chối một số request khi vượt capacity.

Thay vì:

Nhận 100.000 request
→ tất cả timeout sau 30 giây

ta có thể:

Xử lý 20.000 request quan trọng
→ từ chối phần còn lại ngay.

flowchart LR
    Requests --> Gate{Capacity available?}
    Gate -->|Có| Core[Process]
    Gate -->|Không| Reject[Fail fast / Fallback]

Response có thể là:

503 Service Unavailable
Retry-After: 5

51. Admission Control

Admission control quyết định request có được vào hệ thống không.

Có thể dựa trên:

- Current concurrency
- Queue length
- CPU
- Memory
- Tenant quota
- Priority
- Estimated request cost

Ví dụ:

Payment request:
Ưu tiên cao.

Recommendation refresh:
Ưu tiên thấp.

Khi quá tải, giữ payment và bỏ recommendation.

52. Priority và Criticality

Không phải request nào cũng quan trọng như nhau.

Ví dụ e-commerce:

Priority 1:
Checkout, payment, order status

Priority 2:
Product details, search

Priority 3:
Recommendation, analytics, view count

Có thể dùng:

- Queue riêng
- Worker riêng
- Rate limit riêng
- Connection pool riêng

Đây là bulkhead kết hợp graceful degradation.

53. Rate Limiting là Reliability Pattern

Rate limiting thường được xem là security pattern, nhưng nó cũng bảo vệ reliability.

Giới hạn:

- Theo user
- Theo API key
- Theo tenant
- Theo IP
- Theo endpoint

Mục tiêu:

Một client lỗi hoặc độc hại
không được dùng hết capacity của toàn hệ thống.

Rate limit cũng có thể đặt cho outbound dependency:

Không gửi quá 1.000 request/giây tới Payment Provider.

54. Redundancy

Redundancy là có nhiều bản sao hoặc đường thay thế.

Ví dụ:

- Nhiều app server
- Database replica
- Nhiều load balancer
- Multi-AZ
- Backup network route

Nhưng redundancy không có failover thì chưa đủ.

Có replica
nhưng không ai phát hiện primary lỗi
→ replica không được sử dụng.

Cần:

Detection
Decision
Traffic switch
Recovery

55. Failover

Failover là chuyển hoạt động từ thành phần lỗi sang thành phần dự phòng.

sequenceDiagram
    participant Monitor
    participant Primary
    participant Replica
    participant Router

    Monitor->>Primary: Health check
    Primary--xMonitor: Failure
    Monitor->>Replica: Promote
    Monitor->>Router: Route to replica

Failover có thể:

- Automatic
- Manual
- Active-passive
- Active-active

56. Failover cũng có rủi ro

Automatic failover sai có thể gây split-brain:

Primary thật ra vẫn hoạt động
nhưng monitor mất kết nối.
Replica được promote.

Bây giờ có hai primary cùng nhận write.

Giải pháp có thể cần:

- Consensus
- Quorum
- Fencing token
- Leader election
- STONITH trong một số hệ thống

Không nên nói “chỉ cần failover” mà bỏ qua consistency.

57. Fencing Token

Fencing token là số phiên bản tăng dần khi cấp quyền sở hữu tài nguyên.

Ví dụ:

Leader cũ token = 41
Leader mới token = 42

Storage chỉ chấp nhận request từ token mới nhất.

Nếu leader cũ quay lại và ghi với token 41:

Storage từ chối.

Điều này giúp chống stale leader gây split-brain.

58. Health Check và Self-Healing

Self-healing:

- Phát hiện instance lỗi
- Loại khỏi traffic
- Khởi tạo instance mới
- Chờ readiness
- Thêm lại vào pool

flowchart TD
    Monitor --> Check{Healthy?}
    Check -->|Có| Serve[Continue serving]
    Check -->|Không| Remove[Remove from traffic]
    Remove --> Replace[Start replacement]
    Replace --> Ready{Ready?}
    Ready -->|Có| Add[Add to pool]

Nhưng restart không phải giải pháp cho mọi lỗi.

Nếu bug có trong mọi instance:

Restart liên tục
→ crash loop

Nếu database down:

Restart toàn bộ API
→ connection storm
→ database càng khó phục hồi.

59. Graceful Shutdown

Khi deploy hoặc scale-in:

1. Mark instance not ready
2. Load balancer ngừng gửi request mới
3. Chờ request hiện tại hoàn tất
4. Dừng nhận message mới
5. Commit hoặc release công việc đang xử lý
6. Shutdown

Không graceful shutdown:

- Request bị cắt
- Message xử lý dở
- Upload hỏng
- Payment có trạng thái không rõ

66. Pattern kết hợp

Các pattern thường đi cùng nhau:

flowchart LR
    Request --> Rate[Rate Limit]
    Rate --> Bulkhead[Bulkhead / Concurrency Limit]
    Bulkhead --> Breaker[Circuit Breaker]
    Breaker --> Timeout[Timeout]
    Timeout --> Retry[Bounded Retry + Backoff + Jitter]
    Retry --> Dependency
    Breaker --> Fallback[Fallback / Degradation]

Một trình tự khái niệm:

1. Admission control bảo vệ capacity.
2. Bulkhead giới hạn blast radius.
3. Circuit breaker tránh gọi dependency đang lỗi.
4. Timeout giới hạn từng call.
5. Retry xử lý lỗi tạm thời.
6. Fallback giữ chức năng cốt lõi.

67. Thứ tự wrapper trong code

Có nhiều cách tùy thư viện, nhưng logic cần rõ.

Pseudo-code:

def get_recommendations(user_id: str):
    if circuit_breaker.is_open("recommendation-service"):
        return get_popular_products()

    if not recommendation_bulkhead.try_acquire():
        return get_popular_products()

    try:
        return retry_with_backoff(
            lambda: call_with_timeout(
                lambda: recommendation_client.get(user_id),
                timeout_seconds=0.15,
            ),
            max_attempts=2,
            retry_on=(TemporaryNetworkError,),
        )
    except TemporaryNetworkError:
        circuit_breaker.record_failure("recommendation-service")
        return get_popular_products()
    finally:
        recommendation_bulkhead.release()

Trong production cần thư viện battle-tested thay vì tự viết tất cả.

68. Retry và Circuit Breaker phải hiểu Error Type

Không nên tính mọi response là circuit failure.

Ví dụ:

404 Product Not Found

Không nhất thiết chứng minh Product Service đang lỗi.

Những lỗi thường tính vào breaker:

- Timeout

- 5xx

Những lỗi thường không tính:

- Validation error
- Expected business rejection
- 404 hợp lệ

70. Fallback success có thể che giấu outage

Nếu Recommendation Service lỗi nhưng fallback luôn trả popular products:

API success rate vẫn 100%.

Có thể tưởng hệ thống khỏe.

Do đó cần metric riêng:

Recommendation fallback rate = 80%

HTTP 200 không có nghĩa toàn bộ dependency khỏe.

Phải theo dõi:

- Full success
- Degraded success
- Hard failure

71. SLI, SLO và Error Budget

SLI

Chỉ số đo thực tế.

Ví dụ:

- Availability
- Latency
- Correctness
- Freshness

SLO

Mục tiêu nội bộ.

99.9% checkout requests thành công trong 2 giây.

SLA

Cam kết với khách hàng, có thể có hậu quả tài chính.

Error budget

Nếu SLO là 99.9%:

Cho phép 0.1% request không đạt mục tiêu.

Error budget giúp cân bằng:

Reliability
↕
Tốc độ phát triển tính năng

Khi error budget gần hết:

- Giảm deploy rủi ro
- Tập trung sửa reliability
- Thắt chặt rollout

Mục tiêu không phải phá hệ thống tùy tiện.

Mục tiêu:

Kiểm tra giả định reliability có đúng không.

Ví dụ:

Ta tin rằng mất Redis chỉ làm latency tăng.

Chaos test cho thấy:

→ Thiết kế fallback đang sai.

73. Game Day

Game day là buổi diễn tập sự cố có kế hoạch.

Ví dụ:

- Queue backlog tăng nhanh

Đánh giá:

- Alert có kích hoạt không?
- On-call có hiểu dashboard không?
- Failover có thành công không?
- Runbook có chính xác không?
- Recovery mất bao lâu?

Reliability không chỉ là code; nó còn là quy trình vận hành.

74. Runbook

Runbook mô tả cách xử lý sự cố.

Ví dụ circuit breaker mở liên tục:

1. Kiểm tra dependency latency.
2. Kiểm tra error rate.
3. Kiểm tra deploy gần nhất.
4. Xác nhận fallback đang hoạt động.
5. Kiểm tra retry volume.
6. Rollback hoặc disable feature nếu cần.

Một hệ thống phức tạp nhưng không có runbook sẽ khó phục hồi nhanh.

75. Những sai lầm phổ biến

Lỗi 1: Không đặt timeout

Một dependency treo giữ toàn bộ tài nguyên.

Lỗi 2: Timeout ở mọi tầng đều giống nhau

Không có end-to-end deadline budget.

Lỗi 3: Xem timeout là thất bại chắc chắn

Với operation có side effect, trạng thái có thể unknown.

Lỗi 4: Retry mọi lỗi

Validation error và business rejection không trở nên đúng sau retry.

Lỗi 5: Retry ở mọi tầng

Tạo retry amplification.

Lỗi 6: Retry không có backoff và jitter

Tạo retry storm.

Lỗi 7: Retry operation không idempotent

Tạo duplicate order/payment.

Lỗi 8: Circuit breaker không có half-open

Dependency vừa phục hồi bị traffic dồn lại.

Lỗi 9: Dùng một circuit cho mọi operation

Một endpoint lỗi làm chặn cả service.

Lỗi 10: Dùng chung mọi resource pool

Một tính năng phụ chiếm hết thread hoặc connection.

Lỗi 11: Queue vô hạn

Chỉ chuyển lỗi quá tải thành latency vô hạn.

Lỗi 12: Fallback quá đắt

Fallback làm dependency khác sập.

Lỗi 13: Graceful degradation nhưng không đo degraded response

Outage bị che bởi HTTP 200.

Lỗi 14: Có replica nhưng không test failover

Đến lúc lỗi thật mới phát hiện replica không dùng được.

Lỗi 15: Autoscaling được xem là giải pháp cho mọi overload

Autoscaling có độ trễ và không sửa được dependency đang nghẽn.

76. Framework thiết kế Reliability như Senior Engineer

Với mỗi dependency, hãy trả lời:

1. Dependency này có quan trọng với request không?
2. Nếu nó lỗi, chức năng nào mất?
3. Timeout là bao nhiêu?
4. Timeout dựa trên latency distribution nào?
5. Operation có idempotent không?
6. Lỗi nào được retry?
7. Retry ở tầng nào?
8. Max attempts là bao nhiêu?
9. Có exponential backoff và jitter không?
10. Retry budget là bao nhiêu?
11. Khi nào circuit breaker mở?
12. Half-open cho bao nhiêu probe?
13. Resource pool có được cô lập không?
14. Queue/concurrency limit là bao nhiêu?
15. Fallback là gì?
16. Fallback có rẻ và đáng tin không?
17. Có thể trả stale data không?
18. Có thể tắt tính năng phụ không?
19. Blast radius của failure là bao nhiêu?
20. Metric và alert nào phát hiện lỗi?

78. Cách trình bày trong System Design Interview

Không nên chỉ nói:

Em thêm retry và circuit breaker để tăng reliability.

Nên nói:

Recommendation Service là dependency không bắt buộc, nên tôi đặt timeout ngắn khoảng 100–200 ms. Chỉ lỗi network và 5xx mới được retry một lần với exponential backoff và jitter. Nếu failure hoặc slow-call rate vượt threshold, circuit breaker mở và hệ thống trả danh sách sản phẩm phổ biến từ cache. Recommendation dùng thread pool và connection pool riêng để không chiếm tài nguyên của checkout. Tôi theo dõi riêng fallback rate vì response 200 có thể che giấu việc recommendation đang lỗi.

Với Payment:

Payment là operation có side effect nên timeout không được xem là thất bại chắc chắn. Mỗi payment attempt dùng idempotency key ổn định. Khi provider timeout, trạng thái chuyển thành pending hoặc unknown và được reconcile qua status API hoặc webhook. Retry phải dùng cùng key và nằm trong retry budget.

Đó là tư duy reliability có chiều sâu.

81. Những điều phải nhớ sau Bài 10

1. Failure là điều bình thường trong distributed systems.
2. Reliability tốt tập trung vào giới hạn và phục hồi lỗi.
3. Timeout ngăn request chờ vô hạn.
4. End-to-end deadline phải được truyền qua các service.
5. Timeout không có nghĩa side effect chắc chắn chưa xảy ra.
6. Chỉ retry lỗi tạm thời.
7. Retry operation có side effect cần idempotency.
8. Retry phải có giới hạn, backoff và jitter.
9. Không retry ở mọi tầng vì sẽ gây amplification.
10. Retry budget giới hạn retry traffic.
11. Circuit breaker fail fast khi dependency đang lỗi.
12. Circuit breaker có Closed, Open và Half-open.
13. Circuit breaker không thay thế timeout.
14. Bulkhead cô lập thread, connection, queue hoặc instance.
15. Queue vô hạn không phải overload protection.
16. Graceful degradation giữ chức năng cốt lõi hoạt động.
17. Fallback phải rẻ và đáng tin hơn đường chính.
18. Fault isolation giúp giảm blast radius.
19. Cell architecture giới hạn lỗi trong một nhóm user.
20. Shared dependency có thể phá hỏng isolation.
21. Load shedding tốt hơn để mọi request cùng timeout.
22. Redundancy chỉ hữu ích khi có detection và failover.
23. Failover tự động phải chống split-brain.
24. Fallback rate phải được đo riêng.
25. Chaos testing và game day giúp kiểm tra giả định reliability.
