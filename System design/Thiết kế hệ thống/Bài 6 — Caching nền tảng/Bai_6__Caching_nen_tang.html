Bài 6 — Caching nền tảng

Caching là kỹ thuật lưu tạm dữ liệu ở một nơi có tốc độ truy cập nhanh hơn để tránh phải tính toán hoặc đọc lại từ nguồn dữ liệu gốc cho mỗi request.

Nói đơn giản:

Cache đổi storage và độ phức tạp lấy tốc độ và khả năng chịu tải.

Trong tài liệu System Design bạn đã cung cấp, caching được trình bày ở nhiều tầng như browser cache, server-side cache, database/query cache và CDN; các chiến lược ghi phổ biến gồm cache-aside, write-through và write-back.

1. Tại sao cần cache?

Giả sử endpoint:

GET /products/p_123

Không dùng cache:

sequenceDiagram
    participant User
    participant API
    participant DB

    User->>API: GET /products/p_123
    API->>DB: SELECT product
    DB-->>API: Product data
    API-->>User: Response

Nếu có 20.000 request/giây cùng đọc một sản phẩm nổi tiếng, database phải xử lý 20.000 query/giây.

Có cache:

sequenceDiagram
    participant User
    participant API
    participant Cache
    participant DB

    User->>API: GET /products/p_123
    API->>Cache: GET product:p_123
    Cache-->>API: Product data
    API-->>User: Response

Phần lớn request không cần chạm database.

Cache giúp:

- Giảm latency
- Giảm tải database
- Giảm số lần gọi service bên ngoài
- Giảm CPU do tính toán lặp lại
- Tăng throughput
- Giảm chi phí hạ tầng
- Hấp thụ traffic spike

Nhưng cache cũng tạo ra vấn đề mới:

- Dữ liệu cũ
- Invalidation
- Cache miss
- Stampede
- Hot key
- Memory giới hạn
- Cache và database không đồng nhất

Do đó:

Cache không chỉ là thêm Redis. Cache là một chiến lược quản lý dữ liệu tạm thời.

2. Cache nằm ở đâu?

Cache không chỉ có Redis.

flowchart LR
    User --> Browser[Browser Cache]
    Browser --> CDN[CDN / Edge Cache]
    CDN --> API[Application]
    API --> Local[Local In-memory Cache]
    API --> Distributed[Distributed Cache]
    Distributed --> DB[(Database)]

2.1 Browser cache

Lưu trên thiết bị người dùng:

- HTML
- CSS
- JavaScript
- Images
- API responses phù hợp

Điều khiển bằng HTTP headers:

Cache-Control: public, max-age=3600
ETag: "product-123-v5"
Last-Modified: Fri, 10 Jul 2026 08:00:00 GMT

Browser có thể sử dụng lại dữ liệu mà không tải lại hoàn toàn.

2.2 CDN cache

CDN lưu static content hoặc cacheable response ở edge server gần user.

Phù hợp:

- Images
- Video segments
- CSS/JS
- Download files
- Public product pages

flowchart LR
    U1[User Việt Nam] --> E1[Asia Edge]
    U2[User châu Âu] --> E2[Europe Edge]
    U3[User Mỹ] --> E3[US Edge]

    E1 --> Origin[Origin Storage]
    E2 --> Origin
    E3 --> Origin

CDN vừa giảm latency, vừa giảm bandwidth và tải lên origin.

2.3 Local in-memory cache

Cache nằm trực tiếp trong memory của mỗi application instance.

Ví dụ:

- Java Caffeine
- Guava Cache
- Node.js memory map
- Python lru_cache

Ưu điểm:

- Cực nhanh
- Không có network call
- Dễ dùng

Nhược điểm:

- Mỗi server có cache riêng
- Dữ liệu không đồng nhất giữa các instance
- Mất khi process restart
- Khó invalidation toàn cluster
- Memory bị giới hạn theo từng máy

Ví dụ:

flowchart TD
    LB[Load Balancer] --> A1[API 1 + Local Cache]
    LB --> A2[API 2 + Local Cache]
    LB --> A3[API 3 + Local Cache]

API 1 có thể thấy version mới, trong khi API 2 vẫn giữ version cũ.

2.4 Distributed cache

Cache chạy thành một hệ thống riêng và được nhiều application instance dùng chung.

Ví dụ:

Redis
Memcached

flowchart TD
    LB --> A1[API 1]
    LB --> A2[API 2]
    LB --> A3[API 3]

    A1 --> C[(Redis)]
    A2 --> C
    A3 --> C
    C --> DB[(Database)]

Ưu điểm:

- Cache được chia sẻ
- Dễ scale application
- Quản lý TTL và eviction tập trung
- Hỗ trợ nhiều cấu trúc dữ liệu

Nhược điểm:

- Thêm network hop
- Thêm dependency
- Cache có thể trở thành bottleneck
- Cần replication, sharding và monitoring

3. Các thuật ngữ cơ bản

Cache hit

Dữ liệu được tìm thấy trong cache.

Request → Cache → Found

Cache miss

Dữ liệu không có trong cache.

Request → Cache → Not found → Database

Hit ratio

Cache Hit Ratio =
Cache Hits / Total Cache Lookups

Ví dụ:

900.000 cache hit
100.000 cache miss

Hit ratio = 900.000 / 1.000.000 = 90%

Hit ratio cao thường tốt, nhưng không phải metric duy nhất.

Cache hit ratio 99% vẫn có thể không đủ nếu 1% miss tương đương 50.000 DB QPS.

Miss penalty

Chi phí khi cache miss:

- Đọc database
- Gọi API bên ngoài
- Tính toán dữ liệu
- Serialize response
- Ghi lại vào cache

Nếu miss penalty lớn, việc bảo vệ cache miss rất quan trọng.

4. Cache-aside — Lazy Loading

Đây là chiến lược phổ biến nhất.

Application tự quản lý cache.

Luồng đọc:

1. Đọc cache
2. Nếu cache hit → trả dữ liệu
3. Nếu cache miss → đọc database
4. Ghi dữ liệu vào cache
5. Trả response

sequenceDiagram
    participant Client
    participant App
    participant Cache
    participant DB

    Client->>App: Get product
    App->>Cache: GET product:123

    alt Cache hit
        Cache-->>App: Product
        App-->>Client: Product
    else Cache miss
        Cache-->>App: Not found
        App->>DB: SELECT product
        DB-->>App: Product
        App->>Cache: SET product:123 + TTL
        App-->>Client: Product
    end

Pseudo-code:

def get_product(product_id: str):
    cache_key = f"product:{product_id}"

    cached = cache.get(cache_key)
    if cached is not None:
        return deserialize(cached)

    product = database.get_product(product_id)
    if product is None:
        return None

    cache.set(cache_key, serialize(product), ttl=300)
    return product

Cách cập nhật với cache-aside

Thông thường:

1. Ghi database
2. Xóa cache

sequenceDiagram
    participant App
    participant DB
    participant Cache

    App->>DB: UPDATE product
    DB-->>App: Success
    App->>Cache: DELETE product:123

Request tiếp theo cache miss và nạp dữ liệu mới.

Pseudo-code:

def update_product(product_id: str, changes: dict):
    product = database.update_product(product_id, changes)

    cache.delete(f"product:{product_id}")

    return product

Ưu điểm cache-aside

- Đơn giản
- Chỉ cache dữ liệu thực sự được đọc
- Cache failure không nhất thiết làm mất dữ liệu
- Database vẫn là source of truth
- Phù hợp nhiều workload read-heavy

Nhược điểm

- Request đầu tiên luôn cache miss
- Có thể đọc dữ liệu cũ
- Application phải tự quản lý cache
- Dễ xảy ra stampede
- Có khoảng thời gian DB và cache không nhất quán

5. Vì sao thường “update DB rồi delete cache”?

Ta có ba lựa chọn tưởng như hợp lý:

A. Update database rồi update cache
B. Delete cache rồi update database
C. Update database rồi delete cache

Phổ biến nhất là C.

5.1 Update database rồi update cache

Có thể xảy ra race condition.

Giả sử hai request:

Request A cập nhật giá = 100
Request B cập nhật giá = 120

Thứ tự:

A update DB = 100
B update DB = 120
B update cache = 120
A update cache = 100

Trạng thái cuối:

Database = 120
Cache = 100

Cache bị cũ lâu dài cho tới khi TTL hết.

5.2 Delete cache rồi update database

Race condition khác:

1. Writer xóa cache
2. Reader cache miss
3. Reader đọc giá cũ từ DB
4. Writer cập nhật DB
5. Reader ghi giá cũ vào cache

Kết quả:

Database = dữ liệu mới
Cache = dữ liệu cũ

5.3 Update database rồi delete cache

Luồng:

1. Database được cập nhật thành công
2. Cache cũ bị xóa
3. Read tiếp theo nạp dữ liệu mới

Đây thường là phương án ít rủi ro hơn.

Nhưng vẫn chưa hoàn hảo. Nếu update DB thành công nhưng delete cache thất bại, cache vẫn cũ.

Các cách giảm rủi ro:

- TTL
- Retry invalidation
- Publish event thay đổi
- Transactional outbox
- Change Data Capture
- Versioned cache key

6. Write-through cache

Trong write-through, ứng dụng ghi vào cache, và cache đồng thời hoặc đồng bộ ghi xuống database.

Khái niệm:

Application → Cache → Database

sequenceDiagram
    participant Client
    participant App
    participant Cache
    participant DB

    Client->>App: Update product
    App->>Cache: Write product
    Cache->>DB: Persist product
    DB-->>Cache: Success
    Cache-->>App: Success
    App-->>Client: Success

Một biến thể do application điều phối:

1. Write database
2. Write cache
3. Chỉ trả success khi cả hai hoàn thành

Ưu điểm

- Cache luôn được làm nóng sau write
- Read sau write thường thấy dữ liệu mới
- Giảm cache miss với dữ liệu vừa cập nhật

Nhược điểm

- Write latency cao hơn
- Mỗi write phải cập nhật hai nơi
- Có thể cache dữ liệu không bao giờ được đọc
- Phải xử lý partial failure

Ví dụ:

Database write thành công
Cache write thất bại

Hoặc ngược lại.

Do đó cần xác định rõ:

Database hay cache là source of truth?
Thứ tự write ra sao?
Retry có idempotent không?

Phù hợp khi

- Dữ liệu vừa ghi thường được đọc ngay
- Read-after-write quan trọng
- Write không quá lớn
- Có cơ chế cache/database integration đáng tin cậy

Ví dụ:

- User profile
- Configuration
- Product metadata
- Session state bền vững

7. Write-back / Write-behind cache

Trong write-back, dữ liệu được ghi vào cache trước và trả success nhanh. Cache sẽ ghi xuống storage bền vững sau.

Application → Cache → trả success
                     ↓
               Database sau

sequenceDiagram
    participant Client
    participant App
    participant Cache
    participant DB

    Client->>App: Write data
    App->>Cache: Store data
    Cache-->>App: Success
    App-->>Client: Success

    Note over Cache,DB: Later / asynchronous
    Cache->>DB: Flush data
    DB-->>Cache: Persisted

Ưu điểm

- Write latency rất thấp
- Có thể batch nhiều write
- Giảm write pressure lên database
- Tăng write throughput

Nhược điểm

- Có nguy cơ mất dữ liệu nếu cache chết trước khi flush
- Logic phức tạp
- Recovery khó
- Database tạm thời không có dữ liệu mới
- Cần durability cho cache hoặc write log

Phù hợp khi

- Write throughput rất cao
- Chấp nhận mất một lượng nhỏ dữ liệu
- Dữ liệu có thể batch
- Cache/store trung gian đủ bền vững

Ví dụ:

- View counters
- Like counters
- Analytics counters
- Telemetry
- Một số game statistics

Không phù hợp làm nguồn ghi trực tiếp duy nhất cho:

- Banking ledger
- Payment
- Order confirmation
- Inventory reservation quan trọng

Trừ khi lớp write-back có durability và recovery được thiết kế rất nghiêm túc.

8. Write-around

Write-around nghĩa là ghi thẳng xuống database, bỏ qua cache.

sequenceDiagram
    participant App
    participant DB
    participant Cache

    App->>DB: Write data
    DB-->>App: Success
    Note over Cache: Không ghi cache

Khi có read:

Cache miss → DB → cache

Ưu điểm

- Không đưa dữ liệu ít được đọc vào cache
- Tránh cache bị lấp đầy bởi write-heavy data
- Write path đơn giản hơn

Nhược điểm

- Read đầu tiên sau write bị cache miss
- Read-after-write có latency cao hơn

Phù hợp với dữ liệu:

- Ghi nhiều nhưng hiếm khi đọc ngay
- Log
- Event history
- Archival records

9. So sánh các chiến lược

Chiến lược Read Write Ưu điểm Rủi ro chính
Cache-aside App đọc cache rồi DB Ghi DB, xóa cache Đơn giản, phổ biến Dữ liệu cũ, stampede
Write-through Cache và DB cùng cập nhật Đồng bộ Cache luôn nóng Write latency
Write-back Ghi cache trước DB ghi sau Write rất nhanh Mất dữ liệu
Write-around Miss thì nạp cache Ghi thẳng DB Không cache dữ liệu lạnh Read sau write bị miss

Không có chiến lược luôn tốt nhất.

10. TTL — Time To Live

TTL là thời gian một cache entry tồn tại trước khi tự hết hạn.

SET product:123 value TTL 300 seconds

Sau 5 phút, key tự biến mất.

TTL giải quyết:

- Dữ liệu không nằm vĩnh viễn
- Cache cũ cuối cùng sẽ tự mất
- Giới hạn memory usage
- Giảm hậu quả invalidation thất bại

TTL dài

Ưu điểm:

- Hit ratio cao
- Giảm tải database
- Ít cache miss

Nhược điểm:

- Dữ liệu có thể cũ lâu
- Invalidation sai gây ảnh hưởng dài

TTL ngắn

Ưu điểm:

- Dữ liệu mới hơn
- Giảm stale data

Nhược điểm:

- Hit ratio thấp hơn
- Database bị đọc nhiều hơn
- Dễ stampede khi nhiều key hết hạn

11. Chọn TTL thế nào?

TTL phải dựa vào business tolerance.

Ví dụ:

Exchange rate:
Vài giây hoặc vài phút, tùy nghiệp vụ

Product description:
Vài phút đến vài giờ

Product inventory:
Rất ngắn hoặc không chỉ dựa vào TTL

User profile:
Vài phút

Country list:
Nhiều giờ hoặc nhiều ngày

Feature configuration:
Vài giây đến vài phút

News feed:
Tùy cá nhân hóa và độ mới yêu cầu

Static image có version:
Có thể cache rất lâu

Câu hỏi cần hỏi:

Dữ liệu được phép cũ bao lâu?
Nếu user thấy dữ liệu cũ thì hậu quả gì?
Source thay đổi thường xuyên không?
Cache miss đắt đến mức nào?
Có cơ chế invalidation chủ động không?

12. TTL jitter

Nếu một triệu key được tạo cùng lúc với TTL 5 phút, chúng có thể hết hạn cùng lúc.

12:00:00 → 1.000.000 key được cache
12:05:00 → 1.000.000 key cùng expire

Database nhận một cơn bão request.

Giải pháp: thêm jitter ngẫu nhiên.

TTL = 300 giây + random(0, 60 giây)

Hoặc:

TTL nằm trong khoảng 270–330 giây

Nhờ đó expiration được phân tán theo thời gian.

13. Eviction là gì?

Cache memory có giới hạn.

Khi đầy, cache phải quyết định key nào bị loại bỏ. Đó là eviction policy.

TTL trả lời:

Key tồn tại tối đa bao lâu?

Eviction trả lời:

Khi không đủ memory, key nào phải rời cache trước?

14. Các eviction policy phổ biến

14.1 LRU — Least Recently Used

Xóa key lâu nhất chưa được sử dụng.

A được đọc vừa rồi
B được đọc 10 phút trước
C được đọc 2 giờ trước

→ Xóa C

Phù hợp khi dữ liệu được truy cập gần đây có khả năng tiếp tục được truy cập.

Đây là lựa chọn phổ biến cho application cache.

14.2 LFU — Least Frequently Used

Xóa key có tần suất truy cập thấp nhất.

A: 10.000 lượt đọc
B: 100 lượt đọc
C: 2 lượt đọc

→ Xóa C

Phù hợp khi có một tập dữ liệu nóng ổn định.

Nhược điểm:

Một key từng rất nóng trong quá khứ có thể giữ điểm cao dù hiện tại không còn cần.

Thực tế thường cần cơ chế decay theo thời gian.

14.3 FIFO — First In, First Out

Key vào cache trước bị xóa trước.

Đơn giản nhưng không quan tâm key có đang được dùng nhiều hay không.

14.4 Random

Xóa ngẫu nhiên một key.

Nghe kém thông minh nhưng:

- Đơn giản
- Overhead thấp
- Có thể đủ tốt cho một số workload

14.5 TTL-based eviction

Ưu tiên xóa key sắp hết hạn.

Có thể hữu ích nhưng không đảm bảo key ít giá trị nhất bị loại.

15. Chọn eviction policy

Recent popularity quan trọng:
LRU

Long-term frequency quan trọng:
LFU

Workload đơn giản, overhead thấp:
Random/FIFO

Dữ liệu có expiration rõ:
TTL-aware

Nhưng cách tốt nhất là đo:

- Hit ratio
- Evictions/second
- Memory usage
- Miss latency
- Hot key distribution

16. Cache invalidation

Cache invalidation là quá trình loại bỏ hoặc cập nhật cache khi dữ liệu gốc thay đổi.

Đây là một trong những vấn đề khó nhất của caching.

Ba chiến lược chính:

1. Expiration bằng TTL
2. Invalidation chủ động
3. Versioned keys

16.1 Invalidation bằng TTL

Không xóa ngay. Chờ cache hết hạn.

Ưu điểm:

- Đơn giản
- Ít coupling

Nhược điểm:

- User thấy dữ liệu cũ cho tới khi TTL hết

Phù hợp nếu stale data được chấp nhận.

16.2 Invalidation chủ động

Khi dữ liệu thay đổi:

Update database
→ Delete cache key

Hoặc publish event:

flowchart LR
    Service[Product Service] --> DB[(Database)]
    Service --> Q[ProductUpdated Event]
    Q --> C1[Invalidate Redis]
    Q --> C2[Invalidate CDN]
    Q --> C3[Update Search Index]

Ưu điểm:

- Dữ liệu mới được phản ánh nhanh

Nhược điểm:

- Event có thể mất hoặc trễ
- Nhiều cache layer khó đồng bộ
- Partial failure

Thường kết hợp invalidation chủ động với TTL làm safety net.

16.3 Versioned cache key

Thay vì:

product:123

dùng:

product:123:v7

Khi dữ liệu thay đổi, tăng version:

product:123:v8

Key cũ không còn được đọc và sẽ tự hết hạn.

Phù hợp với static assets:

app.a82fd1.js
logo.v3.png

Có thể đặt cache rất lâu vì URL thay đổi khi nội dung đổi.

17. Cache invalidation theo entity và collection

Giả sử cập nhật product p_123.

Ta có thể phải invalidation:

product:p_123
products:category:laptop:page:1
products:brand:apple:page:1
search:laptop
homepage:featured-products

Đây gọi là fan-out invalidation.

Một thay đổi nhỏ ảnh hưởng nhiều cache key.

Các hướng xử lý:

- Cache object riêng thay vì cache quá nhiều query result
- Dùng tag-based invalidation
- Dùng dependency graph
- TTL ngắn cho collection
- Event-driven invalidation
- Chấp nhận eventual consistency

18. Cache stampede

Cache stampede xảy ra khi một key nóng hết hạn và rất nhiều request cùng cache miss.

Ví dụ:

product:iphone-new

Key hết hạn đúng lúc 50.000 user truy cập.

flowchart TD
    R1[Request 1] --> C[Cache Miss]
    R2[Request 2] --> C
    R3[Request 3] --> C
    R4[...50.000 requests] --> C

    C --> DB[(Database)]

Thay vì một query DB, database nhận 50.000 query giống nhau.

Stampede còn được gọi là:

Cache breakdown
Dogpile effect
Thundering herd

19. Giải pháp chống stampede

19.1 Request coalescing / Single flight

Chỉ cho một request tải dữ liệu từ DB.

Các request còn lại chờ kết quả đó.

sequenceDiagram
    participant R1 as Request 1
    participant R2 as Request 2
    participant Cache
    participant Lock
    participant DB

    R1->>Cache: GET key
    R2->>Cache: GET key
    Cache-->>R1: Miss
    Cache-->>R2: Miss

    R1->>Lock: Acquire
    Lock-->>R1: Granted
    R2->>Lock: Acquire
    Lock-->>R2: Wait

    R1->>DB: Query once
    DB-->>R1: Data
    R1->>Cache: SET key
    R1->>Lock: Release

    R2->>Cache: GET key
    Cache-->>R2: Data

Pseudo-code:

def get_product(product_id):
    key = f"product:{product_id}"

    value = cache.get(key)
    if value is not None:
        return value

    with distributed_lock(f"lock:{key}"):
        value = cache.get(key)
        if value is not None:
            return value

        value = database.get_product(product_id)
        cache.set(key, value, ttl=300)
        return value

Lưu ý phải kiểm tra cache lần hai sau khi lấy lock.

19.2 Stale-while-revalidate

Cho phép trả dữ liệu cũ trong thời gian ngắn, đồng thời một worker refresh cache nền.

Fresh TTL = 5 phút
Stale window = thêm 1 phút

Trong phút thứ 6:

- User vẫn nhận dữ liệu cũ
- Một request kích hoạt refresh
- Không dồn toàn bộ traffic vào DB

sequenceDiagram
    participant Client
    participant Cache
    participant Worker
    participant DB

    Client->>Cache: Get key
    Cache-->>Client: Stale data
    Cache->>Worker: Trigger refresh
    Worker->>DB: Fetch fresh data
    DB-->>Worker: Fresh data
    Worker->>Cache: Replace value

Phù hợp khi availability và latency quan trọng hơn freshness tuyệt đối.

19.3 Refresh-ahead

Refresh key trước khi TTL hết.

Nếu key thường được truy cập:

TTL còn dưới 10%
→ async refresh

Nhờ vậy key nóng ít khi thực sự expire.

19.4 TTL jitter

Phân tán thời điểm expiration, đặc biệt khi nhiều key được preload cùng lúc.

19.5 Rate limit và circuit breaker

Nếu cache down hoặc miss tăng đột biến, không cho toàn bộ request tràn xuống database.

- Rate limit request
- Fail fast
- Serve stale data
- Load shedding
- Circuit breaker

20. Cache penetration

Cache penetration khác stampede.

Nó xảy ra khi request liên tục hỏi dữ liệu không tồn tại.

Ví dụ attacker hoặc bug gọi:

GET /products/not_exist_1
GET /products/not_exist_2
GET /products/not_exist_3

Cache không có. Database cũng không có. Nhưng mỗi request vẫn chạm DB.

Giải pháp 1: Negative caching

Cache cả kết quả “không tồn tại”.

product:not_exist → NULL, TTL 30 giây

Pseudo-code:

NOT_FOUND = "__NOT_FOUND__"

cached = cache.get(key)

if cached == NOT_FOUND:
    return None

if cached is not None:
    return cached

value = database.get(key)

if value is None:
    cache.set(key, NOT_FOUND, ttl=30)
    return None

Dùng TTL ngắn để tránh trường hợp object được tạo ngay sau đó nhưng cache vẫn nói không tồn tại quá lâu.

Giải pháp 2: Bloom filter

Bloom filter cho biết:

Object chắc chắn không tồn tại
hoặc
có thể tồn tại

Nếu Bloom filter nói chắc chắn không tồn tại, bỏ qua DB.

Nhược điểm:

- Có false positive
- Không trả dữ liệu, chỉ kiểm tra membership
- Việc delete/update phức tạp hơn

Giải pháp 3: Validate input và rate limit

Không để request ID vô nghĩa đi sâu vào hệ thống.

21. Cache avalanche

Cache avalanche là khi một lượng lớn key hết hạn gần nhau hoặc cache cluster bị down.

Khác stampede:

Stampede:
Một hoặc vài hot key bị miss đồng thời.

Avalanche:
Rất nhiều key cùng miss hoặc toàn cache unavailable.

Hậu quả:

Cache miss tăng mạnh
→ Database overload
→ API timeout
→ Retry storm
→ Hệ thống sập dây chuyền

Giải pháp:

- TTL jitter
- Cache cluster replication
- Graceful degradation
- Request throttling
- Circuit breaker
- Prewarming
- Serve stale data
- Database capacity reserve

22. Hot key

Hot key là một key nhận traffic vượt xa các key khác.

Ví dụ:

homepage:trending
celebrity:profile:123
live-match:score
product:flash-sale

Nếu tất cả traffic vào một Redis node chứa key đó, node có thể quá tải dù cluster tổng thể còn dư capacity.

flowchart TD
    Requests[1 triệu requests] --> K[Hot Key]
    K --> N1[Redis Node 1 overloaded]

    N2[Redis Node 2 idle]
    N3[Redis Node 3 idle]

Giải pháp hot key

- Local cache trước distributed cache
- Replicate hot key
- Split/shard key
- CDN/edge cache
- Request coalescing
- Precompute response
- Increase TTL
- Rate limit

Ví dụ shard counter:

likes:post123:shard0
likes:post123:shard1
...
likes:post123:shard99

Write phân tán, read cộng các shard hoặc dùng aggregate định kỳ.

23. Two-level cache

Kết hợp local cache và distributed cache:

flowchart LR
    App --> L1[L1 Local Cache]
    L1 --> L2[L2 Redis]
    L2 --> DB[(Database)]

Luồng:

1. Đọc local cache
2. Nếu miss, đọc Redis
3. Nếu Redis miss, đọc DB
4. Nạp ngược lên Redis và local cache

Ưu điểm:

- L1 cực nhanh
- Giảm tải Redis
- Giảm network calls

Nhược điểm:

- Invalidation khó hơn
- Local cache giữa các instance có thể lệch
- Hot data duplicate trên nhiều server

Thường cần:

- L1 TTL ngắn
- Pub/sub invalidation
- Version checks

24. Cache key design

Cache key phải:

- Unique
- Dễ hiểu
- Có namespace
- Bao gồm các tham số ảnh hưởng kết quả
- Không quá dài
- Không chứa dữ liệu nhạy cảm

Ví dụ tốt:

product:v1:123
user:v2:456:profile
tasks:v1:user_123:status_open:cursor_abc

Ví dụ sai:

profile
page1
result

Cache key phải chứa toàn bộ input quan trọng

API:

GET /products?category=laptop&sort=price&currency=VND

Key không đủ:

products:laptop

Vì request USD và VND có thể nhận cùng cache sai.

Tốt hơn:

products:v1:category=laptop:sort=price:currency=VND

Các yếu tố thường bị quên:

- User identity
- Permission/role
- Language
- Currency
- Region
- Feature flag
- API version
- Filter
- Sort
- Pagination cursor

25. Không cache dữ liệu riêng tư sai phạm vi

Sai lầm nguy hiểm:

GET /me/profile
Cache key = profile

User B có thể nhận profile của User A.

Phải scope theo user:

profile:user_123

Hoặc không cache response cá nhân ở shared CDN.

HTTP header phù hợp:

Cache-Control: private, max-age=60

Dữ liệu public:

Cache-Control: public, max-age=3600

Dữ liệu nhạy cảm:

Cache-Control: no-store

26. Những gì không nên cache

Không nên cache chỉ vì “cache nhanh”.

Cân nhắc tránh cache:

- Dữ liệu thay đổi liên tục và cần chính xác tuyệt đối
- Payment balance
- Seat availability ở bước commit
- Security permission nhạy cảm nếu invalidation không đáng tin
- Dữ liệu hiếm khi được đọc lại
- Response quá lớn và ít reuse
- Query đã đủ nhanh nhưng invalidation rất phức tạp

Ví dụ inventory có thể cache để hiển thị:

“Còn khoảng 10 sản phẩm”

Nhưng lúc đặt hàng phải kiểm tra source of truth bằng transaction hoặc atomic reservation.

Cache không được dùng để xác nhận cuối cùng rằng hàng vẫn còn.

27. Cache failure phải được thiết kế thế nào?

Cache thường là optimization, không nên luôn trở thành điểm làm hệ thống sập hoàn toàn.

Nếu Redis down:

Option A:
Fallback xuống DB

Rủi ro:
DB có thể bị overload.

Option B:
Fail request ngay

Rủi ro:
Availability thấp.

Option C:
Serve stale/local data

Rủi ro:
Dữ liệu cũ.

Thiết kế phù hợp có thể kết hợp:

- Circuit breaker
- Rate limiting
- Fallback có giới hạn
- Stale response
- Load shedding
- Cache replication

Không nên để một cache outage biến thành database outage.

28. Cache prewarming

Sau khi deploy, restart hoặc flush cache, cache hoàn toàn trống.

Đây là cold cache.

Nếu toàn bộ traffic ngay lập tức chạm DB, hệ thống có thể quá tải.

Prewarming là nạp trước dữ liệu quan trọng:

- Top products
- Homepage content
- Popular profiles
- Configuration
- Frequently used reference data

Nhưng không nên preload mọi thứ vì:

- Tốn thời gian
- Tốn memory
- Nhiều dữ liệu có thể không bao giờ được đọc

29. Observability cho cache

Không thể vận hành cache chỉ dựa trên cảm giác.

Các metric quan trọng:

- Cache hit ratio
- Cache miss ratio
- Get/set latency
- Evictions per second
- Expired keys
- Memory usage
- CPU usage
- Network throughput
- Connection count
- Error rate
- Hot key distribution
- DB QPS caused by misses

Đặc biệt phải theo dõi:

Hit ratio giảm
→ DB QPS tăng
→ DB latency tăng
→ API latency tăng

flowchart LR
    Hit[Cache hit ratio giảm] --> Miss[Cache miss tăng]
    Miss --> DB[DB load tăng]
    DB --> Latency[Latency tăng]
    Latency --> Retry[Client retry]
    Retry --> More[Load tăng thêm]

30. Hit ratio cao chưa chắc hệ thống tốt

Ví dụ:

Total requests = 10 triệu/giây
Hit ratio = 99%
Miss = 100.000/giây

Nếu database chỉ chịu được 20.000 QPS, hệ thống vẫn gặp vấn đề.

Ngoài hit ratio, cần biết:

- Absolute miss QPS
- Miss penalty
- Cache latency
- Key distribution
- Database headroom

34. Case study — News feed

Feed có thể cache theo user:

Nhưng invalidation rất khó:

Một creator đăng bài mới
→ Có phải cập nhật cache của 10 triệu follower?

Hai chiến lược lớn:

Fan-out on write:
Khi có post mới, push vào feed của follower.

Fan-out on read:
Khi user mở feed, tổng hợp từ các nguồn.

Cache strategy phụ thuộc vào kiến trúc feed, celebrity problem và freshness requirement.

Điểm cần nhớ:

Cache không thể được thiết kế tách rời access pattern và data flow.

35. Các lỗi caching phổ biến

Lỗi 1: Cache mọi thứ

Cache dữ liệu ít được reuse chỉ làm tốn memory và tăng invalidation complexity.

Lỗi 2: Không có TTL

Một lần invalidation thất bại có thể khiến dữ liệu cũ tồn tại vô hạn.

Lỗi 3: Cùng TTL cho mọi key

Các loại dữ liệu có freshness và access pattern khác nhau.

Lỗi 4: Không thêm TTL jitter

Hàng loạt key cùng expire gây avalanche.

Lỗi 5: Tin cache là source of truth

Cache có thể bị flush, mất key hoặc eviction bất kỳ lúc nào.

Lỗi 6: Không cache negative result

Request cho object không tồn tại liên tục xuyên xuống database.

Lỗi 7: Cache key thiếu context

Bỏ quên user, region, language hoặc permission gây trả sai dữ liệu.

Lỗi 8: Không bảo vệ cache miss

Một hot key expire làm database bị stampede.

Lỗi 9: Chỉ theo dõi hit ratio

Không theo dõi miss QPS, eviction, memory và database load.

Lỗi 10: Cache dữ liệu bảo mật sai cách

Shared cache hoặc CDN vô tình trả dữ liệu riêng tư giữa các user.

41. Những điều phải nhớ sau Bài 6

1. Cache là optimization, không mặc định là source of truth.
2. Cache-aside là chiến lược phổ biến và đơn giản nhất.
3. Với cache-aside, thường update DB trước rồi delete cache.
4. Write-through tăng consistency nhưng làm write chậm hơn.
5. Write-back tăng throughput nhưng có nguy cơ mất dữ liệu.
6. TTL cân bằng freshness và hit ratio.
7. TTL jitter giúp tránh nhiều key expire cùng lúc.
8. Eviction xảy ra do memory giới hạn; LRU và LFU là hai chiến lược phổ biến.
9. Invalidation có thể dùng TTL, event hoặc versioned key.
10. Stampede phải được chống bằng lock/single-flight, stale response hoặc refresh-ahead.
11. Negative caching giúp bảo vệ DB khỏi request dữ liệu không tồn tại.
12. Hot key có thể làm một node quá tải dù cluster còn tài nguyên.
13. Cache key phải chứa đầy đủ user, region, language và các tham số ảnh hưởng response.
14. Không dùng cache để xác nhận cuối cùng cho payment, balance hoặc inventory reservation.
15. Phải theo dõi cả hit ratio, absolute miss QPS, eviction và database load.
