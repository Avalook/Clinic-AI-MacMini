Bài 11 — Observability nền tảng

Khi một hệ thống nhỏ gặp lỗi, ta có thể mở terminal, đọc log và kiểm tra database.

Nhưng trong distributed system, một request có thể đi qua:

CDN
→ API Gateway
→ Authentication Service
→ Order Service
→ Inventory Service
→ Payment Service
→ Message Queue
→ Notification Worker

Nếu user báo:

“Tôi bấm đặt hàng nhưng trang quay 8 giây rồi báo lỗi.”

Ta cần trả lời được:

- Request đã đi qua những service nào?
- Nó chậm ở đâu?
- Service nào trả lỗi đầu tiên?
- Database có chậm không?
- Có retry bao nhiêu lần?
- Payment đã thành công chưa?
- Event có vào queue không?
- Consumer có xử lý chưa?
- Đây là lỗi một user hay toàn hệ thống?

Observability là khả năng hiểu trạng thái bên trong hệ thống thông qua các tín hiệu mà hệ thống phát ra. Nó là phần bắt buộc của một hệ thống production-ready, bên cạnh reliability, scaling, database, caching và load balancing.

Ba tín hiệu nền tảng:

Logs
Metrics
Traces

1. Monitoring và Observability khác nhau thế nào?

Hai khái niệm có liên quan nhưng không hoàn toàn giống nhau.

Monitoring

Monitoring trả lời các câu hỏi đã biết trước:

- CPU có vượt 80% không?
- Error rate có tăng không?
- Database còn hoạt động không?
- Queue backlog có vượt ngưỡng không?

Ta xác định metric và alert từ trước.

Observability

Observability giúp điều tra cả những vấn đề chưa dự đoán trước.

Ví dụ:

Chỉ user dùng phiên bản mobile 7.3,
ở khu vực châu Á,
thanh toán bằng một provider cụ thể,
mới gặp timeout sau khi retry lần hai.

Bạn có thể chưa tạo alert riêng cho trường hợp này, nhưng dữ liệu observability đủ phong phú để điều tra.

Cách nhớ:

Monitoring nói hệ thống có vấn đề. Observability giúp giải thích vì sao.

2. Ba trụ cột: Logs, Metrics và Traces

flowchart TD
    O[Observability] --> L[Logs]
    O --> M[Metrics]
    O --> T[Traces]

    L --> L1[Chi tiết từng sự kiện]
    M --> M1[Xu hướng và số liệu tổng hợp]
    T --> T1[Hành trình request qua nhiều service]

Mỗi loại trả lời một nhóm câu hỏi khác nhau.

3. Logs là gì?

Log là bản ghi về một sự kiện đã xảy ra.

Ví dụ:

Order ord_123 was created.
Payment provider returned timeout.
User user_456 failed authentication.

Log thường có độ chi tiết cao và gắn với một thời điểm cụ thể.

Log dạng text truyền thống

2026-07-11 10:25:13 ERROR Payment failed for order ord_123

Dễ đọc bằng mắt nhưng khó query chính xác.

Structured logging

Tốt hơn là log dưới dạng có cấu trúc, thường là JSON:

{
  "timestamp": "2026-07-11T03:25:13.482Z",
  "level": "ERROR",
  "service": "payment-service",
  "environment": "production",
  "message": "Payment provider timed out",
  "orderId": "ord_123",
  "paymentId": "pay_456",
  "provider": "provider-a",
  "durationMs": 2003,
  "traceId": "trace_7f91",
  "spanId": "span_31ab",
  "errorCode": "PROVIDER_TIMEOUT"
}

Structured logs cho phép query:

service = payment-service
AND errorCode = PROVIDER_TIMEOUT
AND provider = provider-a

Dễ hơn tìm bằng chuỗi tự do.

Nhưng phải tránh log dữ liệu nhạy cảm.

5. Log levels

Các mức phổ biến:

TRACE

Cực kỳ chi tiết.

Entered method X.
Parsed field Y.

Thường chỉ dùng tạm thời hoặc trong môi trường phát triển.

DEBUG

Thông tin giúp debug.

Cache miss for product p_123.
Retry attempt 2 for provider-a.

Production có thể bật có chọn lọc vì volume rất lớn.

INFO

Sự kiện nghiệp vụ hoặc lifecycle bình thường.

Order created.
Worker started.
Configuration loaded.

WARN

Tình huống bất thường nhưng hệ thống vẫn tiếp tục.

Payment provider latency is elevated.
Cache unavailable; falling back to database.

ERROR

Operation thất bại.

Payment failed after retries.
Database transaction rolled back.

FATAL

Application không thể tiếp tục vận hành.

Cannot load mandatory configuration.
Database schema incompatible.

Không nên dùng ERROR cho mọi thứ, vì alert và việc điều tra sẽ bị nhiễu.

6. Event log và debug log

Nên phân biệt:

Business event log

OrderCreated

Có giá trị audit hoặc điều tra nghiệp vụ.

Technical/debug log

Hai loại có retention, quyền truy cập và mục đích khác nhau.

8. Không log toàn bộ request/response mù quáng

Một lỗi phổ biến:

Log toàn bộ request body và response body để dễ debug.

Hậu quả:

- Log volume rất lớn
- Tăng chi phí
- Giảm hiệu năng
- Khó tìm tín hiệu quan trọng

Nên log metadata và field cần thiết:

{

  "requestSizeBytes": 850,
  "statusCode": 503,
  "durationMs": 2100,
  "paymentId": "pay_123"

9. Log aggregation

Trong distributed system, log nằm trên nhiều máy và container.

flowchart TD
    A1[API Server 1] --> Agent1[Log Agent]
    A2[API Server 2] --> Agent2[Log Agent]
    W1[Worker] --> Agent3[Log Agent]

    Agent1 --> Pipeline[Log Pipeline]
    Agent2 --> Pipeline
    Agent3 --> Pipeline

    Pipeline --> Store[(Central Log Store)]
    Store --> Search[Search / Dashboard]

Nếu không aggregate:

Request có thể chạy ở Server 2,
nhưng bạn đang SSH vào Server 1.

Trong môi trường autoscaling, container có thể đã biến mất trước khi bạn kiểm tra.

Do đó logs cần được gửi đến hệ thống tập trung.

10. Log retention

Không phải mọi log cần giữ mãi.

Ví dụ:

Debug logs: 3–7 ngày
Application logs: 14–30 ngày
Security audit logs: lâu hơn theo policy
Financial audit records: theo yêu cầu pháp lý

Retention cần cân bằng:

- Chi phí
- Điều tra sự cố
- Compliance
- Quyền riêng tư

Có thể chuyển log cũ sang object storage rẻ hơn.

11. Log sampling

Hệ thống có 1 triệu request/giây không thể luôn log chi tiết mọi request.

Sampling:

- Log 1% request bình thường
- Log 100% request lỗi
- Log 100% request latency cao
- Log 100% request thuộc canary deployment

Đây là tail-aware hoặc condition-aware sampling ở mức khái niệm.

Không nên sample mất toàn bộ lỗi hiếm.

12. Metrics là gì?

Metric là số liệu được tổng hợp theo thời gian.

Ví dụ:

http_requests_total = 5.000.000
http_errors_total = 20.000
request_duration_p95 = 320 ms
queue_depth = 40.000
cpu_utilization = 72%

Metric không kể toàn bộ câu chuyện của từng request, nhưng rất tốt để thấy:

- Xu hướng
- Spike
- So sánh
- Alert
- Capacity

13. Các loại metric

Counter

Chỉ tăng, thường reset khi process restart.

Ví dụ:

http_requests_total
payment_failures_total
messages_processed_total

Counter phù hợp để tính rate:

Requests per second
Errors per minute

Gauge

Có thể tăng hoặc giảm.

Ví dụ:

current_queue_depth
active_connections
memory_usage_bytes
healthy_instances

Histogram

Phân phối các giá trị theo bucket.

Ví dụ latency:

≤ 50 ms
≤ 100 ms
≤ 250 ms
≤ 500 ms
≤ 1.000 ms

Histogram cho phép tính percentile tổng hợp tốt hơn.

Summary

Theo dõi distribution và percentile phía client/process.

Cách triển khai cụ thể tùy hệ thống metrics. Điều quan trọng là hiểu rằng average không đủ.

14. Average latency có thể đánh lừa

Giả sử:

99 request mất 100 ms
1 request mất 10.000 ms

Average:

(99 × 100 + 10.000) / 100
≈ 199 ms

Average trông chưa quá tệ.

Nhưng một user phải chờ 10 giây.

Do đó cần percentile.

15. p50, p95, p99

p50

50% request nhanh hơn giá trị này.

Gần với trải nghiệm median.

p95

95% request nhanh hơn giá trị này.

5% request chậm hơn.

p99

99% request nhanh hơn giá trị này.

1% request chậm hơn.

Ví dụ:

p50 = 80 ms
p95 = 250 ms
p99 = 1.800 ms

Điều này cho thấy đa số request nhanh nhưng tail latency rất cao.

16. Tail latency

Trong distributed system, tail latency đặc biệt quan trọng.

Giả sử một API gọi song song 20 service và cần chờ tất cả.

Dù mỗi service chỉ có 1% khả năng chậm, xác suất ít nhất một service chậm sẽ tăng khi fan-out lớn.

flowchart TD
    Gateway --> S1[Service 1]
    Gateway --> S2[Service 2]
    Gateway --> S3[Service 3]
    Gateway --> SN[... Service 20]

Một dependency chậm có thể quyết định thời gian toàn request.

Vì vậy cần theo dõi:

p95
p99
p99.9

không chỉ average.

17. Cardinality trong metrics

Metric thường có labels:

http_requests_total{
  service="order",
  method="POST",
  status="200"
}

Labels giúp phân tích.

Nhưng không nên dùng label có vô số giá trị:

userId
orderId
requestId
full URL chứa ID

Ví dụ nguy hiểm:

http_requests_total{userId="user_123"}
http_requests_total{userId="user_124"}
...

Nếu có 100 triệu user, hệ thống metrics phải quản lý 100 triệu time series.

Đây là high cardinality.

Số giá trị hữu hạn:

service

status class

Ví dụ route:

/orders/{orderId}

Không dùng URL cụ thể:

Labels nguy hiểm

19. Metrics cần được chuẩn hóa

Các service nên dùng naming và labels nhất quán.

Không tốt:

Service A: request_time
Service B: api_latency_ms

Tốt hơn:

http_server_request_duration_seconds

Sự nhất quán giúp dashboard và alert tái sử dụng được.

20. Tracing là gì?

Distributed tracing theo dõi hành trình của một request qua nhiều service.

Một trace gồm nhiều span.

flowchart LR
    Client --> G[Gateway span]
    G --> O[Order span]
    O --> I[Inventory span]
    O --> P[Payment span]
    P --> F[Fraud span]

Trace trả lời:

- Request đi qua đâu?
- Mỗi bước mất bao lâu?
- Service nào lỗi?
- Có retry không?
- Call nào diễn ra song song?

21. Trace, Span và Context

Trace

Toàn bộ hành trình của một request hoặc workflow.

traceId = trace_abc

Span

Một đơn vị công việc trong trace.

Ví dụ:

Gateway HTTP request
Order DB query
Payment provider call
Kafka publish

Mỗi span có:

spanId
parentSpanId
start time
duration
status
attributes
events

22. Ví dụ một trace

Trace: checkout request — 1.850 ms

Gateway                      1.850 ms
└── Order Service            1.700 ms
    ├── Inventory Service      180 ms
    ├── PostgreSQL query        45 ms
    └── Payment Service       1.420 ms
        └── Provider API      1.350 ms

Ta thấy bottleneck là payment provider.

Nếu chỉ nhìn Gateway log:

Request took 1.850 ms

ta chưa biết vì sao.

gantt

Trace cho thấy dependency nào chạy tuần tự, song song hoặc chậm.

24. Span attributes

Ví dụ span của database:

{
  "traceId": "trace_abc",
  "spanId": "span_db1",
  "name": "SELECT orders",
  "service": "order-service",
  "durationMs": 42,
  "attributes": {
    "db.system": "postgresql",
    "db.operation": "SELECT",
    "db.table": "orders",
    "region": "asia-southeast"
  }
}

Không nên ghi raw SQL có dữ liệu nhạy cảm nếu không cần.

Có thể dùng normalized statement hoặc operation name.

25. Trace sampling

Tracing mọi request có thể rất đắt.

Sampling strategies:

Head-based sampling

Quyết định sample ngay khi request bắt đầu.

Ví dụ:

Lưu 1% trace.

Đơn giản nhưng có thể bỏ lỡ lỗi hiếm.

Tail-based sampling

Quyết định sau khi trace hoàn tất.

Ưu tiên giữ:

- Trace lỗi
- Trace chậm
- Trace hiếm
- Trace từ canary

Tốn tài nguyên hơn nhưng hữu ích hơn khi điều tra.

26. Async tracing

Trace không dừng ở HTTP.

Khi publish message, phải truyền trace context:

{
  "eventId": "evt_123",
  "traceId": "trace_abc",
  "data": {}
}

Luồng:

sequenceDiagram
    participant API
    participant Broker
    participant Worker
    participant DB

    API->>Broker: Publish event + trace context
    Broker->>Worker: Deliver event
    Worker->>DB: Process

Worker tạo span con hoặc linked span.

Nếu không truyền context, trace sẽ bị đứt tại message queue.

27. Correlation ID là gì?

Correlation ID là một ID dùng để liên kết các sự kiện thuộc cùng một request hoặc workflow.

Ví dụ:

correlationId = order_ord_123

Nó có thể xuất hiện trong:

- API logs
- Queue messages
- Payment logs
- Notification logs

Query correlation ID cho phép tìm toàn bộ workflow.

28. Request ID, Trace ID và Correlation ID

Ba khái niệm có thể khác nhau.

Request ID

Định danh một HTTP request cụ thể.

Nếu client retry, mỗi attempt có thể có request ID khác.

req_1
req_2

Trace ID

Định danh một distributed trace.

Một attempt xuyên nhiều service thường dùng một trace ID.

Correlation ID

Liên kết nhiều request, trace hoặc event thuộc cùng một nghiệp vụ.

Ví dụ một order tồn tại nhiều ngày:

PlaceOrder trace
Payment webhook trace
Shipping event trace
Refund trace

Tất cả có thể dùng:

correlationId = ord_123

29. Ví dụ ID hierarchy

Business workflow:
correlationId = ord_123

HTTP attempt 1:
requestId = req_a
traceId = trace_a

HTTP retry:
requestId = req_b
traceId = trace_b

Payment webhook:
requestId = req_c
traceId = trace_c

Tất cả cùng correlation ID:

ord_123

Điều này giúp điều tra workflow dài hơn một request.

30. Propagate correlation context

Gateway nhận request:

X-Request-ID: req_123
X-Correlation-ID: ord_456

Nếu client không gửi, gateway tạo mới.

Sau đó truyền qua:

HTTP headers
Message headers
Job metadata
Log context
Trace context

Mỗi service không nên tự tạo correlation ID mới, nếu không chuỗi sẽ bị đứt.

31. Không tin hoàn toàn ID từ client

Client có thể gửi:

X-Request-ID rất dài
ký tự độc hại
ID của user khác

Gateway nên:

- Validate format
- Giới hạn độ dài
- Tạo internal ID riêng nếu cần
- Không dùng trực tiếp làm authorization

Correlation ID dùng để theo dõi, không phải bằng chứng quyền truy cập.

32. Logs, Metrics và Traces phối hợp thế nào?

Giả sử alert:

Checkout p99 latency tăng từ 800 ms lên 4 giây.

Bước 1 — Metrics

Xác định:

- Bắt đầu từ lúc nào?
- Region nào?
- Endpoint nào?
- Error rate có tăng không?

Bước 2 — Traces

Lọc trace chậm:

POST /checkout
duration > 3 giây
region = asia

Phát hiện Payment Provider span chiếm 90% thời gian.

Bước 3 — Logs

Dùng traceId từ trace để xem log chi tiết:

Retry attempt
Provider response
Circuit breaker state
Payment ID

Cách nhớ:

Metrics:
Có vấn đề gì và phạm vi bao nhiêu?

Traces:
Vấn đề nằm ở bước nào?

Logs:
Chi tiết chính xác chuyện gì xảy ra?

33. RED Method

RED dùng để quan sát các request-driven services.

R — Rate
E — Errors
D — Duration

Rate

Số request mỗi đơn vị thời gian.

Requests per second
Messages per second
Transactions per minute

Rate tăng có thể là:

- Traffic thật tăng
- Retry storm
- Bot/abuse
- Client bug

Errors

Tỷ lệ request thất bại.

Không chỉ HTTP 5xx.

Có thể gồm:

- Timeout
- Business operation failed
- Circuit breaker rejection
- Invalid response từ dependency
- Message processing failure

Cần phân biệt:

4xx expected client errors
5xx server failures
degraded success

Duration

Thời gian xử lý request.

Nên theo dõi:

p50
p95
p99

theo:

service
route
region
status

Không dùng raw URL hoặc user ID làm label.

34. RED dashboard

Ví dụ cho Order Service:

Rate:
8.200 RPS

Error rate:
0.4%

Duration:
p50 = 90 ms
p95 = 280 ms
p99 = 1.4 s

Một dashboard RED cho từng service giúp phát hiện nhanh:

- Traffic tăng
- Error spike
- Latency regression

35. USE Method

USE phù hợp để quan sát tài nguyên hệ thống.

U — Utilization
S — Saturation
E — Errors

Áp dụng cho:

CPU
Memory
Disk
Network
Thread pool
Connection pool
Queue

Utilization

Phần trăm thời gian hoặc capacity đang được sử dụng.

Ví dụ:

CPU utilization = 85%
Disk utilization = 70%
DB connection usage = 90/100

Saturation

Mức độ công việc đang phải chờ vì tài nguyên không đủ.

Ví dụ:

- CPU run queue
- Thread pool queue
- DB connection waiters
- Disk I/O queue
- Message backlog

CPU 70% chưa chắc có vấn đề, nhưng nếu run queue rất cao thì workload đang chờ.

Errors

Lỗi của resource:

- Disk read errors
- Network packet drops
- Out-of-memory
- Connection acquisition timeout
- Thread rejection

36. RED và USE dùng khi nào?

RED:
Nhìn từ góc độ workload/request.

USE:
Nhìn từ góc độ tài nguyên.

Ví dụ:

RED cho thấy:
Order API p99 latency tăng.

USE cho thấy:
DB connection pool saturation 100%.

Kết nối hai góc nhìn giúp tìm root cause.

37. Golden Signals

Một framework gần RED gồm bốn tín hiệu:

Latency
Traffic
Errors
Saturation

Có thể hiểu:

Traffic ≈ Rate
Latency ≈ Duration
Errors ≈ Errors
Saturation được bổ sung từ góc tài nguyên

Không cần tranh luận framework nào “đúng nhất”. Điều quan trọng là không bỏ sót các tín hiệu chính.

38. SLI, SLO và SLA

SLI — Service Level Indicator

Chỉ số đo thực tế.

Ví dụ:

Tỷ lệ checkout thành công dưới 2 giây.

SLO — Service Level Objective

Mục tiêu nội bộ.

99.9% checkout hoàn tất thành công trong 2 giây mỗi tháng.

SLA — Service Level Agreement

Cam kết với khách hàng, có thể kèm hậu quả tài chính hoặc pháp lý.

39. Availability SLI

Không nên chỉ định nghĩa availability là:

HTTP status != 500

Ví dụ API trả 200 nhưng body:

{
  "success": false,
  "message": "Payment unavailable"
}

Về nghiệp vụ, request vẫn thất bại.

SLI nên phản ánh user outcome:

Successful checkout
Successful login
Message delivered
Video started playing

40. Error budget

SLO 99.9% cho phép 0.1% không đạt.

Error budget = 100% − SLO

Nếu có 10 triệu request/tháng:

0.1% × 10.000.000
= 10.000 request được phép không đạt SLO

Error budget giúp quyết định:

- Có tiếp tục deploy nhanh không?
- Có cần đóng băng release?
- Có cần ưu tiên reliability?

41. Alerting là gì?

Alert là tín hiệu yêu cầu con người hoặc automation chú ý.

Không phải mọi metric bất thường đều nên đánh thức on-call.

Alert tốt phải:

- Có tác động thật
- Có hành động rõ
- Ít nhiễu
- Đúng người
- Đúng mức khẩn cấp

42. Symptom-based và cause-based alert

Cause-based alert

CPU > 80%
Disk usage > 85%

Có thể hữu ích nhưng chưa chắc user bị ảnh hưởng.

Symptom-based alert

Checkout error rate > 2%
Checkout p99 latency > 3 giây

Phản ánh trực tiếp trải nghiệm user hơn.

Nguyên tắc:

Page on-call chủ yếu vì symptom; dùng cause metrics để điều tra.

43. Alert severity

Critical/Page

Cần hành động ngay.

- Payment success rate giảm mạnh
- Database primary unavailable
- Toàn region mất traffic

Warning/Ticket

Cần xử lý nhưng không nhất thiết đánh thức lúc nửa đêm.

- Disk sẽ đầy sau 5 ngày
- Certificate hết hạn sau 20 ngày
- DLQ tăng nhẹ

Informational

Dùng cho dashboard hoặc notification.

Deployment completed
Autoscaling occurred

44. Alert phải actionable

Alert không tốt:

CPU high.

Không nói:

- Service nào?
- Cao bao lâu?
- User có bị ảnh hưởng không?
- Cần làm gì?

Alert tốt:

Order Service p99 latency > 2s for 10 minutes
in Asia region.

Impact:
Checkout requests are timing out.

Likely signals:
DB connection pool saturation is 98%.

Runbook:
<internal runbook reference>

45. Tránh alert flapping

Nếu metric dao động quanh threshold:

79%
81%
79%
82%

alert có thể bật/tắt liên tục.

Giải pháp:

- Threshold duy trì một khoảng thời gian
- Hysteresis
- Separate trigger/recovery threshold
- Alert grouping

Ví dụ:

Trigger:
Error rate > 5% trong 5 phút

Recover:
Error rate < 2% trong 10 phút

46. Multi-window alerting

Spike 30 giây chưa chắc cần page.

Nhưng chờ 30 phút có thể quá chậm.

Có thể dùng hai cửa sổ:

Fast window:
Lỗi rất nghiêm trọng trong vài phút.

Slow window:
Lỗi nhẹ nhưng kéo dài.

Ví dụ:

Page nếu:
Error budget burn rất nhanh trong 5 phút

Hoặc:
Burn chậm nhưng kéo dài 1 giờ

47. Burn rate alert

Burn rate cho biết hệ thống đang tiêu error budget nhanh đến đâu.

Nếu error budget của tháng bị tiêu hết trong vài giờ, cần alert ngay.

Burn rate tốt hơn một threshold lỗi cố định vì nó gắn trực tiếp với SLO.

Khái niệm:

Burn rate = tốc độ tiêu error budget thực tế
            / tốc độ được phép

48. Alert fatigue

Nếu on-call nhận quá nhiều alert không hữu ích:

- Người trực bắt đầu bỏ qua
- Alert quan trọng bị chìm
- Stress tăng
- Phản ứng chậm

Nguyên nhân:

- Alert theo mọi metric
- Threshold quá nhạy
- Không deduplicate
- Một lỗi tạo 100 alert downstream

Cần alert theo root symptom hoặc service boundary phù hợp.

49. Dashboard tốt

Dashboard không nên chỉ là hàng trăm biểu đồ.

Một dashboard service tốt thường có:

1. Traffic
2. Error rate
3. Latency percentiles
4. Saturation
5. Dependency health
6. Deployment markers
7. Regional breakdown
8. SLO/error budget

Nên cho phép đi từ tổng quan xuống chi tiết.

50. Deployment marker

Khi latency tăng lúc 14:05, rất hữu ích nếu dashboard cho thấy:

Version 2.4.1 deployed at 14:03.

flowchart LR
    Deploy[Deploy v2.4.1] --> Errors[Error rate rises]
    Errors --> Rollback[Rollback]

Mọi deployment, config change, feature flag change và failover nên có event trên observability timeline.

51. Business metrics

Technical metrics chưa đủ.

Ví dụ hệ thống vẫn trả 200 nhưng business funnel hỏng.

Cần theo dõi:

- Orders created/minute
- Payment success rate
- Login success rate
- Videos reaching ready state
- Messages delivered
- Upload completion rate

Ví dụ:

HTTP error rate bình thường
nhưng orders/minute giảm 80%.

Có thể frontend, business validation hoặc integration bị lỗi.

52. Synthetic monitoring

Synthetic monitoring tạo request giả định kỳ.

Ví dụ:

1. Mở trang
2. Đăng nhập bằng test account
3. Search sản phẩm
4. Tạo test order

Mục tiêu:

- Kiểm tra end-to-end
- Phát hiện lỗi trước user
- Đo từ nhiều region

Health check chỉ biết service còn sống; synthetic test kiểm tra luồng user thật.

53. Real User Monitoring

RUM thu thập trải nghiệm thật từ browser/mobile:

- Page load time
- API latency từ client
- JavaScript errors
- Crash rate
- Network type
- Device/version

Backend có thể nhanh nhưng user vẫn thấy chậm do:

- Mobile network
- Bundle JavaScript lớn
- Device yếu
- CDN issue

Observability nên bao phủ cả phía client nếu sản phẩm yêu cầu.

54. Profiling

Logs, metrics và traces cho biết request chậm ở service nào.

Profiling giúp biết code bên trong tốn CPU hoặc memory ở đâu.

Ví dụ:

- Function nào dùng nhiều CPU
- Allocation nào tạo nhiều memory
- Lock nào gây contention
- Garbage collection có vấn đề không

Profiling là tín hiệu bổ sung, đặc biệt cho performance investigation.

55. Continuous profiling

Thay vì chỉ profile khi sự cố xảy ra, hệ thống có thể lấy mẫu liên tục với overhead thấp.

Lợi ích:

- So sánh trước và sau deploy
- Tìm CPU regression
- Tìm memory leak
- Phân tích code path nóng

Có thể coi profiling là một trụ quan sát bổ sung bên cạnh logs, metrics và traces.

56. Quy trình debug distributed system

Giả sử nhận alert:

Checkout p99 latency tăng từ 900 ms lên 5 giây.

Không nên bắt đầu bằng việc đọc hàng triệu log ngẫu nhiên.

Dùng quy trình có cấu trúc.

57. Bước 1 — Xác nhận impact

Hỏi:

- User nào bị ảnh hưởng?
- Bao nhiêu phần trăm traffic?
- Region nào?
- Endpoint nào?
- Bắt đầu lúc nào?
- Error hay chỉ chậm?

Kiểm tra business metrics:

Payment success
Orders created
Checkout completion

58. Bước 2 — Kiểm tra thay đổi gần đây

- Deploy mới?
- Config change?
- Feature flag?
- Database migration?
- Traffic campaign?
- Third-party change?

Nếu lỗi bắt đầu đúng sau deployment, đó là tín hiệu mạnh nhưng chưa phải bằng chứng tuyệt đối.

59. Bước 3 — Dùng RED

Kiểm tra từng service:

Ví dụ:

Bình thường

60. Bước 4 — Dùng traces

3.6 giây

2 lần

61. Bước 5 — Dùng logs

Từ trace lấy:

Phát hiện:

62. Bước 6 — Dùng USE cho tài nguyên

Kiểm tra Payment Service:

Memory: bình thường
Thread pool: 95% saturated
Outbound connection pool: 100%

Root cause có thể là outbound provider connections bị giữ quá lâu.

63. Bước 7 — Kiểm tra dependency

provider-a latency tăng

Có thể:

64. Bước 8 — Mitigate trước, root cause sau

Trong incident:

1. Giảm impact
2. Ổn định hệ thống
3. Sau đó điều tra sâu

Mitigation:

- Rollback
- Disable feature flag
- Mở circuit breaker
- Route sang provider khác
- Scale worker
- Giảm traffic
- Serve fallback

Không nên mất 45 phút chứng minh root cause hoàn hảo trong khi user vẫn bị ảnh hưởng.

65. Bước 9 — Xác minh phục hồi

Sau mitigation:

- Error rate giảm chưa?
- p99 latency bình thường chưa?

- Business conversion đã phục hồi chưa?

Không chỉ nhìn CPU.

- Những gì làm tốt

68. MTTR, MTTD và MTBF

MTTD — Mean Time To Detect

Thời gian trung bình từ lúc lỗi bắt đầu đến lúc phát hiện.

MTTR — Mean Time To Recover/Repair

Thời gian trung bình từ lúc sự cố xảy ra hoặc được phát hiện đến lúc phục hồi.

MTBF — Mean Time Between Failures

Thời gian trung bình giữa các lần lỗi.

Observability tốt giúp giảm:

MTTD
MTTR

Nó không nhất thiết làm lỗi không xảy ra, nhưng giúp phát hiện và phục hồi nhanh hơn.

69. Root cause và contributing factors

Một sự cố hiếm khi chỉ có một nguyên nhân.

Ví dụ:

Root cause:
Provider latency tăng.

Contributing factors:
- Timeout quá dài
- Retry ở ba tầng
- Không có circuit breaker
- Outbound connection pool dùng chung
- Alert chỉ dựa trên CPU

Nếu chỉ ghi:

Provider lỗi.

ta bỏ lỡ các điểm có thể cải thiện trong hệ thống của mình.

94. Cách trình bày trong System Design Interview

Không nên chỉ nói:

Em thêm logging và monitoring.

Nên nói:

Mỗi service phát structured logs chứa service, version, traceId, correlationId, business ID và stable error code, nhưng không ghi token hoặc dữ liệu nhạy cảm. Với request-driven service, tôi theo dõi RED: request rate, error rate và p50/p95/p99 latency. Với hạ tầng và resource pool, tôi dùng USE: utilization, saturation và errors. Trace context được propagate qua HTTP headers và message metadata để có thể theo dõi request xuyên gateway, service và asynchronous consumer. Alert nghiêm trọng dựa trên user-facing SLO và error-budget burn rate; CPU hoặc queue depth chủ yếu dùng để chẩn đoán.

Câu trả lời này cho thấy bạn hiểu:

- Signal nào dùng cho việc gì
- Context xuyên service
- Cardinality
- Alerting
- User impact
- Debug process

95. Các sai lầm phổ biến

Lỗi 1: Chỉ có logs, không có metrics

Khó phát hiện xu hướng và alert.

Lỗi 2: Chỉ có metrics, không có context

Biết error tăng nhưng không biết request nào và vì sao.

Lỗi 3: Không có distributed tracing

Mỗi service nói “phía tôi nhanh”, nhưng không biết tổng request chậm ở đâu.

Lỗi 4: Không propagate correlation ID

Log của các service không thể nối với nhau.

Lỗi 5: Log dạng chuỗi không cấu trúc

Khó query và aggregate.

Lỗi 6: Log secrets và dữ liệu cá nhân

Tạo rủi ro bảo mật nghiêm trọng.

Lỗi 7: Metric labels có cardinality quá cao

Dùng userId, orderId hoặc raw URL làm label.

Lỗi 8: Chỉ nhìn average latency

Bỏ qua tail latency.

Lỗi 9: Alert theo mọi metric

Tạo alert fatigue.

Lỗi 10: Alert không có action

On-call không biết phải làm gì.

Lỗi 11: Chỉ alert theo CPU

User có thể gặp lỗi trong khi CPU vẫn thấp.

Lỗi 12: Fallback trả 200 che giấu outage

Không đo degraded success.

Lỗi 13: Telemetry backend làm request chính chậm

Gửi log đồng bộ hoặc block khi collector lỗi.

Lỗi 14: Không ghi deployment/config events

Khó liên hệ regression với thay đổi.

Lỗi 15: DLQ, queue lag hoặc replication lag không có alert

Sự cố âm thầm kéo dài.

98. Những điều phải nhớ sau Bài 11

1. Monitoring phát hiện vấn đề đã biết; observability hỗ trợ điều tra vấn đề chưa biết.
2. Ba tín hiệu chính là logs, metrics và traces.
3. Logs cung cấp chi tiết từng sự kiện.
4. Metrics cho thấy xu hướng, rate và phạm vi.
5. Traces theo dõi request qua nhiều service.
6. Logs nên có cấu trúc, không chỉ là chuỗi text.
7. Không log password, token, secret hoặc dữ liệu nhạy cảm không cần thiết.
8. Correlation ID liên kết các sự kiện thuộc cùng workflow.
9. Request ID thường định danh một attempt.
10. Trace ID định danh một distributed trace.
11. Metrics nên dùng labels có cardinality thấp.
12. User ID, order ID và trace ID không nên là metric labels.
13. Average latency không đủ; phải theo dõi p95 và p99.
14. RED gồm Rate, Errors và Duration.
15. USE gồm Utilization, Saturation và Errors.
16. RED nhìn từ request; USE nhìn từ tài nguyên.
17. Alert quan trọng nên dựa trên user impact và SLO.
18. CPU cao không luôn đồng nghĩa user đang bị ảnh hưởng.
19. Fallback thành công phải được ghi nhận là degraded success.
20. Deployment và config changes phải xuất hiện trên timeline.
21. Async message cần propagate trace/correlation context.
22. Sampling phải ưu tiên giữ lỗi và trace chậm.
23. Telemetry pipeline lỗi không nên làm request chính thất bại.
24. Debug nên đi từ impact → metrics → traces → logs → resources.
25. Observability tốt giúp giảm MTTD và MTTR.
