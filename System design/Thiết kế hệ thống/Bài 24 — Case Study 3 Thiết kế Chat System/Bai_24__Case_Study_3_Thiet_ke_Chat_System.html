Bài 24 — Case Study 3: Thiết kế Chat System

Một hệ thống chat hiện đại cần hỗ trợ:

- Nhắn tin 1-1
- Group chat
- Kết nối realtime
- Gửi khi người nhận offline
- Đồng bộ nhiều thiết bị
- Trạng thái online/offline
- Typing indicator
- Delivered/read receipts
- Ảnh, video và file
- Chỉnh sửa, thu hồi và reaction
- Push notification
- Hoạt động xuyên nhiều region

Bề ngoài, chat có vẻ chỉ là:

User A gửi message
→ User B nhận message

Nhưng ở quy mô lớn, hệ thống phải giải quyết:

- Hàng triệu kết nối giữ lâu
- Connection có thể mất bất kỳ lúc nào
- Message có thể bị retry và duplicate
- Người dùng có nhiều thiết bị
- Các message có thể đến sai thứ tự
- Thành viên group thay đổi liên tục
- Người nhận có thể offline nhiều tháng
- Một group có thể có hàng triệu thành viên
- Region hoặc network có thể bị chia cắt

1. Xác định phạm vi

Trong case study này, ta thiết kế một hệ thống chat tổng quát hỗ trợ:

1. Chat 1-1.
2. Group chat.
3. WebSocket realtime.
4. Offline delivery và sync.
5. Presence và typing.
6. Delivered/read receipts.
7. Multi-device.
8. Media messages.
9. Push notification.
10. Multi-region.

Tạm thời không đi sâu vào:

- Voice/video call realtime
- End-to-end encryption protocol hoàn chỉnh
- Livestream
- Public social feed
- Full-text search chuyên sâu

2. Functional Requirements

Messaging

- Gửi text message
- Gửi media/file
- Nhận message realtime
- Retry khi mất kết nối
- Chỉnh sửa hoặc thu hồi message
- Reaction

Conversation

- Tạo conversation 1-1
- Tạo group
- Thêm/xóa thành viên
- Phân quyền admin/member
- Rời group

State

- Online/offline
- Last seen
- Typing
- Delivered
- Read
- Unread count

Synchronization

- Đồng bộ lịch sử khi login
- Đồng bộ nhiều thiết bị
- Tiếp tục từ cursor cũ
- Khôi phục sau khi offline

3. Non-Functional Requirements

- Latency gửi message thấp
- Không làm mất message đã được server xác nhận
- Không tạo duplicate message logic
- Giữ ordering trong cùng conversation
- Availability cao
- Có thể scale hàng triệu concurrent connections
- Hỗ trợ hot conversations
- Eventual consistency chấp nhận được cho presence và receipts
- Dữ liệu được mã hóa khi truyền và khi lưu

4. Điều gì cần Strong Consistency?

Không phải toàn hệ thống cần cùng consistency.

Cần mạnh hơn

- Message ID uniqueness
- Conversation sequence
- Membership authorization lúc gửi
- Không cho user ngoài group đọc message
- Message durable trước khi trả accepted

Có thể eventual

- Presence
- Typing indicator
- Read receipt
- Unread count
- Search index
- Analytics

Điều này giúp tránh coordination không cần thiết.

5. Các trạng thái Message

Cần phân biệt:

CREATED_LOCALLY
SENT_TO_SERVER
SERVER_ACCEPTED
DELIVERED_TO_DEVICE
READ_BY_USER

Một dấu tick không nên mang nghĩa mơ hồ.

Ví dụ:

Một tick:
Server đã lưu bền vững.

Hai tick:
Ít nhất một thiết bị người nhận đã nhận.

Hai tick màu:
Người nhận đã đọc.

Semantics cụ thể là quyết định sản phẩm.

6. Capacity Estimation

Giả sử:

100 triệu DAU
10 triệu concurrent connections
50 messages/user/ngày

Tổng message/ngày:

100 triệu × 50
= 5 tỷ messages/ngày

Average message write rate:

5.000.000.000 / 86.400
≈ 58.000 messages/giây

Peak gấp 5–10 lần:

300.000–600.000 messages/giây

Chưa tính:

- Delivery fan-out
- Receipts
- Typing events
- Presence heartbeats

7. Connection Scale

Giả sử 10 triệu WebSocket connections.

Nếu mỗi gateway giữ 100.000 connections:

10.000.000 / 100.000
= khoảng 100 gateway instances

Trong thực tế cần dư capacity cho:

- Failover
- Rebalancing
- Traffic skew
- Maintenance

Có thể cần hàng trăm instances.

8. Storage Estimation

Giả sử message metadata và text trung bình:

500 byte/message

5 tỷ messages/ngày:

≈ 2,5 TB raw/ngày

Trong một năm:

≈ 912 TB raw

Sau replication, indexes và overhead:

Có thể lên nhiều petabyte.

Media không nên được lưu trực tiếp trong message database.

10. Tách Connection Layer khỏi Message Layer

WebSocket Gateway chịu trách nhiệm:

- Giữ connection
- Authenticate connection
- Nhận frame
- Gửi frame
- Heartbeat
- Backpressure

Chat Service chịu trách nhiệm:

- Validate membership
- Deduplicate
- Cấp sequence
- Lưu message
- Publish event

Không nên đặt toàn bộ business logic trong WebSocket Gateway.

Gateway nên tương đối stateless ngoài connection state.

11. WebSocket là gì?

WebSocket tạo kết nối hai chiều lâu dài:

Client ↔ Server

Sau HTTP handshake, hai phía có thể chủ động gửi frame.

Phù hợp chat vì:

- Server push message ngay
- Không polling liên tục
- Overhead thấp hơn tạo HTTP request cho mỗi event
- Hỗ trợ bidirectional communication

12. Vì sao không chỉ dùng HTTP Polling?

Polling:

Mỗi vài giây:
Client hỏi “có message mới không?”

Nhược điểm:

- Nhiều request rỗng
- Latency phụ thuộc polling interval
- Tốn connection và CPU
- Không phù hợp typing/presence realtime

Long polling tốt hơn polling thường nhưng vẫn phức tạp hơn WebSocket cho tương tác hai chiều liên tục.

13. SSE có phù hợp không?

Server-Sent Events hỗ trợ:

Server → Client

Nhưng client gửi message vẫn qua HTTP riêng.

SSE có thể phù hợp cho notification một chiều.

Chat cần:

Client ↔ Server

nên WebSocket thường tự nhiên hơn.

14. WebSocket Handshake

sequenceDiagram

    Client->>Gateway: HTTP Upgrade + access token
    Gateway->>Auth: Validate token
    Auth-->>Gateway: userId, session claims

Gateway gắn connection với:

userId

sessionId
region
connectionId

15. Authentication trên Connection dài

Access token có thể hết hạn trong khi WebSocket vẫn mở.

Các lựa chọn:

- Đóng connection khi token hết hạn
- Yêu cầu client refresh authentication
- Cho session tồn tại theo policy riêng

Gateway phải xử lý:

- Token revoked
- Account disabled
- Device logout

Không nên coi authentication tại handshake là hợp lệ vĩnh viễn.

16. Heartbeat

Connection có thể chết mà TCP chưa báo ngay.

Dùng heartbeat:

Client → ping
Server → pong

hoặc ngược lại.

Ví dụ:

Heartbeat mỗi 30 giây
Timeout sau 90 giây không phản hồi

Các con số phụ thuộc mobile network và battery trade-off.

17. Connection Registry

Cần biết user đang kết nối tới gateway nào.

userId
→ [
    {deviceId, gatewayId, connectionId},
    ...
  ]

Có thể lưu:

- Memory trong gateway
- Distributed registry
- Sharded presence service

Registry dùng để route message realtime.

18. Registry không nên là Global Hot Database

Mỗi connect/disconnect đều update registry.

Với hàng triệu connections, nếu mọi update đi một database trung tâm:

- Write bottleneck
- High latency
- Single failure domain

Có thể partition theo:

hash(userId)

và dùng TTL/lease.

19. Connection Lease

Gateway đăng ký:

connectionId
gatewayId
expiresAt

Heartbeat gia hạn lease.

Nếu gateway chết:

Lease hết hạn
→ Connection được coi offline

Không cần tin hoàn toàn vào disconnect event, vì process có thể chết đột ngột.

20. User có nhiều Connection

Một user có thể:

- Điện thoại
- Tablet
- Laptop
- Nhiều browser tabs

Registry phải hỗ trợ:

userId → nhiều active connections

Khi gửi message cho user:

Có thể fan-out tới mọi thiết bị active.

21. Protocol Frame

Client gửi:

{
  "type": "SEND_MESSAGE",
  "requestId": "req_123",
  "conversationId": "conv_456",
  "clientMessageId": "deviceA_789",
  "content": {
    "type": "TEXT",
    "text": "Xin chào"
  }
}

Server trả:

{
  "type": "MESSAGE_ACCEPTED",
  "requestId": "req_123",
  "clientMessageId": "deviceA_789",
  "messageId": "msg_01J...",
  "conversationSequence": 10542,
  "acceptedAt": "2026-07-14T03:00:00Z"
}

22. requestId, clientMessageId và messageId

requestId

Theo dõi một request transport cụ thể.

clientMessageId

ID ổn định do client tạo cho một logical message.

Dùng để deduplicate retry.

messageId

ID authoritative do server cấp.

Dùng trong storage và API.

Không nên dùng request ID thay client message ID vì request retry có thể có request ID mới.

23. Gửi Message — Client Side

Client nên:

1. Tạo clientMessageId.
2. Lưu message local ở trạng thái pending.
3. Gửi frame.
4. Nếu timeout, retry cùng clientMessageId.
5. Khi server ACK, map sang messageId và sequence.

UI có thể hiển thị:

Đồng hồ → đang gửi
Một tick → server accepted

24. Send Message Flow

sequenceDiagram
    participant Sender
    participant Gateway
    participant Chat
    participant Store
    participant Stream
    participant Delivery
    participant Receiver

    Sender->>Gateway: SEND_MESSAGE
    Gateway->>Chat: Forward authenticated command
    Chat->>Chat: Validate membership + dedupe
    Chat->>Store: Persist message + sequence
    Store-->>Chat: Committed
    Chat->>Stream: Publish MessageCreated
    Chat-->>Gateway: MESSAGE_ACCEPTED
    Gateway-->>Sender: ACK

    Stream->>Delivery: MessageCreated
    Delivery->>Receiver: Deliver realtime

Server chỉ trả MESSAGE_ACCEPTED sau khi message đã durable.

25. Dual-Write Problem

Nếu Chat Service:

1. Ghi Message Store.
2. Publish event.

và crash giữa hai bước:

Message đã lưu
nhưng Delivery Service không biết.

Nếu publish trước rồi DB fail:

Người nhận thấy message không tồn tại authoritative.

Cần:

- Transactional outbox
- Database change stream
- Log-based message store

26. Transactional Outbox cho Chat

Trong cùng transaction:

- Insert message
- Insert outbox event

Publisher sau đó đưa event vào stream.

Nếu publisher crash:

Outbox vẫn còn
→ Retry.

Event có thể duplicate, nên downstream phải idempotent.

27. Message ID Generation

Message ID cần:

- Unique toàn hệ thống
- Sinh nhanh
- Không phụ thuộc database central sequence

Có thể dùng:

- Snowflake-like ID
- Time-sortable random ID
- UUID

Message ordering không nên chỉ dựa vào message ID nếu nhiều workers hoặc regions có clock lệch.

28. Ordering Requirement

Phần lớn chat cần:

Message trong cùng conversation có một thứ tự ổn định.

Không cần global order giữa:

Conversation A
và
Conversation B

Do đó ordering scope là:

conversationId

29. Conversation Sequence

Mỗi conversation có sequence tăng dần:

Message 1 → sequence 1001
Message 2 → sequence 1002
Message 3 → sequence 1003

Key:

(conversationId, sequence)

Lợi ích:

- Stable ordering
- Detect gaps
- Offline sync
- Cursor pagination
- Read receipts

30. Sequence phải được cấp Atomically

Hai sender cùng gửi:

User A gửi M1
User B gửi M2

Nếu cả hai đọc current sequence 100 rồi cùng tạo 101:

Collision.

Cần:

- Conversation leader/sequencer
- Atomic counter
- Compare-and-set
- Transactional append log

31. Conversation Owner

Có thể route mọi write của một conversation tới một owner shard.

ownerShard = hash(conversationId)

Owner chịu trách nhiệm:

- Validate write
- Cấp sequence
- Append message

Như vậy ordering per conversation được serialize tại owner.

32. Có cần một Worker cho mỗi Conversation?

Không.

Một shard xử lý nhiều conversations:

Shard 1:
conv_1, conv_5, conv_20...

Shard 2:
conv_2, conv_8...

Chỉ cần đảm bảo events cùng conversation được xử lý tuần tự hoặc atomic append đúng.

33. Message Store Data Model

Có thể lưu:

Partition key:
conversationId

Clustering key:
sequence

Record:

{
  "conversationId": "conv_456",
  "sequence": 10542,
  "messageId": "msg_01J...",
  "senderId": "u_123",
  "messageType": "TEXT",
  "content": {
    "text": "Xin chào"
  },
  "createdAt": "2026-07-14T03:00:00Z",
  "status": "ACTIVE",
  "version": 1
}

34. Vì sao Partition theo conversationId?

Access pattern phổ biến:

- Lấy message mới nhất trong conversation
- Lấy messages sau sequence X
- Lấy một page trước sequence Y

Partition theo conversation giúp dữ liệu cùng cuộc trò chuyện nằm gần nhau.

Nhưng conversation cực lớn có thể tạo partition rất lớn.

35. Bucket Partition cho Conversation lớn

Có thể dùng:

partitionKey = conversationId + bucketId

Ví dụ bucket mỗi 100.000 messages:

conv_456:bucket_0
conv_456:bucket_1

Sequence vẫn toàn conversation.

Directory lưu:

sequence 0–99.999 → bucket 0
sequence 100.000–199.999 → bucket 1

36. Hot Conversation

Một livestream chat hoặc group lớn có thể nhận hàng trăm nghìn messages/giây.

Một owner shard có thể quá tải.

Các lựa chọn:

- Rate limiting
- Tách public chat khỏi private chat architecture
- Partition write lanes
- Relax total ordering
- Hierarchical aggregation

Strong total order cho một conversation siêu lớn có giới hạn throughput tự nhiên.

37. Chat 1-1 Conversation

Một cặp user chỉ nên có một conversation logic.

Có thể tạo deterministic key:

min(userA, userB) + max(userA, userB)

Nhưng cần lưu ý:

- Block/unblock
- Xóa conversation cá nhân
- Multi-account semantics

Có thể dùng unique constraint trên participant pair.

38. Group Conversation

Group metadata:

conversationId
type = GROUP
title
avatar
createdBy
createdAt
membershipVersion

Membership:

conversationId
userId
role
joinedAtSequence
leftAtSequence
status

joinedAtSequence giúp xác định user được phép đọc từ thời điểm nào.

39. Membership Authorization lúc Gửi

Khi user gửi message, Chat Service phải kiểm tra:

- User là active member?
- User có bị muted/banned?
- Group có read-only?
- User có quyền gửi loại media này?

Không nên dựa vào membership cache stale quá lâu cho authorization.

Có thể dùng versioned cache và authoritative fallback.

40. Membership Authorization lúc Đọc

User không nên đọc message trước khi tham gia nếu policy không cho phép.

Có thể kiểm tra:

message.sequence >= joinedAtSequence

Khi user rời group:

Có được đọc lịch sử cũ không?

Đây là product policy.

41. Membership Version

Mỗi thay đổi thành viên tăng:

membershipVersion

Message command có thể được xử lý với membership state mới nhất.

Delivery event có thể chứa:

membershipVersionAtSend

để fan-out dùng snapshot phù hợp.

42. Race giữa Remove Member và Send Message

Ví dụ:

1. Admin remove User B.
2. User A gửi message gần như đồng thời.

Cần định nghĩa ordering.

Nếu remove có conversation sequence hoặc membership version:

MemberRemoved sequence 500
Message sequence 501

User B không được nhận message 501.

Nếu Message 499:

Có thể vẫn được nhận theo policy.

43. Conversation Event Log

Không chỉ message, conversation có thể có events:

MESSAGE_CREATED
MEMBER_ADDED
MEMBER_REMOVED
TITLE_CHANGED
MESSAGE_DELETED

Một sequence chung cho conversation giúp client reconstruct timeline ổn định.

Tuy nhiên có thể tách metadata version và message sequence nếu muốn giảm contention.

44. Delivery Service

Delivery Service nhận MessageCreated và quyết định:

- Những user nào cần nhận?
- Những devices nào đang online?
- Gửi qua gateway nào?
- Có cần push notification không?

Delivery không quyết định message có hợp lệ; message đã được Chat Service commit.

45. Fan-Out cho Chat 1-1

Đơn giản:

Sender
Recipient

Message thường được gửi:

- Tới mọi thiết bị người nhận
- Tới các thiết bị khác của sender để đồng bộ

Nếu sender gửi từ điện thoại, laptop của sender cũng phải thấy message mới.

46. Fan-Out cho Group nhỏ

Group 20 người:

Một MessageCreated event
→ Tìm 20 members
→ Route tới online devices

Có thể fan-out on write.

Chi phí hợp lý.

47. Fan-Out cho Group lớn

Group một triệu thành viên:

Một message
→ Một triệu delivery jobs

Không hợp lý.

Các lựa chọn:

- Fan-out on read
- Hybrid fan-out
- Chỉ realtime tới active members
- Offline users sync từ shared conversation log

48. Hybrid Group Delivery

Với group lớn:

Online members:
Push realtime.

Offline members:
Không tạo một delivery row riêng;
khi online, sync từ conversation sequence.

Push notification chỉ gửi theo policy và frequency cap.

Điều này giảm write amplification.

49. Per-User Inbox hay Shared Conversation Log?

Per-user inbox

Mỗi message được copy vào inbox từng user.

Ưu điểm:

- Sync theo user nhanh
- Unread dễ tính

Nhược điểm:

- Group lớn tạo write amplification

Shared conversation log

Message chỉ lưu một lần.

User giữ cursor per conversation.

Ưu điểm:

- Storage hiệu quả

Nhược điểm:

- Sync nhiều conversations phức tạp hơn

Hệ thống có thể dùng hybrid.

51. Delivered Receipt

Khi client nhận và lưu message local:

{
  "type": "DELIVERY_ACK",
  "conversationId": "conv_456",
  "upToSequence": 10542,
  "deviceId": "device_B"
}

Dùng cumulative ACK:

Đã nhận tất cả message tới sequence 10542.

Tốt hơn ACK từng message ở traffic cao.

52. Delivered tới Device hay User?

Có hai semantics:

Device delivered:
Một thiết bị nhận.

User delivered:
Ít nhất một thiết bị của user nhận.

UI thường chỉ cần:

Recipient user đã nhận trên ít nhất một device.

Backend có thể giữ trạng thái per-device ngắn hạn nhưng aggregate per-user.

53. Read Receipt

Client gửi:

{
  "type": "READ_ACK",
  "conversationId": "conv_456",
  "upToSequence": 10540
}

Đây là cumulative read cursor.

Không cần gửi:

Message 1 read
Message 2 read
...

54. Read Receipt per User

Store:

(conversationId, userId)
→ lastReadSequence

Unread count xấp xỉ:

conversationLatestSequence - lastReadSequence

Nhưng system events hoặc messages bị xóa có thể làm công thức không hoàn toàn chính xác.

Có thể dùng unread message counter riêng hoặc chấp nhận approximation.

55. Read Receipt trong Group

Hiển thị “đã đọc bởi 10 người” có thể đắt với group lớn.

Có thể:

- Chỉ hỗ trợ group nhỏ
- Hiển thị count
- Không hiển thị danh sách đầy đủ
- Chỉ hiển thị tới một giới hạn

Không nên update một hot message row mỗi lần một user đọc.

56. Read Receipt Event Stream

Read cursor updates có thể rất nhiều.

Có thể:

- Coalesce tại client
- Chỉ gửi khi cursor tăng đáng kể
- Debounce
- Lưu latest value, không append mọi event lâu dài

Read cursor là state mới nhất, không nhất thiết cần toàn bộ lịch sử.

Thiếu 101.

2. Gọi sync sau sequence 100.
3. Nhận 101.
4. Apply 101 rồi 102.

99. Ordering và Delivery là hai vấn đề khác nhau

M2 sequence 101

Nhưng network khiến client nhận:

101 trước 100

Ordering trong storage không tự động bảo đảm arrival order.

Client phải reorder theo sequence và fetch gaps.

100. Created Time không dùng làm Ordering Authoritative

Hai senders có clock khác nhau.

M1 client time = 10:00:02
M2 client time = 10:00:01

Không thể dùng client timestamp để order.

Server sequence là authoritative.

Client timestamp chỉ dùng cho UX hoặc debug.

101. Server Timestamp cũng chưa đủ

Hai Chat Service instances có clock skew.

Message được commit theo order:

M1 rồi M2

nhưng timestamps có thể đảo.

Vì vậy:

conversationSequence

quan trọng hơn wall-clock timestamp.

102. Message ACK Semantics

Khi server trả ACCEPTED, cần định nghĩa:

- Đã ghi vào durable log?
- Đã replicate tới quorum?
- Chỉ nằm memory?

Một contract tốt:

SERVER_ACCEPTED nghĩa là message đã được lưu bền vững theo durability policy và sẽ được retry delivery ngay cả khi gateway hiện tại chết.

103. Quorum và Message Durability

Nếu Message Store replicate ba nodes:

Có thể trả accepted sau majority ACK.

Trade-off:

- Durability cao
- Latency cao hơn

Nếu chỉ local ACK rồi async replicate:

Region/node failure có thể làm mất message đã báo accepted.

104. Delivery Retry

Delivery Service gửi frame tới Gateway.

Nếu Gateway không ACK:

- Connection có thể chết
- Frame có thể đã tới client
- ACK có thể mất

Có thể retry cùng message ID.

Client dedupe.

Không cần exactly-once transport.

105. Push và Realtime Race

Recipient vừa reconnect.

Delivery Service có thể:

- Gửi WebSocket
- Đồng thời Notification Service gửi push

User thấy push thừa.

Có thể giảm bằng grace period:

Chờ vài giây để xem realtime delivery ACK.

Nhưng làm push chậm.

Đây là UX trade-off, không phải correctness issue.

121. Có nên Multi-Leader theo Conversation?

Với private chat cần ordering ổn định, thường không nên.

Toàn hệ thống vẫn active–active:

- Conversation 1 owner Region A
- Conversation 2 owner Region B
- Conversation 3 owner Region C

Mỗi conversation có một owner, nhưng nhiều regions cùng sở hữu các conversations khác nhau.

Đây là partitioned active–active.

123. Replication của Message Store

Có thể:

- Synchronous replication sang remote region
- Asynchronous replication

Synchronous

RPO gần 0
nhưng write latency cao.

Asynchronous

Latency thấp hơn
nhưng regional failure có thể mất accepted messages.

Durability contract phải nói rõ.

124. Multi-Region Quorum

Có thể dùng consensus group per shard:

Replica A ở Region 1
Replica B ở Region 2
Replica C ở Region 3

Commit majority 2/3.

Ưu điểm:

- Chịu mất một region
- Strong ordering

Nhược điểm:

- Mỗi write chịu WAN latency

Có thể chỉ dùng cho metadata/critical tenants hoặc đặt replicas theo latency topology phù hợp.

125. Regional Failover

Nếu conversation home region chết:

1. Phát hiện owner unavailable.
2. Xác định replica đủ mới.
3. Tăng owner epoch.
4. Promote region mới.
5. Update directory.
6. Fence owner cũ.
7. Resume sequence từ committed log.

Không chỉ đổi traffic routing.

126. Owner Epoch và Fencing

Old owner:

epoch 41

New owner:

epoch 42

Store chỉ nhận append từ epoch mới nhất.

Nếu old owner quay lại:

Append epoch 41
→ Rejected.

Ngăn split-brain.

127. Message Gap sau Failover

Nếu async replication:

Old owner đã ACK message 1005
Replica mới chỉ có tới 1003

Sau failover:

1004–1005 có thể mất.

Không nên tái sử dụng sequence 1004 ngay nếu client đã thấy nó.

Có thể:

- Giữ gaps
- Reconcile từ sender retry
- Dùng globally unique message IDs

RPO phải được xác định trước.

128. Sender Retry sau Failover

Sender chưa nhận ACK hoặc thấy message mất.

Retry cùng:

clientMessageId

New owner dedupe và có thể tái tạo message.

Nếu old message đã replicate, trả record cũ.

Nếu chưa tồn tại, tạo message mới.

129. Conversation Migration

Chuyển conversation owner từ Region A sang B:

1. Chọn cutover sequence.
2. Replicate log tới B.
3. Tạm dừng hoặc buffer writes.
4. Tăng owner epoch.
5. Update directory.
6. Resume writes tại B.
7. Fence A.

Với low traffic conversation có thể migrate nhanh.

Hot conversation cần protocol phức tạp hơn.

130. Presence Multi-Region

Presence nên local-first.

User kết nối Region A:

Presence authoritative tạm thời ở A.

Regions khác có thể nhận replicated presence eventual.

132. Registry Staleness

Global registry có thể nói user online Region A nhưng connection đã chết.

Delivery tới A fail.

Hệ thống:

- Không làm mất message
- Có thể thử region khác
- Recipient sẽ offline sync
- Push notification fallback

Presence/registry stale không phá message durability.

139. Failure Mode — Gateway chết

Connections trên gateway mất.

Clients reconnect sang gateways khác.

Không mất message vì:

- Message Store durable
- Client giữ pending messages
- Offline sync khôi phục missing messages

Registry leases hết hạn tự động.

140. Failure Mode — Connection Registry lỗi

Gateway vẫn biết local connections.

Có thể:

- Realtime routing bị giảm
- Message vẫn lưu
- Push/offline sync bù

Registry nên được xem là routing optimization, không phải source of truth cho message.

141. Failure Mode — Message Store chậm

Không nên ACK message trước durability.

Có thể:

- Backpressure senders
- Rate limit
- Queue commands ngắn hạn nếu semantics rõ
- Trả retryable error

Không nên silently accept rồi làm mất.

142. Failure Mode — Event Stream lỗi

Nếu dùng outbox:

Messages vẫn được lưu.
Delivery bị trễ.
Outbox publisher retry khi stream phục hồi.

Sender nhận accepted vì message durable.

Recipient sẽ nhận muộn hoặc sync sau.

143. Failure Mode — Delivery Service lỗi

Message không mất.

Event stream giữ backlog.

Khi workers phục hồi:

Replay MessageCreated
→ Deliver.

Client dedupe duplicate.

144. Failure Mode — Push Provider lỗi

Realtime chat vẫn hoạt động.

Offline users không nhận push tạm thời nhưng message vẫn chờ trong Message Store.

Push Service retry theo TTL.

Không gửi push cũ nếu message đã quá thời gian hữu ích.

145. Failure Mode — Media Processor lỗi

Text chat không bị ảnh hưởng.

Media ở trạng thái:

PROCESSING hoặc FAILED

Client có thể retry upload.

Không nên block toàn conversation.

148. Thiết kế Khuyến nghị

Một thiết kế cân bằng:

1. WebSocket Gateways chỉ giữ connection và chuyển frame.
2. Chat Service sở hữu validation, dedupe và durable append.
3. Mỗi conversation có sequence và một owner shard.
4. Message Store partition theo conversation, bucket khi lớn.
5. Outbox phát MessageCreated tới delivery stream.
6. Delivery Service route tới mọi active device và push khi cần.
7. Offline clients sync bằng cursor và sequence.
8. Presence/typing là ephemeral và eventual consistent.
9. Media upload trực tiếp Object Storage.

149. Trade-Off — Per-User Inbox hay Shared Log

Per-user inbox

Ưu:
Sync nhanh, unread dễ.

Nhược:
Write amplification cho group lớn.

Shared conversation log

Ưu:
Lưu message một lần.

Nhược:
Sync toàn user phức tạp hơn.

Khuyến nghị:

Chat 1-1 và group nhỏ:
Có thể materialize inbox.

Group lớn:
Shared log + online fan-out.

150. Trade-Off — Strong Ordering hay Throughput

Single sequence per conversation:

- UX ổn định
- Logic dễ
- Throughput giới hạn bởi owner

Relaxed ordering:

- Scale tốt hơn
- Client merge phức tạp
- User thấy reorder

Private chat thường ưu tiên stable per-conversation ordering.

Public massive chat có thể dùng weaker ordering.

151. Trade-Off — Sync Cross-Region hay Async

Synchronous

Không mất acknowledged messages khi mất region,
nhưng latency cao.

Asynchronous

Latency thấp,
nhưng có RPO lớn hơn 0.

Có thể cung cấp tier khác nhau cho:

Consumer chat
Enterprise/compliance chat

152. Trade-Off — Presence Push hay Query

Push mọi presence change:

Fresh nhưng fan-out lớn.

Query khi cần:

Scale tốt nhưng không realtime tuyệt đối.

Hybrid:

Subscribe presence cho contacts/conversations đang hiển thị.

153. Trade-Off — Push ngay hay Chờ Delivery ACK

Push ngay:

Offline user được báo nhanh
nhưng online user có thể nhận push thừa.

Chờ vài giây:

Giảm push thừa
nhưng notification chậm hơn.

Có thể áp policy theo app state và message priority.

154. Cách trình bày trong Phỏng vấn

Một câu trả lời tốt có thể bắt đầu:

Tôi tách connection layer khỏi message layer. WebSocket Gateways giữ hàng triệu long-lived connections và quản lý heartbeat, nhưng mọi message command được chuyển tới Chat Service để kiểm tra membership, deduplicate bằng clientMessageId, cấp sequence theo conversation và lưu bền vững.

Về ordering:

Tôi không cần global ordering. Mỗi conversation có một owner shard và sequence tăng dần. Message Store được partition theo conversationId, còn conversation lớn được chia thêm theo sequence bucket. Client dùng sequence để phát hiện gap và reorder các frame đến sai thứ tự.

Về delivery:

Sau khi message và outbox event cùng commit, Delivery Service route message tới mọi active device của recipient và các thiết bị khác của sender. Nếu user offline, message không nằm chờ trong memory queue mà vẫn ở shared conversation log; client lấy lại bằng offline sync cursor. Transport là at-least-once và cả server lẫn client đều deduplicate bằng message ID.

Về multi-region:

Client kết nối region gần nhất nhưng mỗi conversation có một home region để giữ sequence và write ownership. Toàn hệ thống vẫn active–active vì conversations khác nhau có owners ở các regions khác nhau. Regional failover tăng owner epoch và fence owner cũ để tránh split-brain.
