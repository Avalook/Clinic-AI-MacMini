Bài 32 — Case Study 11: Thiết kế Cloud File Storage như Google Drive/Dropbox

Cloud File Storage cho phép người dùng:

Tải file lên
→ Lưu trữ an toàn
→ Sắp xếp trong thư mục
→ Đồng bộ nhiều thiết bị
→ Chia sẻ với người khác
→ Chỉnh sửa offline
→ Khôi phục phiên bản cũ

Bề ngoài, hệ thống giống một object storage có giao diện thư mục. Nhưng production system còn phải xử lý:

- File từ vài byte đến hàng trăm GB
- Upload mạng yếu và resume sau khi gián đoạn
- Nhiều thiết bị sửa cùng một file
- Rename, move và delete khi thiết bị đang offline
- Đồng bộ hàng triệu thay đổi mà không quét toàn bộ thư mục
- Chia sẻ file và folder với quyền kế thừa
- Version history
- Deduplication nhưng không làm rò rỉ thông tin
- Virus scanning và content moderation
- Multi-region, data residency và disaster recovery

Kiến trúc cốt lõi:

Metadata control plane
+
File content data plane
+
Change log và synchronization engine

3. Non-Functional Requirements

- File content đã commit không được mất.
- Upload lớn phải resume được.
- Download latency thấp toàn cầu.
- Metadata operations phải nhất quán.
- Đồng bộ không được bỏ sót thay đổi.
- Duplicate events không tạo duplicate file versions.
- Permission revocation phải có hiệu lực nhanh.
- Hệ thống chịu được hot shared folders.
- Có thể phục hồi file đã xóa.
- Multi-region không tạo split-brain metadata.

6. Capacity Estimation

Giả sử:

500 triệu users
100 triệu DAU
20 triệu file uploads/ngày
Average file size = 20 MB
1 tỷ metadata operations/ngày

Upload data/ngày:

20.000.000 × 20 MB
= 400 TB/ngày

Nếu replication factor là 3:

≈ 1,2 PB/ngày

chưa tính:

- Version history
- Thumbnails
- Backups
- Erasure coding overhead

Một tỷ metadata operations/ngày:

Peak có thể:

100.000+ QPS

Operations gồm:

File transfer bandwidth thường lớn hơn metadata traffic nhiều lần.

16. Upload Session State Machine

CREATED
→ UPLOADING
→ VERIFYING
→ COMMITTING
→ COMMITTED

Failure:

ABORTED
EXPIRED
FAILED

State phải durable để resume sau khi app restart.

17. Multipart Upload

File được chia:

Part 1
Part 2
Part 3
...

Ưu điểm:

- Retry từng part
- Parallel upload
- Resume
- Không phải gửi lại toàn file

Client có thể upload nhiều parts đồng thời.

18. Chọn Chunk Size

Chunk nhỏ:

- Retry tiết kiệm
- Dedup chi tiết hơn
- Nhiều requests và metadata

Chunk lớn:

- Ít requests
- Throughput tốt
- Retry tốn bandwidth

Ví dụ:

File nhỏ:
4 MB chunks

File lớn:
8–64 MB chunks

Có thể chọn động theo file size và network.

19. Fixed-Size Chunking

File chia theo block cố định:

0–4 MB
4–8 MB
8–12 MB

Ưu điểm:

- Đơn giản
- Parallel upload dễ
- Offset rõ

Nhược điểm:

Chèn một byte đầu file
→ Mọi chunk sau thay đổi
→ Dedup kém

20. Content-Defined Chunking

Ranh giới chunk dựa trên nội dung thay vì offset cố định.

Ví dụ:

Rolling hash
→ Khi hash thỏa điều kiện
→ Tạo chunk boundary

Ưu điểm:

Chèn dữ liệu đầu file
→ Nhiều chunks cũ vẫn được tái sử dụng

Nhược điểm:

- Client phức tạp
- Chunk sizes không đều
- CPU cao hơn
- Security considerations

21. Resumable Upload

Client lưu:

uploadSessionId
file fingerprint
uploaded chunk IDs
chunk checksums

Sau reconnect:

GET /v1/upload-sessions/{uploadSessionId}

Response:

{
  "status": "UPLOADING",
  "uploadedParts": [1, 2, 5, 6]
}

Client chỉ gửi phần thiếu.

22. File Fingerprint

Để đảm bảo resume đúng file:

- File size
- Last modified time
- Sample hashes
- Full content hash nếu khả thi

Không nên resume một file khác vào upload session cũ.

23. Per-Chunk Checksum

Mỗi chunk có:

chunkIndex
offset
size
checksum

Storage hoặc upload gateway xác minh checksum.

Bảo vệ khỏi:

- Network corruption
- Client bug
- Disk read error

24. Full File Checksum

Sau khi upload đủ chunks:

- Verify chunk set
- Verify total size
- Verify full-file hash nếu có

Full hash có thể tính:

- Trên client
- Trong background worker
- Từ manifest/chunk hashes nếu scheme hỗ trợ

25. Upload Completion API

POST /v1/upload-sessions/{uploadSessionId}/complete

{
  "parts": [
    {
      "partNumber": 1,
      "checksum": "..."
    }
  ]
}

Server:

1. Claim session.
2. Verify parts.
3. Create blob manifest.
4. Create immutable file version.
5. Atomically update currentVersionId.
6. Append change-log event.

26. Idempotent Completion

Client có thể timeout sau commit.

Retry phải trả cùng:

fileId
fileVersionId

Không tạo phiên bản trùng.

Dùng:

uploadSessionId → committedVersionId

làm unique mapping.

27. Atomic Version Commit

Không nên:

1. Tạo file version.
2. Sau đó update file pointer.
3. Sau đó publish sync event.

không có transaction/outbox.

Trong metadata transaction:

- Insert file version
- Update file.currentVersionId
- Increment metadata version
- Insert change-log/outbox event

Blob chunks đã tồn tại nhưng chỉ trở nên visible sau metadata commit.

28. Orphan Chunks

Upload thất bại có thể để lại chunks không được manifest nào tham chiếu.

Cần garbage collection:

1. Mark chunks được manifest tham chiếu.
2. Tìm unreferenced chunks quá grace period.
3. Delete.

Không xóa ngay vì completion event có thể đang trễ.

29. Upload Session Cleanup

Session hết hạn:

CREATED/UPLOADING
→ EXPIRED

Cleanup:

- Abort multipart upload
- Release temporary quota
- Schedule orphan-chunk cleanup

33. Folder Hierarchy Models

Có nhiều cách biểu diễn.

34. Adjacency List

Mỗi node lưu parentId.

Ưu điểm:

- Move node đơn giản
- Write nhỏ
- Mô hình tự nhiên

Nhược điểm:

- Tìm toàn subtree cần recursive traversal
- Tính full path cần đi lên ancestors

Phù hợp với phần lớn file storage systems.

35. Materialized Path

Node lưu:

/root/projects/alpha

Ưu điểm:

- Query subtree bằng prefix
- Path resolution nhanh

Nhược điểm:

Move folder lớn
→ Update path của mọi descendant

Không phù hợp nếu move subtree thường xuyên và rất lớn.

36. Closure Table

Lưu:

ancestorId
descendantId
depth

Ưu điểm:

- Ancestor/subtree queries nhanh
- Permission inheritance dễ hơn

Nhược điểm:

- Storage amplification
- Move subtree update nhiều rows

37. Khuyến nghị Folder Model

Một thiết kế cân bằng:

Adjacency list authoritative

+
Search index cho lookup

parentId

Windows, macOS và Linux có khác biệt:

- Case sensitivity

- Reserved names

41. Move Operation

Move node sang folder khác:

{
  "newParentId": "folder_B",
  "expectedVersion": 37
}

Cần kiểm tra:

- Permission ở source
- Permission ở destination
- Destination tồn tại
- Name conflict
- Không move folder vào descendant của chính nó
- Quota/ownership policy

42. Preventing Cycles

Không được:

Folder A
→ chứa Folder B

Sau đó move A vào B

Tạo cycle.

Cần ancestor check:

newParent không được là descendant của node

Có thể dùng:

- Ancestor cache
- Closure table
- Recursive query
- Folder lineage token

43. Copy Operation

Copy file không nhất thiết copy bytes ngay.

Có thể:

New file metadata
→ Tham chiếu cùng immutable blob manifest

Đây là copy-on-write.

Khi một bản được chỉnh sửa:

Tạo version mới

không ảnh hưởng bản kia.

44. Copy Folder

Copy folder lớn có thể chứa hàng triệu nodes.

Không nên làm đồng bộ trong một request.

Flow:

1. Tạo copy job.
2. Snapshot source subtree.
3. Copy metadata theo batches.
4. Reuse blob manifests.
5. Publish progress.

Có thể trả:

202 Accepted

45. Delete và Trash

Delete user-facing thường là soft delete:

ACTIVE
→ TRASHED

Record giữ:

trashedAt
originalParentId
deletedBy

Sau retention:

TRASHED
→ PURGED

46. Trash Restore

Restore cần xử lý:

- Original folder không còn
- Name conflict
- Permission thay đổi

Có thể:

- Restore vào original parent nếu tồn tại
- Tạo tên mới
- Restore vào root/recovered folder

47. Recursive Delete

Xóa folder lớn có hàng triệu children.

Không nên update toàn subtree đồng bộ.

Pattern:

1. Mark folder root TRASHED.
2. Ẩn subtree bằng ancestor state.
3. Background worker materialize deletion.

Permission/list queries phải hiểu ancestor đã trashed.

48. Version History

Mỗi update content tạo version mới:

file_123
├── ver_1
├── ver_2
└── ver_3 current

Versions immutable.

Metadata rename hoặc move không nhất thiết tạo content version mới.

49. Version Retention

Policy:

- Giữ 30 ngày
- Giữ 100 versions gần nhất
- Giữ forever cho enterprise
- Legal hold

GC chỉ xóa blob version khi:

- Hết retention
- Không có snapshot/reference khác
- Không có legal hold

50. Restore Version

Restore version cũ không nên làm current version biến mất.

Thay vào đó:

ver_2 được chọn
→ Tạo ver_4 với cùng manifest như ver_2
→ ver_4 trở thành current

Lịch sử vẫn append-only.

51. Deduplication

Deduplication giảm storage bằng cách tái sử dụng content giống nhau.

Các mức:

- File-level dedup
- Chunk-level dedup
- User-scoped dedup
- Tenant-scoped dedup
- Global dedup

52. File-Level Dedup

Nếu full content hash giống nhau:

File A hash = H
File B hash = H

cả hai tham chiếu cùng blob manifest.

Đơn giản nhưng không tái sử dụng khi file chỉ khác một phần nhỏ.

53. Chunk-Level Dedup

Mỗi chunk có content hash:

chunkId = hash(chunkBytes)

File manifest tham chiếu chunks.

Nếu file mới chỉ thay đổi một chunk:

Chỉ upload/lưu chunk mới

54. Dedup Scope và Privacy

Global dedup có rủi ro side channel.

Attacker có thể kiểm tra liệu nội dung nhạy cảm đã tồn tại bằng cách quan sát:

- Upload có tức thì không
- Quota có giảm không
- Response khác biệt

An toàn hơn:

- Dedup server-side sau upload
- Scope theo user/tenant
- Không tiết lộ dedup hit

55. Convergent Encryption Problem

Nếu chunk encryption key được suy ra từ content hash:

Same plaintext
→ Same ciphertext

dedup dễ hơn nhưng giảm security:

- Dictionary attack
- Confirmation attack

Production design phải cân bằng encryption và dedup scope.

56. Server-Side Encryption

Mỗi blob có thể được mã hóa bằng:

- Random data encryption key
- Key encryption key trong KMS

Metadata lưu encrypted key reference.

Chunk giống nhau chỉ dedup nếu policy và key scope cho phép.

57. Client-Side Encryption

Client mã hóa trước upload.

Ưu điểm:

Server không đọc plaintext

Nhược điểm:

- Full-text search khó
- Virus scan khó
- Preview khó
- Dedup toàn cục kém
- Sharing/key management phức tạp

58. Sync Problem

Desktop client cần biết:

63. Change Log Retention

64. Snapshot + Delta

Sync bootstrap:

1. Lấy snapshot tree tại snapshotVersion V.
2. Download metadata pages.
3. Lấy changes sau V.
4. Chuyển sang incremental sync.

Cần đảm bảo snapshot không bỏ sót thay đổi diễn ra trong lúc scan.

67. Local Change Detection

Có thể dùng:

- Filesystem watcher
- Periodic scan fallback

Chunked phù hợp file lớn và sync desktop.

158. Trade-Off — Fixed Chunk hay Content-Defined Chunk?

Fixed-size

- Đơn giản
- Parallel upload tốt
- Dedup kém khi chèn đầu file

Content-defined

- Delta/dedup tốt
- CPU và implementation phức tạp

Có thể dùng fixed chunk cho upload và content-defined cho background dedup.

159. Trade-Off — Global Dedup hay Tenant Dedup?

Global

- Storage tiết kiệm tối đa
- Privacy side-channel cao

Tenant/user-scoped

- Ít rò rỉ thông tin
- Dedup ratio thấp hơn

Server-side opaque dedup là lựa chọn an toàn hơn client-visible dedup.

160. Trade-Off — Path hay Stable ID?

Path identity

- Dễ hiểu
- Rename/move phá references

Stable ID

- Rename/move rẻ
- Cần metadata lookup để resolve path

Stable ID gần như bắt buộc cho sync đa thiết bị.

161. Trade-Off — LWW hay Conflict Copy?

Last-write-wins

- Đơn giản
- Có thể mất dữ liệu

Conflict copy

- Không mất dữ liệu
- Tạo file dư cần user xử lý

File storage tổng quát nên ưu tiên conflict copy.

162. Trade-Off — Materialize ACL hay Tính từ Ancestors?

Materialize xuống descendants

- Permission check nhanh
- Share folder lớn rất đắt

Tính khi đọc

- Share update rẻ
- Permission check phức tạp

Hybrid:

Inherited ACL authoritative
+
Effective permission cache

163. Trade-Off — Strong Cross-Region Commit hay Async Replication?

Strong

- RPO rất thấp
- Upload commit chậm hơn

Async

- Latency thấp
- Có thể mất phiên bản mới nhất khi region disaster

Có thể cung cấp durability tiers.

164. Cách trình bày trong Phỏng vấn

Có thể mở đầu:

Tôi tách metadata control plane khỏi content data plane. Metadata Service quản lý file identity, folder hierarchy, versions và permissions; file bytes được upload trực tiếp vào object storage bằng resumable multipart sessions.

Về file versioning:

File có stable fileId, còn mỗi nội dung mới tạo một immutable fileVersion. File version tham chiếu blob manifest, manifest tham chiếu chunks. Completion chỉ làm version visible sau khi metadata transaction cập nhật currentVersion và ghi change-log event.

Về sync:

Mỗi user drive hoặc shared workspace có ordered change sequence. Client giữ cursor và gọi delta API thay vì quét toàn bộ tree. Khi cursor hết hạn, client lấy consistent snapshot rồi tiếp tục từ snapshot sequence.

Về conflict:

Client gửi baseVersion khi upload thay đổi. Nếu server current version khác, binary file không bị ghi đè; hệ thống tạo conflict copy hoặc yêu cầu người dùng giải quyết. Điều này tránh mất dữ liệu khi nhiều thiết bị chỉnh sửa offline.

Về multi-region:

Mỗi workspace có metadata owner region và owner epoch. Blob content có thể upload gần người dùng rồi replicate, nhưng metadata mutations route về owner để giữ folder uniqueness và ordered change log. Failover promote replica và fence writer cũ.

Lỗi 22: Permission Cache không Version hóa

Lỗi 23: Signed URL TTL quá dài cho File Private

Revocation khó thực thi.
