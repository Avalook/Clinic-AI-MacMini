Bài 27 — Case Study 6: Thiết kế Search Autocomplete

Search Autocomplete gợi ý nội dung ngay trong lúc người dùng nhập truy vấn:

Input:
"sys"

Suggestions:
- system design
- system design interview
- system architecture
- system administrator

Autocomplete xuất hiện trong:

- Công cụ tìm kiếm
- Sàn thương mại điện tử
- Mạng xã hội
- Ứng dụng video
- Bản đồ
- Kho tài liệu
- IDE và code search

Bài toán cốt lõi là:

prefix → top K suggestions

Nhưng hệ thống production còn phải giải quyết:

- Một request gần như sau mỗi phím bấm
- Prefix ngắn tạo hot key cực lớn
- Latency chỉ vài chục mili giây
- Trending phải cập nhật gần realtime
- Kết quả phải phù hợp ngôn ngữ và khu vực
- Cá nhân hóa nhưng vẫn bảo vệ quyền riêng tư
- Hỗ trợ lỗi chính tả
- Chống spam thao túng bảng gợi ý
- Không làm lộ truy vấn cá nhân hoặc PII
- Hoạt động ở nhiều region

Kiến trúc tổng quát:

Query events
→ Aggregation
→ Prefix index
→ Candidate retrieval
→ Filter
→ Ranking
→ Top K suggestions

1. Xác định phạm vi

Ta thiết kế hệ thống hỗ trợ:

1. Gợi ý query theo prefix.
2. Trả về top K suggestions.
3. Xếp hạng theo popularity, freshness và quality.
4. Cá nhân hóa theo user, session, locale và region.
5. Typo tolerance.
6. Trending gần realtime.
7. Nhiều ngôn ngữ.
8. Safety, PII filtering và chống spam.
9. Multi-region active–active cho serving.

Không đi sâu vào:

- Full search engine
- Ranking tài liệu
- Semantic retrieval hoàn chỉnh
- Voice recognition
- Recommendation hệ thống tổng quát

Autocomplete chỉ gợi ý truy vấn; search engine mới xử lý kết quả cuối cùng.

Safety

3. Non-Functional Requirements

- p99 latency rất thấp
- Availability cao
- Scale tới hàng triệu QPS
- Eventual consistency cho popularity
- Near-realtime freshness cho trending
- Fast consistency cho safety removal
- Chịu được hot prefixes
- Cho phép graceful degradation

Autocomplete lỗi không được ngăn người dùng submit truy vấn tìm kiếm bình thường.

4. Capacity Estimation

Giả sử:

500 triệu DAU
10 search sessions/user/ngày
6 autocomplete requests/session

Tổng request:

500 triệu × 10 × 6
= 30 tỷ requests/ngày

Average QPS:

30.000.000.000 / 86.400
≈ 347.000 QPS

Peak gấp 5 lần:

≈ 1,7 triệu QPS

Đây là hệ thống:

- Read-heavy
- Cache-heavy
- Latency-sensitive
- Có traffic skew cực mạnh

5. Vì sao một Search Session tạo nhiều Request?

User nhập:

system

Client có thể gửi:

s
sy
sys
syst
syste
system

Một truy vấn cuối cùng tạo sáu request.

Nếu người dùng gõ nhanh, phần lớn response cho prefix cũ không còn hữu ích khi tới client.

Do đó tối ưu đầu tiên phải nằm ở client.

6. Client Debounce

Client chờ một khoảng ngắn sau lần nhập cuối trước khi gửi.

Ví dụ:

Debounce = 100 ms

User gõ nhanh:

s → sy → sys

trong dưới 100 ms thì chỉ gửi:

sys

Debounce giúp giảm:

- QPS
- Server load
- Response bị bỏ phí
- UI flicker

Trade-off:

Debounce dài:
Giảm QPS nhưng suggestion chậm.

Debounce ngắn:
UX nhanh hơn nhưng traffic cao.

Khoảng 50–150 ms thường là vùng thử nghiệm hợp lý, nhưng phải đo theo thiết bị và thị trường.

7. Request Cancellation và Response Ordering

Giả sử client gửi:

Request 1: "sys"
Request 2: "syst"

Response "syst" về trước, sau đó "sys" mới về.

Nếu client không kiểm tra, kết quả cũ sẽ ghi đè kết quả mới.

Client cần:

- Gắn request sequence
- Hủy request cũ nếu hỗ trợ
- Bỏ response không còn khớp input hiện tại

Ví dụ:

{
  "requestSequence": 17,
  "prefix": "syst"
}

Chỉ render nếu:

response.requestSequence == latestRequestSequence

9. Minimum Prefix Length

Prefix một ký tự:

"a"

rất mơ hồ và cực nóng.

Các lựa chọn:

1. Không gợi ý cho tới hai ký tự.
2. Cho một ký tự nhưng chỉ dùng precomputed cache.
3. Dùng locale, category và session context để giảm ambiguity.

Minimum prefix length là quyết định sản phẩm, nhưng prefix một ký tự không nên kích hoạt truy vấn nặng.

10. High-Level Architecture

flowchart TD
    Client --> Edge[Edge / Global Router]
    Edge --> API[Autocomplete Service]

    API --> L1[L1 Local Cache]
    L1 --> L2[(Distributed Cache)]
    L2 --> PrefixIndex[Immutable Prefix Index]

    API --> Overlay[(Realtime Trending Overlay)]
    API --> Personal[Personal History/Profile]
    API --> Typo[Typo Correction Index]
    API --> Entity[Entity Index]
    API --> Policy[Safety Policy Store]

    SearchEvents[Search + Selection Events] --> Stream[Event Stream]
    Stream --> Aggregator[Streaming Aggregation]
    Aggregator --> Overlay

    Stream --> Raw[(Historical Query Data)]
    Raw --> Batch[Batch Index Builder]
    Batch --> Snapshot[(Versioned Index Snapshot)]
    Snapshot --> PrefixIndex

Hai đường tách biệt:

Serving path:
prefix → candidates → filter → rank → response

Indexing path:
events → aggregate → build → publish index

Serving không nên phụ thuộc trực tiếp vào analytics pipeline.

11. Query Normalization

Các query:

" System Design "
"SYSTEM DESIGN"
"system   design"

có thể được normalize thành:

"system design"

Các bước phổ biến:

- Trim whitespace
- Collapse repeated spaces
- Unicode normalization
- Locale-aware case folding
- Remove control characters
- Enforce maximum length

Không nên tùy tiện:

- Xóa mọi dấu câu
- Xóa dấu tiếng Việt trong canonical text
- Reorder token

vì có thể thay đổi ý nghĩa.

12. Unicode Normalization

Hai chuỗi có thể hiển thị giống nhau nhưng dùng code-point sequences khác nhau.

Ví dụ ký tự có dấu có thể được biểu diễn bằng:

- Một composed code point
- Base character + combining mark

Nếu không normalize:

"hệ thống"

có thể bị lưu thành nhiều keys logic khác nhau.

Nên normalize trước khi:

- Counting
- Deduplication
- Indexing
- Cache lookup

13. Accent Handling

Người dùng có thể nhập:

"he thong"

nhưng muốn:

"hệ thống"

Có thể duy trì hai forms:

Canonical:
"hệ thống"

Folded:
"he thong"

Serving có thể lookup cả:

- Accent-sensitive index
- Accent-folded auxiliary index

Accent folding phải locale-aware vì ở một số ngôn ngữ việc bỏ dấu có thể tạo ambiguity lớn.

14. Prefix Search

Prefix:

"sys"

khớp:

system
system design
system architecture

Không trực tiếp khớp:

distributed systems
designing systems

Đó là:

- Token search
- Infix search
- Semantic search

Một autocomplete cơ bản nên bắt đầu với left-to-right prefix matching.

15. Trie là gì?

Trie là cây theo ký tự.

Với:

car
card
care
cat

Ta có:

flowchart TD
    Root --> C[c]
    C --> A[a]
    A --> R[r]
    A --> T[t]
    R --> D[d]
    R --> E[e]

Lookup "car":

root → c → a → r

Độ phức tạp:

O(length(prefix))

Điều này rất phù hợp với prefix lookup.

16. Vấn đề của Trie Cơ bản

Nếu node "car" chỉ lưu children, để tìm top 10 suggestions hệ thống phải duyệt subtree:

car
card
care
career
car rental
car insurance
...

Subtree có thể chứa hàng triệu queries.

Vì vậy optimization quan trọng nhất là:

Mỗi node lưu sẵn top N suggestions cho prefix đó.

Node "car" có thể lưu:

1. car
2. car insurance
3. car rental
4. career
5. card

Lookup trở thành:

Traverse prefix
→ Đọc top N

Không cần duyệt descendants tại request time.

17. Trie Node

Một node khái niệm:

{
  "prefix": "sys",
  "topSuggestionIds": [
    "query_12",
    "query_87",
    "query_201"
  ],
  "version": 42
}

Query dictionary lưu riêng:

queryId
→ normalizedText
→ displayText
→ type
→ static features

Nhờ đó full string không bị lặp tại mọi prefix.

18. Top N trong Index và Top K trong Response

Nếu API trả:

K = 10

index không nên chỉ lưu đúng 10.

Nên lưu:

N = 50 hoặc 100

vì sau retrieval có thể loại candidates do:

- Safety
- PII
- Regional policy
- Deduplication
- User block
- Personalization
- Entity overlap

Nếu lưu đúng 10 và 6 bị filter, response chỉ còn 4.

19. Memory Cost của Trie

Trie nguyên thủy có overhead lớn:

- Một node cho mỗi ký tự
- Child pointers
- Node metadata
- Top-N arrays

Với hàng trăm triệu queries, node count có thể cực lớn.

Các giải pháp:

- Radix tree
- Compressed trie
- Minimal finite-state automaton
- Finite-state transducer
- Prefix KV

20. Radix Tree

Các path không phân nhánh được nén.

Thay vì:

s → y → s → t → e → m

dùng một edge:

"system"

Lợi ích:

- Ít node
- Ít pointers
- Cache locality tốt hơn
- Giảm memory

Lookup phải so sánh nhiều ký tự trên một edge, nhưng tổng chi phí vẫn theo chiều dài prefix.

21. Prefix Key-Value Index

Thay vì trie, có thể materialize:

prefix → top N suggestion IDs

Ví dụ:

"s"    → [...]
"sy"   → [...]
"sys"  → [...]
"syst" → [...]

Lưu trong distributed KV hoặc immutable local index.

Ưu điểm:

- Lookup rất đơn giản
- Dễ shard
- Dễ cache
- Dễ replicate

Nhược điểm:

- Storage amplification
- Một query đóng góp vào nhiều prefix keys

22. Trie hay Prefix KV?

Trie

Ưu:
- Chia sẻ common prefixes
- Memory tốt nếu nén
- Lookup tự nhiên

Nhược:
- Distributed updates khó
- Sharding phức tạp hơn

Prefix KV

Ưu:
- Serving đơn giản
- Dễ partition và cache
- Dễ publish immutable snapshot

Nhược:
- Lặp dữ liệu top-N giữa các prefixes

Một production design hợp lý:

Offline builder tạo compressed index shards
→ Serving nodes load shard vào memory/local SSD

queryId → {

Prefix nodes chỉ giữ IDs.

Ví dụ:

- Region

Không nên xếp hạng chỉ bằng raw search count.

26. Ranking cơ bản

Một hàm điểm khái niệm:

score =
w1 × popularity
+ w2 × freshness
+ w3 × queryQuality
+ w4 × regionalRelevance
+ w5 × personalization
+ w6 × entityQuality
- spamPenalty
- typoPenalty
- repetitionPenalty

Không cần mọi candidate gọi một ML model nặng.

Nhiều features có thể được precompute trong index.

27. Popularity Score

Raw count:

query A = 10 triệu
query B = 1 triệu

Không nhất thiết A phải có score gấp 10 lần.

Có thể dùng:

popularityScore = log(1 + count)

Log scaling giảm dominance của queries cực phổ biến.

28. Freshness

Query mới cần cạnh tranh với query phổ biến lâu năm.

Có thể dùng decay:

freshScore =
Σ eventWeight × exp(-age / halfLife)

Search mới xảy ra có trọng số cao hơn search cũ.

Có thể duy trì nhiều time windows:

- 5 phút
- 1 giờ
- 24 giờ
- 7 ngày
- All-time

29. Trending Score

Một query không phải trending chỉ vì volume lớn.

Nên so recent volume với baseline:

trendScore =
recentRate / expectedBaseline

Ví dụ:

"weather":
Baseline 100.000/giờ
Hiện tại 120.000/giờ
→ Tăng 20%

Tên sự kiện X:
Baseline 100/giờ
Hiện tại 50.000/giờ
→ Tăng cực mạnh

Cần minimum volume để tránh:

1 search → 10 searches

bị xem là xu hướng lớn.

30. Query Quality

Một query có volume cao nhưng có thể là suggestion tệ.

Signals:

- Search result click rate
- Dwell time
- Successful completion
- Immediate reformulation
- Result abandonment
- Hide/report rate

Ví dụ:

User chọn suggestion
→ Không click kết quả
→ Sửa query ngay

đây là signal chất lượng thấp.

31. Position Bias

Suggestion vị trí 1 được chọn nhiều hơn chỉ vì nó đứng đầu.

Do đó selection count không phản ánh hoàn toàn chất lượng.

Có thể dùng:

- Randomized exploration
- Position-normalized metrics
- Propensity correction
- A/B testing

Không nên học rằng vị trí 1 tốt chỉ vì chính hệ thống luôn đặt nó ở vị trí 1.

32. Personalization

Personalization có thể boost:

- Query user từng tìm
- Category user hay xem
- Language preference
- Subscriptions
- Current page
- Current session

Ví dụ user thường học System Design:

Input:
"ca"

Personal result:
capacity estimation

Global result:
camera

33. Personal History Index

Lưu:

userId
→ recent normalized queries

Record:

normalizedQuery
lastUsedAt
useCount

Serving:

1. Prefix-match personal history.
2. Lấy global candidates.
3. Merge.
4. Boost personal candidates.
5. Apply safety.

Personal history thường nhỏ nên lookup rất nhanh.

34. Client-Side Personalization

Một lựa chọn bảo vệ privacy:

Server trả global/regional candidates.
Client merge với local search history.

Ưu điểm:

- Ít user data trên server
- Latency thấp
- Hoạt động offline

Nhược điểm:

- Khó đồng bộ nhiều thiết bị
- Ranking logic phân tán
- Khó quan sát đầy đủ

Một kiến trúc hybrid có thể dùng server profile thô và client history chi tiết.

35. Personalization và Safety

Personal history không được bypass safety.

Nếu user từng tìm query hiện đã bị cấm:

Không được gợi ý lại chỉ vì có trong lịch sử.

Pipeline đúng:

Candidate merge
→ Personal boost
→ Safety check
→ Final top K

Safety có thể chạy cả trước và sau ranking.

36. Session Context

User vừa tìm:

"system design"

sau đó nhập:

"ca"

Session context có thể boost:

"capacity estimation"

Session context nên:

- TTL ngắn
- Không trở thành global signal ngay
- Tôn trọng private/incognito mode

37. Typo Tolerance

User nhập:

"sytem design"

Hệ thống nên gợi ý:

"system design"

Typo tolerance không nên làm chậm exact path phổ biến.

Một chiến lược tốt:

1. Exact prefix lookup.
2. Nếu không đủ candidates, chạy fuzzy fallback.
3. Merge fuzzy candidates với penalty.

38. Edit Distance

Levenshtein distance là số thao tác:

- Insert
- Delete
- Replace

cần để biến chuỗi A thành B.

Ví dụ:

sytem → system

cần insert một ký tự:

distance = 1

Có thể mở rộng thêm transposition cho lỗi đảo ký tự.

39. Vì sao không tính Edit Distance với mọi Query?

Giả sử có:

500 triệu query candidates

Mỗi request không thể:

Tính edit distance với 500 triệu strings

Cần index tạo shortlist trước.

Các lựa chọn:

- Fuzzy trie
- N-gram index
- BK-tree
- Delete dictionary
- Finite-state transducer

40. Fuzzy Trie

Trong trie, traversal có thể mang theo edit-distance state.

Nhưng số trạng thái và nhánh tăng nhanh.

Cần giới hạn:

- Chỉ fuzzy sau prefix dài tối thiểu
- Chỉ distance 1 cho prefix ngắn
- Candidate budget
- Time budget
- Exact-first

Ví dụ:

Exact lookup "sytem"
→ Chỉ có 1 candidate

Fuzzy fallback
→ "system"
→ Lookup normal prefix index "system"

41. N-Gram Index

Query:

system

có trigrams:

sys
yst
ste
tem

Input typo vẫn có thể chia sẻ nhiều n-grams.

Flow:

Input n-grams
→ Lấy candidates có overlap
→ Tính edit distance chính xác trên shortlist

Ưu điểm:

- Fuzzy tốt
- Hỗ trợ infix

Nhược điểm:

- Index lớn
- Merge posting lists tốn CPU

42. Delete Dictionary

Với từ "system", precompute các forms sau khi xóa ký tự:

ystem
sstem
sytem
sysem
systm
syste

Input "sytem" có thể map trực tiếp về "system".

Ưu điểm:

- Lookup nhanh cho distance nhỏ

Nhược điểm:

- Storage amplification

Phù hợp typo correction dictionary hoặc tập candidate đã được chọn lọc.

43. Keyboard-Aware Typo

Lỗi replacement không có xác suất bằng nhau.

Trên QWERTY:

o và p nằm gần nhau

Có thể giảm penalty cho:

- Ký tự lân cận
- Transposition
- Thiếu dấu
- Input method errors

Model typo phải xét keyboard và locale.

44. Typo Correction rồi Prefix Lookup

Thay vì fuzzy-match mọi full suggestion:

Input:
"sytem d"

Correction:
"system d"

Normal prefix lookup:
system design
system design interview

Kiến trúc này tái sử dụng prefix index chính và giảm complexity.

flowchart LR

- Count theo query
- Unique users

- Selection rate
- Recent growth
- Spam indicators

48. Minimum Support Threshold

Một query chỉ được xuất hiện công khai khi:

- Đủ số searches
- Đủ số user độc lập
- Đạt quality threshold
- Không có PII
- Không vi phạm policy

Ví dụ:

trong một time window.

55. Vì sao không Update Trie tại chỗ?

Mutable trie trên hàng nghìn servers tạo:

- Locking
- Concurrent readers/writers
- Partial updates
- Version inconsistency
- Rollback khó

Immutable snapshot giúp:

- Lock-free reads
- Atomic version switch
- Rollback nhanh
- Dễ checksum

56. Index Build Pipeline

flowchart TD
    Raw[Historical Query Data] --> Normalize[Normalize]
    Normalize --> Filter[PII / Spam / Policy Filter]
    Filter --> Aggregate[Aggregate Counts]
    Aggregate --> Score[Compute Scores]
    Score --> Prefix[Generate Prefix Top-N]
    Prefix --> Shard[Build Index Shards]
    Shard --> Validate[Validation]
    Validate --> Publish[Publish Snapshot]

Validation gồm:

- Có đủ shards không?
- File có corrupt không?
- Index size có tăng bất thường không?
- Query cấm có lọt không?
- Ranking sanity check

57. Immutable Snapshot Rollout

Các bước:

1. Build version 42.
2. Upload shards vào object storage.
3. Serving nodes tải về staging.
4. Verify checksums.
5. Warm hot prefixes.
6. Atomic pointer swap 41 → 42.
7. Giữ version 41 để rollback.

Node chỉ báo ready sau khi index đã load hoàn chỉnh.

- Trending chậm hơn

93. Failure Mode — Safety Service lỗi

Không nên fail-open hoàn toàn.

Fallback:

- Local cached denylist
- Chỉ dùng pre-approved base index
- Tắt realtime candidates chưa được kiểm duyệt
- Tắt personal suggestions nhạy cảm

Safety cần fail-safe hơn personalization.

94. Failure Mode — Index Build lỗi

Không publish snapshot mới.

- Retry build
- Compare versions

102. Trade-Off — Trie hay Prefix KV?

Trie

- Memory-efficient nếu nén
- Prefix lookup tự nhiên
- Khó update distributed

Prefix KV

- Lookup và sharding đơn giản
- Cache tốt
- Storage amplification lớn hơn

Ở quy mô lớn:

Compressed immutable index

thường phù hợp hơn mutable trie trong database.

Ưu:
- Stable
- Dễ rollback
- Lock-free read

Nhược:
- Freshness chậm hơn

Mutable index

Ưu:
- Realtime

Nhược:
- Concurrency
- Partial update
- Replication phức tạp

Hybrid:

Base snapshot + realtime overlay

là phương án mạnh nhất.

Exact

- Nhanh
- Predictable
- Ít false positives

Fuzzy

- UX tốt khi typo

Nên:

Exact first
→ Fuzzy fallback

105. Trade-Off — Global hay Personalized?

Global

- Cache hit cao
- Đơn giản
- Ít privacy risk

Personalized

- Relevant hơn
- Cache khó
- Cần user state

Tách thành:

Cached global candidate base
+
Lightweight personal reranking

106. Trade-Off — Freshness hay Stability?

Realtime trend có thể khiến results đổi liên tục.

Có thể áp:

- Score smoothing
- Minimum trend duration
- Minimum volume
- Session stability

Mục tiêu là bắt trend nhưng không để UI dao động theo spike vài giây.

107. Cách trình bày trong Phỏng vấn

Có thể mở đầu:

Autocomplete là hệ thống read-heavy vì mỗi search session tạo nhiều request theo số ký tự. Tôi giảm QPS tại client bằng debounce và request cancellation, sau đó phục vụ từ region gần người dùng qua nhiều tầng cache.

Về index:

Tôi sử dụng immutable compressed prefix index. Mỗi prefix lưu sẵn top N suggestion IDs nên request không cần traverse toàn subtree. Base index được build từ historical query data và publish theo version, còn trending được đưa vào một realtime overlay nhỏ.

Về ranking:

Candidate sources gồm global, regional, personal history, entity và typo correction. Hệ thống merge, deduplicate, áp safety filter và dùng lightweight reranker dựa trên popularity, freshness, query quality và personalization.

Về scale:

Prefix ngắn tạo hot keys nên được cache tại edge, local memory và distributed cache. Streaming aggregation dùng salted partition keys và two-stage aggregation để một trending query không làm nóng một partition duy nhất.

109. Những Sai lầm Phổ biến

Lỗi 2: Không bỏ Response cũ

Kết quả prefix cũ ghi đè prefix mới.

Lỗi 3: Dùng LIKE 'prefix%' trên Database chính

Không phù hợp triệu QPS và tail latency thấp.

Lỗi 4: Trie không lưu Top N

Mỗi lookup phải duyệt subtree lớn.

Lỗi 5: Update Trie serving tại chỗ

Khó đồng bộ, rollback và consistency.

Lỗi 6: Chỉ Ranking bằng Raw Count

Query lâu năm và bot traffic thống trị.

Lỗi 7: Không có Freshness

Trending xuất hiện quá muộn.

Lỗi 8: Không có Baseline

Query từ 1 lên 10 được coi là trend lớn.

Kết luận Case Study 6

Autocomplete có thể cô đọng thành:

Collect query events
→ Aggregate popularity và trends
→ Build immutable prefix index
→ Cache hot prefixes
→ Merge global, regional, personal và typo candidates
→ Filter
→ Rank
→ Return top K

Điểm cốt lõi:

Autocomplete nhanh không đến từ việc chạy full search cho mỗi ký tự. Nó đến từ precomputation: lưu sẵn top candidates cho từng prefix, phục vụ bằng index gần như immutable, cache mạnh hot prefixes và tách hoàn toàn serving path khỏi pipeline thu thập, tổng hợp và xây index.
