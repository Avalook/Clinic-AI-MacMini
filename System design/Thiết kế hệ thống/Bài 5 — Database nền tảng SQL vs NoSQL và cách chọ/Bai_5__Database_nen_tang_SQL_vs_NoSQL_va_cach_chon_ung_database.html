Bài 5 — Database nền tảng: SQL vs NoSQL và cách chọn đúng database

Database không nên được chọn theo tiêu chí:

Công nghệ nào đang nổi?
Database nào scale lớn nhất?
Công ty lớn đang dùng gì?

Câu hỏi đúng phải là:

Hệ thống sẽ đọc và ghi dữ liệu như thế nào, cần consistency đến đâu, dữ liệu có quan hệ ra sao và quy mô dự kiến thế nào?

Các tài liệu System Design bạn cung cấp xem database là lớp lưu trữ trung tâm, sau đó mới mở rộng bằng indexing, replication, caching và partitioning khi traffic tăng.

1. Database thực sự giải quyết vấn đề gì?

Database có nhiệm vụ chính:

- Lưu dữ liệu
- Truy xuất dữ liệu
- Cập nhật dữ liệu
- Bảo vệ tính đúng đắn của dữ liệu
- Cho phép nhiều request thao tác đồng thời
- Khôi phục dữ liệu sau sự cố

Ví dụ ứng dụng Todoist có thể chứa:

Users
Projects
Tasks
Labels
Comments
Reminders

Nhưng trước khi chọn database, ta phải biết hệ thống sẽ truy cập chúng thế nào.

Ví dụ:

- Lấy toàn bộ task chưa hoàn thành của một user
- Lấy task trong một project theo deadline
- Cập nhật trạng thái task
- Tìm task theo từ khóa
- Liệt kê task sắp hết hạn

Đây được gọi là access pattern.

2. Access pattern là gì?

Access pattern là cách ứng dụng đọc và ghi dữ liệu.

Ví dụ với ứng dụng chat:

Write:
- Ghi tin nhắn mới
- Cập nhật trạng thái delivered/read

Read:
- Lấy 50 tin nhắn mới nhất của một cuộc trò chuyện
- Lấy tin nhắn cũ hơn một cursor
- Lấy danh sách conversation gần đây của user

Ví dụ với e-commerce:

Write:
- Tạo order
- Cập nhật tồn kho
- Ghi payment transaction

Read:
- Xem sản phẩm theo category
- Tìm kiếm sản phẩm
- Xem lịch sử đơn hàng
- Xem trạng thái order

Hai hệ thống đều lưu dữ liệu, nhưng access pattern rất khác.

Nguyên tắc quan trọng

Đừng thiết kế schema chỉ dựa trên dữ liệu đang có. Hãy thiết kế dựa trên cách dữ liệu sẽ được truy cập.

Đặc biệt với NoSQL, access pattern thường phải được xác định trước khi thiết kế partition key và data model.

3. SQL database là gì?

SQL database còn gọi là relational database.

Ví dụ phổ biến:

PostgreSQL
MySQL
SQL Server
Oracle Database

Dữ liệu được tổ chức thành các bảng có quan hệ.

Ví dụ:

users
projects
tasks

Quan hệ:

erDiagram
    USER ||--o{ PROJECT : owns
    PROJECT ||--o{ TASK : contains
    USER ||--o{ TASK : assigned_to

    USER {
        uuid id
        string email
        string name
    }

    PROJECT {
        uuid id
        uuid owner_id
        string name
    }

    TASK {
        uuid id
        uuid project_id
        uuid assignee_id
        string title
        string status
        datetime due_at
    }

Một task tham chiếu đến project bằng project_id.

4. Đặc điểm chính của SQL

4.1 Schema rõ ràng

Ví dụ:

CREATE TABLE tasks (
    id UUID PRIMARY KEY,
    project_id UUID NOT NULL,
    title VARCHAR(255) NOT NULL,
    status VARCHAR(30) NOT NULL,
    due_at TIMESTAMP,
    created_at TIMESTAMP NOT NULL
);

Database kiểm soát:

- Field nào bắt buộc
- Kiểu dữ liệu
- Primary key
- Foreign key
- Unique constraint
- Check constraint

Điều này giúp dữ liệu có cấu trúc và nhất quán.

4.2 Quan hệ và JOIN

Ví dụ lấy task kèm project:

SELECT
    tasks.id,
    tasks.title,
    projects.name AS project_name
FROM tasks
JOIN projects
    ON tasks.project_id = projects.id
WHERE tasks.id = 'task_123';

SQL rất mạnh khi dữ liệu có nhiều quan hệ và cần truy vấn linh hoạt.

4.3 Transaction

Transaction cho phép nhiều thao tác được xem như một đơn vị.

Ví dụ chuyển tiền:

1. Trừ 1 triệu từ tài khoản A
2. Cộng 1 triệu vào tài khoản B
3. Ghi transaction log

Ta không muốn xảy ra tình huống:

Đã trừ A nhưng chưa cộng B.

Transaction bảo đảm:

Hoặc tất cả thành công,
hoặc tất cả bị rollback.

5. ACID là gì?

ACID là bốn thuộc tính quan trọng của transaction.

A — Atomicity
C — Consistency
I — Isolation
D — Durability

5.1 Atomicity — tính nguyên tử

Transaction thực hiện toàn bộ hoặc không thực hiện gì.

flowchart LR
    A[Trừ tiền tài khoản A] --> B[Cộng tiền tài khoản B]
    B --> C[Ghi transaction]

    C --> D{Tất cả thành công?}
    D -->|Có| E[Commit]
    D -->|Không| F[Rollback toàn bộ]

5.2 Consistency — duy trì quy tắc dữ liệu

Database phải chuyển từ một trạng thái hợp lệ sang một trạng thái hợp lệ khác.

Ví dụ:

- Số dư không được âm nếu business rule cấm
- Email phải unique
- Task phải thuộc một project tồn tại
- Order total không được âm

Lưu ý: consistency trong ACID không hoàn toàn giống consistency trong distributed systems. Phần sau ta sẽ phân biệt.

5.3 Isolation — các transaction không phá nhau

Hai transaction đồng thời không nên tạo kết quả sai.

Ví dụ chỉ còn một vé:

User A đọc: còn 1 vé
User B đọc: còn 1 vé

A đặt vé
B cũng đặt vé

Nếu không kiểm soát concurrency, hệ thống có thể bán cùng một vé hai lần.

Các giải pháp có thể gồm:

- Row lock
- Optimistic locking
- Serializable isolation
- Atomic conditional update
- Unique constraint

5.4 Durability — dữ liệu đã commit không bị mất

Khi database xác nhận transaction thành công, dữ liệu phải tồn tại ngay cả khi server crash sau đó.

Thường dựa trên:

- Write-ahead log
- Disk persistence
- Replication
- Backup

6. Khi nào SQL phù hợp?

SQL thường là lựa chọn tốt khi:

- Dữ liệu có quan hệ rõ
- Cần transaction mạnh
- Cần constraint
- Cần query linh hoạt
- Cần JOIN
- Schema tương đối ổn định
- Tính đúng đắn quan trọng

Ví dụ:

- Banking
- Payment ledger
- Order management
- Inventory
- Booking
- User/account management
- Business applications

Một nguyên tắc thực tế:

Nếu chưa có lý do mạnh để chọn NoSQL, PostgreSQL thường là điểm khởi đầu rất tốt.

7. NoSQL là gì?

NoSQL không phải một loại database duy nhất.

Nó là một nhóm database không sử dụng mô hình quan hệ truyền thống làm mô hình chính.

Các nhóm phổ biến:

1. Key-value database
2. Document database
3. Wide-column database
4. Graph database

Mỗi nhóm giải quyết một loại access pattern khác nhau.

8. Key-value database

Dữ liệu được lưu theo dạng:

key → value

Ví dụ:

"user:123:session" → session data
"product:456"      → product object
"rate:user:789"    → request count

Ví dụ công nghệ:

Redis
Amazon DynamoDB trong một số cách sử dụng
Aerospike

Key-value phù hợp khi

- Biết chính xác key cần tìm
- Cần lookup rất nhanh
- Không cần query phức tạp
- Dữ liệu phù hợp với key → value

Use cases:

- Cache
- Session store
- Rate limiting
- Shopping cart
- Feature flags
- User preferences
- Distributed locks

Hạn chế

Nếu lưu:

user:123 → {...}

thì việc hỏi:

Tìm tất cả user sống tại Hà Nội,
đã đăng ký tháng trước,
và có hơn 10 đơn hàng

không phải access pattern tự nhiên của key-value store.

9. Document database

Dữ liệu được lưu thành document, thường giống JSON.

Ví dụ:

{
  "id": "note_123",
  "userId": "user_456",
  "title": "System Design",
  "content": "Learn database design",
  "labels": ["backend", "learning"],
  "metadata": {
    "color": "yellow",
    "pinned": true
  }
}

Ví dụ công nghệ:

MongoDB
Couchbase
Firestore

Document database phù hợp khi

- Dữ liệu có cấu trúc linh hoạt
- Một object thường được đọc nguyên cụm
- Dữ liệu có nested fields
- Schema thay đổi tương đối thường xuyên
- Không phụ thuộc nhiều vào JOIN phức tạp

Use cases:

- Content management
- Product catalog
- User profiles
- Form submissions
- Configuration data
- Metadata

Nhưng “schema-less” không có nghĩa không cần schema

Một MongoDB collection có thể không ép schema cứng như relational database, nhưng ứng dụng vẫn phải hiểu cấu trúc dữ liệu.

Nếu không quản lý schema, bạn có thể có:

{
  "createdAt": "2026-07-10"
}

Document khác lại là:

{
  "created_at": 1783650000
}

Document khác nữa:

{
  "creationTime": null
}

Kết quả là code rất khó bảo trì.

Cách hiểu đúng:

Document database có schema linh hoạt, không phải dữ liệu hoàn toàn vô tổ chức.

10. Wide-column database

Dữ liệu thường được tổ chức theo:

Partition key
Clustering/sort key
Columns

Ví dụ công nghệ:

Apache Cassandra
ScyllaDB
Google Bigtable
Amazon DynamoDB có nhiều đặc điểm gần nhóm này

Phù hợp với:

- Write throughput rất cao
- Dữ liệu cực lớn
- Phân phối qua nhiều node
- Query pattern biết trước
- Cần scale ngang mạnh

Use cases:

- Time-series events
- IoT data
- Activity feed
- Message history
- Logs
- Large-scale event storage

Ví dụ lưu tin nhắn:

Partition key: conversation_id
Clustering key: message_timestamp

Query chính:

Lấy 50 tin nhắn mới nhất của conversation X.

Mô hình này rất phù hợp với access pattern đó.

Nhưng có thể không phù hợp với:

Tìm tất cả tin nhắn chứa từ “database”
trên toàn bộ conversation của mọi user.

Access pattern đó có thể cần search engine riêng.

11. Graph database

Graph database biểu diễn:

Node
Edge
Property

Ví dụ:

graph LR
    A[Alice] -->|FOLLOWS| B[Bob]
    B -->|FOLLOWS| C[Carol]
    A -->|LIKES| P[Post 123]
    C -->|WORKS_AT| X[Company X]

Ví dụ công nghệ:

Neo4j
Amazon Neptune
JanusGraph

Phù hợp khi trọng tâm là quan hệ và traversal:

- Social graph
- Fraud detection
- Recommendation
- Knowledge graph
- Dependency graph
- Network topology

Ví dụ query:

Bạn bè của bạn bè đang làm ở công ty X là ai?

Trong relational database vẫn làm được, nhưng traversal sâu có thể phức tạp và tốn kém hơn.

12. SQL vs NoSQL: so sánh tổng quan

Tiêu chí SQL NoSQL
Mô hình Bảng và quan hệ Key-value, document, column, graph
Schema Thường chặt chẽ Thường linh hoạt hơn
Transaction Rất mạnh Tùy loại database
JOIN Hỗ trợ tốt Thường hạn chế hoặc không ưu tiên
Query linh hoạt Cao Thường tối ưu cho query biết trước
Scale ngang Có thể làm, nhưng phức tạp hơn Thường được thiết kế tốt cho scale ngang
Consistency Thường mạnh Có thể configurable hoặc eventual
Data duplication Thường giảm nhờ normalization Thường chấp nhận denormalization
Use case Transactional/business data Scale lớn hoặc access pattern chuyên biệt

Nhưng bảng này chỉ là định hướng.

Các database hiện đại đang hội tụ:

- SQL database có JSON, replication và partitioning
- NoSQL database có transaction
- Distributed SQL có transaction và horizontal scaling

Vì thế không nên nghĩ:

SQL = không scale
NoSQL = luôn nhanh

Đó là hai nhận định sai.

13. Normalization là gì?

Normalization là việc tách dữ liệu thành các bảng để giảm trùng lặp.

Ví dụ không normalize:

orders
------------------------------------------------
order_id
customer_name
customer_email
customer_address
product_name
product_price
quantity

Nếu customer đổi email, phải cập nhật nhiều order.

Normalize:

erDiagram
    CUSTOMER ||--o{ ORDER : places
    ORDER ||--o{ ORDER_ITEM : contains
    PRODUCT ||--o{ ORDER_ITEM : referenced_by

Các bảng:

customers
orders
order_items
products

Ưu điểm:

- Giảm duplicate data
- Dễ duy trì tính đúng đắn
- Update một nơi
- Quan hệ rõ ràng

Nhược điểm:

- Query có thể cần nhiều JOIN
- Read path có thể phức tạp
- Scale phân tán khó hơn

14. Denormalization là gì?

Denormalization là cố ý lưu trùng một phần dữ liệu để đọc nhanh hơn.

Ví dụ order lưu snapshot:

{
  "orderId": "ord_123",
  "customerId": "user_456",
  "shippingAddress": {
    "street": "123 Main Street",
    "city": "Bangkok"
  },
  "items": [
    {
      "productId": "p_789",
      "productName": "Mechanical Keyboard",
      "unitPrice": 2500000,
      "quantity": 1
    }
  ]
}

Tại sao lưu productName và unitPrice trong order trong khi product table đã có?

Vì order cần giữ lịch sử tại thời điểm mua.

Nếu giá sản phẩm thay đổi ngày mai, order cũ không được thay đổi.

Denormalization cũng giúp tránh JOIN trên read path.

Đổi lại:

- Tốn storage hơn
- Có duplicate data
- Khó đồng bộ nếu dữ liệu cần luôn giống nhau

15. Index là gì?

Index giống mục lục của một cuốn sách.

Không có index:

Muốn tìm task của user 123,
database có thể phải quét toàn bảng.

Có index:

CREATE INDEX idx_tasks_user_id
ON tasks(user_id);

Database có thể tìm nhanh hơn.

Ví dụ composite index

Query:

SELECT *
FROM tasks
WHERE user_id = ?
  AND status = 'open'
ORDER BY due_at ASC
LIMIT 20;

Index phù hợp:

CREATE INDEX idx_tasks_user_status_due
ON tasks(user_id, status, due_at);

Thứ tự cột trong index rất quan trọng.

Index trên:

(user_id, status, due_at)

không hoàn toàn tương đương với:

(due_at, status, user_id)

16. Index không miễn phí

Index giúp read nhanh hơn nhưng gây chi phí:

- Tốn storage
- Write chậm hơn
- Update phải cập nhật index
- Delete phải cập nhật index
- Quá nhiều index làm database nặng

Trade-off:

Read nhanh hơn
↕
Write và storage tốn hơn

Senior không tạo index cho mọi field. Họ tạo index dựa trên query quan trọng.

17. Cách dùng access pattern để thiết kế index

Giả sử API:

GET /tasks?projectId=p_123&status=open&sort=dueAt

Query:

SELECT *
FROM tasks
WHERE project_id = 'p_123'
  AND status = 'open'
ORDER BY due_at ASC
LIMIT 20;

Ta suy ra index:

(project_id, status, due_at)

Đây là luồng tư duy đúng:

flowchart LR
    A[API endpoint] --> B[Query pattern]
    B --> C[Filter fields]
    B --> D[Sort fields]
    C --> E[Composite index]
    D --> E

Không phải:

Tạo schema trước
→ thêm index ngẫu nhiên
→ hy vọng query nhanh

18. Primary key và partition key

Primary key

Primary key định danh duy nhất một record.

user_id
task_id
order_id
message_id

Ví dụ:

PRIMARY KEY (task_id)

Partition key

Trong distributed database, partition key quyết định dữ liệu được đặt ở node hoặc shard nào.

Ví dụ:

partition key = user_id

Tất cả note của một user có thể nằm cùng partition.

flowchart TD
    R[Request] --> H[Hash user_id]
    H --> S1[(Shard 1)]
    H --> S2[(Shard 2)]
    H --> S3[(Shard 3)]

Partition key tốt phải:

- Phân phối dữ liệu tương đối đều
- Phù hợp query thường gặp
- Tránh hotspot
- Có cardinality đủ lớn

19. Hot partition là gì?

Giả sử partition theo celebrity_id.

Một celebrity có 100 triệu follower và nhận lượng traffic cực lớn.

Dữ liệu của celebrity đó nằm trên một partition:

Partition A: 90% traffic
Partition B: 5%
Partition C: 5%

Mặc dù có ba partition, hệ thống vẫn nghẽn ở A.

Đây là hot partition.

Giải pháp có thể gồm:

- Thêm hash suffix
- Bucket theo thời gian
- Cache dữ liệu nóng
- Fan-out theo nhiều partition
- Dùng composite partition key

Ví dụ:

partition_key = celebrity_id + bucket_id

Nhưng khi đọc, ta phải query nhiều bucket và merge kết quả.

Đây lại là một trade-off.

20. Replication là gì?

Replication là giữ nhiều bản sao của dữ liệu.

flowchart LR
    W[Write] --> P[(Primary)]
    P --> R1[(Replica 1)]
    P --> R2[(Replica 2)]

    Read1[Read] --> R1
    Read2[Read] --> R2

Mục tiêu:

- High availability
- Fault tolerance
- Tăng read capacity
- Disaster recovery

21. Synchronous và asynchronous replication

Synchronous replication

Primary chỉ xác nhận write sau khi replica xác nhận.

sequenceDiagram
    participant Client
    participant Primary
    participant Replica

    Client->>Primary: Write
    Primary->>Replica: Replicate
    Replica-->>Primary: Acknowledged
    Primary-->>Client: Success

Ưu điểm:

- Ít nguy cơ mất dữ liệu
- Replica cập nhật gần như ngay

Nhược điểm:

- Write latency cao hơn
- Replica chậm có thể ảnh hưởng write

Asynchronous replication

Primary trả success trước, sau đó replica cập nhật.

sequenceDiagram
    participant Client
    participant Primary
    participant Replica

    Client->>Primary: Write
    Primary-->>Client: Success
    Primary->>Replica: Replicate later

Ưu điểm:

- Write nhanh hơn
- Primary ít phải chờ

Nhược điểm:

- Replication lag
- Replica có thể trả dữ liệu cũ
- Có thể mất một số write nếu primary chết quá sớm

22. Read-after-write inconsistency

User vừa sửa profile:

Name: Luna → Luna Bailey

Write đi vào primary.

Request tiếp theo đọc từ replica chưa đồng bộ, nên vẫn thấy:

Luna

Đây là read-after-write inconsistency.

Giải pháp:

- Đọc từ primary trong một khoảng thời gian sau write
- Sticky read theo user/session
- Chờ replication position
- Synchronous replication
- Hiển thị dữ liệu từ client state tạm thời

Không phải mọi dữ liệu đều cần giải pháp mạnh nhất.

Ví dụ:

Profile name trễ 1 giây có thể chấp nhận.
Số dư ngân hàng trễ có thể không chấp nhận.

23. Consistency trong distributed systems

Consistency ở đây hỏi:

Sau một write, các client và replica nhìn thấy dữ liệu mới nhanh đến mức nào?

Một số mô hình:

- Strong consistency
- Eventual consistency
- Read-your-writes consistency
- Monotonic reads
- Causal consistency

Strong consistency

Sau khi write thành công, mọi read sau đó đều thấy dữ liệu mới nhất.

Phù hợp với:

- Số dư
- Inventory quan trọng
- Booking seat
- Account permission
- Unique username

Đổi lại có thể tăng:

- Latency
- Coordination
- Giảm availability trong network partition

Eventual consistency

Nếu không có update mới, các replica cuối cùng sẽ hội tụ về cùng dữ liệu.

Trong một khoảng ngắn, user có thể đọc dữ liệu cũ.

Phù hợp với:

- Like count
- View count
- Social feed
- Analytics
- Search index
- Online status

Ví dụ:

User like bài viết.
Số like trên một số thiết bị cập nhật sau vài giây.

Đây thường là trade-off chấp nhận được.

24. CAP theorem

CAP áp dụng khi hệ thống distributed gặp network partition.

Ba thuộc tính:

C — Consistency
A — Availability
P — Partition tolerance

Khi network partition xảy ra, hệ thống phải chọn ưu tiên:

CP: consistency hơn availability
hoặc
AP: availability hơn consistency

Partition tolerance gần như bắt buộc trong distributed system, vì mạng có thể lỗi.

CP system

Khi không thể liên lạc giữa các node, hệ thống có thể từ chối một số request để tránh trả dữ liệu không nhất quán.

Phù hợp khi correctness quan trọng.

Ví dụ khái niệm:

- Distributed lock
- Configuration consensus
- Metadata coordination
- Một số banking operations

AP system

Khi mạng bị chia cắt, các node vẫn phục vụ request, chấp nhận dữ liệu tạm thời khác nhau và reconcile sau.

Phù hợp khi availability quan trọng hơn consistency tức thời.

Ví dụ:

- Social feed
- Shopping cart trong một số thiết kế
- Like/view counters
- Recommendation

Hiểu sai phổ biến

CAP không có nghĩa:

Database luôn chọn cố định 2 trong 3.

Chính xác hơn:

Khi network partition xảy ra, bạn phải chọn giữa consistency và availability cho operation đó.

Nhiều database cho phép lựa chọn consistency khác nhau theo từng request.

25. PACELC — cách nhìn đầy đủ hơn CAP

CAP chỉ nói khi có partition.

PACELC bổ sung:

If Partition:
    Availability vs Consistency

Else:
    Latency vs Consistency

Viết ngắn:

P → A/C
Else → L/C

Ngay cả khi mạng bình thường, strong consistency thường đòi hỏi coordination và làm latency cao hơn.

Đây là trade-off thường xuyên hơn network partition.

26. Sharding là gì?

Sharding là chia dữ liệu thành nhiều database độc lập.

Ví dụ chia user theo hash:

flowchart TD
    A[User request] --> R[Shard Router]
    R --> S1[(Shard 1: users 0-999)]
    R --> S2[(Shard 2: users 1000-1999)]
    R --> S3[(Shard 3: users 2000-2999)]

Hoặc:

shard = hash(user_id) mod N

Mỗi shard xử lý một phần dữ liệu và traffic.

27. Khi nào cần sharding?

Không nên sharding ngay từ đầu.

Chỉ cân nhắc khi:

- Một database không chứa nổi dữ liệu
- Write throughput vượt khả năng một node
- Read replica và cache chưa đủ
- Maintenance window quá lớn
- Index quá lớn
- I/O hoặc connection trở thành giới hạn

Trước khi sharding, thường nên thử:

1. Query optimization
2. Indexing
3. Caching
4. Vertical scaling
5. Read replicas
6. Archiving old data
7. Table partitioning

Sharding tăng complexity rất mạnh.

28. Các chiến lược sharding

28.1 Range-based sharding

User ID 1–1,000,000 → Shard 1
User ID 1,000,001–2,000,000 → Shard 2

Ưu điểm:

- Dễ hiểu
- Range query thuận tiện

Nhược điểm:

- Dễ hotspot nếu ID tăng dần
- Shard mới nhất nhận hầu hết write

28.2 Hash-based sharding

shard = hash(user_id) mod number_of_shards

Ưu điểm:

- Phân phối tương đối đều
- Giảm hotspot

Nhược điểm:

- Range query khó
- Thay đổi số shard có thể phải di chuyển nhiều dữ liệu

Consistent hashing có thể giảm lượng dữ liệu cần di chuyển khi node thay đổi.

28.3 Directory-based sharding

Có service hoặc table ánh xạ:

user_123 → shard_7
user_456 → shard_2

Ưu điểm:

- Linh hoạt
- Có thể di chuyển tenant riêng lẻ

Nhược điểm:

- Directory là dependency quan trọng
- Cần cache và high availability

28.4 Geographic sharding

Asia users → Asia database
Europe users → Europe database
US users → US database

Ưu điểm:

- Giảm latency
- Hỗ trợ data residency

Nhược điểm:

- User di chuyển region
- Cross-region transaction
- Global reporting
- Conflict resolution

29. Sharding gây ra vấn đề gì?

Cross-shard JOIN

User ở shard A, order ở shard B.

Query cần gom dữ liệu từ nhiều shard.

Cross-shard transaction

Chuyển dữ liệu giữa hai shard cần distributed transaction hoặc workflow phức tạp.

Rebalancing

Một shard quá lớn, phải di chuyển dữ liệu sang shard mới.

Hot shard

Một tenant lớn tạo phần lớn traffic.

Global unique constraint

Đảm bảo username unique trên tất cả shard khó hơn.

Giải pháp có thể là:

- Global identity service
- Dedicated uniqueness table
- ID generation service
- Database hỗ trợ global indexes

30. Database partitioning và sharding khác nhau thế nào?

Hai từ đôi khi được dùng lẫn nhau.

Thông thường:

Partitioning:
Chia dữ liệu logic, có thể vẫn trong một database cluster.

Sharding:
Chia dữ liệu sang nhiều database/node độc lập.

Ví dụ PostgreSQL table partition theo tháng:

transactions_2026_01
transactions_2026_02
transactions_2026_03

Vẫn có thể nằm trong cùng một database.

Sharding:

transactions_shard_1
transactions_shard_2
transactions_shard_3

Mỗi shard có thể là một database server riêng.

31. Chọn database dựa trên access pattern

Đây là framework quan trọng nhất của bài.

Câu hỏi 1: Dữ liệu được đọc bằng key hay query phức tạp?

Nếu chủ yếu:

Get object by ID

Key-value hoặc document store có thể phù hợp.

Nếu cần:

JOIN, filter đa chiều, report linh hoạt

SQL thường phù hợp hơn.

Câu hỏi 2: Có transaction nhiều object không?

Ví dụ:

- Trừ inventory
- Tạo order
- Ghi payment

Nếu cần transaction chặt, relational database là lựa chọn tự nhiên.

Câu hỏi 3: Schema ổn định hay linh hoạt?

Schema ổn định, quan hệ rõ:

SQL

Object có nhiều shape khác nhau:

Document database có thể thuận tiện hơn

Câu hỏi 4: Read hay write là chính?

Read-heavy:

- Index
- Cache
- Read replica
- Denormalization

Write-heavy:

- Partitioning
- Append-oriented model
- Queue/batching
- Write-optimized storage

Không nên kết luận ngay “write-heavy thì NoSQL”. SQL vẫn có thể xử lý write lớn tùy quy mô và thiết kế.

Câu hỏi 5: Consistency cần mạnh đến đâu?

Strong consistency:

SQL hoặc distributed database có strong consistency

Eventual consistency chấp nhận được:

Một số NoSQL system có thể scale và available tốt hơn

Câu hỏi 6: Query pattern có biết trước không?

Biết rõ vài query chính:

Wide-column hoặc key-value có thể rất mạnh

Query có thể thay đổi nhiều, cần ad hoc reporting:

SQL thường linh hoạt hơn

Câu hỏi 7: Dữ liệu lớn đến đâu?

Hãy hỏi bằng số:

- Bao nhiêu record?
- Bao nhiêu TB/PB?
- Bao nhiêu read QPS?
- Bao nhiêu write QPS?
- Một object bao nhiêu KB?
- Retention bao lâu?

Không chọn Cassandra chỉ vì “có thể sẽ lớn”.

32. Decision tree chọn database

flowchart TD
    A[Bắt đầu] --> B{Cần transaction và quan hệ phức tạp?}

    B -->|Có| C[Ưu tiên SQL]
    B -->|Không| D{Access pattern chính là gì?}

    D -->|Lookup theo key| E[Key-value]
    D -->|Đọc/ghi document nguyên cụm| F[Document DB]
    D -->|Write cực lớn, query biết trước| G[Wide-column]

    C --> J{Một node có đáp ứng không?}

Đây không phải luật tuyệt đối, nhưng là điểm khởi đầu tốt.

33. Polyglot persistence

Một hệ thống không nhất thiết chỉ dùng một database.

Ví dụ e-commerce:

flowchart TD
    API[Application Services] --> SQL[(PostgreSQL)]
    API --> Redis[(Redis)]
    API --> Search[(OpenSearch)]
    API --> Object[(Object Storage)]
    API --> Analytics[(Data Warehouse)]

    SQL --> A[Orders, payments, inventory]
    Redis --> B[Cache, session, cart]
    Search --> C[Product full-text search]
    Object --> D[Images, invoices]
    Analytics --> E[Reports, BI]

Mỗi storage giải quyết một access pattern:

PostgreSQL:
Transactional source of truth

Redis:
Fast temporary lookup

Search engine:
Text search và ranking

Object storage:
File và media

Data warehouse:
Analytics lớn

Đây gọi là polyglot persistence.

34. Nhưng đừng lạm dụng polyglot persistence

Mỗi database bổ sung thêm:

- Vận hành
- Backup
- Monitoring
- Security
- Data synchronization
- On-call knowledge
- Failure modes
- Chi phí

Đội nhỏ dùng sáu database khác nhau có thể tạo ra nhiều vấn đề hơn lợi ích.

Nguyên tắc senior:

35. Source of truth là gì?

Khi dùng nhiều storage, phải xác định hệ thống nào là nguồn dữ liệu chuẩn.

Ví dụ product:

PostgreSQL = source of truth
Redis = cache
OpenSearch = search projection

Nếu dữ liệu khác nhau:

PostgreSQL được xem là đúng.
Redis và OpenSearch được rebuild từ PostgreSQL hoặc event log.

Sơ đồ:

flowchart LR
    API --> DB[(Primary Database)]
    DB --> Outbox[Outbox/Event]
    Outbox --> Queue[Message Queue]
    Queue --> Search[(Search Index)]
    Queue --> Cache[(Cache)]

Nếu không xác định source of truth, debugging rất khó:

Giá sản phẩm trong DB là 100.
Trong cache là 90.
Trong search index là 110.

Giá nào đúng?

41. Database migration

Schema sẽ thay đổi theo thời gian.

Ví dụ thêm cột:

ALTER TABLE users
ADD COLUMN timezone VARCHAR(50);

Trong hệ thống lớn, migration phải tránh làm downtime.

Mô hình an toàn thường là expand and contract.

Bước 1 — Expand

Thêm field mới nhưng giữ field cũ.

name
first_name
last_name

App có thể dual-write hoặc chuyển dần.

Bước 2 — Migrate dữ liệu

Backfill dữ liệu cũ theo batch.

Không update 500 triệu record trong một transaction.

Bước 3 — Chuyển read path

App đọc field mới.

Theo dõi lỗi và dữ liệu lệch.

Bước 4 — Contract

Khi mọi client đã chuyển, mới xóa field cũ.

Cách này giảm rủi ro breaking change.

42. Backup không giống replication

Replication:

Giữ nhiều bản sao để availability và failover.

Backup:

Giữ snapshot/lịch sử để phục hồi dữ liệu.

Nếu ai đó chạy:

DELETE FROM users;

Lệnh có thể được replicate ngay sang mọi replica.

Replica không cứu được bạn.

Backup có thể giúp phục hồi về thời điểm trước khi xóa.

Do đó cần cả:

- Replication
- Backup
- Point-in-time recovery
- Restore testing

Một backup chưa từng thử restore chưa chắc là backup đáng tin.

43. Các lỗi chọn database phổ biến

Lỗi 1: Chọn theo độ nổi tiếng

Netflix dùng Cassandra nên mình cũng dùng.

Bạn không có workload, đội vận hành hoặc quy mô giống Netflix.

Lỗi 2: Nghĩ NoSQL không có schema

Schema vẫn tồn tại trong application và data contract.

Lỗi 3: Nghĩ SQL không scale

SQL có thể scale rất xa bằng:

- Indexing
- Vertical scaling
- Read replicas
- Partitioning
- Caching
- Sharding
- Distributed SQL

Lỗi 4: Dùng một database cho mọi thứ

PostgreSQL có thể làm rất nhiều việc, nhưng không có nghĩa nên lưu file video lớn trong bảng hoặc dùng nó thay search engine ở mọi quy mô.

Lỗi 5: Sharding quá sớm

Sharding trước khi có bottleneck thật sẽ làm:

- Transaction khó
- Query khó
- Migration khó
- Debug khó
- Vận hành khó

Lỗi 6: Không thiết kế theo query

Schema đẹp về lý thuyết nhưng query chính phải full table scan.

Lỗi 7: Không xác định consistency

Nói “dùng replica” nhưng không trả lời:

User có chấp nhận đọc dữ liệu cũ không?

Lỗi 8: Không xác định source of truth

Cache, search index và database trả ba kết quả khác nhau nhưng không biết hệ thống nào đúng.

Tóm tắt cuối bài

1. Access pattern phải được xác định trước khi chọn database.
2. SQL mạnh về relation, transaction, constraint và query linh hoạt.
3. NoSQL gồm nhiều loại, mỗi loại phục vụ một access pattern khác nhau.
4. Key-value phù hợp lookup nhanh.
5. Document phù hợp object linh hoạt.
6. Wide-column phù hợp write lớn và query biết trước.
7. Graph phù hợp traversal quan hệ.
8. Index tăng tốc read nhưng làm write và storage đắt hơn.
9. Replication tăng availability và read capacity.
10. Sharding tăng write/storage capacity nhưng tạo complexity lớn.
11. Strong consistency phù hợp dữ liệu tài chính và đặt chỗ.
12. Eventual consistency phù hợp feed, counters, search và analytics.
13. Backup không giống replication.
14. Khi dùng nhiều storage, phải xác định source of truth.
15. Database tốt nhất là database phù hợp workload, không phải database nổi tiếng nhất.
