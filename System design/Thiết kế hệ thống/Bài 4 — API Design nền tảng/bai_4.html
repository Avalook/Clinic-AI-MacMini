Bài 4 — API Design nền tảng

API là “hợp đồng giao tiếp” giữa các thành phần trong hệ thống. Client không cần biết server dùng PostgreSQL, Redis hay Kafka; client chỉ cần biết:

Gọi endpoint nào?
Gửi dữ liệu gì?
Nhận kết quả gì?
Khi lỗi thì lỗi theo format nào?
Gọi lặp lại có gây hậu quả không?
Lấy danh sách lớn như thế nào?
Khi API thay đổi thì client cũ có bị hỏng không?

Trong System Design, API thường là một trong những phần được xác định sớm, sau requirements và capacity estimation. Nó giúp làm rõ luồng nghiệp vụ, data model và trách nhiệm giữa các service. Các tài liệu/video bạn cung cấp đặt API bên cạnh database, caching, CDN và load balancing như một thành phần nền tảng của kiến trúc hệ thống.

1. API là gì?

API — Application Programming Interface là giao diện để các chương trình giao tiếp với nhau.

Ví dụ mobile app muốn lấy thông tin user:

GET /users/123

Server trả về:

{
  "id": "123",
  "name": "Luna",
  "email": "luna@example.com"
}

Luồng tổng quát:

sequenceDiagram
    participant Client
    participant API
    participant Service
    participant DB

    Client->>API: GET /users/123
    API->>Service: getUser(123)
    Service->>DB: SELECT user
    DB-->>Service: User data
    Service-->>API: User object
    API-->>Client: 200 OK + JSON

API không chỉ là một URL. Một API contract thường bao gồm:

- HTTP method
- URL/path
- Query parameters
- Headers
- Request body
- Response body
- Status codes
- Authentication rules
- Error format
- Idempotency behavior
- Rate limits
- Version

2. REST là gì?

REST — Representational State Transfer là một phong cách thiết kế API xoay quanh các resource.

Resource có thể là:

User
Note
Order
Product
Payment
Message
Comment

Mỗi resource thường được biểu diễn bằng một URL.

Ví dụ:

/users
/users/123
/users/123/notes
/orders/ord_456

REST không bắt buộc mọi API phải giống hệt nhau, nhưng có một số nguyên tắc phổ biến:

  1. URL đại diện cho resource.
  2. HTTP method đại diện cho hành động.
  3. Request nên stateless.
  4. Dùng HTTP status code đúng ngữ nghĩa.
  5. Resource thường được trao đổi qua JSON.

3. Resource và endpoint

3.1 Dùng danh từ, không dùng động từ

Không nên:

GET /getUsers
POST /createUser
POST /deleteUser
POST /updateUser

Nên:

GET    /users
POST   /users
GET    /users/{userId}
PATCH  /users/{userId}
DELETE /users/{userId}

Lý do: resource là users, còn hành động đã được HTTP method biểu diễn.

3.2 Dùng danh từ số nhiều nhất quán

Nên chọn một convention và giữ nhất quán:

/users
/orders
/products
/notes

Không nên trộn:

/user
/orders
/product-list

3.3 Resource cụ thể dùng ID trong path

GET /users/123
GET /orders/ord_456
GET /products/p_789

Path parameter xác định resource cụ thể:

/users/{userId}
/orders/{orderId}
/products/{productId}

3.4 Resource lồng nhau

Ví dụ lấy note của một user:

GET /users/123/notes

Hoặc lấy comment của một video:

GET /videos/abc/comments

Tuy nhiên không nên lồng quá sâu:

/users/123/projects/456/tasks/789/comments/999/replies

URL như vậy khó dùng và tạo coupling lớn.

Có thể rút gọn thành:

GET /tasks/789/comments
GET /comments/999/replies

Quy tắc thực tế:

Một hoặc hai cấp lồng nhau thường dễ hiểu; nhiều cấp liên tục thường là dấu hiệu cần thiết kế lại.

4. HTTP methods

4.1 GET — đọc dữ liệu

GET /notes
GET /notes/note_123

GET nên:

- Không thay đổi trạng thái hệ thống
- Có thể được cache
- Có tính safe
- Có tính idempotent

Không nên:

GET /delete-note?id=123
GET /pay-order?id=456

Vì GET không nên tạo side effect.

4.2 POST — tạo resource hoặc thực hiện action

Tạo note:

POST /notes

Body:

{
  "title": "System Design",
  "content": "Study API design"
}

Response:

201 Created
Location: /notes/note_123

{
  "id": "note_123",
  "title": "System Design",
  "content": "Study API design",
  "createdAt": "2026-07-10T06:00:00Z"
}

POST thường không idempotent theo mặc định.

Nếu gọi hai lần:

POST /orders
POST /orders

có thể tạo hai order khác nhau.

4.3 PUT — thay thế toàn bộ resource

PUT /users/123

Body:

{
  "name": "Luna Bailey",
  "email": "luna@example.com",
  "timezone": "Asia/Bangkok"
}

Ý nghĩa thường là:

Thay toàn bộ representation hiện tại bằng dữ liệu mới.

PUT thường được xem là idempotent.

Gọi cùng một request nhiều lần vẫn dẫn tới cùng trạng thái cuối.

4.4 PATCH — cập nhật một phần

PATCH /users/123

{
  "timezone": "Asia/Ho_Chi_Minh"
}

PATCH phù hợp khi chỉ sửa một vài field.

So sánh:

PUT:
Thay toàn bộ user.

PATCH:
Chỉ cập nhật timezone.

PATCH có thể idempotent hoặc không, tùy semantics.

Ví dụ idempotent:

{
  "status": "active"
}

Gọi nhiều lần vẫn là active.

Ví dụ không idempotent:

{
  "operation": "increment",
  "amount": 1
}

Gọi 3 lần sẽ tăng 3 lần.

4.5 DELETE — xóa resource

DELETE /notes/note_123

Response thường là:

204 No Content

DELETE thường được xem là idempotent theo trạng thái cuối:

Xóa lần đầu: resource biến mất.
Xóa lần sau: resource vẫn không tồn tại.

Tuy nhiên API có thể trả:

204 khi xóa thành công
404 nếu resource đã không còn

Cả hai cách có thể chấp nhận, miễn contract rõ ràng và nhất quán.

5. Bảng tổng hợp HTTP methods

Method Mục đích chính Safe Idempotent
GET Đọc dữ liệu Có Có
POST Tạo hoặc chạy action Không Thường không
PUT Thay thế resource Không Có
PATCH Cập nhật một phần Không Tùy thiết kế
DELETE Xóa resource Không Có theo trạng thái cuối

Safe nghĩa là không làm thay đổi trạng thái hệ thống.

Idempotent nghĩa là gọi lặp lại cùng request vẫn cho trạng thái cuối giống như gọi một lần.

6. Path parameter, query parameter và request body

6.1 Path parameter — xác định resource

GET /users/123

123 là userId.

Dùng path khi giá trị là một phần của identity hoặc hierarchy.

6.2 Query parameter — lọc, sắp xếp, phân trang

GET /products?category=laptop&brand=apple&sort=price

Ví dụ:

Filter:
?status=active

Sort:
?sort=-createdAt

Search:
?q=system+design

Pagination:
?limit=20&cursor=abc123

Không nên dùng path cho mọi filter:

/products/category/laptop/brand/apple/min-price/1000

Query parameter phù hợp hơn:

/products?category=laptop&brand=apple&minPrice=1000

6.3 Request body — dữ liệu phức tạp

POST /orders
Content-Type: application/json

{
  "items": [
    {
      "productId": "p_123",
      "quantity": 2
    }
  ],
  "shippingAddressId": "addr_456",
  "paymentMethodId": "pm_789"
}

Không nên nhét payload lớn hoặc dữ liệu nhạy cảm vào URL:

POST /orders?cardNumber=...

URL có thể bị ghi vào log, browser history hoặc monitoring tools.

7. Status code

Status code giúp client hiểu kết quả mà không phải đoán từ chuỗi message.

7.1 Nhóm 2xx — thành công

200 OK

Dùng khi request thành công và có response body.

GET /users/123
200 OK

{
  "id": "123",
  "name": "Luna"
}

201 Created

Dùng khi tạo resource thành công.

POST /notes
201 Created

Nên trả resource vừa tạo hoặc ít nhất ID:

{
  "id": "note_123",
  "title": "API Design"
}

202 Accepted

Server đã nhận request nhưng xử lý chưa hoàn tất.

Ví dụ:

POST /video-exports
202 Accepted

{
  "jobId": "job_123",
  "status": "queued"
}

Phù hợp với tác vụ bất đồng bộ:

- Encode video
- Export report
- Import file lớn
- Generate AI report
- Batch processing

204 No Content

Request thành công nhưng không cần body.

DELETE /notes/note_123
204 No Content

7.2 Nhóm 4xx — lỗi phía client

400 Bad Request

Request sai cú pháp hoặc không hợp lệ chung.

{
  "error": {
    "code": "INVALID_REQUEST",
    "message": "Request body is invalid"
  }
}

401 Unauthorized

Tên hơi gây hiểu nhầm. Thực tế thường có nghĩa:

Chưa xác thực hoặc token không hợp lệ.

401 Unauthorized

Ví dụ:

- Không gửi access token
- Token hết hạn
- Token sai chữ ký

403 Forbidden

User đã xác thực nhưng không có quyền.

Ví dụ:

User A đăng nhập hợp lệ,
nhưng cố đọc note riêng của User B.

403 Forbidden

Cách nhớ:

401: Tôi chưa biết bạn là ai.
403: Tôi biết bạn là ai, nhưng bạn không được phép làm việc này.

404 Not Found

Resource không tồn tại.

GET /notes/not_exist
404 Not Found

Trong một số hệ thống bảo mật, API cũng có thể trả 404 thay vì 403 để tránh tiết lộ resource tồn tại.

409 Conflict

Request xung đột với trạng thái hiện tại.

Ví dụ:

- Email đã tồn tại
- Username đã được dùng
- Version update bị conflict
- Order đã bị hủy nhưng client cố thanh toán

{
  "error": {
    "code": "EMAIL_ALREADY_EXISTS",
    "message": "The email is already registered"
  }
}

422 Unprocessable Content

JSON hợp lệ về cú pháp nhưng dữ liệu vi phạm validation nghiệp vụ.

{
  "email": "not-an-email",
  "quantity": -2
}

Có nơi dùng 400 cho tất cả validation errors; có nơi dùng 422. Điều quan trọng nhất là nhất quán.

429 Too Many Requests

Client vượt rate limit.

429 Too Many Requests
Retry-After: 60

{
  "error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "Try again in 60 seconds"
  }
}

7.3 Nhóm 5xx — lỗi phía server

500 Internal Server Error

Lỗi server không xác định hoặc không được xử lý.

Không nên trả stack trace cho client:

{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "An unexpected error occurred"
  }
}

Chi tiết lỗi nên nằm trong internal logs.

502 Bad Gateway

Gateway hoặc proxy nhận response lỗi từ upstream service.

Client → API Gateway → Payment Service
                         ↓ lỗi response
Client ← 502

503 Service Unavailable

Service tạm thời không phục vụ được.

Ví dụ:

- Quá tải
- Maintenance
- Dependency quan trọng bị down

Có thể gửi:

Retry-After: 30

504 Gateway Timeout

Gateway chờ upstream quá lâu.

Ví dụ payment provider timeout.

8. Thiết kế error response

Không nên mỗi endpoint trả lỗi một kiểu.

Endpoint A:

{
  "message": "wrong"
}

Endpoint B:

{
  "error_message": "Not found",
  "status": false
}

Endpoint C:

{
  "errors": ["bad request"]
}

Nên có format chung:

{
  "error": {
    "code": "NOTE_NOT_FOUND",
    "message": "The requested note does not exist",
    "details": {
      "noteId": "note_123"
    },
    "requestId": "req_abc123"
  }
}

Các field hữu ích:

code:
Mã ổn định để client xử lý bằng logic.

message:
Thông báo dễ hiểu cho developer hoặc user.

details:
Validation errors hoặc context bổ sung.

requestId:
Liên kết lỗi phía client với log phía server.

Validation error:

{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "One or more fields are invalid",
    "details": [
      {
        "field": "email",
        "reason": "INVALID_FORMAT"
      },
      {
        "field": "password",
        "reason": "TOO_SHORT"
      }
    ],
    "requestId": "req_abc123"
  }
}

9. Pagination — tại sao phải phân trang?

Giả sử user có 2 triệu transactions.

Không nên:

GET /transactions

rồi trả toàn bộ 2 triệu record.

Hậu quả:

- Response cực lớn
- Database query chậm
- Tốn memory server
- Tốn bandwidth
- Client có thể bị treo
- Latency tăng mạnh

Pagination chia dữ liệu thành từng trang nhỏ:

GET /transactions?limit=20

10. Offset pagination

Ví dụ:

GET /notes?limit=20&offset=0
GET /notes?limit=20&offset=20
GET /notes?limit=20&offset=40

SQL tương ứng:

SELECT *
FROM notes
ORDER BY created_at DESC
LIMIT 20 OFFSET 40;

Ưu điểm

- Dễ hiểu
- Dễ implement
- Có thể nhảy tới trang bất kỳ
- Phù hợp admin dashboard hoặc dataset nhỏ

Nhược điểm

Hiệu năng giảm với offset lớn

LIMIT 20 OFFSET 1000000

Database có thể phải đi qua rất nhiều row trước khi lấy 20 row cần thiết.

Dữ liệu có thể bị trùng hoặc bỏ sót

Ví dụ:

  1. Client lấy trang 1.
  2. Một record mới được thêm vào đầu danh sách.
  3. Client lấy trang 2 bằng offset.
  4. Một record có thể xuất hiện lại.

Minh họa:

Ban đầu:
A B C D E F

Page 1, limit 3:
A B C

Có record X mới:
X A B C D E F

Page 2, offset 3:
C D E

C bị lặp.

11. Cursor pagination

Client không nói “bỏ qua 20 record”, mà nói:

Hãy lấy dữ liệu sau record cuối cùng tôi đã thấy.

Request đầu:

GET /notes?limit=20

Response:

{
  "data": [
    {
      "id": "note_100",
      "title": "API Design"
    }
  ],
  "pagination": {
    "nextCursor": "eyJjcmVhdGVkQXQiOiIyMDI2LTA3LTEwVDA2OjAwOjAwWiIsImlkIjoibm90ZV8xMDAifQ==",
    "hasMore": true
  }
}

Request tiếp:

GET /notes?limit=20&cursor=eyJjcmVhdGVkQXQi...

Query logic có thể giống:

SELECT *
FROM notes
WHERE (created_at, id) < (:created_at, :id)
ORDER BY created_at DESC, id DESC
LIMIT 20;

Ưu điểm

- Hiệu quả hơn với dữ liệu lớn
- Ổn định hơn khi dữ liệu liên tục thay đổi
- Rất phù hợp news feed, chat, notification, timeline

Nhược điểm

- Khó nhảy thẳng tới trang 50
- Cursor phải được thiết kế cẩn thận
- Sorting phải ổn định
- Client không nên tự sửa cursor

12. Cursor phải có thứ tự ổn định

Chỉ dùng createdAt có thể chưa đủ vì nhiều record có cùng timestamp.

Không tốt:

ORDER BY created_at DESC

Tốt hơn:

ORDER BY created_at DESC, id DESC

Cursor chứa cả:

{
  "createdAt": "2026-07-10T06:00:00Z",
  "id": "note_123"
}

id đóng vai trò tie-breaker.

13. Page-based pagination

Một biến thể của offset:

GET /products?page=3&pageSize=20

Server đổi thành:

offset = (page - 1) × pageSize

Cách này thân thiện với UI:

Trang 1 2 3 4 5

Phù hợp với:

- Product catalog
- Admin table
- Search results tương đối ổn định

Không lý tưởng cho:

- Realtime feed
- Chat history
- Notification stream
- Dataset thay đổi liên tục

14. Chọn loại pagination

Trường hợp Nên dùng
Admin dashboard nhỏ Offset/page
Cần nhảy tới trang bất kỳ Offset/page
News feed Cursor
Chat messages Cursor
Notifications Cursor
Transactions lớn Cursor
Dataset gần như tĩnh Offset có thể đủ
Infinite scroll Cursor

Quy tắc:

Dữ liệu lớn và thay đổi liên tục: ưu tiên cursor.

15. Idempotency là gì?

Một operation là idempotent nếu thực hiện cùng request nhiều lần vẫn tạo ra cùng trạng thái cuối như thực hiện một lần.

Ví dụ:

PUT /users/123
{
  "status": "active"
}

Gọi 1 lần hay 10 lần, trạng thái cuối vẫn là:

status = active

Nhưng:

POST /orders

Gọi hai lần có thể tạo hai order.

Đây là vấn đề rất nguy hiểm với:

- Payment
- Order creation
- Booking
- Money transfer
- Coupon redemption
- Inventory reservation

16. Vì sao request có thể bị gửi lặp?

Không nhất thiết user bấm hai lần.

Một request có thể lặp vì:

- Client timeout rồi retry
- Mobile network chập chờn
- Load balancer retry
- Proxy retry
- Message consumer xử lý lại
- User double-click
- Client không nhận được response dù server đã xử lý thành công

Ví dụ:

sequenceDiagram
    participant Client
    participant PaymentAPI
    participant DB

    Client->>PaymentAPI: POST /payments
    PaymentAPI->>DB: Charge 1,000,000đ
    DB-->>PaymentAPI: Success
    Note over PaymentAPI,Client: Response bị mất do network
    Client->>PaymentAPI: Retry POST /payments
    PaymentAPI->>DB: Charge thêm lần nữa

Nếu không có idempotency, user có thể bị trừ tiền hai lần.

17. Idempotency key

Client tạo một key duy nhất cho một logical operation:

POST /payments
Idempotency-Key: 7f9d9dd6-6e15-4faa-93b0-6f2f8f249001

Body:

{
  "orderId": "ord_123",
  "amount": 1000000,
  "currency": "VND"
}

Server lưu:

Idempotency key
Request fingerprint
Processing status
Response result
Expiration time

Luồng:

sequenceDiagram
    participant Client
    participant API
    participant IdempotencyStore
    participant PaymentService

    Client->>API: POST /payments + key=abc
    API->>IdempotencyStore: Lookup abc
    IdempotencyStore-->>API: Not found
    API->>IdempotencyStore: Reserve abc = processing
    API->>PaymentService: Charge payment
    PaymentService-->>API: Payment succeeded
    API->>IdempotencyStore: Store response for abc
    API-->>Client: 201 Created

    Client->>API: Retry with key=abc
    API->>IdempotencyStore: Lookup abc
    IdempotencyStore-->>API: Existing result
    API-->>Client: Return original response

Kết quả:

Request gửi nhiều lần,
nhưng payment chỉ được xử lý một lần.

18. Quy tắc thiết kế idempotency key

18.1 Key phải thuộc phạm vi client/user

Hai user khác nhau có thể vô tình dùng cùng một UUID.

Key lưu có thể là:

(user_id, idempotency_key)

thay vì chỉ:

idempotency_key

18.2 Cùng key nhưng body khác phải bị từ chối

Ví dụ lần đầu:

{
  "orderId": "ord_123",
  "amount": 1000000
}

Lần sau cùng key:

{
  "orderId": "ord_999",
  "amount": 5000000
}

Server không nên trả kết quả cũ một cách im lặng.

Có thể trả:

409 Conflict

{
  "error": {
    "code": "IDEMPOTENCY_KEY_REUSED",
    "message": "The idempotency key was previously used with a different request"
  }
}

Do đó server thường lưu hash của request body.

18.3 Phải xử lý concurrent requests

Hai request cùng key có thể tới gần như đồng thời.

Cần operation atomic:

Insert-if-not-exists
Unique constraint
Distributed lock
Transaction

Ví dụ table:

CREATE TABLE idempotency_keys (
    user_id VARCHAR(64),
    key VARCHAR(128),
    request_hash VARCHAR(128),
    status VARCHAR(20),
    response_body JSONB,
    created_at TIMESTAMP,
    expires_at TIMESTAMP,
    PRIMARY KEY (user_id, key)
);

Unique constraint giúp chỉ một request sở hữu key.

18.4 Key cần thời hạn

Không nhất thiết lưu vĩnh viễn.

Ví dụ:

Payment: 24–72 giờ hoặc theo business policy
Order creation: vài giờ đến vài ngày
Batch job: theo lifecycle của job

TTL là một quyết định nghiệp vụ, không có một con số đúng cho mọi hệ thống.

19. Idempotency không đồng nghĩa exactly-once

Đây là điểm sâu cần nhớ.

Trong distributed systems, “exactly once” rất khó đảm bảo end-to-end.

Idempotency thường giúp ta đạt:

At-least-once delivery
+
Deduplication/idempotent processing
=
Hiệu ứng nghiệp vụ gần như chỉ xảy ra một lần

Ví dụ message queue có thể giao event hai lần:

OrderCreated
OrderCreated

Consumer phải chống xử lý trùng:

- Lưu eventId đã xử lý
- Unique constraint
- Upsert
- Idempotent state transition

20. API versioning

API sẽ thay đổi theo thời gian:

- Thêm field
- Đổi cấu trúc response
- Đổi validation
- Xóa field
- Đổi semantics
- Tách resource

Vấn đề:

Mobile app cũ có thể chưa cập nhật.
Partner bên ngoài có thể dùng API cũ.
Service nội bộ có thể deploy khác thời điểm.

Nếu đổi API trực tiếp, client cũ có thể bị hỏng.

21. Khi nào thay đổi được xem là breaking change?

Thường không breaking

Thêm field mới vào response:

{
  "id": "123",
  "name": "Luna",
  "avatarUrl": "..."
}

Miễn client bỏ qua field không biết.

Thêm endpoint mới:

GET /users/{id}/preferences

Thêm optional request field:

{
  "title": "API Design",
  "color": "yellow"
}

Thường là breaking

Đổi tên field:

name → fullName

Xóa field:

avatarUrl bị loại bỏ

Đổi type:

price: 100
→
price: "100 USD"

Đổi semantics:

status = active trước đây nghĩa A,
sau này lại nghĩa B.

Biến optional field thành required.

Đổi status code khiến client logic hỏng.

Đổi pagination format.

22. Các cách version API

22.1 Version trong URL path

GET /v1/users/123
GET /v2/users/123

Ưu điểm:

- Rõ ràng
- Dễ debug
- Dễ route
- Dễ document

Nhược điểm:

- URL chứa version
- Có thể dẫn đến copy toàn bộ API v1 thành v2 dù chỉ vài thay đổi

Đây là cách phổ biến và dễ quản lý.

22.2 Version trong header

GET /users/123
Accept: application/vnd.example.v2+json

Hoặc:

API-Version: 2

Ưu điểm:

- URL sạch
- Version gắn với representation

Nhược điểm:

- Khó nhìn khi debug
- Browser/manual testing bất tiện hơn
- Cache configuration phức tạp hơn

22.3 Version bằng query parameter

GET /users/123?version=2

Dễ dùng nhưng thường kém rõ ràng hơn path versioning và dễ bị bỏ quên trong cache/routing rules.

22.4 Date-based versioning

API-Version: 2026-07-01

Phù hợp với platform API có nhiều client bên ngoài.

Ý nghĩa:

Client yêu cầu behavior theo phiên bản hợp đồng tại một ngày cụ thể.

23. Không nên tạo version mới cho mọi thay đổi

Sai lầm:

Thêm field optional → tạo v2
Thêm endpoint → tạo v3
Sửa message lỗi → tạo v4

Version mới chỉ nên dùng khi có breaking change đáng kể.

Các thay đổi tương thích ngược nên giữ trong cùng version.

Nguyên tắc:

Prefer additive changes.
Avoid destructive changes.

Ví dụ tốt:

Thay vì đổi:

{
  "name": "Luna"
}

thành:

{
  "firstName": "Luna",
  "lastName": "Bailey"
}

ngay lập tức, có thể chuyển tiếp:

{
  "name": "Luna Bailey",
  "firstName": "Luna",
  "lastName": "Bailey"
}

Sau một giai đoạn deprecation mới loại bỏ name.

24. Chiến lược deprecation

Khi cần bỏ API cũ:

1. Công bố version mới.
2. Document migration guide.
3. Theo dõi traffic version cũ.
4. Cảnh báo client đang dùng version cũ.
5. Đặt ngày sunset.
6. Chỉ tắt sau khi client quan trọng đã migrate.

Có thể sử dụng headers:

Deprecation: true
Sunset: Wed, 31 Dec 2026 23:59:59 GMT
Link: </docs/migration/v2>; rel="deprecation"

Không nên tắt API cũ đột ngột nếu có mobile app hoặc external partners phụ thuộc vào nó.

27. Action không phù hợp CRUD thì thiết kế thế nào?

Không phải mọi nghiệp vụ đều biểu diễn đẹp bằng CRUD.

Ví dụ:

Cancel order
Capture payment
Refund payment
Publish article
Archive project

Có thể dùng action endpoint:

POST /orders/ord_123/cancel
POST /payments/pay_123/capture
POST /payments/pay_123/refund
POST /articles/article_123/publish

Đây vẫn là thiết kế thực tế và dễ hiểu.

Một lựa chọn khác là update trạng thái:

PATCH /orders/ord_123

{
  "status": "cancelled"
}

Nhưng action endpoint thường tốt hơn nếu operation có:

- Business validation phức tạp
- Side effects
- Audit requirements
- Workflow rõ ràng

Ví dụ refund không chỉ là đổi field status; nó có thể gọi payment provider, ghi ledger và gửi notification.

28. Concurrent update và optimistic locking

Giả sử hai thiết bị cùng sửa một note.

Ban đầu:

version = 5

Thiết bị A gửi:

PATCH /notes/note_123
If-Match: "5"

Thiết bị B cũng gửi:

PATCH /notes/note_123
If-Match: "5"

A cập nhật trước, version thành 6.

B cập nhật sau với version 5, server trả:

409 Conflict

Hoặc:

412 Precondition Failed

Sơ đồ:

sequenceDiagram
    participant A as Device A
    participant B as Device B
    participant API

    A->>API: PATCH note, version=5
    API-->>A: 200 OK, version=6

    B->>API: PATCH note, version=5
    API-->>B: 409 Conflict, latest version=6

Đây là optimistic concurrency control.

Phù hợp khi conflict không quá thường xuyên.

29. Một API response có nên bọc data không?

Hai style phổ biến:

Không bọc:

{
  "id": "123",
  "name": "Luna"
}

Có bọc:

{
  "data": {
    "id": "123",
    "name": "Luna"
  }
}

Bọc data giúp dễ thêm metadata:

{
  "data": [],
  "pagination": {},
  "meta": {
    "requestId": "req_123"
  }
}

Không có lựa chọn tuyệt đối đúng. Điều quan trọng là:

- Nhất quán
- Document rõ
- Không bọc nhiều lớp vô nghĩa

Không tốt:

{
  "result": {
    "data": {
      "payload": {
        "items": []
      }
    }
  }
}

30. API stateless là gì?

Mỗi request nên mang đủ thông tin để server xử lý.

Ví dụ:

Authorization: Bearer <access-token>

Bất kỳ API server nào cũng có thể xử lý request:

flowchart LR
    Client --> LB[Load Balancer]
    LB --> A1[API Server 1]
    LB --> A2[API Server 2]
    LB --> A3[API Server 3]

Nếu session state chỉ nằm trong memory của Server 1:

Request đầu tới Server 1 → đăng nhập được
Request sau tới Server 2 → không biết session

Giải pháp:

- Token tự chứa thông tin phù hợp
- Shared session store như Redis
- Sticky session, nhưng thường kém linh hoạt hơn

Stateless API server dễ horizontal scaling hơn.

31. Những lỗi API Design phổ biến

Lỗi 1: Dùng POST cho tất cả

POST /getUser
POST /updateUser
POST /deleteUser

Mất semantics của HTTP và khó caching/tooling.

Lỗi 2: Luôn trả 200

Không tốt:

200 OK

{
  "success": false,
  "error": "User not found"
}

Nên:

404 Not Found

Lỗi 3: Không có pagination

Endpoint hoạt động lúc 1.000 record nhưng chết khi có 10 triệu record.

Lỗi 4: Không xử lý duplicate request

Đặc biệt nguy hiểm với payment/order.

Lỗi 5: Response không nhất quán

Field lúc là:

created_at

lúc là:

createdAt

lúc lại là:

creationTime

Nên chọn một convention.

Lỗi 6: Để lộ nội bộ

Không nên trả:

{
  "error": "NullPointerException at OrderService.java:194",
  "sql": "SELECT ..."
}

Lỗi 7: Breaking change âm thầm

Đổi response mà không version, không thông báo và không migration period.

Lỗi 8: Trộn resource identity với user input

Không nên cho client tùy ý truyền userId rồi tin tưởng:

GET /notes?userId=another_user

Server phải lấy identity từ authentication context và kiểm tra authorization.

Response

[ ] Error response có stable error code không?

33. Công thức thiết kế API trong System Design Interview

Khi trình bày, bạn không cần liệt kê hàng chục endpoint. Chỉ cần core APIs.

Ví dụ thiết kế app note:

POST   /v1/notes
GET    /v1/notes/{noteId}
PATCH  /v1/notes/{noteId}
DELETE /v1/notes/{noteId}
GET    /v1/notes?limit=20&cursor=...
GET    /v1/notes?q=...

Sau đó giải thích:

- Authentication lấy user identity từ token.
- List endpoint dùng cursor pagination.
- Note update dùng version để chống lost update.
- Create request có thể dùng idempotency key nếu client retry.
- Errors dùng status code và stable application error code.

Đó là đủ để thể hiện tư duy senior hơn việc viết 50 endpoint.

35. Những điều cần thuộc sau Bài 4

1. REST thiết kế quanh resource, không phải quanh tên function.
2. URL nên dùng danh từ; HTTP method thể hiện hành động.
3. GET đọc, POST tạo/action, PUT thay thế, PATCH cập nhật phần, DELETE xóa.
4. Status code phải phản ánh đúng kết quả.
5. Danh sách lớn luôn cần pagination.
6. Offset đơn giản nhưng yếu khi dữ liệu lớn hoặc thay đổi liên tục.
7. Cursor phù hợp feed, chat, notification và transaction lớn.
8. Payment/order cần idempotency để retry an toàn.
9. Cùng idempotency key nhưng payload khác phải bị từ chối.
10. API nên ưu tiên backward-compatible changes.
11. Chỉ tạo version mới khi có breaking change đáng kể.
12. API tốt là một contract rõ ràng, nhất quán và có thể phát triển lâu dài.
