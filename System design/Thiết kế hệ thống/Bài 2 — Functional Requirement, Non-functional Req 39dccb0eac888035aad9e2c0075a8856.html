Bài 2 — Functional Requirement, Non-functional Requirement và cách hỏi yêu cầu như Senior Engineer

Bài này cực kỳ quan trọng, vì trong System Design, người thiết kế giỏi không phải người vẽ sơ đồ nhanh nhất, mà là người hỏi đúng câu hỏi trước khi vẽ. Các video/tài liệu bạn đưa đều xoay quanh tư duy này: trước khi chọn API, database, cache, CDN, load balancer hay queue, ta phải hiểu hệ thống cần làm gì và cần làm tốt đến mức nào.

1. Vấn đề lớn của người mới học System Design

Người mới thường nghe đề bài xong sẽ vẽ ngay:

Client -> Load Balancer -> API Server -> Database -> Cache

Nhìn có vẻ đúng, nhưng thực ra có thể rất nguy hiểm, vì bạn chưa biết:

- User cần tính năng gì?
- Hệ thống phục vụ bao nhiêu người?
- Read nhiều hay write nhiều?
- Có cần realtime không?
- Dữ liệu có cần chính xác tuyệt đối không?
- Nếu service bị lỗi thì hậu quả thế nào?
- Latency bao nhiêu là chấp nhận được?

Ví dụ đề bài: “Thiết kế hệ thống chat.”

Nếu bạn vẽ ngay WebSocket + Redis + Kafka + Cassandra thì nghe rất chuyên nghiệp, nhưng có thể sai nếu thực tế chỉ cần:

- Chat support 1-1 đơn giản
- 1,000 user/ngày
- Không cần realtime tuyệt đối
- Không cần group chat
- Không cần gửi file

Ngược lại, nếu là chat app như Messenger/Zalo với hàng chục triệu user, thì thiết kế đơn giản lại không đủ.

Bài học:

Trước khi thiết kế, phải làm rõ yêu cầu.

2. Functional Requirement là gì?

Functional Requirement là những thứ hệ thống phải làm được.

Bạn có thể nhớ đơn giản:

Functional Requirement = “Hệ thống có chức năng gì?”

Ví dụ với app ghi chú giống Google Keep:

- User có thể tạo ghi chú
- User có thể sửa ghi chú
- User có thể xoá ghi chú
- User có thể tìm kiếm ghi chú
- User có thể gắn nhãn ghi chú
- User có thể đồng bộ ghi chú giữa nhiều thiết bị

Ví dụ với YouTube:

- User upload video
- User xem video
- User search video
- User like/comment video
- User subscribe channel
- Creator xem analytics

Ví dụ với Shopee:

- User xem sản phẩm
- User thêm sản phẩm vào giỏ
- User đặt hàng
- User thanh toán
- Seller quản lý sản phẩm
- Admin xử lý tranh chấp

Functional Requirement thường trả lời câu hỏi:

User làm được gì?
Admin làm được gì?
Hệ thống tự động làm gì?
Dữ liệu nào được tạo/sửa/xoá?
Luồng nghiệp vụ chính là gì?

3. Non-functional Requirement là gì?

Non-functional Requirement là hệ thống cần hoạt động tốt đến mức nào.

Bạn có thể nhớ:

Non-functional Requirement = “Hệ thống phải chạy tốt ra sao?”

Ví dụ:

- Phải nhanh
- Phải chịu tải lớn
- Phải bảo mật
- Phải ít downtime
- Phải không mất dữ liệu
- Phải dễ mở rộng
- Phải dễ monitor

Cùng một chức năng “user xem video”, nhưng non-functional requirement sẽ quyết định kiến trúc khác nhau rất nhiều.

Nếu chỉ 100 user:

flowchart LR
    User --> Server[App Server]
    Server --> Storage[Video Storage]

Nếu hàng triệu user toàn cầu:

flowchart LR
    User --> CDN[CDN Edge Location]
    CDN --> Origin[Origin Video Storage]
    User --> API[API Server]
    API --> DB[(Metadata DB)]
    API --> Cache[(Cache)]

Chức năng vẫn là “xem video”, nhưng yêu cầu về tốc độ và quy mô làm kiến trúc thay đổi hoàn toàn.

4. So sánh Functional và Non-functional

Loại yêu cầuCâu hỏi chínhVí dụ
FunctionalHệ thống làm gì?Upload video, tạo note, gửi tin nhắn
Non-functionalHệ thống làm tốt đến mức nào?Nhanh, scale tốt, bảo mật, không mất dữ liệu

Một cách nhớ rất hay:

Functional = WHAT
Hệ thống làm CÁI GÌ?

Non-functional = HOW WELL
Hệ thống làm TỐT ĐẾN MỨC NÀO?

Ví dụ với hệ thống chat:

Functional:
- Gửi tin nhắn 1-1
- Tạo group chat
- Gửi ảnh
- Hiển thị trạng thái đã đọc
- Hiển thị typing indicator

Non-functional:
- Tin nhắn gửi dưới 200ms
- Không mất tin nhắn
- Hỗ trợ 10 triệu DAU
- Tin nhắn được lưu ít nhất 5 năm
- Hệ thống vẫn chạy nếu một server chết

5. Vì sao Non-functional Requirement quan trọng hơn bạn nghĩ?

Trong coding, bạn thường được giao task rõ:

Viết API tạo ghi chú.

Nhưng trong System Design, yêu cầu thật thường mơ hồ:

Thiết kế Google Keep.

Nếu không hỏi non-functional requirement, bạn không biết nên chọn gì:

Database: PostgreSQL hay Cassandra?
Cache: có cần Redis không?
Search: query DB hay Elasticsearch?
Sync: polling hay WebSocket?
Storage: local disk hay object storage?
Scale: một server hay nhiều server?
Consistency: mạnh hay eventual?

Ví dụ: Google Keep bản cá nhân nhỏ thì PostgreSQL là đủ.

Nhưng nếu thiết kế cho hàng trăm triệu user:

- Cần phân vùng dữ liệu theo user
- Cần sync đa thiết bị
- Cần conflict resolution
- Cần search index
- Cần backup
- Cần high availability
- Cần monitoring

Một chức năng giống nhau, nhưng non-functional requirement khác nhau sẽ tạo ra kiến trúc khác nhau.

6. Các nhóm Non-functional Requirement quan trọng

6.1 Scalability — khả năng mở rộng

Câu hỏi:

Nếu user tăng 10 lần, hệ thống có chịu nổi không?

Ví dụ:

1,000 users/ngày
100,000 users/ngày
10 triệu users/ngày

Cách nghĩ:

flowchart TD
    A[Traffic tăng] --> B{Nghẽn ở đâu?}
    B --> C[App Server]
    B --> D[Database]
    B --> E[Cache]
    B --> F[Network]
    B --> G[Third-party API]

Senior sẽ không chỉ nói “thêm server”. Họ hỏi:

- Bottleneck hiện tại là gì?
- Read hay write đang tăng?
- DB CPU cao hay connection pool đầy?
- Cache hit rate bao nhiêu?
- Queue có backlog không?

6.2 Availability — hệ thống có sẵn sàng không?

Availability trả lời:

User có truy cập được hệ thống không?

Ví dụ:

99% uptime     ≈ downtime khoảng 3.65 ngày/năm
99.9% uptime   ≈ downtime khoảng 8.76 giờ/năm
99.99% uptime  ≈ downtime khoảng 52.6 phút/năm

Với blog cá nhân, downtime vài giờ có thể chấp nhận.

Với payment system, downtime vài phút đã rất nghiêm trọng.

6.3 Reliability — hệ thống có đáng tin cậy không?

Reliability khác availability.

Availability là:

Hệ thống có mở được không?

Reliability là:

Hệ thống có làm đúng và không mất dữ liệu không?

Ví dụ payment app:

User chuyển 1 triệu đồng.
Hệ thống không được trừ tiền 2 lần.
Hệ thống không được báo thành công nhưng không ghi transaction.
Hệ thống không được mất lịch sử giao dịch.

6.4 Latency — độ trễ

Latency là thời gian từ lúc user gửi request đến lúc nhận response.

Ví dụ:

Search dưới 300ms
Chat message dưới 200ms
Payment confirmation dưới vài giây
Video start dưới 2 giây

Latency ảnh hưởng trực tiếp đến trải nghiệm người dùng.

Một request có thể chậm vì:

- Query database chậm
- Gọi nhiều service liên tiếp
- Cache miss
- Network xa
- File/video chưa có CDN
- Third-party API chậm

6.5 Throughput — lượng tải xử lý được

Throughput là số lượng request/event hệ thống xử lý trong một khoảng thời gian.

Ví dụ:

- 10,000 requests/second
- 1 triệu messages/minute
- 100,000 orders/hour

Latency và throughput khác nhau:

Latency: một request mất bao lâu?
Throughput: hệ thống xử lý được bao nhiêu request?

6.6 Consistency — dữ liệu có nhất quán không?

Câu hỏi:

Sau khi dữ liệu thay đổi, mọi nơi có thấy cùng một kết quả không?

Ví dụ ngân hàng:

Bạn chuyển tiền xong, số dư phải cập nhật chính xác ngay.

Ví dụ mạng xã hội:

Bạn vừa like bài viết, người khác có thể thấy số like cập nhật trễ vài giây.

Không phải hệ thống nào cũng cần consistency cực mạnh.

Senior phải biết hỏi:

Dữ liệu này có được phép trễ không?
Nếu trễ thì trễ bao lâu?
Nếu sai tạm thời thì hậu quả là gì?

6.7 Durability — dữ liệu có bị mất không?

Durability trả lời:

Khi đã ghi thành công, dữ liệu có được lưu bền vững không?

Ví dụ:

- Tin nhắn không được mất
- Đơn hàng không được mất
- Transaction ngân hàng không được mất
- File upload không được mất

Một số dữ liệu có thể mất được:

- Typing indicator
- Online status
- Cache tạm
- Metrics chưa quan trọng

Một số dữ liệu không được mất:

- Payment transaction
- Order record
- User document
- Medical record

6.8 Security — bảo mật

Security là non-functional requirement rất quan trọng.

Câu hỏi:

Ai được truy cập?
Ai được sửa?
Dữ liệu có cần mã hóa không?
Có chống spam/brute force không?
Có chống injection/XSS/CSRF không?

Ví dụ hệ thống ghi chú cá nhân:

- User chỉ được xem note của mình
- Note riêng tư cần được bảo vệ
- API cần authentication
- Có rate limit để tránh abuse
- Có audit log nếu dữ liệu nhạy cảm

7. Framework hỏi yêu cầu như Senior Engineer

Khi nhận đề bài, bạn có thể hỏi theo khung sau:

1. Scope
2. Users
3. Core features
4. Scale
5. Data
6. Performance
7. Reliability
8. Security
9. Constraints
10. Out of scope

Sơ đồ:

flowchart TD
    A[Nhận đề bài] --> B[Scope]
    B --> C[Users]
    C --> D[Core Features]
    D --> E[Scale]
    E --> F[Data]
    F --> G[Performance]
    G --> H[Reliability]
    H --> I[Security]
    I --> J[Constraints]
    J --> K[Out of Scope]
    K --> L[Chốt yêu cầu trước khi vẽ kiến trúc]

8. Bộ câu hỏi chuẩn khi làm System Design

8.1 Hỏi về scope

- Ta đang thiết kế toàn bộ hệ thống hay chỉ một phần?
- Cần mobile app, web app, backend hay cả infra?
- Có cần admin dashboard không?
- Có cần analytics không?
- Có cần recommendation/search/notification không?

Ví dụ đề: “Thiết kế YouTube.”

Senior sẽ hỏi:

Ta tập trung vào video upload/playback, hay cả comment, like, subscribe, recommendation?

Vì YouTube quá lớn, không thể thiết kế hết trong một lần.

8.2 Hỏi về user

- Ai là người dùng chính?
- Có bao nhiêu loại user?
- User ở một quốc gia hay toàn cầu?
- User dùng web, mobile hay cả hai?
- Có admin/operator không?

Ví dụ e-commerce:

- Buyer
- Seller
- Admin
- Delivery partner
- Payment provider

Mỗi loại user tạo ra yêu cầu khác nhau.

8.3 Hỏi về core features

- 3-5 tính năng quan trọng nhất là gì?
- Tính năng nào bắt buộc?
- Tính năng nào có thể bỏ qua ở version đầu?
- Luồng chính của user là gì?

Ví dụ Google Keep bản đơn giản:

Core:
- Create note
- Read note
- Update note
- Delete note
- Search note

Có thể bỏ qua ban đầu:
- Collaboration
- Voice note
- Drawing
- Reminder

8.4 Hỏi về scale

- Daily active users là bao nhiêu?
- Peak concurrent users là bao nhiêu?
- Requests per second khoảng bao nhiêu?
- Read/write ratio là bao nhiêu?
- Dữ liệu tăng bao nhiêu mỗi ngày?

Ví dụ URL Shortener:

- 1 triệu URL mới/ngày
- 100 triệu redirect/ngày
- Read nhiều hơn write rất nhiều

Từ đó bạn biết redirect path phải cực nhanh, cache rất quan trọng.

8.5 Hỏi về data

- Dữ liệu chính là gì?
- Dữ liệu có quan hệ phức tạp không?
- Dữ liệu có cần transaction không?
- Dữ liệu có thể mất không?
- Dữ liệu cần lưu bao lâu?
- Dữ liệu có cần search không?

Ví dụ hệ thống ghi chú:

Entities:
- User
- Note
- Label
- Attachment

Câu hỏi sâu hơn:

- Note có cần version history không?
- Có cần khôi phục note đã xoá không?
- Có cần sync offline không?
- Có cần conflict resolution khi sửa trên 2 thiết bị không?

8.6 Hỏi về performance

- Latency mục tiêu là bao nhiêu?
- API nào cần nhanh nhất?
- Có tác vụ nào có thể xử lý async không?
- Có cần realtime không?

Ví dụ:

Search note: nên dưới 300ms
Create note: có thể dưới 500ms
Sync background: có thể vài giây
Email notification: có thể async

8.7 Hỏi về reliability/failure

- Nếu database down thì sao?
- Nếu cache down thì sao?
- Nếu third-party API timeout thì sao?
- Có cần retry không?
- Có cần backup/restore không?
- Có cần multi-region không?

Senior luôn giả định:

Failure will happen.

8.8 Hỏi về security

- User xác thực bằng gì?
- Role/permission như thế nào?
- Dữ liệu nào là private?
- Có cần encryption không?
- Có cần rate limiting không?
- Có cần audit log không?

Ví dụ Google Keep:

Note là dữ liệu cá nhân.
User A tuyệt đối không được đọc note của User B.

8.9 Hỏi về constraints

- Có giới hạn ngân sách không?
- Team có kinh nghiệm với công nghệ nào?
- Phải dùng cloud nào?
- Có yêu cầu pháp lý không?
- Có deadline MVP không?

Senior không chỉ thiết kế cho “lý tưởng”, mà còn thiết kế cho thực tế.

8.10 Hỏi về out of scope

Đây là kỹ năng rất senior.

Bạn cần nói rõ:

Trong version này, ta chưa xử lý phần nào?

Ví dụ thiết kế Google Keep đơn giản:

In scope:
- CRUD note
- Search note
- Sync đa thiết bị cơ bản

Out of scope:
- Collaboration realtime
- Drawing note
- Voice transcription
- Reminder notification
- AI summary

Out of scope giúp thiết kế tập trung, không bị lan man.

11. Mẫu ghi yêu cầu chuẩn trước khi thiết kế

Khi bắt đầu một bài system design, hãy viết như sau:

Problem:
Design a personal note-taking app like Google Keep.

Functional Requirements:
1. Users can create, read, update, and delete notes.
2. Users can search notes by title/content.
3. Users can organize notes with labels.
4. Users can sync notes across devices.

Non-functional Requirements:
1. Low latency for reading and searching notes.
2. High durability: saved notes should not be lost.
3. Strong privacy: users can only access their own notes.
4. High availability for read/write operations.
5. The system should scale to millions of users.

Out of Scope:
1. Realtime collaboration.
2. Voice transcription.
3. Drawing notes.
4. Reminder notifications.

Đây là phần mở đầu rất tốt cho mọi bài design.

Điểm cần nhớ:

Requirement không phải phần “nói cho có”. Requirement quyết định toàn bộ kiến trúc phía sau.

13. Cách Senior Engineer chuyển requirement thành quyết định kỹ thuật

Requirement: Search note phải nhanh

Có thể dẫn đến:

- Tạo index trong database
- Dùng full-text search
- Dùng Elasticsearch/OpenSearch nếu search phức tạp

Requirement: Không mất note

Có thể dẫn đến:

- Dùng database có durability tốt
- Backup định kỳ
- Replication
- Transaction khi ghi dữ liệu quan trọng

Requirement: Sync đa thiết bị

Có thể dẫn đến:

- Lưu updated_at/version
- Client pull changes
- Conflict resolution
- Event-based sync

Requirement: User A không xem được note User B

Có thể dẫn đến:

- Authentication
- Authorization check ở mọi query
- Data partition theo user_id
- Security test

Requirement: Scale tới hàng triệu user

Có thể dẫn đến:

- Stateless API servers
- Load balancer
- Database indexing
- Read replicas
- Cache
- Sharding theo user_id khi cần

14. Lỗi thường gặp khi hỏi yêu cầu

Lỗi 1: Hỏi quá chung

Không nên hỏi:

Có cần scale không?

Nên hỏi:

Ta dự kiến có bao nhiêu DAU?
Peak traffic khoảng bao nhiêu request/second?
Read/write ratio khoảng bao nhiêu?

Lỗi 2: Hỏi quá nhiều thứ không liên quan

Không nên hỏi lan man:

Có cần blockchain không?
Có cần AI không?
Có cần AR/VR không?

Senior hỏi những câu ảnh hưởng trực tiếp đến kiến trúc.

Lỗi 3: Không chốt scope

Nếu không chốt scope, đề “Design YouTube” sẽ nổ tung vì quá lớn.

Nên chốt:

Trong bài này, em sẽ tập trung vào:
- Upload video
- Process video
- Watch video
- Metadata/search cơ bản

Em sẽ không đi sâu vào:
- Recommendation
- Comment moderation
- Creator monetization

Lỗi 4: Không phân biệt “must-have” và “nice-to-have”

Ví dụ chat app:

Must-have:
- Gửi/nhận tin nhắn
- Lưu lịch sử tin nhắn
- Hiển thị tin mới

Nice-to-have:
- Typing indicator
- Emoji reaction
- Sticker
- Voice message

Must-have quyết định core architecture. Nice-to-have có thể thêm sau.

15. Công thức 5 phút đầu trong System Design Interview

Khi nhận đề, bạn có thể đi theo thứ tự này:

Minute 1: Clarify scope
Minute 2: Define core functional requirements
Minute 3: Define non-functional requirements
Minute 4: Estimate scale/read-write pattern
Minute 5: Confirm assumptions and out-of-scope

Ví dụ nói thành lời:

Before jumping into the design, I’d like to clarify the scope.

For this design, I’ll focus on creating, reading, updating, deleting, searching, and syncing notes across devices.

I’ll assume we need low-latency reads, strong data durability, user-level privacy, and the ability to scale to millions of users.

I’ll keep realtime collaboration, voice transcription, and reminders out of scope for the first version.

Đây là cách nói rất senior.

16. Mini case study: thiết kế hệ thống đặt đồ ăn

Functional Requirements

- User xem danh sách nhà hàng
- User xem menu
- User tạo đơn hàng
- User thanh toán
- User theo dõi trạng thái đơn
- Nhà hàng nhận/chấp nhận/từ chối đơn
- Shipper nhận đơn giao hàng

Non-functional Requirements

- Order không được mất
- Không được thanh toán hai lần
- Trạng thái đơn hàng gần realtime
- Hệ thống chịu peak traffic giờ ăn trưa/tối
- Payment phải bảo mật
- Nếu notification lỗi, order vẫn phải tạo thành công

Từ yêu cầu này, bạn bắt đầu thấy kiến trúc:

flowchart TD
    User[User App] --> API[API Gateway]
    Restaurant[Restaurant App] --> API
    Driver[Driver App] --> API

    API --> Order[Order Service]
    API --> Menu[Menu Service]
    API --> Payment[Payment Service]
    API --> Tracking[Tracking Service]

    Order --> OrderDB[(Order DB)]
    Menu --> MenuDB[(Menu DB)]
    Payment --> PaymentProvider[Payment Provider]

    Order --> Queue[Message Queue]
    Queue --> Notification[Notification Worker]
    Queue --> Analytics[Analytics Worker]

Vì sao có queue?

- Tạo order là tác vụ chính
- Gửi notification là tác vụ phụ
- Analytics là tác vụ phụ
- Không nên để notification/analytics làm chậm hoặc làm fail order

Đây chính là việc non-functional requirement ảnh hưởng đến kiến trúc.

18. Cách ghi nhớ bài này

Hãy nhớ công thức:

FR = What should the system do?
NFR = How well should the system do it?

Hoặc tiếng Việt:

Functional Requirement:
Hệ thống làm gì?

Non-functional Requirement:
Hệ thống làm tốt đến mức nào?

Và câu quan trọng nhất:

Không hỏi requirement thì mọi kiến trúc chỉ là đoán mò.

3. Senior Engineer không vẽ kiến trúc ngay.
4. Senior Engineer hỏi scope, user, scale, data, performance, reliability, security trước.
5. Requirement quyết định API, database, cache, queue, CDN, replication, sharding và monitoring.
6. Thiết kế tốt bắt đầu từ câu hỏi tốt.
