Bài 19 — Batch Processing và Stream Processing

Trong nhiều hệ thống, dữ liệu không chỉ được lưu để truy vấn trực tiếp. Nó còn phải được xử lý để tạo ra:

- Báo cáo doanh thu
- Dashboard realtime
- Recommendation
- Fraud detection
- Search index
- Notification
- Billing
- Machine-learning features
- Materialized views

Có hai mô hình xử lý chính:

Batch processing:
Xử lý một tập dữ liệu hữu hạn.

Stream processing:
Xử lý dòng dữ liệu liên tục hoặc không có điểm kết thúc rõ ràng.

Bài này nối tiếp nội dung về message queue, event ordering, consistency và observability trong bộ System Design bạn đã tải lên.

Các khái niệm trọng tâm:

- Batch job
- Event stream
- Bounded và unbounded data
- Event time, ingestion time, processing time
- Tumbling, sliding và session windows
- Watermark
- Late events
- At-most-once, at-least-once, exactly-once
- Checkpoint và replay
- Stateful stream processing
- Stream joins
- Backpressure và consumer lag

1. Batch Processing là gì?

Batch processing xử lý một lượng dữ liệu đã được gom lại thành một lô.

Ví dụ:

- Mỗi đêm tính doanh thu ngày hôm trước
- Mỗi giờ tổng hợp số lượt click
- Mỗi tuần tạo báo cáo tài chính
- Reindex toàn bộ product catalog
- Huấn luyện recommendation model

Một batch job thường có:

Input hữu hạn
→ Xử lý
→ Output
→ Kết thúc

flowchart LR
    Input[(Files / Tables)] --> Job[Batch Job]
    Job --> Output[(Report / Table)]

2. Ví dụ Batch Job

Giả sử có bảng orders:

order_id
user_id
amount
status
created_at

Mỗi ngày lúc 01:00 chạy:

SELECT
    DATE(created_at) AS order_date,
    SUM(amount) AS revenue
FROM orders
WHERE status = 'COMPLETED'
  AND created_at >= '2026-07-12 00:00:00'
  AND created_at <  '2026-07-13 00:00:00'
GROUP BY DATE(created_at);

Kết quả:

Revenue ngày 12/07/2026:
2.500.000.000 VND

3. Đặc điểm của Batch Processing

Batch thường ưu tiên:

- Throughput cao
- Xử lý lượng dữ liệu lớn
- Tính chính xác và khả năng chạy lại
- Không cần kết quả ngay lập tức

Latency có thể là:

- Vài phút
- Vài giờ
- Một ngày

Tùy use case.

4. Stream Processing là gì?

Stream processing xử lý dữ liệu khi các event liên tục xuất hiện.

Ví dụ:

- User click vào sản phẩm
- Payment thành công
- Sensor gửi nhiệt độ
- Order được tạo
- Driver thay đổi vị trí
- Log được sinh ra

flowchart LR
    Producers --> Stream[Event Stream]
    Stream --> Processor[Stream Processor]
    Processor --> Sink[(State / Alert / Output Stream)]

Stream có thể không bao giờ “kết thúc”:

Event 1
Event 2
Event 3
...

5. Stream không nhất thiết xử lý từng Event riêng lẻ

Có hai cách triển khai phổ biến:

Record-at-a-time

Mỗi event được xử lý gần như ngay lập tức.

Event đến
→ xử lý
→ cập nhật state

Micro-batch

Gom event trong khoảng ngắn:

500 ms
1 giây
5 giây

rồi xử lý thành batch nhỏ.

Về mặt sản phẩm, cả hai đều có thể được gọi là stream processing nếu dữ liệu được xử lý liên tục với latency thấp.

6. Bounded và Unbounded Data

Một cách nhìn sâu hơn:

Bounded data

Tập dữ liệu có điểm đầu và cuối rõ ràng.

Tất cả orders của tháng 6
Một file log 100 GB
Snapshot database ngày hôm qua

Phù hợp với batch.

Unbounded data

Dòng dữ liệu tiếp tục tăng:

Click stream
Transaction stream
Sensor stream

Phù hợp với stream processing.

7. Batch và Stream không hoàn toàn đối lập

Một stream vô hạn có thể được chia thành các cửa sổ hữu hạn:

Mỗi 1 phút
Mỗi 5 phút
Mỗi session

Ngược lại, batch processing có thể chạy rất thường xuyên:

Mỗi 30 giây

Do đó batch và stream là một phổ:

Batch lớn, latency cao
←────────────────────────────→
Micro-batch, continuous stream

8. Khi nào chọn Batch?

Batch phù hợp khi:

- Không cần realtime
- Dataset lớn nhưng hữu hạn
- Muốn chạy lại toàn bộ dễ dàng
- Thuật toán cần nhìn toàn bộ dữ liệu
- Tối ưu throughput hơn latency

Ví dụ:

- Báo cáo cuối ngày
- Monthly billing
- Historical analytics
- Model training
- Data warehouse transformation
- Full reindex

9. Khi nào chọn Stream?

Stream phù hợp khi:

- Phải phản ứng nhanh với event
- Dữ liệu đến liên tục
- Cần cập nhật materialized view
- Cần cảnh báo tức thời
- Không thể đợi batch tiếp theo

Ví dụ:

- Fraud detection
- Realtime dashboard
- Ride location tracking
- Notification
- Inventory projection
- Recommendation features

10. So sánh Batch và Stream

Tiêu chí Batch Stream

Tối ưu Throughput Latency và freshness
State Thường đọc toàn dataset Duy trì state lâu dài
Failure recovery Chạy lại job Checkpoint + replay
Late data Thường đã có đủ dữ liệu Phải xử lý trực tiếp
Complexity Thấp hơn Cao hơn
Use case Reporting, backfill Alert, realtime view

11. Event Stream

Event stream là chuỗi record biểu diễn những sự kiện đã xảy ra.

Ví dụ:

{
  "eventId": "evt_123",
  "eventType": "OrderCreated",
  "orderId": "ord_456",
  "userId": "u_789",
  "amount": 500000,
  "occurredAt": "2026-07-13T10:00:00Z"
}

Một stream thường có:

- Topic hoặc stream name
- Partitions
- Ordered offsets trong từng partition
- Retention
- Consumers

12. Event Stream khác Work Queue

Work queue

Một task thường được một worker xử lý.

Generate thumbnail
Send email
Process upload

Event stream

Nhiều consumer độc lập có thể đọc cùng event:

OrderCreated
→ Inventory
→ Analytics
→ Notification
→ Fraud detection

Event stream thường lưu event trong một thời gian để consumer có thể replay.

13. Event phải là Business Fact

Event tốt thường mô tả điều đã xảy ra:

OrderCreated
PaymentAuthorized
InventoryReserved
UserRegistered

Không nên đặt tên quá mơ hồ:

DataChanged
SomethingUpdated

Event rõ ràng giúp:

- Consumer hiểu semantics
- Debug workflow
- Quản lý schema
- Replay an toàn hơn

14. Event Time

Event time là thời điểm sự kiện thực sự xảy ra tại nguồn.

Ví dụ thiết bị ghi:

Nhiệt độ đo lúc 10:00:00

Event được gửi sau:

{
  "temperature": 35,
  "eventTime": "10:00:00"
}

Event time quan trọng khi kết quả cần phản ánh thời điểm nghiệp vụ thực sự.

15. Ingestion Time

Ingestion time là lúc event đi vào hạ tầng xử lý, ví dụ broker.

Event xảy ra:
10:00:00

Đi vào broker:
10:00:05

Độ trễ ingestion:

5 giây

16. Processing Time

Processing time là thời điểm stream processor thực sự xử lý event.

Event time:      10:00:00
Ingestion time:  10:00:05
Processing time: 10:00:12

Processing có thể muộn do:

- Queue backlog
- Worker quá tải
- Retry
- Network
- Pause hoặc restart

17. Ba loại thời gian

flowchart LR
    Event[Event xảy ra
10:00:00] --> Broker[Đi vào broker
10:00:05]
    Broker --> Worker[Được xử lý
10:00:12]
Loại Ý nghĩa
Event time Khi sự kiện thực sự xảy ra
Ingestion time Khi event vào hệ thống
Processing time Khi processor xử lý event

18. Vì sao Processing Time có thể sai với nghiệp vụ?

Giả sử mobile offline.

User click sản phẩm lúc:

10:00

Điện thoại có mạng lại lúc:

10:30

Nếu tính click theo processing time:

Click thuộc cửa sổ 10:30

Nhưng về nghiệp vụ:

Click thuộc cửa sổ 10:00

Analytics lịch sử thường cần event time.

19. Processing-Time Window

Processor gom event theo thời điểm xử lý.

Ví dụ:

Tính số event được xử lý từ 10:00 đến 10:05.

Ưu điểm:

- Đơn giản
- Không cần watermark
- Kết quả nhanh

Nhược điểm:

- Không phản ánh đúng thời điểm event xảy ra
- Kết quả thay đổi khi backlog hoặc retry
- Chạy lại có thể cho kết quả khác

20. Event-Time Window

Processor nhóm event theo timestamp nghiệp vụ.

Ví dụ:

Tính tất cả giao dịch xảy ra từ 10:00 đến 10:05.

Dù event được xử lý lúc 10:10, nó vẫn thuộc cửa sổ 10:00–10:05.

Ưu điểm:

- Kết quả đúng theo thời gian nghiệp vụ
- Ổn định hơn khi backlog
- Replay dễ tái tạo kết quả

Nhược điểm:

- Phải xử lý event đến muộn
- Cần watermark
- Giữ state lâu hơn

21. Windowing là gì?

Stream không có điểm kết thúc, nên để tính aggregation ta phải chia nó thành các cửa sổ.

Ví dụ:

Số orders mỗi phút
Doanh thu mỗi giờ
Unique users mỗi ngày

flowchart LR
    Stream[Continuous Events] --> W1[Window 10:00–10:05]
    Stream --> W2[Window 10:05–10:10]
    Stream --> W3[Window 10:10–10:15]

22. Tumbling Window

Tumbling window có:

- Kích thước cố định
- Không overlap

Ví dụ cửa sổ 5 phút:

10:00–10:05
10:05–10:10
10:10–10:15

Mỗi event thuộc đúng một window.

timeline
    title Tumbling Windows
    10:00–10:05 : Window 1
    10:05–10:10 : Window 2
    10:10–10:15 : Window 3

Phù hợp:

- Revenue mỗi giờ
- Requests mỗi phút
- Daily active users

23. Sliding hoặc Hopping Window

Sliding window có:

- Window size
- Slide interval

Ví dụ:

Window size = 10 phút
Slide = 5 phút

Các window:

10:00–10:10
10:05–10:15
10:10–10:20

Các window overlap.

Một event có thể thuộc nhiều window.

24. Ví dụ Sliding Window

Yêu cầu:

Tính error rate trong 10 phút gần nhất, cập nhật mỗi phút.

Window size:
10 phút

Slide:
1 phút

Mỗi phút hệ thống tính trên 10 phút gần nhất.

Phù hợp:

- Alerting
- Moving average
- Fraud velocity
- Realtime trends

25. Chi phí Sliding Window

Nếu triển khai ngây thơ, một event có thể được copy vào nhiều window.

Ví dụ:

Window = 1 giờ
Slide = 1 phút

Một event có thể thuộc 60 windows.

Cách tối ưu:

- Pane aggregation
- Incremental add/remove
- Bucket nhỏ rồi kết hợp

26. Session Window

Session window nhóm event theo thời gian hoạt động của một user hoặc entity.

Ví dụ:

Nếu không có event mới trong 30 phút
→ session kết thúc

User event lúc:
10:00
10:05
10:12

Không hoạt động 30 phút
→ Session 1 kết thúc

Event mới 11:00
→ Session 2

27. Session Window có biên động

Khác tumbling window:

10:00–10:05 cố định

Session window phụ thuộc vào dữ liệu:

Session A:
10:00–10:12

Session B:
11:00–11:20

Phù hợp:

- User session
- Shopping journey
- Machine activity burst
- Network connection session

28. Session Merge

Hai session đang tách biệt có thể phải merge khi late event xuất hiện.

Giả sử inactivity gap là 10 phút:

Session 1:
10:00–10:05

Session 2:
10:16–10:20

Late event lúc:

10:10

Có thể nối hai session thành:

10:00–10:20

Session windows vì vậy cần state và logic merge phức tạp hơn.

29. Global Window

Global window đặt toàn bộ event vào một window logic.

Nó chỉ hữu ích khi đi kèm trigger hoặc logic tùy chỉnh:

- Phát kết quả mỗi 1.000 events
- Phát mỗi 10 giây
- Phát khi condition đạt

Nếu không có trigger, global window không bao giờ kết thúc với stream vô hạn.

30. Window Key

Aggregation thường được nhóm theo key.

Ví dụ:

Doanh thu mỗi 5 phút theo merchant

Key:

merchantId

Window:

5 phút

State logic:

(merchantId, windowStart)
→ revenue

31. Window Boundary

Cần định nghĩa rõ:

[start, end)

Ví dụ window:

[10:00, 10:05)

Bao gồm:

10:00:00
10:04:59.999

Không bao gồm:

10:05:00

Event 10:05:00 thuộc window tiếp theo.

32. Timezone và Daily Window

“Doanh thu mỗi ngày” có thể nghĩa:

- Ngày UTC
- Ngày theo Asia/Bangkok
- Ngày theo timezone merchant

Nếu business hoạt động đa quốc gia, daily window cần timezone rõ ràng.

Daylight-saving time cũng có thể tạo ngày:

23 giờ
hoặc
25 giờ

Không nên giả định mọi ngày luôn chính xác 24 giờ theo local calendar.

33. Watermark là gì?

Watermark là ước lượng tiến độ của event time.

Watermark T có nghĩa gần đúng:

Hệ thống tin rằng phần lớn event có event time nhỏ hơn hoặc bằng T đã đến.

Ví dụ:

Watermark = 10:05

Processor có thể cân nhắc đóng window:

10:00–10:05

34. Watermark không phải cam kết tuyệt đối

Watermark không nói:

Không còn event cũ nào đến nữa.

Nó chỉ là policy hoặc ước lượng.

Sau watermark 10:05, event time 10:02 vẫn có thể đến.

Đó là:

Late event

35. Vì sao cần Watermark?

Nếu dùng event-time window và chờ mọi event:

Ta không bao giờ biết chắc đã nhận đủ.

Network có thể trì hoãn vô hạn.

Watermark cho phép hệ thống cân bằng:

- Chờ dữ liệu muộn để tăng chính xác
- Phát kết quả sớm để giảm latency

36. Watermark đơn giản theo Maximum Event Time

Một policy khái niệm:

watermark =
maximum observed event time
- allowed out-of-orderness

Ví dụ:

Max event time đã thấy:
10:10

Cho phép out-of-order:
2 phút

Watermark:
10:08

Windows kết thúc trước 10:08 có thể được đóng sơ bộ.

37. Watermark theo Partition

Mỗi partition có watermark riêng.

Global operator thường phải dùng watermark nhỏ nhất:

Partition A watermark = 10:10
Partition B watermark = 10:09
Partition C watermark = 09:30

Global watermark = 09:30

Partition C làm toàn pipeline chậm.

38. Idle Partition

Partition C có thể không chậm; nó chỉ không có event.

Nếu watermark dựa trên event mới nhất:

Partition không có event
→ watermark không tiến

Cần idle-partition detection:

Nếu partition không có activity trong N phút,
tạm loại khỏi global watermark calculation.

Phải cẩn thận vì event cũ vẫn có thể xuất hiện khi partition hoạt động lại.

39. Watermark từ Source

Source đáng tin cậy có thể gán watermark tốt hơn processor.

Ví dụ sensor gateway biết:

Tất cả events trước sequence X đã được gửi.

Hoặc file source biết:

Đã đọc xong toàn bộ file của giờ 10.

Watermark dựa trên source semantics thường chính xác hơn chỉ đo arrival delay.

40. Late Event là gì?

Late event là event đến sau khi watermark đã vượt qua window mà event thuộc về.

Ví dụ:

Window:
10:00–10:05

Watermark hiện tại:
10:08

Event mới đến:
eventTime = 10:03

Event này late.

41. Late khác Delayed

Mọi late event đều bị trì hoãn, nhưng “late” được định nghĩa tương đối với watermark và window policy.

Event đến chậm 10 phút chưa chắc late nếu watermark vẫn chưa tiến.

Event chậm 30 giây có thể late nếu watermark aggressive.

42. Chính sách xử lý Late Event

Các lựa chọn:

1. Bỏ event.
2. Gửi vào side output.
3. Cập nhật kết quả window cũ.
4. Phát correction/retraction.
5. Ghi raw storage để batch sửa sau.

Lựa chọn phụ thuộc nghiệp vụ.

43. Drop Late Event

Phù hợp khi:

- Late event rất hiếm
- Kết quả realtime chỉ mang tính gần đúng
- Chi phí sửa cao hơn giá trị

Ví dụ:

Realtime dashboard không cần chính xác tuyệt đối.

Nhưng cần metric:

late_events_dropped_total

Không nên âm thầm bỏ.

44. Allowed Lateness

Cho phép window tiếp tục nhận event sau watermark trong một khoảng.

Ví dụ:

Window:
10:00–10:05

Allowed lateness:
10 phút

Window có thể giữ state đến:

10:15

Event tới trước deadline được cập nhật.

Sau đó state mới bị xóa.

45. Chi phí Allowed Lateness

Allowed lateness lớn:

- Chính xác hơn
- Giữ state lâu hơn
- Tăng memory/disk
- Nhiều correction hơn

Allowed lateness nhỏ:

- Kết quả nhanh
- State ít
- Bỏ nhiều late data hơn

Đây là trade-off trực tiếp giữa latency, cost và completeness.

46. Early Result và Final Result

Processor có thể phát nhiều phiên bản kết quả.

Ví dụ window 10:00–10:05:

10:01:
Early result = 100 orders

10:05:
On-time result = 520 orders

10:08:
Late correction = 525 orders

Sink phải biết xử lý update.

47. Append, Update và Retract

Append mode

Mỗi output chỉ được thêm một lần.

Phù hợp khi window đã thực sự đóng.

Update mode

Phát giá trị mới của kết quả:

count = 520
sau đó
count = 525

Retract mode

Phát:

-520
+525

để downstream sửa kết quả trước.

Sink phải hỗ trợ semantics tương ứng.

48. Upsert Sink

Một cách xử lý correction:

Primary key:
(windowStart, merchantId)

Mỗi output upsert:

UPDATE revenue_windows
SET revenue = :latest_value
WHERE merchant_id = :merchant_id
  AND window_start = :window_start;

Late result ghi đè bản cũ.

Cần version hoặc deterministic ordering để event output cũ không ghi đè output mới.

49. Side Output cho Late Events

Late event quá giới hạn có thể được gửi tới:

late-events topic

Sau đó:

- Điều tra
- Batch correction
- Reconciliation
- Manual review

Điều này tốt hơn bỏ im lặng khi dữ liệu có giá trị tài chính.

50. Trigger

Trigger xác định khi nào window phát output.

Có thể theo:

- Event time
- Processing time
- Số lượng event
- Điều kiện tùy chỉnh

Ví dụ:

Phát early result mỗi phút
và final result khi watermark qua window end.

51. Accumulating và Discarding

Sau khi trigger phát output:

Accumulating

Giữ dữ liệu trước và tiếp tục cộng thêm.

Output 1:
100

Output 2:
150

Discarding

Xóa phần đã phát và chỉ tính delta mới.

Output 1:
100

Output 2:
50

Sink phải biết output là tổng hay delta.

52. Stateful Stream Processing

Stateless processing:

Event vào
→ biến đổi
→ event ra

Ví dụ:

Parse JSON
Mask email
Convert currency

Stateful processing cần nhớ dữ liệu từ event trước.

Ví dụ:

- Count events
- Deduplicate
- Window aggregation
- Join streams
- Detect fraud pattern
- Sessionization

54. Keyed State

key = userId

56. State Size

Ví dụ deduplicate mọi eventId mãi mãi:

- TTL

Maximum expected retry hoặc lateness

57. Approximate State

Một số use case chấp nhận xấp xỉ.

HyperLogLog-like sketch

Đổi lại:

- Có sai số

58. Deduplication

Processor lưu:

Nếu event đến lại:

Bỏ qua.

Nhưng cần TTL.

Nếu broker chỉ retry trong 7 ngày:

Có thể giữ dedupe state hơn 7 ngày

tùy backfill và replay policy.

59. Deduplicate theo Business Key

Event ID đôi khi thay đổi dù operation nghiệp vụ giống nhau.

Ví dụ retry payment tạo event mới sai thiết kế.

transactionReference

Không có match.

69. Delivery Semantics

Ba thuật ngữ thường gặp:

- At-most-once
- At-least-once
- Exactly-once

Chúng phải được phân tích xuyên suốt:

Source
→ Processor
→ State
→ Sink

Không chỉ nhìn broker.

70. At-Most-Once

Event được xử lý:

0 hoặc 1 lần

Nếu failure xảy ra:

Event có thể mất.

Ví dụ:

1. Consumer nhận event.
2. ACK broker trước.
3. Consumer crash trước xử lý.

Event không được gửi lại.

Ưu điểm:

- Đơn giản
- Không duplicate
- Latency thấp

Nhược điểm:

- Có thể mất dữ liệu

71. At-Least-Once

Event được xử lý:

Một hoặc nhiều lần

Ví dụ:

1. Consumer xử lý event.
2. Cập nhật state.
3. Crash trước ACK.
4. Broker giao lại.

Event được xử lý lại.

Ưu điểm:

- Không mất event nếu retry hoạt động

Nhược điểm:

- Duplicate
- Cần idempotency hoặc deduplication

72. Exactly-Once

Exactly-once thường có nghĩa cụ thể hơn:

Mỗi input event chỉ tạo một hiệu ứng logic đúng một lần trong phạm vi được hệ thống bảo vệ.

Không nên hiểu:

Mọi byte trên mạng chỉ được gửi đúng một lần.

Message vẫn có thể:

- Được gửi lại
- Được đọc lại
- Được xử lý lại khi recovery

Nhưng state/output cuối không bị nhân đôi.

73. Exactly-Once Processing khác Exactly-Once Effect

Processor có thể bảo đảm state nội bộ exactly-once.

Nhưng nếu gọi external API:

Charge credit card
Send email

external side effect có thể vẫn duplicate.

Cần thêm:

- Idempotency key
- Transactional sink
- Deduplication tại destination

74. End-to-End Semantics

Phải xem toàn bộ pipeline:

Broker source
→ Stream processor
→ Database sink

Nếu source offset được checkpoint nhưng database write không atomic với checkpoint:

Có thể mất hoặc lặp output.

Exactly-once end-to-end cần coordination giữa:

- Input positions
- Processor state
- Output commits

75. Offset

Offset xác định vị trí consumer đã đọc trong partition.

Partition 0:
offset 100
101
102
103

Consumer checkpoint:

Đã xử lý tới offset 102.

Sau restart:

Tiếp tục từ 103.

76. Commit Offset quá sớm

1. Đọc offset 100.
2. Commit offset 100.
3. Xử lý event.
4. Crash trước bước 3.

Event bị mất.

Đây gần at-most-once.

77. Commit Offset sau xử lý

1. Đọc offset 100.
2. Xử lý.
3. Ghi output.
4. Commit offset.

Nếu crash giữa bước 3 và 4:

Event được xử lý lại.

Đây gần at-least-once.

78. Checkpoint

Checkpoint lưu snapshot nhất quán của:

- Input offsets
- Operator state
- Timers
- Window state

Ví dụ:

Checkpoint 42:
Partition A offset 1000
Partition B offset 850
Fraud state snapshot X
Window state snapshot Y

Sau failure, job phục hồi từ checkpoint 42 và replay event sau các offsets đó.

79. Checkpoint Interval

Checkpoint thường xuyên:

- Recovery ít replay
- Overhead cao

Checkpoint thưa:

- Throughput tốt hơn
- Recovery phải replay nhiều hơn

Ví dụ:

Checkpoint mỗi 10 giây

thì có thể cần replay gần 10 giây dữ liệu sau crash.

80. Consistent Checkpoint

Không thể snapshot từng operator tại thời điểm ngẫu nhiên nếu messages đang truyền giữa chúng.

Có thể tạo state không tương ứng với bất kỳ execution hợp lệ nào.

Cần snapshot nhất quán bao gồm:

- State của operators
- Messages hoặc boundaries giữa operators
- Input positions

81. Checkpoint Barrier

Một số engine đưa barrier vào stream.

flowchart LR
    Source --> E1[Events]
    E1 --> B[Checkpoint Barrier]
    B --> E2[Later Events]

Khi operator nhận barrier trên tất cả input:

- Snapshot state trước barrier
- Chuyển barrier downstream

Tạo distributed consistent snapshot mà không dừng toàn pipeline quá lâu.

82. Aligned Checkpoint

Operator có nhiều input.

Khi barrier đến từ Input A trước B:

A tạm dừng
→ chờ barrier từ B

Điều này bảo đảm alignment.

Nhược điểm:

Input chậm gây checkpoint delay và backpressure.

83. Unaligned Checkpoint

Có thể snapshot cả:

- Operator state
- In-flight buffers

không cần chờ inputs alignment hoàn toàn.

Ưu điểm:

Tốt hơn khi backpressure lớn.

Nhược điểm:

Checkpoint lớn hơn
Recovery phức tạp hơn

84. Transactional Sink

Để exactly-once, sink có thể hỗ trợ transaction.

Quy trình:

1. Processor ghi output vào transaction tạm.
2. Checkpoint hoàn tất.
3. Commit sink transaction.

Nếu checkpoint thất bại:

Abort output transaction.

Input state và output cùng tiến theo checkpoint boundary.

85. Idempotent Sink

Nếu sink không hỗ trợ distributed transaction, có thể dùng idempotency.

Ví dụ output key:

(windowId, merchantId)

Ghi:

UPSERT latest aggregate

Replay cùng result không tạo duplicate row.

Đây thường dễ hơn exactly-once transaction xuyên nhiều hệ thống.

86. Output Deduplication

Mỗi output mang:

jobId
partition
checkpointId
recordSequence

Sink lưu IDs đã nhận.

Duplicate bị bỏ qua.

Nhưng dedupe state cũng cần retention và HA.

87. Exactly-Once không miễn phí

Chi phí:

- Checkpoint
- Durable state
- Transactional commit
- Coordination
- Latency
- Storage

Không phải use case nào cũng cần exactly-once.

Ví dụ:

Realtime view counter

có thể chấp nhận at-least-once cộng reconciliation.

Billing tài chính cần semantics mạnh hơn.

88. Restart Strategy

Khi task fail:

- Restart task đó
- Restart region pipeline
- Restart toàn job

Tùy topology và checkpoint mechanism.

Restart quá nhanh có thể tạo crash loop.

Cần:

- Exponential backoff
- Restart budget
- Alert
- Poison event handling

89. Poison Event

Một event có schema lỗi làm processor crash mỗi lần replay.

Nếu restart vô hạn:

Job không thể tiến.

Giải pháp:

- Schema validation
- Retry giới hạn
- DLQ/side output
- Skip có audit nếu được phép
- Manual repair

Không nên bỏ event tài chính mà không có quy trình xử lý.

90. Savepoint

Checkpoint thường phục vụ automatic recovery.

Savepoint thường là snapshot có chủ đích để:

- Upgrade job
- Thay code
- Rescale
- Migration
- Rollback

Savepoint cần tương thích với state schema của version mới.

91. State Schema Evolution

Job v1 lưu:

userId → count

Job v2 cần:

userId → {count, totalAmount}

Phải xử lý:

- Deserialize state cũ
- Default fields
- Migration
- Rollback

Stateful job upgrade khó hơn stateless service deployment.

92. Rescaling Stateful Job

Tăng workers từ 4 lên 8.

Keyed state phải được phân phối lại:

Worker 1 trước:
keys A–F

Sau rescale:
một phần chuyển sang workers mới.

Quá trình cần:

- Snapshot
- State transfer
- Routing update
- Recovery

State lớn làm rescale lâu.

93. Key Groups hoặc Logical Partitions

Có thể tạo nhiều logical partitions hơn workers.

Ví dụ:

1.024 key groups
8 workers

Mỗi worker sở hữu nhiều key groups.

Khi rescale, chỉ cần đổi mapping key group → worker.

Ý tưởng tương tự virtual shards.

94. Hot Key

Nếu key:

celebrity_123

nhận 1 triệu event/giây, tất cả đi cùng worker để giữ ordering.

Worker trở thành bottleneck.

Đây là hot-key problem.

95. Cách xử lý Hot Key

- Local pre-aggregation ở source
- Salt/bucket key
- Two-stage aggregation
- Dedicated worker
- Approximate aggregation
- Rate limiting

Ví dụ count:

celebrity_123_bucket_0
...
celebrity_123_bucket_99

Sau đó merge 100 partial counts.

Trade-off:

Phân tán tốt hơn
nhưng ordering và exact state phức tạp hơn.

96. Two-Stage Aggregation

Stage 1:

Local partial sums theo partition

Stage 2:

Merge partial sums theo final key

flowchart LR
    Events --> P1[Partial Aggregate 1]
    Events --> P2[Partial Aggregate 2]
    Events --> P3[Partial Aggregate 3]

    P1 --> Final[Final Aggregate]
    P2 --> Final
    P3 --> Final

Giảm network và hot-key pressure.

97. Backpressure

Backpressure xảy ra khi downstream xử lý chậm hơn upstream.

Producer rate:
100.000 events/s

Processor capacity:
60.000 events/s

Backlog tăng:

40.000 events/s

Nếu kéo dài:

- Queue lag tăng
- Memory buffer đầy
- Latency tăng
- Checkpoint chậm
- Job có thể crash

98. Backpressure Propagation

flowchart LR
    Source --> OperatorA
    OperatorA --> OperatorB
    OperatorB --> Sink

    Sink -. slow .-> OperatorB
    OperatorB -. pressure .-> OperatorA
    OperatorA -. pressure .-> Source

Một pipeline tốt phải làm chậm upstream có kiểm soát thay vì buffer vô hạn.

99. Nguyên nhân Backpressure

- Sink database chậm
- External API rate limit
- Hot key
- CPU-heavy transformation
- Serialization lớn
- Network bandwidth
- Checkpoint/merge pressure
- Garbage collection

Scale consumers không luôn giải quyết nếu bottleneck là sink.

100. Consumer Lag

Lag có thể đo:

latest broker offset
-
processed offset

Nhưng offset lag không luôn phản ánh thời gian.

1 triệu event có thể tương ứng:

- 10 giây ở traffic cao
- 10 giờ ở traffic thấp

Nên theo dõi thêm:

Oldest unprocessed event age

101. Event-Time Lag

Có thể đo:

current wall time
-
maximum processed event time

Ví dụ:

Current:
10:20

Processor đã xử lý tới event time:
10:12

Event-time lag:
8 phút

Cẩn thận nếu source tạo event có clock sai.

102. Scaling Stream Processor

Có thể tăng:

- Số partitions
- Số workers
- CPU/memory
- Batch size
- Parallelism từng operator

Nhưng maximum parallelism thường bị giới hạn bởi partition count hoặc key distribution.

Nếu topic có 10 partitions:

Một consumer group chỉ có tối đa khoảng 10 active partition consumers.

103. Rebalancing Consumer

Khi worker join hoặc leave:

Partitions được phân phối lại.

Với stateless consumer, khá đơn giản.

Với stateful consumer:

- State phải restore
- Cache lạnh
- Processing pause
- Watermark có thể chậm

Frequent rebalance làm latency không ổn định.

104. Small Files Problem trong Batch

Batch pipeline thường tạo hàng triệu file nhỏ.

Hậu quả:

- Metadata overhead
- Scheduling overhead
- Read throughput thấp
- Nhiều network request

Cần:

- Compaction
- Partition sizing
- File format phù hợp
- Batch output coalescing

105. Data Partitioning trong Batch

Batch data thường được partition theo:

country=VN/
region=HN/

Query chỉ đọc partitions liên quan.

Nhưng partition quá chi tiết:

user_id=...

có thể tạo hàng triệu directories/files nhỏ.

106. Map và Reduce ở mức trực giác

109. Incremental Batch

Không nhất thiết mỗi ngày đọc toàn bộ lịch sử.

Có thể chỉ đọc dữ liệu mới:

updated_at > last_successful_watermark

Sau đó:

Merge vào output hiện tại.

Ưu điểm:

- Nhanh hơn
- Rẻ hơn

Nhược điểm:

- Phải quản lý checkpoint
- Handle late update
- Delete khó hơn

110. Batch Watermark

Trong batch ingestion, watermark cũng có thể là:

Đã xử lý source tới timestamp/ID/LSN nào?

Ví dụ:

last_processed_order_id = 1.000.000

Job sau đọc:

order_id > 1.000.000

Phải tránh mất dữ liệu khi job fail giữa đọc và commit output.

111. Batch Job Idempotency

Nếu batch job chạy lại cùng ngày:

Không được tạo doanh thu gấp đôi.

Các cách:

- Overwrite partition
- MERGE theo business key
- Atomic table swap
- Output versioned directory

Không tốt:

INSERT thêm mà không deduplicate.

112. Atomic Batch Publish

Job có thể ghi vào thư mục tạm:

/output/date=2026-07-13/_temporary/

Sau khi thành công:

Atomically publish metadata hoặc rename.

Consumer không thấy output nửa hoàn chỉnh.

113. Partial Batch Failure

Job có 1.000 tasks, 999 thành công, một task lỗi.

Không nên publish toàn bộ output như hoàn chỉnh.

Cần:

- Retry task lỗi
- Job-level success marker
- Atomic commit
- Output validation

114. Backfill

Backfill xử lý dữ liệu lịch sử.

Ví dụ:

Thêm field mới:
customer_segment

Cần tính cho 5 năm orders cũ.

Backfill có thể gây:

- Tải lớn
- Queue backlog
- Search merge pressure
- Database reads cao

Phải throttle và tách khỏi realtime workload khi có thể.

115. Backfill và Realtime Events

Trong khi backfill dữ liệu cũ, event mới vẫn đến.

Cần ngăn event cũ ghi đè state mới.

Ví dụ:

Realtime version 100 đã được xử lý.
Backfill version 20 đến sau.

Dùng:

Entity version
Event time
Commit sequence
Conditional upsert

116. Batch Correction cho Stream

Một pattern thực tế:

Stream:
Kết quả nhanh nhưng có thể gần đúng

Định kỳ tính lại chính xác từ raw data

Đây là một ý tưởng của Lambda Architecture.

117. Lambda Architecture

1. Batch layer

118. Nhược điểm Lambda Architecture

119. Kappa Architecture

Replay raw event log

Ưu điểm:

Một processing model.

Nhược điểm:

- Replay lịch sử rất lớn có thể lâu

- Không phải thuật toán batch nào cũng phù hợp streaming

120. Batch–Stream Unified Model

Một cách nhìn hiện đại:

Batch:
Xử lý bounded stream.

Streaming:

151. Cách trình bày trong System Design Interview

Không nên chỉ nói:

Em dùng Kafka và stream processing.

Nên nói:

Source phát immutable events vào partitioned event log. Tôi partition theo business key để giữ ordering trong phạm vi cần thiết, chẳng hạn cardId cho fraud detection. Processor sử dụng event time thay vì processing time vì event có thể đến trễ hoặc bị replay.

Về window:

Tôi dùng sliding window 10 phút, cập nhật mỗi phút. Watermark được đặt thấp hơn maximum observed event time hai phút. Window phát early result để giảm latency và tiếp tục nhận late events trong mười phút. Output là idempotent upsert theo (entityId, windowStart) để correction không tạo duplicate.

Về reliability:

Source offsets, keyed state và timers được snapshot trong consistent checkpoints. Khi worker lỗi, job restore checkpoint rồi replay từ offsets tương ứng. Pipeline cung cấp at-least-once communication; exactly-once business effect phụ thuộc sink hỗ trợ transaction hoặc idempotent upsert. External side effects như email vẫn cần idempotency key riêng.

Về scale:

State được partition theo key. Tôi theo dõi hot partitions, consumer lag, watermark progress, checkpoint duration và backpressure. Với hot keys, tôi dùng local pre-aggregation hoặc bucketed two-stage aggregation.

State tăng vô hạn.

Downstream càng quá tải.

Watermark có thể nhảy sai.

Thiếu version guard.
