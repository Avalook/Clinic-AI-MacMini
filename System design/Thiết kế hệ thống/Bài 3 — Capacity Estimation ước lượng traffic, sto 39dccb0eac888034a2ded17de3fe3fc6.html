Bài 3 — Capacity Estimation: ước lượng traffic, storage, bandwidth, QPS để thiết kế có cơ sở

Trong System Design, Capacity Estimation là bước biến yêu cầu mơ hồ kiểu “hệ thống cần scale lớn” thành các con số cụ thể:

Có bao nhiêu user?
Mỗi user tạo bao nhiêu request?
Mỗi request tạo bao nhiêu dữ liệu?
Mỗi ngày cần lưu bao nhiêu GB?
Peak traffic là bao nhiêu QPS?
Database đọc/ghi bao nhiêu lần mỗi giây?
Cache cần chứa bao nhiêu dữ liệu?
Bandwidth cần bao nhiêu?

Các video/tài liệu bạn đưa nhấn mạnh rằng hệ thống nhỏ có thể bắt đầu đơn giản, nhưng khi traffic lớn hơn thì single server sẽ gặp giới hạn và cần scale từng phần như web tier, data tier, load balancer, cache, database replication.

1. Capacity Estimation là gì?

Capacity Estimation là quá trình ước lượng quy mô hệ thống trước khi thiết kế kiến trúc.

Nó giúp bạn trả lời:

- Cần bao nhiêu server?
- Database có chịu nổi không?
- Có cần cache không?
- Có cần queue không?
- Có cần CDN không?
- Có cần sharding không?
- Storage tăng bao nhiêu mỗi ngày/tháng/năm?

Nói dễ hiểu:

Capacity Estimation là “tính nháp trên giấy” để biết hệ thống sẽ đau ở đâu trước khi nó thật sự đau.

2. Vì sao cần Capacity Estimation?

Nếu không ước lượng, bạn sẽ thiết kế bằng cảm tính.

Ví dụ đề bài:

Thiết kế hệ thống ghi chú giống Google Keep.

Nếu không có số liệu, bạn có thể nói:

Dùng API server + database là được.

Nhưng nếu hỏi thêm:

- 50 triệu DAU
- Mỗi user đọc 100 note/ngày
- Mỗi user tạo/sửa 10 note/ngày
- Mỗi note trung bình 2 KB

Bạn sẽ thấy hệ thống có:

Read: 5 tỷ lượt đọc note/ngày
Write: 500 triệu lượt ghi note/ngày
Storage mới: khoảng 1 TB/ngày, nếu tính cả metadata/version/replication có thể lớn hơn

Lúc này thiết kế sẽ khác hẳn.

3. Các khái niệm cần nhớ

3.1 DAU — Daily Active Users

Số user hoạt động mỗi ngày.

DAU = số user dùng hệ thống trong 1 ngày

Ví dụ:

10 triệu DAU = mỗi ngày có 10 triệu user hoạt động

3.2 MAU — Monthly Active Users

Số user hoạt động mỗi tháng.

MAU = số user dùng hệ thống trong 1 tháng

MAU thường lớn hơn DAU.

Ví dụ:

MAU = 100 triệu
DAU = 20 triệu

3.3 RPS / QPS

RPS = Requests Per Second.

QPS = Queries Per Second.

Trong phỏng vấn System Design, nhiều người dùng QPS gần giống RPS, nhưng nên phân biệt:

RPS: số request tới hệ thống mỗi giây
QPS: số query tới database/search/cache mỗi giây

Một API request có thể tạo nhiều query.

Ví dụ:

1 request xem profile
=> 1 query user
=> 1 query posts
=> 1 query follower count
=> 1 query notification badge

Vậy:

RPS = 1
DB QPS = 4

3.4 Peak traffic

Traffic không đều cả ngày.

Ví dụ trung bình:

1,000 RPS trung bình

Nhưng giờ cao điểm có thể:

3,000 - 10,000 RPS

Công thức thường dùng:

Peak RPS = Average RPS × Peak Factor

Peak factor thường lấy 2x, 3x, 5x hoặc 10x tùy hệ thống.

Ví dụ:

Average RPS = 1,000
Peak factor = 5
Peak RPS = 5,000

3.5 Read/write ratio

Hệ thống nào cũng có tỷ lệ đọc/ghi khác nhau.

Ví dụ:

URL Shortener:
Read nhiều hơn write rất nhiều
Có thể 100:1 hoặc 1000:1

Chat:
Read/write tương đối cao cả hai phía

Banking:
Write ít hơn read nhưng write cực kỳ quan trọng

YouTube:
Read/watch cực lớn, upload ít hơn nhiều

Read/write ratio ảnh hưởng trực tiếp đến kiến trúc:

Read nhiều:
- Cache
- CDN
- Read replica
- Search index

Write nhiều:
- Queue
- Partitioning
- Sharding
- Write-optimized database

4. Công thức tính cơ bản

Bạn chỉ cần nhớ vài công thức sau.

4.1 Tính request mỗi ngày

Daily Requests = DAU × Requests per user per day

Ví dụ:

DAU = 10 triệu
Mỗi user tạo 50 request/ngày

Daily Requests = 10,000,000 × 50
               = 500,000,000 requests/day

4.2 Tính average RPS

Một ngày có:

24 × 60 × 60 = 86,400 giây

Công thức:

Average RPS = Daily Requests / 86,400

Ví dụ:

500,000,000 requests/day / 86,400
≈ 5,787 RPS

Làm tròn:

≈ 5.8K RPS trung bình

4.3 Tính peak RPS

Peak RPS = Average RPS × Peak Factor

Ví dụ:

Average RPS = 5.8K
Peak Factor = 5

Peak RPS ≈ 29K RPS

Vậy hệ thống phải thiết kế cho khoảng 30K RPS peak, không phải chỉ 5.8K.

4.4 Tính storage mỗi ngày

Daily Storage = Number of new records per day × Average record size

Ví dụ:

100 triệu note mới/ngày
Mỗi note trung bình 2 KB

Daily Storage = 100,000,000 × 2 KB
              = 200,000,000 KB
              ≈ 200 GB/ngày

Nhưng thực tế phải cộng thêm:

- Metadata
- Index
- Replication
- Backup
- Version history
- Compression hoặc overhead

Nếu replication factor = 3:

Raw storage = 200 GB/ngày
With replication = 600 GB/ngày

4.5 Tính bandwidth

Bandwidth là lượng dữ liệu truyền qua mạng.

Bandwidth = Requests per second × Response size

Ví dụ:

Peak RPS = 30,000
Average response size = 10 KB

Bandwidth = 30,000 × 10 KB/s
          = 300,000 KB/s
          ≈ 300 MB/s

Nếu là video/image thì bandwidth tăng rất mạnh, vì response size có thể là MB thay vì KB. Đó là lý do video, ảnh, static content thường cần CDN.

5. Quy trình Capacity Estimation chuẩn

Khi gặp đề System Design, bạn có thể làm theo quy trình này:

flowchart TD
    A[Đề bài] --> B[Ước lượng users]
    B --> C[Ước lượng actions/user/day]
    C --> D[Tính daily requests]
    D --> E[Tính average RPS]
    E --> F[Tính peak RPS]
    F --> G[Tách read/write]
    G --> H[Tính storage]
    H --> I[Tính bandwidth]
    I --> J[Xác định bottleneck]
    J --> K[Quyết định kiến trúc]

6. Ví dụ 1: Capacity Estimation cho Google Keep đơn giản

Đề bài:

Thiết kế app ghi chú cá nhân giống Google Keep.

6.1 Giả định

Ta chốt giả định:

DAU = 10 triệu user
Mỗi user đọc 50 note/ngày
Mỗi user tạo/sửa 5 note/ngày
Mỗi note trung bình = 2 KB
Peak factor = 5
Replication factor = 3

6.2 Tính read requests

Daily reads = 10 triệu × 50
            = 500 triệu reads/day

Average read RPS:

500,000,000 / 86,400
≈ 5,787 read RPS

Peak read RPS:

5,787 × 5
≈ 28,935 read RPS
≈ 29K read RPS

6.3 Tính write requests

Daily writes = 10 triệu × 5
             = 50 triệu writes/day

Average write RPS:

50,000,000 / 86,400
≈ 579 write RPS

Peak write RPS:

579 × 5
≈ 2,895 write RPS
≈ 3K write RPS

6.4 Read/write ratio

Read = 500 triệu/day
Write = 50 triệu/day

Read/write ratio = 10:1

Kết luận:

Đây là hệ thống read-heavy.

Thiết kế nên ưu tiên:

- Index tốt cho note lookup/search
- Cache cho note được mở thường xuyên
- Read replica nếu database chính quá tải đọc
- Search index nếu full-text search phức tạp

6.5 Tính storage

New/updated notes per day = 50 triệu
Average note size = 2 KB

Raw daily storage = 50,000,000 × 2 KB
                  = 100,000,000 KB
                  ≈ 100 GB/day

Nếu replication factor = 3:

Physical storage ≈ 300 GB/day

Nếu lưu 1 năm:

300 GB/day × 365
≈ 109,500 GB
≈ 109.5 TB/year

Nhưng đây là ước lượng đơn giản. Thực tế có thể tăng do:

- Index
- Metadata
- Backup
- Version history
- Attachments
- Deleted notes retained temporarily

6.6 Kiến trúc bắt đầu từ con số

Vì peak read khoảng 29K RPS và write khoảng 3K RPS, kiến trúc hợp lý:

flowchart TD
    User[Web/Mobile User] --> LB[Load Balancer]
    LB --> API1[API Server 1]
    LB --> API2[API Server 2]
    LB --> API3[API Server 3]

    API1 --> Cache[Redis Cache]
    API2 --> Cache
    API3 --> Cache

    API1 --> DB[(Primary DB)]
    API2 --> DB
    API3 --> DB

    DB --> R1[(Read Replica 1)]
    DB --> R2[(Read Replica 2)]

    API1 --> Search[Search Index]
    API2 --> Search
    API3 --> Search

Vì sao?

- Load balancer chia traffic cho nhiều API server.
- API server nên stateless để scale ngang.
- Cache giảm read pressure lên DB.
- Read replicas xử lý read-heavy workload.
- Search index phục vụ tìm kiếm note nhanh hơn.

7. Ví dụ 2: URL Shortener

Đề bài:

Thiết kế hệ thống rút gọn URL như bit.ly.

7.1 Giả định

100 triệu short URL mới/tháng
10 tỷ redirects/tháng
Average long URL size = 500 bytes
Short code + metadata = 100 bytes
Peak factor = 5

7.2 Tính write

100 triệu URL mới/tháng
≈ 3.3 triệu URL mới/ngày

Write RPS:

3,300,000 / 86,400
≈ 38 writes/second

Write rất nhỏ.

7.3 Tính read/redirect

10 tỷ redirects/tháng
≈ 333 triệu redirects/ngày

Read RPS:

333,000,000 / 86,400
≈ 3,854 reads/second

Peak read RPS:

3,854 × 5
≈ 19,270 reads/second
≈ 20K read RPS

7.4 Read/write ratio

Read ≈ 333 triệu/day
Write ≈ 3.3 triệu/day

Read/write ratio ≈ 100:1

Kết luận:

URL Shortener là hệ thống cực kỳ read-heavy.

Thiết kế nên ưu tiên redirect path cực nhanh:

flowchart TD
    User[User opens short URL] --> LB[Load Balancer]
    LB --> API[Redirect Service]
    API --> Cache[Redis Cache]
    Cache --> DB[(URL Mapping DB)]
    API --> Queue[Click Event Queue]
    Queue --> Analytics[Analytics Worker]
    Analytics --> AnalyticsDB[(Analytics DB)]

Vì sao analytics đi qua queue?

Redirect là tác vụ chính, cần nhanh.
Click analytics là tác vụ phụ, có thể xử lý async.
Không nên làm user chờ analytics ghi xong mới redirect.

8. Ví dụ 3: App chat đơn giản

Đề bài:

Thiết kế hệ thống chat 1-1.

8.1 Giả định

DAU = 20 triệu
Mỗi user gửi 40 tin nhắn/ngày
Mỗi message trung bình = 1 KB
Peak factor = 5
Replication factor = 3

8.2 Tính write message

Daily messages = 20 triệu × 40
               = 800 triệu messages/day

Average message write QPS:

800,000,000 / 86,400
≈ 9,259 messages/second

Peak message write QPS:

9,259 × 5
≈ 46,295 messages/second
≈ 46K messages/s

Đây là write-heavy hơn Google Keep.

8.3 Tính storage

800 triệu messages/day × 1 KB
= 800 GB/day raw

Với replication factor = 3:

≈ 2.4 TB/day

Một năm:

2.4 TB/day × 365
≈ 876 TB/year

Kết luận:

Chat system cần suy nghĩ nghiêm túc về storage partitioning, retention, compression, archiving, message ordering và delivery guarantee.

8.4 Kiến trúc bị ảnh hưởng bởi con số

flowchart TD
    UserA[User A] --> Gateway[WebSocket Gateway]
    UserB[User B] --> Gateway

    Gateway --> ChatService[Chat Service]
    ChatService --> MessageDB[(Message Store)]
    ChatService --> Queue[Message Queue]

    Queue --> Delivery[Delivery Worker]
    Queue --> Notification[Push Notification Worker]

    ChatService --> Presence[Presence Service]
    Presence --> PresenceCache[Redis]

Vì sao cần nhiều thành phần?

- WebSocket Gateway giữ kết nối realtime.
- Message Store lưu tin nhắn bền vững.
- Queue hỗ trợ delivery async/retry.
- Presence có thể dùng Redis vì online status là dữ liệu tạm.
- Notification không nên nằm trong request path chính.

9. Từ con số sang quyết định kiến trúc

Đây là phần quan trọng nhất.

9.1 Nếu RPS thấp

Ví dụ:

Peak RPS < 100

Thiết kế đơn giản là đủ:

flowchart LR
    User --> API[API Server]
    API --> DB[(Database)]

Không cần Kafka, Kubernetes, sharding, microservices.

9.2 Nếu API server quá tải

Dấu hiệu:

- CPU app server cao
- Request queue dài
- Latency tăng khi traffic tăng

Giải pháp:

- Scale ngang API server
- Dùng load balancer
- Làm API server stateless
flowchart LR
    User --> LB[Load Balancer]
    LB --> A1[API 1]
    LB --> A2[API 2]
    LB --> A3[API 3]

Load balancer dùng để phân phối traffic qua nhiều server, giúp không một server nào phải gánh toàn bộ tải; đây cũng là nội dung chính trong video về scaling/load balancing của bạn.

9.3 Nếu database đọc quá tải

Dấu hiệu:

- Read query nhiều
- DB CPU cao
- Query latency tăng
- Nhiều request đọc cùng dữ liệu

Giải pháp:

- Add index
- Add cache
- Add read replica
- Denormalize nếu hợp lý
flowchart TD
    API --> Cache[Redis]
    Cache --> DB[(Primary DB)]
    DB --> R1[(Read Replica)]
    DB --> R2[(Read Replica)]

9.4 Nếu database ghi quá tải

Dấu hiệu:

- Write QPS rất cao
- Lock contention
- Disk I/O cao
- Replication lag

Giải pháp:

- Batch writes
- Queue/buffer writes
- Sharding
- Partitioning
- Write-optimized database

Ví dụ:

flowchart TD
    API --> Queue[Message Queue]
    Queue --> Worker1[Write Worker 1]
    Queue --> Worker2[Write Worker 2]
    Worker1 --> DB1[(Shard 1)]
    Worker2 --> DB2[(Shard 2)]

9.5 Nếu response size lớn

Ví dụ:

Ảnh, video, file, static assets

Vấn đề chính là bandwidth.

Giải pháp:

- Object storage
- CDN
- Compression
- Streaming
- Thumbnail/resized versions
flowchart LR
    User --> CDN[CDN]
    CDN --> ObjectStorage[Object Storage]
    User --> API[API for metadata]
    API --> DB[(Metadata DB)]

10. Các con số tham khảo nên nhớ

Không cần chính xác tuyệt đối, nhưng nên có trực giác.

1 ngày = 86,400 giây
1 KB × 1 triệu = khoảng 1 GB
1 MB × 1 triệu = khoảng 1 TB
1 GB × 1,000 = khoảng 1 TB
1 TB × 1,000 = khoảng 1 PB

Cực kỳ hữu ích:

1 triệu request/ngày ≈ 12 RPS trung bình
10 triệu request/ngày ≈ 116 RPS trung bình
100 triệu request/ngày ≈ 1,157 RPS trung bình
1 tỷ request/ngày ≈ 11,574 RPS trung bình

Nếu peak factor = 5:

100 triệu request/ngày
=> 1.1K RPS trung bình
=> 5.8K RPS peak

Nếu peak factor = 10:

100 triệu request/ngày
=> 1.1K RPS trung bình
=> 11.5K RPS peak

11. Cách tính nhanh trong phỏng vấn

Bạn không cần tính quá chính xác. System Design thích order-of-magnitude estimation.

Nghĩa là:

Không cần biết chính xác 5,787 RPS.
Nói 5.8K hoặc 6K RPS là đủ.

Một câu nói tốt:

Assuming 10 million DAU and each user performs around 50 reads per day, we get around 500 million reads per day. Dividing by 86,400 seconds, that gives roughly 6K read RPS on average. With a 5x peak factor, we should design for around 30K peak read RPS.

Phiên bản tiếng Việt:

Giả sử có 10 triệu DAU, mỗi user đọc khoảng 50 note/ngày, ta có khoảng 500 triệu read/ngày. Chia cho 86,400 giây thì được khoảng 6K read RPS trung bình. Nếu nhân peak factor 5 lần, hệ thống nên chịu được khoảng 30K read RPS ở giờ cao điểm.

13. Ví dụ hoàn chỉnh: Todoist bản đơn giản

Đây là bài tập từ bài trước, giờ ta thêm capacity estimation.

13.1 Giả định

DAU = 5 triệu
Mỗi user xem task list 20 lần/ngày
Mỗi user tạo/sửa/xoá task 10 lần/ngày
Task size trung bình = 1 KB
Peak factor = 5
Replication factor = 3

Daily reads = 5 triệu × 20
            = 100 triệu reads/day

Average read RPS = 100,000,000 / 86,400
                 ≈ 1,157 RPS

Peak read RPS = 1,157 × 5
              ≈ 5,785 RPS
              ≈ 6K RPS

13.3 Writes

Daily writes = 5 triệu × 10
             = 50 triệu writes/day

Average write RPS = 50,000,000 / 86,400
                  ≈ 579 RPS

Peak write RPS = 579 × 5
               ≈ 2,895 RPS
               ≈ 3K RPS

13.4 Storage

50 triệu task changes/day × 1 KB
≈ 50 GB/day raw

Với replication factor = 3:

≈ 150 GB/day

Một năm:

150 GB/day × 365
≈ 54.75 TB/year

13.5 Kết luận kiến trúc

Với Todoist bản này:

Peak reads ≈ 6K RPS
Peak writes ≈ 3K RPS
Storage replicated ≈ 150 GB/day

Thiết kế hợp lý:

flowchart TD
    User[User] --> LB[Load Balancer]
    LB --> API1[API Server 1]
    LB --> API2[API Server 2]

    API1 --> Cache[Redis Cache]
    API2 --> Cache

    API1 --> DB[(Primary PostgreSQL)]

Lý do:

- API server scale ngang vì peak RPS không quá nhỏ.
- PostgreSQL vẫn hợp lý vì task có quan hệ user/project/list.
- Cache có thể dùng cho task list được mở thường xuyên.
- Read replica giúp giảm tải read.
- Queue dùng cho notification, sync event, activity log.

14. Sai lầm thường gặp khi estimate

Sai lầm 1: Quên peak traffic

Chỉ tính trung bình là chưa đủ.

Average RPS = 1K
Peak RPS có thể = 5K hoặc 10K

Sai lầm 2: Quên read/write ratio

Nói “10K RPS” vẫn chưa đủ.

Phải biết:

10K RPS đó là:
- 9K read + 1K write?
- Hay 1K read + 9K write?

Hai trường hợp này thiết kế khác nhau rất nhiều.

Sai lầm 3: Quên response size

10K RPS với response 1 KB khác xa 10K RPS với video 5 MB.

10K × 1 KB = 10 MB/s
10K × 5 MB = 50,000 MB/s = 50 GB/s

Sai lầm 4: Quên replication và backup

Nếu raw data là 100 GB/ngày, storage thật có thể là:

100 GB × 3 replicas = 300 GB/ngày
+ index
+ backup
+ logs
+ metadata

Sai lầm 5: Estimate quá chính xác giả tạo

Không cần nói:

5,787.037 RPS

Nên nói:

Khoảng 5.8K RPS, làm tròn thành 6K RPS.

System Design cần tư duy đúng, không cần máy tính kế toán.

[ ] Peak factor là bao nhiêu?
[ ] Peak RPS là bao nhiêu?
[ ] Read/write ratio là bao nhiêu?
[ ] Mỗi object trung bình bao nhiêu KB/MB?
[ ] Dữ liệu mới mỗi ngày là bao nhiêu?

[ ] Bandwidth peak là bao nhiêu?

16. Cách ghi nhớ bài này

Nhớ công thức cốt lõi:

Daily Requests = DAU × Requests/User/Day

Average RPS = Daily Requests / 86,400

Peak RPS = Average RPS × Peak Factor

Daily Storage = New Objects/Day × Object Size

Bandwidth = RPS × Response Size

Và nhớ câu này:

Capacity Estimation không cần chính xác tuyệt đối, nhưng phải đủ đúng để dẫn đến quyết định kiến trúc hợp lý.

17. Bài tập cho bạn

Hãy estimate hệ thống sau:

Thiết kế app lưu ảnh cá nhân giống Google Photos bản đơn giản.

Giả định có thể dùng:

DAU = 20 triệu
Mỗi user upload 5 ảnh/ngày
Mỗi user xem 50 ảnh/ngày
Mỗi ảnh trung bình = 2 MB
Peak factor = 5
Replication factor = 3

Bạn hãy tính:

1. Daily upload count
2. Daily view count
3. Average upload QPS
4. Peak upload QPS
5. Average view QPS
6. Peak view QPS
7. Raw storage/day
8. Storage/day with replication
9. Storage/year
10. Vì sao hệ thống này gần như chắc chắn cần object storage + CDN?

Tóm tắt cuối bài

Bài 3 cần nhớ:

1. Capacity Estimation giúp thiết kế dựa trên con số, không đoán mò.
2. DAU × action/user/day giúp tính daily requests.
3. Daily requests / 86,400 giúp tính average RPS.
4. Average RPS × peak factor giúp tính peak RPS.
5. Read/write ratio quyết định cache, replica, queue, sharding.
6. Object size quyết định storage và bandwidth.
7. Video/ảnh/file thường cần object storage và CDN.
8. Estimate càng tốt thì kiến trúc càng có cơ sở.
