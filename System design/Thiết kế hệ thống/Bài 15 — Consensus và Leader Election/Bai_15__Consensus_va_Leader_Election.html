Bài 15 — Consensus và Leader Election

Replication tạo nhiều bản sao dữ liệu. Nhưng chỉ replication thôi chưa trả lời được:

- Node nào được quyền nhận write?
- Nếu leader chết, ai trở thành leader mới?
- Hai nhóm node bị mất kết nối có được cùng nhận write không?
- Một log entry được xem là commit khi nào?
- Làm sao mọi node đồng ý về cùng một thứ tự thao tác?

Đây là bài toán consensus.

Consensus là quá trình nhiều node thống nhất về một quyết định hoặc một chuỗi quyết định, dù node có thể crash, message có thể trễ và mạng có thể bị phân vùng.

Các ứng dụng phổ biến:

- Leader election
- Replicated transaction log
- Cluster membership
- Distributed configuration
- Metadata management
- Distributed lock
- Coordination service
- Distributed database

Bài này dùng Raft để xây trực giác. Mục tiêu không phải thuộc mọi dòng của thuật toán, mà là hiểu tại sao quorum, term, log replication, commit index và fencing phối hợp với nhau để bảo vệ correctness.

1. Replication chưa phải Consensus

Giả sử có ba database node:

flowchart LR
    A[(Node A)]
    B[(Node B)]
    C[(Node C)]

    A --> B
    A --> C

Node A đang là leader và replicate dữ liệu sang B, C.

Nếu A mất kết nối với B và C nhưng vẫn còn phục vụ client:

flowchart TD
    Client1 --> A[(Old Leader A)]

    Client2 --> B[(Node B)]
    B --- C[(Node C)]

    A -. Network partition .- B

B và C có thể bầu B thành leader mới vì chúng tạo thành majority.

Nếu A vẫn tiếp tục nhận write, hệ thống có hai leader:

Leader A:
Nhận write từ Client 1

Leader B:
Nhận write từ Client 2

Đây là split-brain.

Replication chỉ tạo bản sao. Consensus xác định:

- Ai có quyền quyết định?
- Quyết định nào đã được chấp nhận?
- Node nào phải dừng khi không còn quorum?

2. Consensus cần thống nhất điều gì?

Tùy hệ thống, các node có thể cần thống nhất:

- Ai là leader hiện tại?
- Giá trị của một configuration key
- Thứ tự các database transaction
- Shard nào thuộc node nào
- Thành viên nào đang thuộc cluster
- Một distributed lock thuộc về client nào

Trong replicated state machine, các node chủ yếu thống nhất một ordered log:

Index 1: SET x = 10
Index 2: SET y = 20
Index 3: TRANSFER A → B 100
Index 4: DELETE session_123

Nếu mọi node áp dụng cùng command theo cùng thứ tự, chúng sẽ đạt cùng state.

3. Replicated State Machine

Mô hình tổng quát:

flowchart TD
    Client --> Consensus[Consensus Module]
    Consensus --> L1[Replicated Log Node 1]
    Consensus --> L2[Replicated Log Node 2]
    Consensus --> L3[Replicated Log Node 3]

    L1 --> S1[State Machine 1]
    L2 --> S2[State Machine 2]
    L3 --> S3[State Machine 3]

Mỗi node có:

1. Consensus module
2. Replicated log
3. State machine

Nếu log giống nhau:

Node A:
[SET x=1, SET y=2]

Node B:
[SET x=1, SET y=2]

Node C:
[SET x=1, SET y=2]

và các command deterministic, state cuối cũng giống nhau.

4. Safety và Liveness

Một consensus protocol phải quan tâm hai nhóm tính chất.

Safety

Không được xảy ra điều sai.

Ví dụ:

- Không có hai leader hợp lệ trong cùng một term.
- Hai node không commit hai command khác nhau tại cùng log index.
- Entry đã commit không được mất sau leader election.

Safety có thể hiểu là:

Hệ thống thà tạm dừng còn hơn đưa ra hai quyết định mâu thuẫn.

Liveness

Hệ thống cuối cùng vẫn tiếp tục tiến lên khi điều kiện đủ tốt.

Ví dụ:

- Cluster có majority node hoạt động.
- Network cuối cùng ổn định.
- Cluster cuối cùng bầu được leader.
- Client write cuối cùng được commit.

Consensus thường ưu tiên safety khi phải lựa chọn.

5. Majority là gì?

Với N voting nodes:

Majority = floor(N / 2) + 1

Ví dụ:

Số node Majority Chịu được số node lỗi
1 1 0
2 2 0
3 2 1
4 3 1
5 3 2
7 4 3

Công thức số lỗi crash có thể chịu:

f = floor((N - 1) / 2)

Để chịu f lỗi, thường cần:

N = 2f + 1

6. Vì sao Majority quan trọng?

Hai majority trong cùng một cluster luôn giao nhau ít nhất một node.

Với năm node:

Majority A:
Node 1, 2, 3

Majority B:
Node 3, 4, 5

Hai nhóm giao nhau tại Node 3.

Tính chất giao nhau giúp ngăn hai quyết định độc lập hoàn toàn.

Ví dụ không thể có:

Majority 1 commit X
Majority 2 commit Y

mà không có ít nhất một node tham gia cả hai quyết định.

Consensus protocol dùng thêm term, log rules và voting rules để node giao nhau này không thể hợp lệ hóa hai lịch sử mâu thuẫn.

7. Vì sao cluster thường dùng số node lẻ?

So sánh:

3 nodes:
Majority = 2
Chịu 1 lỗi

4 nodes:
Majority = 3
Cũng chỉ chịu 1 lỗi

Node thứ tư tăng chi phí nhưng không tăng số failure mà majority cluster chịu được.

Tương tự:

5 nodes:
Majority = 3
Chịu 2 lỗi

6 nodes:
Majority = 4
Cũng chỉ chịu 2 lỗi

Vì vậy voting cluster thường có:

3, 5 hoặc 7 nodes

Không nên tăng quá nhiều vì mỗi write cần giao tiếp với quorum, làm tăng latency và operational cost.

8. Quorum không đồng nghĩa Consensus

Quorum chỉ nói:

Cần bao nhiêu node tham gia?

Consensus còn phải xác định:

- Node được vote thế nào?
- Vote thuộc nhiệm kỳ nào?
- Log nào mới hơn?
- Hai candidate cạnh tranh ra sao?
- Entry nào được commit?
- Node cũ quay lại xử lý thế nào?

Một hệ thống có W=2 trên ba replica chưa chắc đã là consensus system.

Nếu hai coordinator khác nhau có thể ghi hai giá trị cạnh tranh mà không có term, ordering và conflict rules rõ ràng, quorum đơn thuần chưa đủ.

9. Raft giải quyết bài toán gì?

Raft là consensus algorithm tổ chức cluster thành:

- Leader
- Followers
- Candidate trong thời gian election

Raft chia bài toán thành các phần dễ hiểu:

1. Leader election
2. Log replication
3. Safety
4. Membership changes
5. Log compaction

Phần lõi của bài này:

- Term
- Election timeout
- RequestVote
- AppendEntries
- Log index và log term
- Commit index
- Majority

10. Ba trạng thái của một Raft node

stateDiagram-v2
    [*] --> Follower

    Follower --> Candidate: Election timeout
    Candidate --> Leader: Wins majority
    Candidate --> Follower: Sees higher term
    Candidate --> Candidate: New election timeout

    Leader --> Follower: Sees higher term

Follower

Trạng thái bình thường của phần lớn node.

Follower:

- Nhận heartbeat từ leader
- Nhận log entries
- Trả lời RequestVote
- Không tự nhận client write

Candidate

Follower không nhận heartbeat đúng hạn sẽ:

- Tăng term
- Chuyển thành candidate
- Vote cho chính mình
- Gửi RequestVote tới các node khác

Leader

Candidate nhận majority vote trở thành leader.

Leader:

- Nhận client command
- Append command vào log
- Replicate log tới followers
- Quyết định commit
- Gửi heartbeat

11. Term — nhiệm kỳ logic

Raft chia thời gian logic thành các term tăng dần.

Term 1:
Node A là leader

Term 2:
Node B là leader

Term 3:
Election không chọn được leader

Term 4:
Node C là leader

Term không phải thời gian đồng hồ.

Nó giống một epoch hoặc generation number:

1, 2, 3, 4, ...

Mỗi node lưu bền vững:

currentTerm

12. Vai trò của Term

Term giúp node phát hiện thông tin cũ.

Ví dụ:

Node A nghĩ mình là leader Term 5.
Node B gửi message từ Term 6.

A phải hiểu rằng:

Tôi đã lỗi thời.

A chuyển thành follower và cập nhật currentTerm = 6.

Quy tắc khái niệm:

Nếu nhận message có term lớn hơn:
- Cập nhật term
- Step down thành follower

Nếu nhận message có term nhỏ hơn:
- Từ chối hoặc bỏ qua

Term là cơ sở quan trọng để chặn leader cũ tiếp tục hành xử như leader hợp lệ trong cluster.

13. Mỗi Term có tối đa một Leader hợp lệ

Một node chỉ vote tối đa một candidate trong một term.

Candidate phải nhận majority.

Giả sử hai candidate A và B cùng tranh cử trong Term 7.

A cần ít nhất ba vote trong cluster năm node.

B cũng cần ít nhất ba vote.

Hai tập majority phải giao nhau ít nhất một node.

Nhưng node giao nhau không thể vote cho cả A và B trong cùng term.

Vì thế:

Không thể có hai candidate cùng giành majority hợp lệ trong cùng một term.

14. Heartbeat

Leader định kỳ gửi AppendEntries, kể cả khi không có log mới.

Một AppendEntries rỗng đóng vai trò heartbeat:

sequenceDiagram
    participant L as Leader
    participant F1 as Follower 1
    participant F2 as Follower 2

    loop Every heartbeat interval
        L->>F1: AppendEntries, no new entries
        L->>F2: AppendEntries, no new entries
    end

Heartbeat cho followers biết:

Leader vẫn còn hoạt động.
Không cần bắt đầu election.

15. Election Timeout

Mỗi follower có election timeout.

Nếu không nhận heartbeat hoặc AppendEntries hợp lệ trước timeout:

Follower → Candidate

Ví dụ:

Heartbeat interval: 50 ms
Election timeout: ngẫu nhiên 150–300 ms

Con số thực tế phụ thuộc môi trường.

Election timeout phải:

Lớn hơn đáng kể so với heartbeat interval và network delay bình thường.

16. Vì sao Election Timeout phải ngẫu nhiên?

Nếu mọi follower timeout đúng 200 ms:

- Tất cả cùng thành candidate
- Tất cả vote cho chính mình
- Vote bị chia đều
- Không ai đạt majority

Đây là split vote.

Raft dùng randomized election timeout:

Node A: 167 ms
Node B: 224 ms
Node C: 281 ms

A timeout trước, gửi RequestVote khi B và C còn là follower.

A có xác suất cao giành majority.

17. Bắt đầu Election

Giả sử cluster có năm node:

A, B, C, D, E

Leader cũ chết.

Node B timeout đầu tiên.

B thực hiện:

1. currentTerm tăng từ 8 lên 9
2. Chuyển thành Candidate
3. Vote cho B
4. Gửi RequestVote(term=9) tới A, C, D, E

sequenceDiagram
    participant B as Candidate B
    participant A
    participant C
    participant D
    participant E

    B->>B: term=9, vote for self
    B->>A: RequestVote term=9
    B->>C: RequestVote term=9
    B->>D: RequestVote term=9
    B->>E: RequestVote term=9

    C-->>B: Vote granted
    D-->>B: Vote granted

    Note over B: B has 3 votes including itself
    Note over B: Majority achieved

B trở thành leader Term 9.

18. RequestVote chứa gì?

Ở mức trực giác, candidate gửi:

- Candidate term
- Candidate ID
- Last log index
- Last log term

Ví dụ:

{
  "term": 9,
  "candidateId": "B",
  "lastLogIndex": 142,
  "lastLogTerm": 8
}

Follower không chỉ nhìn term.

Follower còn kiểm tra log của candidate có đủ mới không.

19. Quy tắc Vote cơ bản

Follower vote cho candidate khi:

1. Candidate term không cũ hơn follower.
2. Follower chưa vote cho node khác trong term đó.
3. Candidate log ít nhất cập nhật bằng follower log.

Điều kiện thứ ba cực kỳ quan trọng.

Nếu candidate có log thiếu entry đã commit, candidate đó không nên trở thành leader.

20. Log nào được xem là “up-to-date” hơn?

Raft so sánh:

1. Last log term
2. Nếu last term bằng nhau, so last log index

Ví dụ:

Candidate A:
lastLogTerm = 8
lastLogIndex = 100

Candidate B:
lastLogTerm = 7
lastLogIndex = 150

A được xem là up-to-date hơn vì last term 8 mới hơn 7, dù log ngắn hơn.

Nếu:

Candidate A:
term = 8, index = 100

Candidate B:
term = 8, index = 110

B mới hơn vì cùng last term nhưng index lớn hơn.

21. Vì sao Candidate Log phải đủ mới?

Giả sử entry X đã được commit trên majority:

Node A: [X]
Node B: [X]
Node C: [X]
Node D: []
Node E: []

Một candidate chỉ có thể giành majority nếu nhận vote từ ít nhất ba node.

Bất kỳ majority mới nào cũng giao với majority đã chứa X.

Node giao nhau biết candidate thiếu X và sẽ không vote cho candidate có log cũ.

Nhờ vậy:

Một leader mới hợp lệ phải chứa mọi entry đã commit.

Đây là phần cốt lõi của Leader Completeness.

22. Split Vote

Giả sử bốn node cùng timeout gần nhau:

A vote A
B vote B
C vote A
D vote B
E chưa phản hồi

Không candidate nào đạt ba vote.

Election thất bại nhưng safety không bị vi phạm.

Sau election timeout mới:

- Candidate tăng term
- Random timeout lại
- Tổ chức election mới

Cuối cùng một candidate thường timeout trước và thắng.

23. Khi Candidate nhận Heartbeat từ Leader khác

Candidate B đang tranh cử Term 10.

Nó nhận AppendEntries từ A:

Case 1:
A term = 11

B phải step down vì term 11 cao hơn.

Case 2:
A term = 9

B từ chối vì A đã cũ.

Nếu term bằng nhau và A là leader hợp lệ, B thường chuyển về follower.

24. Client Write đi qua Leader

Client gửi command:

SET x = 5

Leader không áp dụng ngay rồi tuyên bố thành công một cách tùy tiện.

Luồng cơ bản:

1. Leader append command vào local log.
2. Leader gửi entry tới followers.
3. Followers ghi entry vào log và ACK.
4. Khi entry đủ điều kiện commit, leader tăng commitIndex.
5. Leader apply entry vào state machine.
6. Leader trả thành công cho client.
7. Followers học commitIndex và apply entry.

25. Cấu trúc một Log Entry

Mỗi log entry thường có:

- Index
- Term
- Command

Ví dụ:

Index Term Command
1 1 SET x=10
2 1 SET y=20
3 2 DELETE z
4 4 SET x=15

Index xác định vị trí.

Term cho biết entry được leader của nhiệm kỳ nào tạo ra.

26. AppendEntries RPC

Leader gửi tới follower:

- Leader term
- Leader ID
- prevLogIndex
- prevLogTerm
- Entries mới
- leaderCommit

Ví dụ:

{
  "term": 12,
  "leaderId": "B",
  "prevLogIndex": 42,
  "prevLogTerm": 11,
  "entries": [
    {
      "index": 43,
      "term": 12,
      "command": "SET x=5"
    }
  ],
  "leaderCommit": 42
}

27. prevLogIndex và prevLogTerm

Follower chỉ append entry mới nếu log trước đó khớp.

Leader nói:

Entry trước có:
index = 42
term = 11

Follower kiểm tra log của mình.

Nếu follower cũng có:

index 42, term 11

thì log prefix khớp và có thể append entry 43.

Nếu không:

Follower từ chối AppendEntries.

Leader phải quay lại vị trí cũ hơn để tìm điểm log chung.

28. Log Matching Property

Trực giác của Raft:

Nếu hai log có entry cùng index và cùng term, toàn bộ prefix trước entry đó cũng giống nhau.

Điều này được xây dựng bởi quy tắc kiểm tra:

prevLogIndex + prevLogTerm

Leader không được nối entry mới vào một prefix không khớp.

29. Follower bị thiếu Log

Leader:

Index: 1 2 3 4 5
Term:  1 1 2 2 3

Follower:

Index: 1 2 3
Term:  1 1 2

Leader gửi entry 4 và 5.

Follower kiểm tra entry 3 khớp, rồi append:

Follower sau đồng bộ:
1 2 3 4 5

30. Follower có Log xung đột

Leader:

Index: 1 2 3 4 5
Term:  1 1 2 4 4

Follower cũ:

Index: 1 2 3 4 5 6
Term:  1 1 2 3 3 3

Entry 4 khác term:

Leader index 4 term 4
Follower index 4 term 3

Leader tìm điểm chung cuối cùng là index 3.

Follower xóa suffix xung đột:

4, 5, 6

rồi append log của leader:

Index: 1 2 3 4 5
Term:  1 1 2 4 4

31. Vì sao Log chưa Commit có thể bị ghi đè?

Một leader cũ có thể append entry vào một số ít node nhưng chưa đạt majority.

Ví dụ:

Node A: [X]
Node B: [X]
Node C: []
Node D: []
Node E: []

A chết trước khi X được replicate lên majority.

Một leader mới không có X vẫn có thể được bầu.

Leader mới có quyền ghi đè suffix chưa commit trên A và B.

Điều này an toàn vì X chưa bao giờ được commit hoặc trả thành công theo đúng protocol.

32. nextIndex và matchIndex

Leader thường theo dõi cho mỗi follower:

nextIndex

Entry tiếp theo leader sẽ gửi cho follower.

nextIndex[Follower C] = 43

matchIndex

Index cao nhất đã biết được replicate trên follower đó.

matchIndex[Follower C] = 42

Nếu AppendEntries thất bại:

Leader giảm nextIndex
→ thử lại vị trí sớm hơn

Khi thành công:

Leader tăng nextIndex và matchIndex

33. Commit Index

commitIndex là index cao nhất mà node biết đã commit.

Ví dụ:

Log:
1 2 3 4 5 6

commitIndex = 4

Ý nghĩa:

Entries 1–4 đã commit.
Entries 5–6 chưa chắc chắn.

Chỉ entries đã commit mới được apply như quyết định cuối cùng vào state machine.

34. Replicated không luôn đồng nghĩa Committed

Giả sử cluster năm node.

Entry X nằm trên:

Leader A
Follower B
Follower C

Đây là majority ba node.

Có phải X luôn được commit ngay?

Với entry thuộc current leader term, leader có thể commit khi replicated trên majority.

Nhưng Raft có một nuance quan trọng:

Leader không trực tiếp dùng việc đếm majority để commit entry từ term cũ. Leader commit một entry thuộc current term trên majority; việc đó gián tiếp commit toàn bộ prefix trước nó.

35. Vì sao có quy tắc Current-Term Commit?

Một entry từ term cũ có thể xuất hiện trên majority tại một thời điểm nhưng vẫn có lịch sử election phức tạp khiến việc commit trực tiếp theo số lượng replica không an toàn.

Raft dùng quy tắc đơn giản hơn:

Leader chỉ advance commitIndex bằng majority counting
cho entry thuộc currentTerm.

Khi entry current term được commit:

Tất cả entry trước đó trong log prefix cũng được commit.

Nuance này thường bị bỏ qua trong các giải thích Raft sơ cấp nhưng rất quan trọng cho safety.

36. Ví dụ Commit trong Current Term

Leader B đang ở Term 8.

Log:

Index Term Command
10 6 X
11 7 Y
12 8 Z

Z tại index 12 được replicate lên majority.

Leader có thể commit index 12 vì Z thuộc current term 8.

Khi commit index 12:

X, Y và Z đều trở thành committed

vì chúng nằm trong cùng prefix.

37. Leader trả Success khi nào?

Đối với write yêu cầu consensus mạnh, leader thường chỉ trả success khi:

- Entry đã được append bền vững theo yêu cầu.
- Entry đã replicate tới majority.
- Entry đã được commit.
- Thường đã apply hoặc chắc chắn sẽ apply theo contract.

Nếu leader trả success trước majority replication:

Leader chết
→ entry có thể mất

Điều này phá durability và linearizability.

38. Followers biết Entry đã Commit thế nào?

Leader gửi leaderCommit trong AppendEntries.

Follower:

commitIndex = min(leaderCommit, index cuối của follower)

Sau đó follower apply các entry mới commit theo thứ tự.

sequenceDiagram
    participant L as Leader
    participant F as Follower

    L->>F: AppendEntries, leaderCommit=52
    F->>F: Advance commitIndex to 52
    F->>F: Apply entries up to 52
    F-->>L: Success

39. lastApplied

Mỗi node thường theo dõi:

commitIndex:
Entry cao nhất đã commit

lastApplied:
Entry cao nhất đã apply vào state machine

Điều kiện:

lastApplied ≤ commitIndex

Nếu:

commitIndex = 100
lastApplied = 96

node còn bốn entry cần apply.

40. Ordering rất quan trọng

Giả sử log:

1. balance = 100
2. debit 30
3. credit 10

Mọi node phải apply:

1 → 2 → 3

Không được apply:

1 → 3 → 2

Nếu command có dependency thứ tự, state có thể khác nhau.

Consensus thống nhất không chỉ tập giá trị mà còn thứ tự của chúng.

41. Leader chết trước khi Commit

Leader A append X vào local log rồi gửi cho B.

A: X
B: X
C: -
D: -
E: -

Chưa có majority.

A chết.

X chưa commit.

Leader mới có thể:

- Chứa X và tiếp tục replicate X
- Hoặc không chứa X và ghi đè X

Client không nên đã nhận success cho X.

42. Leader chết sau khi Commit nhưng trước Response

Luồng:

1. Client gửi command X.
2. X được replicate lên majority.
3. X được commit.
4. Leader chết trước khi response đến client.

Client thấy timeout nhưng X có thể đã commit.

Đây là trạng thái:

Unknown from the client’s perspective

Client retry phải dùng:

- Stable request ID
- Idempotency key
- Deduplication

Consensus không tự giải quyết duplicate business request do lost response.

43. Client Redirect

Follower nhận client write thường không tự xử lý.

Nó có thể:

- Redirect client tới leader
- Proxy request tới leader
- Trả “not leader” cùng leader hint

sequenceDiagram
    participant Client
    participant F as Follower
    participant L as Leader

    Client->>F: Write command
    F-->>Client: Not leader; leader is L
    Client->>L: Write command

Client hoặc SDK cần xử lý leader change.

44. Network Partition trong Cluster năm Node

Cluster:

A, B | C, D, E

Giả sử A là leader nhưng nằm phía minority cùng B.

Phía A, B chỉ có hai node:

Không đạt majority 3/5

A có thể vẫn nghĩ mình là leader trong một thời gian, nhưng không commit được write mới.

Phía C, D, E:

Có majority
→ Có thể bầu leader mới
→ Tiếp tục commit

flowchart TD
    subgraph Minority
        A[Old Leader A]
        B[Node B]
    end

    subgraph Majority
        C[New Leader C]
        D[Node D]
        E[Node E]
    end

    A -. Network partition .- C

45. Minority Leader phải làm gì?

Leader phía minority có thể nhận client request, nhưng không đạt majority.

Nó không được báo write đã commit.

Hành vi phù hợp:

- Request timeout
- Trả unavailable
- Step down khi nhận higher term sau network recovery

Không được:

- Commit local-only write
- Trả success chỉ vì ghi vào local disk

46. Khi Network phục hồi

Old Leader A term 10 gặp New Leader C term 11.

A nhận message term 11:

- Cập nhật currentTerm = 11
- Step down thành follower
- Đồng bộ log từ C

Các entry chưa commit của A có thể bị xóa nếu xung đột với log leader mới.

Các entry đã commit không được mất.

47. Split-Brain được ngăn thế nào?

Raft phối hợp nhiều cơ chế:

1. Mỗi term chỉ vote một lần.
2. Leader phải có majority.
3. Hai majority luôn giao nhau.
4. Candidate log phải đủ mới.
5. Node nhận higher term phải step down.
6. Entry chỉ commit theo quorum rules.
7. Minority không thể commit.

Nhưng cần phân biệt:

Raft ngăn split-brain trong state machine mà nó quản lý. External resource vẫn cần fencing nếu leader có side effect ngoài consensus group.

48. Raft Term có phải Fencing Token không?

Term có tính chất giống epoch tăng dần.

Bên trong Raft cluster:

Term giúp phát hiện leader cũ.

Nhưng giả sử leader điều khiển một external storage hoặc thiết bị không tham gia Raft.

Old leader term 10 có thể gửi:

WRITE file X

New leader term 11 cũng gửi:

WRITE file Y

Nếu external storage không kiểm tra term:

Nó có thể chấp nhận cả hai.

Vì vậy cần fencing token được resource đích thực thi.

49. Fencing Token

Mỗi lần quyền sở hữu thay đổi, hệ thống cấp token tăng dần:

Leader cũ:
fencingToken = 41

Leader mới:
fencingToken = 42

External resource lưu token lớn nhất đã thấy.

sequenceDiagram
    participant Old as Old Leader token 41
    participant New as New Leader token 42
    participant Storage

    New->>Storage: Write with token 42
    Storage->>Storage: highestToken = 42
    Storage-->>New: Accepted

    Old->>Storage: Write with token 41
    Storage-->>Old: Rejected as stale

Điểm quan trọng:

Không đủ để leader mới “nói” leader cũ đã chết. Resource phải từ chối operation từ token cũ.

50. Ví dụ Distributed Lock không có Fencing

Client A lấy lock và xử lý chậm.

1. A lấy lock.
2. A bị pause lâu.
3. Lock lease hết hạn.
4. B lấy lock mới.
5. B cập nhật file.
6. A tỉnh lại và cập nhật file.

A có thể ghi đè kết quả của B dù A không còn giữ lock.

Lock lease một mình chưa đủ.

51. Distributed Lock có Fencing

Lock service trả:

A nhận token 100
B nhận token 101

Storage chấp nhận B token 101.

Sau đó A token 100 quay lại:

Storage từ chối.

Fencing bảo vệ khỏi:

- Process pause
- Network delay
- Lease expiry
- Old leader recovery
- Stale lock holder

52. Fencing không thể chỉ kiểm tra trong Application

Không tốt:

if my_token_is_current():
    external_storage.write(data)

Giữa check và write, token có thể trở nên stale.

Đây là race condition.

Tốt hơn:

External storage nhận token cùng operation
và atomically từ chối token cũ.

Ví dụ:

UPDATE resource
SET value = :value,
    fencing_token = :token
WHERE id = :id
  AND fencing_token < :token;

53. Leader Lease

Một số hệ thống dùng lease để leader phục vụ read nhanh hoặc điều phối resource.

Leader được quyền trong khoảng thời gian nhất định.

Lease valid until logical deadline T

Nếu không renew được:

Leader phải ngừng hoạt động đặc quyền.

Lease có thể giảm coordination cost, nhưng phải cẩn thận với:

- Clock skew
- Process pause
- Network delay
- Lease renewal failure

Consensus term/epoch và fencing thường an toàn hơn việc chỉ tin wall-clock lease.

54. Linearizable Write

Một write linearizable phải có vẻ xảy ra tại một điểm duy nhất giữa lúc client gọi và lúc nhận response.

Với Raft, điểm tuyến tính hóa của write thường gắn với việc entry được commit bởi quorum.

Sau khi client nhận success:

Mọi operation sau đó phải quan sát hiệu ứng phù hợp với write đó.

55. Linearizable Read khó hơn tưởng tượng

Leader nhận read không thể luôn trả local state ngay lập tức.

Vấn đề:

Old leader bị network partition.
Majority đã elect leader mới.
Old leader chưa biết term mới.

Nếu old leader trả local read:

Có thể trả dữ liệu cũ như thể vẫn là leader.

Để phục vụ linearizable read, leader cần xác nhận mình vẫn là leader hợp lệ.

Các hướng phổ biến:

- Ghi một log entry/no-op qua quorum
- ReadIndex/quorum confirmation
- Leader lease với giả định thời gian cẩn thận

56. ReadIndex ở mức trực giác

Leader muốn trả linearizable read:

1. Xác nhận leadership với quorum.
2. Xác định commit index an toàn.
3. Chờ local state machine apply tới index đó.
4. Trả kết quả read.

Không nhất thiết append một log entry cho mỗi read, nhưng vẫn phải có bằng chứng leadership đủ mới.

57. Stale Read từ Follower

Follower có thể phục vụ read mà không cần quorum.

Ưu điểm:

- Latency thấp
- Scale read
- Giảm tải leader

Nhược điểm:

- Có thể stale
- Không bảo đảm read-your-writes
- Có thể chưa apply entry đã commit

Phải công bố rõ consistency contract:

- Linearizable read
- Bounded stale read
- Eventual read

58. No-op Entry khi Leader mới được bầu

Leader mới thường append một no-op entry trong current term.

Mục tiêu:

- Thiết lập authority của current term
- Cho phép commit an toàn prefix trước đó
- Xác định commit point trong nhiệm kỳ mới

No-op không thay đổi business state nhưng vẫn là một log entry consensus.

59. Leader Completeness

Tính chất quan trọng:

Nếu một log entry đã commit trong một term, entry đó sẽ xuất hiện trong log của mọi leader ở các term sau.

Raft đạt được điều này qua:

- Majority replication
- Quorum intersection
- Up-to-date log voting rule

Nếu candidate thiếu entry đã commit, ít nhất một voter trong majority biết log candidate cũ và không cấp vote.

60. State Machine Safety

Một node không được apply command X tại index 50 trong khi node khác apply command Y tại index 50.

Raft bảo vệ:

Nếu một node đã apply entry tại index i,
không node nào khác được apply entry khác tại index i.

Đây là correctness nền tảng của replicated state machine.

61. Crash Failure và Byzantine Failure

Raft truyền thống giả định crash fault model.

Node có thể:

- Dừng hoạt động
- Restart
- Mất message
- Gửi message trễ

Nhưng node không được giả định là cố tình nói dối hoặc gửi message mâu thuẫn có chủ đích.

Byzantine fault model cho phép node:

- Gửi thông tin giả
- Gửi dữ liệu khác nhau cho các peer
- Hành xử độc hại

Raft không phải Byzantine Fault Tolerant consensus.

62. Bao nhiêu Node cho Byzantine Fault?

Crash consensus:

Để chịu f crash failures:
N ≥ 2f + 1

Byzantine consensus thường cần:

N ≥ 3f + 1

Ví dụ chịu một Byzantine node thường cần ít nhất bốn node.

Trong System Design thông thường, Raft/Paxos hay được thảo luận trong crash-fault setting.

63. Stable Storage

Một số state phải được ghi bền vững trước khi response:

- currentTerm
- votedFor
- Log entries

Nếu node vote cho A, crash, restart rồi quên vote và vote cho B trong cùng term:

Có thể phá election safety.

Do đó votedFor và currentTerm cần persistent storage.

64. Log Durability

Follower ACK một AppendEntries có thể mang semantics:

- Đã nhận vào memory
- Đã ghi OS cache
- Đã flush durable storage

Consensus durability phụ thuộc contract cụ thể.

Nếu majority ACK chỉ ở volatile memory và toàn bộ mất điện cùng lúc:

Committed entry có thể mất.

Cần hiểu durability guarantee của implementation, không chỉ số replica.

65. Snapshot và Log Compaction

Log không thể tăng vô hạn:

1, 2, 3, ... 10 tỷ entries

Node định kỳ tạo snapshot state machine tại một index:

Snapshot at index 1.000.000, term 57

Sau đó có thể loại bỏ log cũ trước snapshot nếu không còn cần.

flowchart LR
    OldLog[Entries 1..1,000,000] --> Snapshot[State Snapshot]
    Snapshot --> NewLog[Entries 1,000,001...]

66. Follower tụt quá xa

Nếu follower thiếu log mà leader đã compact:

Leader không còn đủ entries cũ để gửi từng entry.

Leader gửi snapshot:

InstallSnapshot

Follower:

- Cài snapshot
- Cập nhật state
- Tiếp tục nhận log mới từ snapshot index

67. Snapshot phải nhất quán

Snapshot cần tương ứng với:

lastIncludedIndex
lastIncludedTerm

Ví dụ:

Snapshot chứa state sau index 1000
Entry index 1000 thuộc term 20

Node cần giữ metadata này để tiếp tục log matching sau snapshot.

68. Cluster Membership Change

Thêm hoặc xóa voting node không nên cập nhật cấu hình một cách ngây thơ.

Ví dụ đổi:

Old cluster:
A, B, C

New cluster:
C, D, E

Nếu mỗi phía dùng config khác nhau, có thể hình thành hai majority độc lập.

Raft thường dùng ý tưởng joint consensus:

Giai đoạn chuyển tiếp yêu cầu agreement từ cả old config và new config.

Sau đó mới chuyển hoàn toàn sang new config.

69. Vì sao không thay Membership cùng lúc tùy tiện?

Giả sử old config:

A, B, C
Majority = 2

New config:

D, E, F
Majority = 2

A, B có thể elect một leader theo old config.

D, E có thể elect leader khác theo new config.

Hai majority không giao nhau.

Joint configuration bảo đảm quorum intersection trong quá trình chuyển.

70. Learner / Non-voting Replica

Khi thêm node mới, nó chưa có đầy đủ log.

Không nên cho nó vote ngay.

Có thể thêm dưới vai trò:

Learner / non-voting member

Quy trình:

1. Add learner.
2. Đồng bộ snapshot và log.
3. Đợi catch up.
4. Promote thành voter.
5. Có thể remove node cũ.

Điều này tránh làm giảm khả năng đạt quorum trong lúc node mới còn chậm.

71. Consensus và 2PC khác nhau thế nào?

Consensus

Các node thống nhất về:

- Một leader
- Một log
- Một thứ tự quyết định

Nó chịu được một số node crash nếu còn quorum.

2PC

Các participant thống nhất:

Commit hoặc abort một transaction cụ thể

Coordinator failure có thể làm participants prepared bị block.

Consensus có thể được dùng để làm coordinator hoặc transaction metadata highly available, nhưng hai khái niệm không giống nhau.

72. Raft và Database Replication

Một database có thể dùng:

- Raft/Paxos cho replicated log
- Leader–follower replication không consensus đầy đủ
- External consensus service cho leader election

Không phải mọi “primary + replicas” đều dùng Raft.

Cần hỏi:

- Ai chọn primary?
- Commit cần bao nhiêu ACK?
- Leader cũ bị fence thế nào?
- Metadata election nằm đâu?

73. Consensus Service và Data Plane

Một hệ thống có thể dùng consensus cho metadata nhỏ:

- Shard ownership
- Cluster membership
- Leader ID
- Configuration

Trong khi data lớn đi qua một data plane riêng.

flowchart TD
    Control[Consensus Control Plane]
    Control --> Metadata[Shard and Leader Metadata]

    Client --> Router
    Router --> Data1[(Data Node 1)]
    Router --> Data2[(Data Node 2)]

    Metadata --> Router

Không nên lưu mọi payload lớn trong coordination store chỉ vì nó có consensus.

74. Consensus là đắt

Một write consensus thường cần:

- Leader processing
- Network round trip tới quorum
- Durable log write
- Replication
- State-machine apply

Latency phụ thuộc:

- Quorum node đủ nhanh
- Disk latency
- Network latency
- Leader load

Consensus nên dùng cho dữ liệu cần thứ tự và correctness mạnh, không phải mọi telemetry hoặc cache entry.

75. Cross-Region Consensus

Nếu voting nodes nằm ở nhiều region:

Asia
Europe
US

Write phải chờ majority qua WAN.

Ví dụ leader Asia, quorum cần Europe:

Write latency gồm inter-region round trip.

Lợi ích:

- Chịu region failure tốt hơn
- RPO gần 0 tùy durability

Nhược điểm:

- Latency cao
- Network partition thường xuyên hơn
- Chi phí lớn

Replica không voting hoặc async replicas có thể được dùng cho DR/read scaling mà không nằm trên write quorum.

76. Quorum Placement

Cluster năm node:

Asia: 3
Europe: 1
US: 1

Nếu Asia region chết:

Còn 2/5
→ Không có majority

Không chịu được Asia region failure.

Placement phải dựa trên fault domain, không chỉ tổng số node.

Ví dụ ba voting locations:

Zone A: 1
Zone B: 1
Zone C: 1

chịu mất một zone.

Multi-region placement cần phân tích majority khi từng region lỗi.

77. Witness Node

Witness có thể tham gia vote nhưng không giữ toàn bộ data.

Ví dụ:

Primary region A: Data node
Primary region B: Data node
Third site: Witness

Witness giúp phá tie trong election.

Nhưng:

- Không thay thế data replica
- Không giúp read scaling
- Không nhất thiết chứa state đầy đủ

Nếu chỉ còn data node và witness, khả năng tiếp tục phục vụ còn phụ thuộc implementation và durability contract.

78. Failure Detector không hoàn hảo

Trong asynchronous network, không nhận heartbeat không chứng minh node đã chết.

Nó có thể:

- Bị network delay
- Bị GC pause
- Disk stall
- CPU starvation
- Packet loss

Consensus không cố “biết chắc node đã chết”.

Nó dùng quorum và term để bảo đảm:

Dù đánh giá sai một node, chỉ phía có majority mới tiếp tục commit.

79. Election Timeout quá ngắn

Hậu quả:

- Election thường xuyên
- Leader flapping
- Term tăng liên tục
- Write latency cao
- Availability giảm

Node follower có thể timeout chỉ vì một network spike ngắn.

80. Election Timeout quá dài

Hậu quả:

- Leader chết nhưng cluster phát hiện chậm
- Failover lâu
- RTO tăng

Cần cân bằng:

Failure detection speed
↕
False election risk

81. Leader Flapping

Leader thay đổi liên tục:

Term 100: A
Term 101: B
Term 102: C
Term 103: A

Nguyên nhân có thể:

- Network không ổn định
- Disk leader chậm
- CPU pause
- Election timeout quá thấp
- Một node overload

Leader changes cao là metric reliability quan trọng.

82. Slow Follower

Một follower chậm không nhất thiết chặn write nếu leader vẫn đạt quorum với các follower khác.

Cluster năm node:

Leader A
Fast followers B, C
Slow followers D, E

A + B + C là majority.

Write vẫn commit.

Nhưng nếu B lỗi:

Leader phải chờ D hoặc E
→ latency tăng mạnh hoặc mất quorum.

Slow replicas làm giảm failure headroom.

83. Slow Leader

Leader chậm ảnh hưởng toàn cluster:

- Client write chậm
- Heartbeat trễ
- Followers bắt đầu election
- Leadership có thể chuyển

Một follower mạnh nhưng leader yếu vẫn làm throughput thấp.

Một số hệ thống hỗ trợ leadership transfer có kế hoạch.

84. Leadership Transfer

Trong maintenance:

1. Chọn follower đã catch up.
2. Ngừng hoặc giảm write ngắn hạn.
3. Chuyển leadership.
4. Leader cũ step down.

Khác với failover bất ngờ vì:

- Có thể đợi follower đồng bộ
- Giảm data uncertainty
- Giảm downtime

85. Idempotency vẫn cần với Consensus

Consensus bảo đảm log entry không bị commit mâu thuẫn.

Nhưng client có thể retry cùng business request:

Request 1:
Create order, requestId=R

Response bị mất

Request 2:
Create order, requestId=R

Nếu state machine không deduplicate:

Hai order khác nhau có thể được tạo và cả hai đều được consensus commit.

Cần:

requestId → stored result

hoặc business unique constraint.

86. Deterministic State Machine

Mọi node phải áp dụng cùng command và đạt cùng kết quả.

Không nên đưa command kiểu:

SET created_at = local_now()
SET token = random()

và để mỗi node tự tính.

Kết quả có thể khác nhau.

Tốt hơn leader quyết định giá trị:

SET created_at = 2026-07-11T...
SET token = abc123

rồi replicate giá trị cụ thể.

87. External Side Effect từ State Machine

Không nên để mọi replica cùng gửi email khi apply log entry:

Node A sends email
Node B sends email
Node C sends email

Sẽ gửi ba email.

Các cách:

- Chỉ leader thực hiện side effect với idempotency.
- Commit một outbox record trong state machine.
- Worker bên ngoài xử lý outbox.
- Dùng fencing token cho external resource.

External side effect vẫn cần reliable workflow design.

88. Consensus không thay thế Outbox

Consensus có thể commit:

OrderCreated

trong replicated database.

95. Case Study — Distributed Lock cho Job Scheduler

Yêu cầu:

Chỉ một scheduler được chạy settlement job.

Lock service dùng consensus để cấp quyền:

Scheduler A receives:
lock token 205

A bị pause.

Lock hết hạn, Scheduler B nhận:

lock token 206

Database settlement chỉ chấp nhận operation token mới hơn:

UPDATE settlement_job
SET owner_token = 206
WHERE owner_token < 206;

A quay lại với token 205 bị từ chối.

Consensus chọn lock holder; fencing bảo vệ resource thật.

96. Case Study — Configuration Store

Các service đọc config:

97. Case Study — Booking Seat

Authoritative booking state được replicate bằng consensus.

Leader append vào log.

Khi commit:

- State machine kiểm tra seat còn available.
- Nếu còn, tạo reservation.
- Nếu đã reserved, trả conflict.

Mọi replica áp dụng cùng command theo cùng thứ tự.

Nhờ đó hai request cạnh tranh không cùng thắng.

99. Các sai lầm phổ biến

Lỗi 1: Nghĩ replication tự động ngăn split-brain

Replication không quyết định node nào có quyền ghi.

Lỗi 2: Nghĩ health check có thể xác nhận node chắc chắn đã chết

Không nhận heartbeat có thể chỉ là network partition.

Lỗi 3: Cluster hai voting nodes nhưng kỳ vọng chịu một failure

Hai node cần cả hai để đạt majority.

Lỗi 4: Cho minority tiếp tục commit để tăng availability

Có thể tạo hai lịch sử mâu thuẫn.

Lỗi 5: Chỉ dựa vào term trong application, không fencing resource

External storage vẫn có thể nhận write từ leader cũ.

Lỗi 6: Candidate log cũ vẫn được vote

Có thể làm mất entry đã commit.

Lỗi 7: Xem entry nằm trên majority là commit trong mọi trường hợp

Raft có quy tắc current-term commit quan trọng.

Lỗi 8: Trả success trước khi entry commit

Leader crash có thể làm mất write đã báo thành công.

Lỗi 9: Old leader phục vụ linearizable read mà không xác nhận leadership

Có thể trả dữ liệu stale sau partition.

Lỗi 10: Election timeout quá ngắn

Tạo election storm và leader flapping.

Lỗi 11: Thêm voting node trước khi nó catch up

Có thể làm cluster khó đạt quorum.

Lỗi 12: Thay membership trực tiếp từ old sang new config

Có thể hình thành hai majority không giao nhau.

Lỗi 13: State machine dùng random hoặc local clock tùy node

Các replica có thể diverge.

Lỗi 14: Mọi replica cùng thực hiện external side effect

Tạo email, payment hoặc job duplicate.

Lỗi 15: Nghĩ consensus thay thế backup, outbox hoặc idempotency

Consensus chỉ giải quyết agreement trong phạm vi của nó.

102. Cách trình bày trong System Design Interview

Không nên chỉ nói:

Em dùng Raft để bầu leader.

Nên nói:

Tôi dùng một consensus group gồm ba hoặc năm voting nodes. Mỗi nhiệm kỳ có một term tăng dần. Follower không nhận heartbeat trước randomized election timeout sẽ trở thành candidate, tăng term, vote cho mình và yêu cầu vote từ các peers. Candidate chỉ thắng khi có majority, và follower chỉ vote nếu candidate chưa cũ và log của candidate ít nhất cập nhật bằng log của follower. Điều này giúp bảo đảm leader mới chứa mọi entry đã commit.

Với write path:

Leader append command vào log rồi replicate bằng AppendEntries. Follower chỉ append nếu prevLogIndex và prevLogTerm khớp, nhờ đó các log có cùng prefix. Entry thuộc current term được commit khi nằm trên majority; khi commit index tiến lên, toàn bộ prefix trước đó cũng được xem là committed và được apply theo thứ tự vào state machine.

Với partition và fencing:

Khi network partition xảy ra, chỉ phía có majority có thể elect leader và commit. Leader cũ ở phía minority không thể commit write mới. Nếu leader điều khiển external resource, tôi dùng term hoặc epoch làm fencing token và yêu cầu chính resource từ chối token cũ; chỉ step-down trong application là chưa đủ để ngăn stale leader gây side effect.

105. Những điều phải nhớ sau Bài 15

1. Replication tạo bản sao; consensus quyết định lịch sử nào hợp lệ.
2. Consensus thống nhất leader, log hoặc một chuỗi quyết định.
3. Safety bảo đảm không có quyết định mâu thuẫn.
4. Liveness bảo đảm hệ thống cuối cùng tiếp tục khi còn majority và mạng ổn định.
5. Majority bằng floor(N/2)+1.
6. Ba node chịu một crash; năm node chịu hai crash.
7. Số voting node lẻ thường hiệu quả hơn số chẵn.
8. Hai majority luôn giao nhau.
9. Quorum đơn thuần chưa phải consensus.
10. Raft có follower, candidate và leader.
11. Term là epoch logic tăng dần.
12. Node thấy term cao hơn phải step down.
13. Mỗi node chỉ vote một candidate trong một term.
14. Election timeout được random hóa để giảm split vote.
15. Candidate cần majority để trở thành leader.
16. Candidate log phải ít nhất cập nhật bằng voter log.
17. Heartbeat thường là AppendEntries không có entry mới.
18. Client write đi qua leader.
19. Mỗi log entry có index, term và command.
20. prevLogIndex và prevLogTerm giúp kiểm tra log prefix.
21. Follower xóa suffix chưa commit nếu xung đột với leader.
22. Entry chưa commit có thể bị leader mới ghi đè.
23. commitIndex là entry cao nhất đã commit.
24. Chỉ entry committed mới được coi là quyết định cuối cùng.
25. Raft chỉ trực tiếp majority-commit entry thuộc current term.
26. Commit entry current term cũng commit toàn bộ prefix trước nó.
27. Leader chỉ nên trả success sau khi entry commit theo contract.
28. Leader crash trước response tạo kết quả unknown cho client.
29. Idempotency vẫn cần dù hệ thống dùng consensus.
30. Trong network partition, chỉ phía majority có thể tiếp tục commit.
31. Minority leader có thể còn sống nhưng không còn quyền commit.
32. Leader cũ nhận term cao hơn phải trở thành follower.
33. Term bảo vệ cluster nhưng external resource vẫn cần fencing.
34. Fencing token phải được resource đích kiểm tra atomically.
35. Linearizable read cần xác nhận leader vẫn hợp lệ.
36. Follower read có thể stale.
37. State machine phải deterministic.
38. External side effects không nên được mọi replica thực hiện.
39. Snapshot giúp log không tăng vô hạn.
40. Node tụt xa có thể được khôi phục bằng snapshot.
41. Membership change cần quorum intersection, thường qua joint consensus.
42. Node mới nên catch up trước khi trở thành voter.
43. Consensus không thay thế outbox, backup hay reconciliation.
44. Leader changes, commit lag và quorum health phải được quan sát.
45. Network-partition testing quan trọng hơn chỉ kill process.

106. Bài tập thực hành

Thiết kế consensus layer cho một hệ thống quản lý shard ownership.

Yêu cầu

- Có hàng nghìn database shards.
- Mỗi shard chỉ được có một write leader hợp lệ.
- Router cần biết leader hiện tại của từng shard.
- Node có thể crash hoặc mất kết nối mạng.
- Không được để hai node cùng nhận write cho một shard.
- Cần chuyển shard giữa các server khi rebalancing.

Hãy trả lời:

1. Consensus group cần ba hay năm voting nodes?
2. Các voting nodes nên đặt qua những zone nào?
3. Consensus log cần lưu những command gì?
4. Term có vai trò gì trong leader election?
5. Election timeout cần được random hóa vì sao?
6. Candidate cần cung cấp thông tin log gì khi xin vote?
7. Khi nào một shard-assignment entry được commit?
8. Router được phép dùng assignment chưa commit không?
9. Khi old metadata leader bị partition, nó có được tiếp tục cấp shard ownership không?
10. Shard server dùng fencing token nào?
11. Database shard từ chối stale owner ra sao?
12. Khi thêm metadata node mới, có nên cho vote ngay không?
13. Membership change được triển khai thế nào?
14. Snapshot metadata cần chứa gì?
15. Metrics nào phát hiện consensus cluster không còn tiến?
16. Làm sao test split-brain trước production?
17. Client retry assignment command được deduplicate thế nào?
18. Nếu entry commit nhưng response mất, client xử lý ra sao?

Kiến trúc gợi ý:

flowchart TD
    Admin[Shard Controller] --> ConsensusLeader[Metadata Consensus Leader]

    ConsensusLeader --> V1[(Voting Node 1)]
    ConsensusLeader --> V2[(Voting Node 2)]
    ConsensusLeader --> V3[(Voting Node 3)]

    ConsensusLeader --> MetadataLog[Shard Ownership Log]

Điểm cốt lõi:

Consensus không cố chứng minh node nào đã chết. Nó bảo đảm rằng chỉ một tập node có quorum được quyền quyết định, và mọi quyết định đã commit sẽ tồn tại trong lịch sử của các leader tương lai. Fencing tiếp tục bảo vệ thế giới bên ngoài khỏi những leader cũ chưa nhận ra mình đã mất quyền.
