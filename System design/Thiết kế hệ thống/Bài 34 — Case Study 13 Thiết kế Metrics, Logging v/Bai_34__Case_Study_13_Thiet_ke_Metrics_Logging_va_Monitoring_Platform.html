Bài 34 — Case Study 13: Thiết kế Metrics, Logging và Monitoring Platform

Một nền tảng monitoring thu thập tín hiệu từ hàng nghìn hoặc hàng triệu máy chủ, container và ứng dụng để trả lời:

Hệ thống có đang hoạt động không?
Có thành phần nào chậm hoặc lỗi không?
Sự cố bắt đầu từ khi nào?
Những request, service hoặc khách hàng nào bị ảnh hưởng?
Có cần cảnh báo đội vận hành ngay không?

Ba loại tín hiệu observability phổ biến:

Metrics:
Số liệu tổng hợp theo thời gian.

Logs:
Các bản ghi sự kiện chi tiết.

Traces:
Đường đi của một request qua nhiều service.

Trong bài này, trọng tâm là metrics và logs, nhưng traces sẽ được đề cập khi cần liên kết dữ liệu.

Kiến trúc cốt lõi:

Agents/Collectors
→ Ingestion Gateway
→ Durable Stream
→ Metrics/Log Processing
→ Time-Series và Log Storage
→ Query Engine
→ Dashboards và Alerting

1. Xác định phạm vi

Hệ thống hỗ trợ:

1. Thu thập metrics từ hosts, containers và applications.
2. Thu thập structured/unstructured logs.
3. Push hoặc pull collection.
4. Multi-tenant ingestion.
5. Time-series storage.
6. Log storage và indexing.
7. Aggregation và downsampling.
8. Retention nhiều tầng.
9. Query và dashboard.
10. Alerting.
11. Silencing, deduplication và notification routing.
12. High-cardinality protection.
13. Multi-region.
14. RBAC, audit và quota.

Tạm chưa đi sâu vào:

- APM tracing engine hoàn chỉnh
- Full security information and event management
- Machine-learning anomaly detection chuyên sâu
- Incident management platform hoàn chỉnh
- Long-term data lake analytics tổng quát

2. Functional Requirements

Metrics

- Ghi samples theo timestamp.
- Query theo khoảng thời gian.
- Filter theo labels.
- Aggregate sum, avg, min, max, count.
- Tính rate, percentile và histogram.
- Group by service, region hoặc status.

Logs

- Ingest log lines hoặc structured events.
- Search theo thời gian.
- Filter theo service, host, severity và fields.
- Full-text search.
- Aggregate log counts.
- Xem log context trước và sau một event.

Monitoring

- Dashboard.
- Alert rules.
- Notification.
- Silence.
- Alert grouping.
- Alert history.
- Service health overview.

3. Non-Functional Requirements

- Ingestion throughput rất cao.
- Không để monitoring làm ảnh hưởng production workload.
- Chấp nhận một phần eventual consistency.
- Dữ liệu mới phải query được gần realtime.
- Query lịch sử phải hoàn thành trong thời gian hợp lý.
- Alert không được bỏ sót sự cố nghiêm trọng.
- Một tenant không làm chậm tenant khác.
- Hệ thống phải chịu được cardinality tăng đột biến.
- Có thể mất một node hoặc một zone mà không mất dữ liệu đã ACK.
- Có retention và cost controls rõ ràng.

4. Metrics, Logs và Traces khác nhau thế nào?

Metrics

Ví dụ:

http_requests_total{
  service="checkout",
  status="500",
  region="ap-southeast"
} 12543

Đặc điểm:

- Dữ liệu số.
- Có labels.
- Được tối ưu cho aggregation.
- Storage trên mỗi sự kiện thấp.
- Không giữ toàn bộ chi tiết của từng request.

Logs

Ví dụ:

{
  "timestamp": "2026-07-14T10:00:00Z",
  "service": "checkout",
  "level": "ERROR",
  "requestId": "req_123",
  "message": "Payment provider timeout"
}

Đặc điểm:

- Chi tiết hơn.
- Có thể chứa text hoặc structured fields.
- Volume lớn.
- Search linh hoạt nhưng đắt hơn metrics.

Traces

Request
→ API Gateway
→ Order Service
→ Payment Service
→ Provider

Traces liên kết spans bằng trace ID.

5. Khi nào dùng Metrics, Logs hay Traces?

Metrics:
Phát hiện hệ thống đang có vấn đề.

Logs:
Giải thích sự kiện cụ thể đã xảy ra.

Traces:
Xác định request bị chậm ở service nào.

Ví dụ:

Metric:
Error rate tăng từ 1% lên 20%.

Log:
Payment provider trả timeout.

Trace:
90% latency nằm ở Payment Service → Provider.

6. Capacity Estimation

Giả sử nền tảng phục vụ:

100.000 hosts
2 triệu containers
10 triệu active time series
50 triệu log events/giây peak
2 triệu metric samples/giây trung bình

Nếu một metric sample sau encoding trung bình 20 byte:

2.000.000 × 20
= 40 MB/giây
≈ 3,5 TB/ngày

Với replication và indexes:

Có thể thành 10–20 TB/ngày.

Logs lớn hơn nhiều.

Nếu:

10 triệu log events/giây trung bình
Average event = 500 bytes

thì:

5 GB/giây
≈ 432 TB/ngày raw

Đây là lý do logs cần compression, tiered storage và selective indexing.

Một metric name:

có labels:

Mỗi tổ hợp labels tạo một time series riêng.

Ví dụ:

100 services
× 5 regions

= 25 triệu series

Dù số samples/giây không quá lớn, metadata và indexes có thể rất đắt.

10. Agent Collection

Agent chạy gần workload:

- Trên host
- Sidecar container
- DaemonSet trong Kubernetes
- Library trong application
- Central collector

Agent chịu trách nhiệm:

- Đọc metrics và logs.
- Gắn metadata.
- Buffer.
- Batch.
- Compress.
- Retry.
- Rate limit.

11. Vì sao cần Agent?

Nếu mọi ứng dụng gửi trực tiếp tới backend:

- Mỗi ứng dụng phải tự retry.
- Monitoring endpoint lỗi có thể làm application chậm.
- Không kiểm soát batching.
- Khó cập nhật protocol.
- Không có local buffering.

Agent tạo một lớp cách ly giữa production application và observability backend.

12. Agent phải không làm ảnh hưởng Application

Agent cần:

- CPU limit.
- Memory limit.
- Disk buffer limit.
- Network bandwidth limit.
- Backpressure policy.

Nếu backend monitoring lỗi:

Ứng dụng vẫn phải tiếp tục hoạt động.

Tùy signal, agent có thể:

- Buffer.
- Sample.
- Drop dữ liệu cũ.
- Drop low-priority logs.

13. Push và Pull Collection

Push

Application hoặc agent gửi dữ liệu tới backend.

Ưu điểm:

- Phù hợp logs và events.
- Phù hợp short-lived jobs.
- Không cần backend biết mọi target.

Nhược điểm:

- Khó biết target đã chết hay chỉ không gửi.
- Clients phải retry và buffer.

Pull

Collector định kỳ scrape target.

Ưu điểm:

- Backend kiểm soát schedule.
- Dễ phát hiện target unreachable.
- Target không cần biết backend.

Nhược điểm:

- Cần service discovery.
- Khó với short-lived workload.
- Network topology có thể phức tạp.

14. Thiết kế Hybrid

Một hệ thống thực tế có thể:

Metrics:
Pull từ service endpoints hoặc push qua agent.

Logs:
Push qua agents.

Cloud/provider metrics:
Pull từ APIs.

Short-lived jobs:
Push qua gateway hoặc collector.

Không cần ép mọi loại dữ liệu vào một collection model.

15. Agent Buffer

Agent giữ local queue:

memory queue
→ disk WAL
→ remote backend

Nếu backend tạm lỗi:

- Ghi xuống disk.
- Retry với backoff.
- Xóa sau ACK.

Nếu disk đầy:

- Drop oldest.
- Drop debug logs trước.
- Sample.
- Alert local health.

16. Agent Write-Ahead Log

Agent WAL record:

batchId
tenantId
signalType
payload
createdAt
retryCount

Sau khi backend ACK:

Đánh dấu segment có thể xóa.

WAL không nên tăng vô hạn.

Cần:

maxDiskBytes
maxAge
segmentRotation

17. Batching

Không gửi từng metric sample hoặc từng log line riêng lẻ.

Batch theo:

- Số events.
- Tổng bytes.
- Thời gian.

Ví dụ:

Gửi khi:
- Đủ 1 MB
- Hoặc 5.000 events
- Hoặc sau 1 giây

Batch lớn:

- Compression tốt.
- Ít network calls.

Batch quá lớn:

- Tăng latency.
- Retry tốn kém.
- Memory cao.

18. Compression

Metrics và logs có nhiều lặp lại:

service names
timestamps gần nhau
label names
common log templates

Có thể dùng:

- Snappy-like compression cho low latency.
- Zstd-like compression cho storage.
- Delta encoding cho timestamps.
- Dictionary encoding cho labels.

19. Ingestion Gateway

Gateway chịu trách nhiệm:

- Authenticate.
- Resolve tenant.
- Validate payload.
- Enforce limits.
- Normalize protocol.
- Assign ingestion timestamp.
- Route shard.
- Write durable stream.

Gateway không nên thực hiện query hoặc aggregation nặng.

21. Authentication và Tenant Resolution

Có thể dùng:

- API key
- mTLS
- Workload identity
- OAuth token
- Cloud role

Không tin tenantId do client gửi nếu token không cho phép tenant đó.

Gateway suy ra:

credential → tenantId → limits/policies

22. Ingestion Validation

Kiểm tra:

- Timestamp hợp lệ.
- Metric name hợp lệ.
- Label name/value length.
- Payload size.
- Log line size.
- Number of labels.
- Number of new series.
- Future/past timestamp limits.

Không nên để malformed payload đi sâu vào storage pipeline.

23. Timestamp Semantics

Có hai timestamp:

eventTimestamp:
Do client tạo.

ingestionTimestamp:
Backend nhận.

Client timestamp có thể sai vì:

- Clock skew.
- Device resume.
- Buffer lâu.
- Time zone bug.

Backend cần giới hạn:

Không chấp nhận sample quá xa trong tương lai.

24. Out-of-Order Samples

Metrics có thể tới:

t=100
t=120
t=110

do batching và retry.

Các lựa chọn:

1. Reject sample cũ.
2. Cho phép một out-of-order window.
3. Buffer và sort.
4. Ghi vào late-data block riêng.

Cho phép out-of-order quá rộng làm TSDB phức tạp và giảm compression.

25. Duplicate Samples

Agent retry batch do mất ACK.

Backend có thể nhận cùng sample nhiều lần.

Đối với metrics:

Same series + same timestamp

có thể:

- Deduplicate.
- Last value wins.
- Reject nếu value khác.

Đối với logs, duplicate detection khó hơn vì nhiều log thật có nội dung giống nhau.

26. Ingestion ACK Semantics

ACK nên nghĩa:

Dữ liệu đã được ghi bền vững vào ingestion log/quorum.

Không cần chờ:

- Compaction
- Long-term storage
- Dashboard update

Nếu ACK trước durable write:

Node chết có thể làm mất dữ liệu mà client đã xóa khỏi buffer.

27. Durable Ingestion Stream

Một durable stream giúp:

- Tách ingestion và storage.
- Hấp thụ traffic spike.
- Replay.
- Scale consumers độc lập.
- Xử lý nhiều downstream.

Partition key có thể là:

tenantId + seriesHash

cho metrics, và:

tenantId + streamHash

cho logs.

28. Backpressure

Nếu storage chậm:

Stream lag tăng.

Nếu lag vượt giới hạn:

- Autoscale consumers.
- Throttle tenant.
- Sample/drop low-priority data.
- Increase agent buffering.

Không để ingestion gateway giữ request connections vô hạn.

29. Metric Types

Counter

Chỉ tăng hoặc reset:

http_requests_total

Dùng:

rate()
increase()

Gauge

Có thể tăng hoặc giảm:

memory_usage_bytes
queue_depth

Histogram

Phân phối observations theo buckets:

request_duration_seconds_bucket

Summary

Client tính quantiles hoặc aggregated statistics.

30. Counter Reset

Counter có thể reset khi process restart:

1000 → 20

Query rate phải phát hiện reset thay vì coi là negative traffic.

Counter nên:

- Chỉ tăng.
- Reset về giá trị thấp hơn khi restart.

31. Gauge

Gauge phù hợp:

- CPU temperature.
- Active connections.
- Queue size.

Không dùng gauge cho cumulative event count vì không thể tính rate chính xác qua reset hoặc missing samples.

32. Histogram

Ví dụ buckets:

≤ 100 ms
≤ 250 ms
≤ 500 ms
≤ 1 s
+Inf

Metric:

http_duration_bucket{le="0.1"} 100
http_duration_bucket{le="0.25"} 180
...

Histogram cho phép aggregate giữa instances.

33. Summary Trade-Off

Client-side summary có thể tính p95 trực tiếp, nhưng:

p95 của instance A
+
p95 của instance B

không thể cộng để tạo global p95 chính xác.

Histograms aggregate tốt hơn giữa machines.

34. Metric Labels

Labels tốt:

service="checkout"
region="asia-southeast"
status_class="5xx"
method="POST"

Labels nguy hiểm:

user_id
request_id
session_id
email
full_url_with_query

Mỗi giá trị duy nhất tạo series mới.

35. High Cardinality

Cardinality là số series riêng biệt.

Ví dụ:

metric:
http_request_total

labels:
service=checkout
user_id=1...100.000.000

có thể tạo hàng trăm triệu series.

Hậu quả:

- Metadata memory tăng.
- Index lớn.
- Compaction chậm.
- Query fan-out lớn.
- Cache hit thấp.

36. Cardinality Budget

Mỗi tenant có limits:

- Active series.
- New series/minute.
- Labels/series.
- Label value length.
- Samples/second.
- Total stored series.

Ví dụ:

Max active series: 10 triệu
Max new series: 100.000/phút

37. Cardinality Explosion Detection

Theo dõi:

- New series rate.
- Active series by metric.
- Top label names by distinct values.
- Top tenants by series creation.
- Series churn.

Alert:

Metric X tạo 1 triệu series mới trong 5 phút.

38. Series Churn

Một tenant có thể không có quá nhiều active series cùng lúc nhưng liên tục tạo series mới:

pod_id thay đổi mỗi deployment
request_id thay đổi mỗi request

Điều này tạo metadata và small chunks lớn.

Cần limit cả:

- Active cardinality.
- Series creation rate.

39. Label Dropping và Relabeling

Collector có thể:

- Drop labels.
- Rename labels.
- Map dynamic paths.
- Convert status code thành status class.

Ví dụ:

/api/users/123
/api/users/456

chuẩn hóa thành:

/api/users/:id

40. Exemplar

Thay vì đưa trace_id thành metric label, lưu một số trace IDs như exemplar:

Histogram bucket
→ Sample trace ID liên quan

Giúp từ metric spike chuyển sang trace mà không làm tăng series cardinality.

41. Time-Series Data Model

Một time series được xác định bởi:

tenantId
metricName
sorted label set

Ví dụ:

http_requests_total{
  service="checkout",
  region="vn",
  status="500"
}

Series ID có thể là hash của canonical label set.

42. Canonical Label Encoding

Labels phải được sort:

region=vn,service=checkout,status=500

để:

Hash ổn định bất kể thứ tự client gửi.

Cần lưu original labels để xử lý hash collision hoặc query display.

43. TSDB Write Path

flowchart LR
    Stream --> Distributor
    Distributor --> Ingester
    Ingester --> WAL
    Ingester --> HeadBlock[In-Memory Head Block]
    HeadBlock --> Flush[Block Builder]
    Flush --> ObjectStore[(Immutable TSDB Blocks)]
    Flush --> IndexStore[(Block Index)]

44. Ingester

Ingester chịu trách nhiệm:

- Nhận samples theo series shard.
- Validate ordering.
- Append WAL.
- Giữ recent samples trong memory.
- Nén chunks.
- Flush immutable blocks.

Ingester thường là stateful.

45. Metrics WAL

Trước khi ACK nội bộ:

Append sample batch vào WAL.

Sau crash:

Replay WAL
→ Rebuild recent head state.

WAL cần:

- Segmentation.
- Checksums.
- Truncation sau flush.

46. Head Block

Recent data nằm trong:

- Memory.
- Local disk/WAL.

Lợi ích:

- Query dữ liệu vài phút gần nhất.
- Append hiệu quả.

Sau time window, ví dụ hai giờ:

Head block được đóng và flush thành immutable block.

47. Immutable TSDB Blocks

Một block có thể chứa:

- Time range.
- Compressed chunks.
- Series index.
- Label index.
- Statistics.

Ví dụ:

Block:
10:00–12:00

Immutable blocks dễ:

- Upload object storage.
- Cache.
- Replicate.
- Compact.

48. Time Partitioning

Data thường partition theo:

tenant
time range
series hash

Time partition giúp queries theo khoảng thời gian chỉ đọc blocks liên quan.

Nhưng một block quá nhỏ tạo:

- Nhiều metadata.
- Nhiều object requests.

Block quá lớn:

- Compaction nặng.
- Query phải đọc nhiều dữ liệu không cần.

49. Series Index

Query:

http_requests_total{
  service="checkout",
  region="vn"
}

cần tìm series IDs phù hợp.

Dùng inverted index:

label_name=service,label_value=checkout
→ series IDs

Intersect postings lists của nhiều matchers.

50. Matcher Types

Query có thể dùng:

=
!=
=~
!~

Regex query trên labels có thể rất đắt.

Ví dụ:

pod=~".*"

khớp mọi series.

Cần query limits và optimization.

51. Chunk Encoding

Time-series data có:

- Timestamps gần nhau.
- Values thường biến đổi nhỏ.

Compression có thể dùng:

- Delta-of-delta cho timestamps.
- XOR encoding cho floating values.

Làm giảm storage đáng kể.

52. Compaction

Nhiều small blocks được merge:

2 giờ
→ 12 giờ
→ 1 ngày

Compaction giúp:

- Giảm số objects.
- Merge indexes.
- Xóa duplicates.
- Áp tombstones.
- Tăng query efficiency.

53. Compaction Failure

Compaction phải idempotent.

Flow:

1. Chọn input blocks.
2. Tạo output block mới.
3. Verify checksum.
4. Publish block metadata.
5. Đánh dấu input superseded.
6. Xóa input sau grace period.

Không xóa input trước khi output visible.

54. Downsampling

Dữ liệu raw:

Mỗi 10 giây

sau 30 ngày có thể chỉ giữ:

1 phút:
min, max, sum, count

5 phút:
min, max, sum, count

Downsampling giảm storage và query cost cho khoảng thời gian dài.

55. Downsampling mất gì?

Nếu chỉ giữ average:

Một spike 100% CPU trong 5 giây

có thể biến mất trong average 5 phút.

Tốt hơn lưu:

min
max
sum
count

và histogram aggregates khi cần.

56. Retention Tiers

Ví dụ:

Recent raw:
7 ngày trên SSD/fast storage.

Raw object blocks:
30–90 ngày.

Downsampled:
1–2 năm.

Archive:
Object storage lạnh.

Retention theo tenant hoặc data class.

57. Metrics Query Engine

Query flow:

1. Parse query.
2. Authenticate tenant.
3. Plan time ranges.
4. Select blocks/ingesters.
5. Resolve series.
6. Fetch chunks.
7. Execute functions.
8. Merge partial results.
9. Return response.

58. Query Fan-Out

Một query có thể cần đọc:

- Nhiều ingesters.
- Hàng trăm blocks.
- Nhiều storage shards.

Query frontend chia request thành:

- Time partitions.
- Series partitions.

sau đó merge kết quả.

59. Query Frontend

Trách nhiệm:

- Parse và validate.
- Split query.
- Cache.
- Retry partial failures.
- Enforce limits.
- Queue theo tenant.
- Merge results.

Không nên cho client gọi trực tiếp mọi storage shard.

60. Query Limits

Giới hạn:

- Maximum time range.
- Maximum series matched.
- Maximum samples loaded.
- Maximum query runtime.
- Maximum concurrent queries/tenant.
- Maximum response size.

Nếu không, một query regex có thể làm sập cluster.

61. Query Fairness

Một tenant chạy 1.000 queries nặng không được làm tenant khác timeout.

Dùng:

- Per-tenant queues.
- Weighted fair scheduling.
- Concurrency limits.
- Query cost estimates.

62. Query Result Cache

Cache key:

tenant
query expression
time range
step
data version/block set

Historical queries dễ cache vì blocks immutable.

Recent queries có TTL ngắn hoặc không cache.

63. Query Splitting theo Time

Một query 30 ngày có thể chia:

Ngày 1
Ngày 2
...
Ngày 30

thực thi song song.

Nhưng fan-out quá lớn lại gây overload.

Query planner cần giới hạn concurrency.

64. Recording Rules

Một query nặng thường xuyên:

sum by(service)(
  rate(http_requests_total[5m])
)

có thể được tính định kỳ và ghi thành metric mới:

service:http_requests_rate5m

Đây là recording rule.

Lợi ích:

- Dashboard nhanh.
- Alert evaluation rẻ.

65. Recording Rule Trade-Off

Ưu điểm:

- Giảm query CPU.
- Pre-aggregate cardinality.

Nhược điểm:

- Tốn thêm storage.
- Có evaluation lag.
- Rule sai cần recompute.

66. Logs Collection

Agent có thể đọc:

- stdout/stderr containers.
- System log files.
- Application files.
- Journald.
- Cloud logging API.

67. Log Rotation

File:

được rename:

app.log.1

và tạo app.log mới.

Agent không nên:

- Đọc lại toàn bộ file cũ.
- Bỏ sót phần cuối.

Theo dõi inode/file ID và offset.

68. Multiline Logs

  at service.A

- Start pattern.
- Continuation pattern.
- Timeout.
- Maximum lines/bytes.

69. Structured Logs

71. Log Indexing Trade-Off

Index mọi field

- Query linh hoạt.
- Index rất lớn.
- High-cardinality fields cực đắt.

Chỉ index labels chọn lọc

- Storage thấp.
- Full-text hoặc field query chậm hơn.

Một thiết kế cân bằng:

Index low-cardinality labels.
Lưu full log body trong compressed chunks/object storage.

72. Log Stream

Một log stream có thể được xác định bởi:

tenant

Các log entries trong stream được ghi theo thời gian.

73. Structured Metadata không Index

High-cardinality fields như:

traceId

có thể lưu trong body/structured metadata.

- Scan limited time range.
- Dùng secondary bloom filter.
- Dùng optional specialized index.

flowchart LR

75. Log Chunks

Một chunk chứa:

- Một log stream.
- Một time range.
- Compressed entries.
- Optional bloom filters.
- Min/max timestamps.

Chunk đóng khi:

- Đạt size.
- Đạt time limit.
- Stream inactive.

76. Full-Text Log Index

Một số hệ thống tạo inverted index:

token "timeout"
→ document/log IDs

Ưu điểm:

- Search text nhanh.

Nhược điểm:

- Index rất lớn.
- Write amplification.
- Tokenization đa ngôn ngữ.
- High-cardinality terms.

Có thể chỉ giữ full-text index trong recent hot tier.

77. Bloom Filters cho Logs

Mỗi chunk lưu bloom filter cho tokens/fields.

Query "payment timeout":

- Bloom nói chắc chắn không có → bỏ chunk.
- Bloom nói có thể có → scan chunk.

False positives làm scan thêm nhưng không bỏ sót log.

78. Log Query Flow

1. Chọn tenant và time range.
2. Filter stream labels.
3. Lấy candidate chunks.
4. Dùng bloom/index để bỏ chunks.
5. Decompress.
6. Apply text/field filters.
7. Merge theo timestamp.

79. Context Query

Khi tìm thấy log lỗi, user muốn xem:

20 logs trước
20 logs sau

Nếu log được sharding theo streams, context cần:

- Cùng stream.
- Cùng host/container.
- Cùng request/trace nếu có.

Không nhất thiết có global total ordering giữa mọi logs.

80. Log Ordering

Logs từ nhiều hosts có clock skew.

Backend có thể sắp theo event timestamp nhưng:

Không đảm bảo thứ tự tuyệt đối toàn hệ thống.

Giữ:

giúp điều tra.

81. Late Logs

Có thể:

- Chấp nhận trong late-arrival window.
- Ghi vào historical chunks.
- Reject quá cũ.

Có thể tạo late blocks rồi compact sau.

115. Regional Ingestion

nearest healthy region

Lợi ích:

- Latency thấp.
- Egress thấp.
- Local buffering ngắn hơn.

Nhưng data ownership cần rõ:

tenant + source region + time

116. Local Ingest, Global Query

Một mô hình:

- Data ghi vào region nguồn.
- Long-term blocks replicate vào object storage.
- Global query frontend fan-out tới regions liên quan.

Query planner dùng:

tenant

để tránh hỏi mọi region.

117. Regional vs Global Metrics

Metrics có thể có label:

sum across regions

Nhưng alert regional nên chạy tại region để giảm latency và dependency.

118. Alerting Multi-Region

Các lựa chọn:

Regional alert evaluation

- Latency thấp.
- Tiếp tục khi global query lỗi.
- Khó alert trên dữ liệu toàn cầu.

Global alert evaluation

- Có view toàn hệ thống.
- Phụ thuộc WAN và nhiều regions.

Hybrid:

Regional alerts cho service health.

- Raw data.

- Log chunks.
- Query cache.
- Alert state.
- Dashboard exports.
- Backups.

124. Multi-Region Query Failure

- Partial response.

125. Failure Mode — Agent mất kết nối

Agent:

- Buffer local disk.
- Retry với exponential backoff.
- Drop theo priority khi disk đầy.

Monitoring phải có metric:

agent_buffer_usage
agent_dropped_events_total

126. Failure Mode — Agent Restart

Replay local WAL.

Batch IDs giúp backend chịu duplicate retries.

Không reset file offsets về 0 gây đọc lại toàn bộ logs.

127. Failure Mode — Ingestion Gateway Down

Global/region load balancer chuyển sang replicas.

Agents retry.

Gateway stateless nên scale ngang.

128. Failure Mode — Stream Lag

Khi consumers chậm:

- Dữ liệu mới chưa query được.
- Alert có thể trễ.

Cần:

- Autoscaling.
- Priority streams.
- Throttle tenants.
- Alert trên ingestion-to-query lag.

129. Failure Mode — Ingester Crash

WAL replay phục hồi recent data.

Nếu WAL replicate hoặc node disk mất:

Có thể mất dữ liệu chưa flush.

Dùng replication factor:

Sample batch ghi tới N ingesters.
ACK khi quorum.

130. Replicated Ingestion

Distributor chọn replicas:

seriesHash
→ ingester A, B, C

ACK khi:

2/3 durable writes thành công.

Query recent data dedupe samples từ replicas.

131. Failure Mode — Object Storage Down

Recent head vẫn có thể phục vụ dữ liệu mới.

Historical queries có thể lỗi hoặc dùng cache.

Compaction/flush cần retry.

Không xóa local flushed data trước khi object durable.

132. Failure Mode — Compactor Crash

Input immutable blocks vẫn còn.

Output chưa publish được bỏ hoặc resume.

Không gây mất dữ liệu.

133. Failure Mode — Index Corruption

Blocks có checksums.

Nếu index hỏng nhưng chunks còn:

- Rebuild index từ block metadata/chunks.
- Dùng replica.
- Mark block quarantined.

134. Failure Mode — Query Storm

Dashboard hoặc incident tạo hàng nghìn queries.

Cần:

- Admission control.
- Query queue.
- Cache.
- Deduplicate identical requests.
- Degrade expensive panels.

135. Failure Mode — Alert Query Timeout

Không nên tự động coi timeout là condition false.

Các lựa chọn:

- Giữ previous state.
- Đánh dấu evaluation error.
- Gửi meta-alert.
- Retry có giới hạn.

Nếu coi timeout là resolved, có thể che giấu sự cố.

136. Failure Mode — Notification Provider Down

Alert vẫn ở FIRING.

Alert Manager:

- Retry.
- Route fallback.
- Ghi notification failure.

Không mất alert state.

137. Failure Mode — Cardinality Spike

Ingestion gateway có thể:

- Reject new series.
- Tiếp tục chấp nhận existing series.
- Drop offending label.
- Throttle tenant.

Cần trả lỗi rõ để đội phát triển sửa instrumentation.

138. Failure Mode — Log Line cực lớn

Giới hạn:

maxLogEventBytes

Có thể:

- Truncate.
- Reject.
- Store oversized payload riêng.

Phải ghi metadata rằng log đã bị truncate.

139. Failure Mode — Tenant chạy Query quá nặng

Query frontend:

- Estimate cost.
- Reject sớm.
- Apply timeout.
- Limit samples.
- Require recording rule.

Không để storage shards bị OOM.

140. Reconciliation

Kiểm tra:

- Stream offsets vs ingested blocks.
- WAL data vs flushed blocks.
- Block catalog vs object storage.
- Compaction input/output.
- Alert state vs rule ownership.
- Retention deletions.
- Tenant usage vs billing records.

141. Retention Deletion

1. Mark block expired.
2. Remove khỏi query catalog.
3. Chờ grace period.
4. Delete object.
5. Audit.

Grace period cho phép rollback policy lỗi.

time range
hold reason

145. Dead Man's Switch

153. Trade-Off — Push hay Pull Metrics?

Push

- Phù hợp short-lived jobs.
- Client phải retry.
- Khó phân biệt target chết.

Pull

- Discovery và health rõ.
- Backend kiểm soát schedule.
- Khó qua network boundaries.

Hybrid thường tốt nhất.

154. Trade-Off — Index toàn bộ Logs hay Chỉ Labels?

Full index

- Search nhanh.
- Storage và write cost cao.

Label index + scan chunks

- Rẻ hơn.
- Text search chậm hơn.

Có thể dùng full-text index cho recent hot tier và object chunks cho lịch sử.

155. Trade-Off — Raw Metrics hay Downsample?

Raw lâu dài

- Điều tra chi tiết.
- Storage và query cost cao.

Downsample

- Rẻ.
- Mất spikes và chi tiết.

Giữ raw ngắn hạn, downsample dài hạn.

156. Trade-Off — Regional hay Global Alerting?

Regional

- Nhanh và resilient.
- Không có global view hoàn chỉnh.

Global

- Dễ alert business toàn cầu.
- Phụ thuộc multi-region query.

Dùng cả hai theo loại alert.

157. Trade-Off — Reject hay Drop khi Cardinality quá cao?

Reject

- Client biết lỗi.
- Có thể mất toàn batch.

Drop offending series/labels

- Hệ thống tiếp tục.
- Có thể che giấu instrumentation bug.

Nên hỗ trợ partial rejection với diagnostics rõ.

158. Trade-Off — Strong Log Ordering hay Throughput?

Global ordering mọi log:

- Rất đắt.
- Không cần thiết.

Thường chỉ cần:

- Ordering theo source/stream.
- Event và ingestion timestamps.

159. Cách trình bày trong Phỏng vấn

Có thể mở đầu:

Tôi tách metrics và logs sau ingestion vì access pattern khác nhau. Metrics cần time-series compression và aggregation theo labels; logs cần stream labels, compressed chunks và optional full-text indexing.

Về collection:

Agents chạy gần workload để batch, compress và ghi disk WAL. Monitoring backend lỗi không được làm ứng dụng chậm; agent có local buffer và drop policy có kiểm soát.

Về metrics storage:

Mỗi unique metric name và label set tạo một series. Ingester append samples vào WAL và recent head block, sau đó flush thành immutable time-partitioned blocks trên object storage. Query frontend fan-out tới recent ingesters và historical blocks.

Về cardinality:

Tôi giới hạn active series và new-series rate theo tenant. Các labels như user ID hoặc request ID không được dùng làm metric dimensions; chúng có thể nằm trong logs, traces hoặc exemplars.

Về alerting:

Alert rules được shard cho evaluators có lease. Mỗi alert instance có state inactive, pending, firing và resolved. Alert Manager thực hiện grouping, deduplication, silence, inhibition và routing.

161. Những Sai lầm Phổ biến

Lỗi 1: Ứng dụng gửi trực tiếp từng Log Line

Tạo network overhead và làm application phụ thuộc backend.

Lỗi 2: Agent không có Disk Buffer

Backend outage làm mất toàn bộ dữ liệu.

Lỗi 3: Agent Buffer không có Giới hạn

Monitoring làm đầy disk production.

Lỗi 4: ACK trước Durable Write

Client xóa buffer nhưng backend có thể mất dữ liệu.

Lỗi 5: Dùng một Pipeline cho Metrics và Logs

Access pattern và storage requirements khác nhau.

Lỗi 6: Đưa Request ID vào Metric Label

Tạo cardinality cực lớn.

Lỗi 7: Chỉ Limit Active Series

Không ngăn series churn.

Lỗi 8: Không giới hạn Timestamp trong Tương lai

Một sample sai clock làm query/time partitions lỗi.

Lỗi 9: Không có Out-of-Order Policy

Late samples làm storage behavior không xác định.

Lỗi 10: Mỗi Sample là một Database Row thông thường

Không tận dụng time-series compression và batching.

Lỗi 11: TSDB Blocks Mutable lâu dài

Compaction, cache và replication phức tạp.

Lỗi 12: Không có Compaction

Số block/object tăng vô hạn.

Lỗi 13: Downsample chỉ lưu Average

Làm mất spikes.

Lỗi 14: Query Client gọi trực tiếp mọi Shard

Không có planning, limits hoặc fairness.

Lỗi 15: Không Limit Regex Query

Một matcher có thể scan mọi series.

Lỗi 16: Dashboard Refresh quá nhanh

Tạo query storm.

Lỗi 17: Index mọi Log Field

Index lớn hơn dữ liệu gốc.

Lỗi 18: Dùng Trace ID làm Log Stream Label

Tạo một stream/request.

Lỗi 19: Không xử lý Log Rotation

Đọc trùng hoặc mất logs.

Lỗi 20: Multiline Rule không có Size Limit

Một stack trace lỗi có thể nuốt cả file.

Lỗi 21: Không Redact Secrets gần Nguồn

Sensitive data đã lan vào buffers và storage.

Lỗi 22: Alert Evaluator tự gửi Notifications

Duplicate và routing khó kiểm soát.

Lỗi 23: Alert Query Timeout được coi là Resolved

Che giấu outage.

Lỗi 24: Không Group Alerts

Một node outage tạo hàng nghìn pager events.

Lỗi 25: Multi-Tenant Cache Key thiếu Tenant ID

Có thể rò rỉ dữ liệu giữa khách hàng.
